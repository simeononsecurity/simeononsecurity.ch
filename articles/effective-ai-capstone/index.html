Вернуться к курсу «Практический ИИ-рабочий процесс»

Создайте новый формат вывода и подтвердите его работу. Ранее вы добавили фильтр статуса. Этот итоговый проект начинается с новой лабораторной копии и добавляет JSON-отчёт, который прочитает другая программа. Новое требование проверяет, умеете ли вы переносить рабочий процесс на другую функцию.

Результат обучения: вы подготовите проверенный JSON-отчёт, журнал доказательств по источникам и инструментам и передачу, понятную новой сессии.

Главное #

  • Отдельное требование определяет функцию итогового проекта.
  • Изменение агента-программиста ограничено названными файлами.
  • Независимые проверки определяют приёмку.
  • Передача новой сессии позволяет восстановить ход работы.

Перед началом #

Предварительные требования: завершите уроки 0–10, включая контекст репозитория, первое задание по программированию, MCP или его вариант в браузере, делегирование и ограниченные циклы. Урок 11 необязателен. Выделите 90–120 минут. Сложность средняя.

Используйте свежую распаковку стартовой лабораторной работы . До любых изменений выполните python3 task_report.py tasks.json и два базовых теста. В Windows используйте py -3, если в настройке задействован Python Launcher. Создайте локальную исходную точку Git, как при настройке курса. Фильтр статуса из урока 5 намеренно отсутствует.

Прочитайте docs/capstone-requirements.md, редакция 1. Требование задаёт --format text|json. Текстовый вывод по умолчанию остаётся Total tasks: 4. JSON-вывод содержит числовой итог и количество записей для каждого статуса в данных. Проверьте пустой список, отсутствующий статус и неподдерживаемый формат. Не используйте docs/requirements.md как источник требований для этой новой функции.

Выберите маршрут. Подключённый маршрут использует наблюдаемое изменение от агента-программиста, реальный вызов MCP только для чтения и нативного worker или отдельную сессию worker. Учебный маршрут использует чат-ассистента для предложения кода, браузерный источник вместо MCP и отдельные чаты в роли симулированных worker. Недоступные шаги с инструментами отметьте «не запускались». Оба маршрута требуют локальных тестов и проверки файлов. Ключ ответов ниже содержит полные файлы для восстановления. Сохраните первую попытку в заметках, прежде чем копировать ключ в свежую распаковку.

Контрольная точка 1: Бриф проекта #

Откройте синтетический учебный проект ChatGPT или Claude. Попросите составить напоминание из двух предложений. Сверьте время 19:00 с approved-schedule.md. Расписание задаёт время напоминания. Требование проекта задаёт программу.

Доказательство: запишите имя проекта, редакцию источника, время из наблюдаемого черновика и исправления. Не отправляйте сообщение.

Контрольная точка 2: Контекст репозитория #

Откройте свежую лабораторию. Создайте краткий AGENTS.md со ссылками на docs/capstone-requirements.md, task_report.py, тесты и команду проверки, подтверждённую при настройке. Если вы используете Claude Code, подключите общий файл через CLAUDE.md. Создайте человеческий setup-коммит для этих файлов с инструкциями, затем убедитесь, что git status --short не выводит изменений. Агент-программист не должен коммитить изменение функции.

Доказательство: сохраните карту и чистую копию инструкций. Запишите JSON-ключи и поведение при недопустимых входных данных из редакции 1. Если в предыдущем чате обсуждался фильтр статуса, считайте это контекстом другой задачи.

Контрольная точка 3: Внешний источник #

Подключённый маршрут: используйте сервер OpenAI Docs MCP только для чтения через совместимый клиент. Попросите инструмент MCP вернуть актуальные рекомендации для AGENTS.md. Запишите имя инструмента, URL источника и полезный для лаборатории пункт. Затем удалите учебное подключение.

Учебный маршрут: откройте в браузере официальную документацию AGENTS.md . Запишите заголовок, URL и полезный пункт. Поиск и запуск MCP отметьте как «не запускались».

Доказательство: запись настроенного сервера не доказывает его использование. Подключённый маршрут требует видимого вызова инструмента и полученного содержимого источника.

Контрольная точка 4: Делегирование одной проверки #

Попросите worker с доступом только на чтение изучить docs/capstone-requirements.md, task_report.py и базовые тесты. Запросите отчёт максимум из пяти строк с отсутствующими проверками и путями файлов. В учебном маршруте используйте отдельный чат и обозначьте его как симуляцию worker.

Ожидаемый результат: стартовые тесты проверяют общий итог и значение JSON, которое не является списком. Они не проверяют JSON-вывод, пустой список, отсутствующий статус или неверный формат. Самостоятельно откройте тестовый файл и проверьте отчёт. Короткая независимая проверка полезна, поскольку критерии приёмки отличаются от урока 5.

Доказательство: сохраните краткий отчёт и решение об интеграции одним предложением. Храните стенограмму worker отдельно от основного журнала задачи.

Контрольная точка 5: Запрос на изменение #

Передайте агенту-программисту следующий пакет. В учебном маршруте чат-ассистент предлагает исправление, которое вы вручную применяете в лаборатории.

Цель: добавить --format text|json после пути к JSON-файлу.
Источник: docs/capstone-requirements.md, редакция 1.
Разрешённые изменения: task_report.py и tests/test_task_report.py.
Сохранить: вывод Total tasks: 4 по умолчанию и tasks.json без изменений.
JSON: один объект с total и счётчиками by_status, без дополнительного текста в stdout.
Обязательные проверки: текстовый режим по умолчанию и явно заданный, JSON 4/2/2,
пустой список, отсутствующий статус, неверный формат и базовые тесты.
Остановиться при: конфликте источников, постороннем сбое базового теста или изменении вне области.
Отчёт: изменённые файлы, команды, наблюдаемый вывод, нерешённая проблема.
Не коммитить, не отправлять push, не публиковать и не отправлять сообщения.

Проверьте план перед изменениями. Выбор схемы важен: total — число, а не строка "4". by_status содержит каждый статус из входных данных, включая будущие значения. Ограничьте изменение распакованной лабораторией.

Контрольная точка 6: Проверка и ревью #

Выполните эти проверки самостоятельно. В Windows замените python3 на py -3. Порядок ключей и пробелы в JSON не имеют значения. Разберите вывод как JSON и сравните типы значений.

git status --short
git diff -- task_report.py tests/test_task_report.py
python3 -m unittest discover -s tests -v
python3 task_report.py tasks.json
python3 task_report.py tasks.json --format text
python3 task_report.py tasks.json --format json
python3 task_report.py tasks.json --format invalid

Ожидаемое поведение: тесты проходят. Обе текстовые команды выводят Total tasks: 4. Команда JSON возвращает один объект с total 4, by_status.open 2 и by_status.done 2. Неверный формат завершает работу с ненулевым кодом. Тесты также покрывают пустые данные и задачу без строкового status. Прочитайте наблюдаемый текст ошибки и код завершения для этих случаев.

Бриф проекта В напоминании указано 19:00 Обновить источник расписания
Карта репозитория Названы требование и пути тестов Исправить файлы инструкций

Поведение Проверены текст, JSON, пустой ввод и ошибки Найти одну причину и повторить проверку

Для безопасного сброса используйте новую распаковку. Сохраните заметки вне лаборатории, удалите только одноразовую распакованную копию и снова распакуйте исходный ZIP. Не выполняйте общий сброс Git в репозитории с нужной вам работой.

Контрольная точка 7: Передача новой сессии #

Подготовьте передачу менее чем на 180 слов вне каталога лаборатории. Укажите редакцию требования, изменённые файлы, точную команду теста и результат, текстовый и JSON-вывод, проверки недопустимых входных данных, журнал использования и следующий шаг. Откройте новую сессию и попросите назвать JSON-ключи и определить, прошла ли функция проверку.

Ожидаемый ответ: новая сессия называет total и by_status, указывает редакцию 1, сообщает только о наблюдавшихся проверках и отмечает пропущенные.

Ключ ответов и критерии оценки #

Ниже приведена допустимая реализация. Сохраните первый блок как task_report.py, а второй как tests/test_task_report.py в свежей распаковке лаборатории. Не изменяйте tasks.json и оба файла требований. Выполните проверки из контрольной точки 6. Сравните другие решения с требованием и наблюдаемым поведением.

task_report.py:

"""Выводит текстовый итог или JSON-сводку учебных задач."""

import argparse
import json
import sys
from collections import Counter
from pathlib import Path


def load_tasks(path: Path) -> list:
    tasks = json.loads(path.read_text(encoding="utf-8"))
    if not isinstance(tasks, list):
        raise ValueError("task data must be a list")
    for index, task in enumerate(tasks, start=1):
        if not isinstance(task, dict) or not isinstance(task.get("status"), str):
            raise ValueError(f"task {index} needs a string status")
    return tasks


def count_tasks(path: Path) -> int:
    return len(load_tasks(path))


def summarize_tasks(path: Path) -> dict:
    tasks = load_tasks(path)
    counts = Counter()
    for task in tasks:
        counts[task["status"]] += 1
    return {"total": len(tasks), "by_status": dict(sorted(counts.items()))}


def main() -> int:
    parser = argparse.ArgumentParser(description="Отчёт по учебным задачам")
    parser.add_argument("path", type=Path, help="путь к списку задач в JSON")
    parser.add_argument("--format", choices=("text", "json"), default="text")
    args = parser.parse_args()
    try:
        if args.format == "json":
            print(json.dumps(summarize_tasks(args.path)))
        else:
            print(f"Total tasks: {count_tasks(args.path)}")
    except (OSError, ValueError) as exc:
        print(f"Error: {exc}", file=sys.stderr)
        return 1
    return 0


if __name__ == "__main__":
    raise SystemExit(main())

tests/test_task_report.py:

"""Проверки текстовых отчётов и JSON-сводок учебных задач."""

import json
import subprocess
import sys
import tempfile
import unittest
from pathlib import Path
from sys import path as module_path

ROOT = Path(__file__).resolve().parents[1]
module_path.insert(0, str(ROOT))
from task_report import count_tasks  # noqa: E402


def run_report(path: Path, *options: str) -> subprocess.CompletedProcess:
    return subprocess.run(
        [sys.executable, str(ROOT / "task_report.py"), str(path), *options],
        capture_output=True, text=True, check=False,
    )


class TaskReportTests(unittest.TestCase):
    def test_counts_four_sample_tasks(self):
        self.assertEqual(count_tasks(ROOT / "tasks.json"), 4)

    def test_rejects_non_list_data(self):
        with tempfile.TemporaryDirectory() as directory:
            sample = Path(directory) / "invalid.json"
            sample.write_text(json.dumps({"tasks": []}), encoding="utf-8")
            with self.assertRaises(ValueError):
                count_tasks(sample)

    def test_default_and_explicit_text(self):
        for options in ((), ("--format", "text")):
            result = run_report(ROOT / "tasks.json", *options)
            self.assertEqual(result.returncode, 0)
            self.assertEqual(result.stdout.strip(), "Total tasks: 4")

    def test_json_counts_and_types(self):
        result = run_report(ROOT / "tasks.json", "--format", "json")
        self.assertEqual(result.returncode, 0)
        self.assertEqual(json.loads(result.stdout), {
            "total": 4, "by_status": {"open": 2, "done": 2},
        })

    def test_empty_list(self):
        with tempfile.TemporaryDirectory() as directory:
            sample = Path(directory) / "empty.json"
            sample.write_text("[]", encoding="utf-8")
            result = run_report(sample, "--format", "json")
            self.assertEqual(result.returncode, 0)
            self.assertEqual(json.loads(result.stdout), {
                "total": 0, "by_status": {},
            })

    def test_missing_status(self):
        with tempfile.TemporaryDirectory() as directory:
            sample = Path(directory) / "missing.json"
            sample.write_text('[{"id": 1}]', encoding="utf-8")
            for options in ((), ("--format", "json")):
                result = run_report(sample, *options)
                self.assertNotEqual(result.returncode, 0)
                self.assertIn("status", result.stderr)

    def test_invalid_format(self):
        result = run_report(ROOT / "tasks.json", "--format", "invalid")
        self.assertNotEqual(result.returncode, 0)
        self.assertIn("invalid", result.stderr)


if __name__ == "__main__":
    unittest.main()

Сбросьте лабораторию после использования ключа: сохраните заметки вне лаборатории, удалите распакованную копию и снова распакуйте исходную стартовую лабораторию. В новой копии будут два базовых теста и не будет реализации функции.

Начислите по баллу за каждую точку в таблице выше. Семь баллов завершают подключённый маршрут, если в строке внешнего источника указан реальный вызов MCP, а в строке worker задокументирована реальная сессия. Семь баллов завершают учебный маршрут, если источник — проверенная страница браузера, а шаги с инструментами явно отмечены как незапущенные. Отсутствие проверки поведения, источника или области файлов блокирует оба маршрута.

Проверьте понимание #

  1. Какое требование определяет эту функцию? docs/capstone-requirements.md, редакция 1. Предыдущее требование к фильтру статуса относится к уроку 5.
  2. Что подтверждает JSON-контракт? Разберите вывод команды, сравните числовые значения и счётчики каждого статуса, проверьте пустые и неверные входные данные. Аккуратного резюме агента недостаточно.

Устранение неполадок #

  • Базовый тест не проходит до изменений: восстановите лабораторию из ZIP и повторите настройку.
  • Агент изменил другой файл: проверьте diff и восстановите только лишнее изменение лаборатории.
  • Не работает подключение MCP: используйте источник в браузере и отметьте точку как учебный маршрут.
  • Worker повторяет неверное значение: перечитайте требование проекта и исправьте отчёт.
  • Закончились попытки: сохраните журнал ошибок и попросите человека-рецензента указать следующий шаг.
