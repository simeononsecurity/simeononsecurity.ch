AI連携コースに戻る

**タスクの前と公開が中断した後にドリフトを確認します。**リポジトリまたは作業用サンドボックスで、ソース、アダプターの各バージョンと配信状況を比較してください。1つのトラックを完了した後に行います。古い要約が現在の正式な情報源として扱われるのを防ぎ、確認可能な復旧履歴を残すためです。

要点 #

  • ソースのドリフトとアダプターのドリフトは異なります。
  • 一部だけ公開された場合は、システムごとの台帳が必要です。
  • 復旧では、履歴を残し、レビュー済みの変更を記録します。
  • 引き継ぎでは、別のレビュアーが最新ソースを自分で読みます。

開始前の準備 #

前提条件: GitHubブラウザーワークフロー または 混合公開ワークフロー 。所要時間: 60～90分。難易度: 高度なレビュー。

安全性: 合成データのみを使います。復旧テストの前に自動公開を停止してください。稼働中の削除サービスは含まれていません。

読者の成果: 状態一覧、オーナーの判断、レビュー済みの修復内容、別のレビュアーが最新ソースから再構成できる引き継ぎを完成させます。演習を完了しても公開承認にはなりません。

ドリフトを分類する #

ドリフト兆候修復担当
要件ソースがマニフェストと異なるプロダクトオーナー
ポリシーアダプターがPOL-01と異なるポリシーオーナー
実装設定が意図に反しているメンテナー
ランブック手順が承認済みの動作に反している運用オーナー
アクセス以前は読めたソースが拒否される管理者、タスクを停止
配信台帳が未完成のまま完了扱い配信オーナー

**最新のテキストが承認済みの正式情報とは限りません。**直近の未承認編集は自動採用せず、調査してください。値をコピーする前にステータスとオーナーを確認します。

事前確認を行う #

Read MAP-01 and capture its revision.
Read POL-01 and compare active adapter versions.
Read REQ-17 and RUN-04 from mapped homes.
Read config.json at protected main.
Read frozen proposal and current role reviews.
Compare current sources with reviewed bases.
List mismatches, denied reads, and pending publications.
Stop consequential writes until owners resolve each mismatch.

**作成者は草案の作成前に事前確認を行います。公開担当者は書き込み前に再確認します。**バージョン比較を提案と一緒に保存してください。週次チェックはこれらの読み取りを補いますが、置き換えるものではありません。

アダプターのドリフト例: POL-01がバージョン2になっても、CLAUDE.mdにはバージョン1が記載されています。停止し、レビュー済みのポリシー変更を読み、保護されたPRを通じてアダプターを更新して新しいセッションを開始してください。ポリシーを読み込まずに番号だけ変えてもコンテキストは修復されません。

オフラインラボでソースのドリフトを発生させる: 提供されたZIPを新たに空の一時ディレクトリへ展開します。ルートからbaseline/をcandidate/へコピーし、python3 check.py capture --base baseline > candidate/context.jsonを実行してから、python3 check.py validate --base baseline --candidate candidateを実行します。最初のPASSを記録します。テキストエディターでbaseline/requirement.jsonを開き、"retention_days": 7だけを"retention_days": 8に変更します。同じvalidateコマンドを再実行します。終了ステータスはゼロ以外になり、STALE_CONTEXT: capture the trusted base againが表示される想定です。両方の出力と変更したソースのパスを記録します。個人用の証拠を保存したら、この一時展開を削除し、新しいコピーを展開してリセットします。8日への変更を公開済みリポジトリに適用せず、再キャプチャをオーナー承認と見なさないでください。

一時リポジトリでアダプターのドリフトを発生させる: 新しい提案ブランチで承認済みのPOL-01バージョン1アダプター文をCLAUDE.mdへコピーし、バージョン1と記載します。別のレビュー対象ポリシー提案に、具体的な新しい停止条件を含むバージョン2への変更を書きます。アダプターはバージョン1のままにします。マージやエージェント実行の前に、2つの記録を比較してアダプターを古いと判定するようレビュアーに依頼します。テスト提案を閉じるか、レビュー済みPRでアダプターを更新してリセットし、新しいセッションを開始して両方のバージョンと新しい停止条件を確認します。古いdiffと修正後のdiffを保存します。これは文書のテストであり、プラットフォーム拒否のシミュレーションではありません。

中断した公開を復旧する #

  1. **PROP-042の公開を停止し、**復旧担当者を割り当てます。
  2. **関係するすべてのシステムで実状態を読み取ります。**完了、失敗、未実施を区別します。
  3. **プロダクト担当に選択を求めます。**続行、レビュー済みの取り消し、または保留です。
  4. **復旧提案を準備します。**最新のベースを使い、明示的にレビューされていない限り範囲と例外を維持します。
  5. **レビュー済みの手順を一度に1つ適用し、**各結果を記録して読み戻します。
  6. **通常作業を再開する前に、**最終状態と残る制約を確認します。
recovery_id: RECOVERY-042
proposal_id: PROP-042
mode: awaiting-owner-choice
illustrative_state:
  requirement: thirty-days-published
  implementation: seven-days-on-main
  runbook: seven-days
  delivery: blocked
choices:
  forward: finish approved implementation and runbook
  backout: restore baseline through reviewed changes
  hold: wait for evidence or access

**例示状態を、観測したリビジョンと値に置き換えます。**以前の台帳記録やアシスタントの主張は、読み戻しの証拠になりません。

選択肢使用する状況制約
続行承認が有効で、ソースが整合している最新の検証が必要
取り消しオーナーが変更を撤回する、または実装に失敗した削除済みデータは復元しない
保留証拠またはアクセスが不足している配信は未完了のまま

**証拠が不足しているときは保留します。**合成演習に、無確認の上書きを急ぐ運用上の理由はありません。次の担当ロールと不足している証拠を明示してください。

GitHubの復旧では、レビュー済みのrevertまたは補償変更を使います。Confluenceの復旧では、履歴を比較してレビュー済みの復元または補償変更を行います。Jiraの復旧では、提案履歴を保持しながら配信を再オープンまたはブロックします。履歴番号がリセットされると仮定せず、結果のリビジョンを読み取ります。

独立した引き継ぎを検証する #

Handoff: HANDOFF-042
Task: PROP-042
Map and policy: attach current approved revisions
Evidence: requirement, runbook, configuration references
Ledger: completed, failed, pending
Decision: owner choice and fixed proposal revision
Limits: no runtime deletion test or production data
Next role: accountable role
Next action: one bounded step
Stop: changed base, access denial, conflicting authority

以前の会話ではなく、マップと引き継ぎ情報を使って別のツールまたはクリーンなセッションを開きます。最新ソースの読み取り、新しいマニフェスト、保留中のアクションの特定を必須にします。手動のブラウザー証拠は、スナップショットと明記し、書き込み前に再確認すれば有効です。

否定的な引き継ぎ: REQ-17へのアクセスを拒否します。推測した値や特権付きの抜粋ではなく、明示的なブロックを期待します。管理を通じて承認済みのアクセスだけを復元し、検証を繰り返します。

修復前に原因を診断する #

状態一覧から始めます。「アシスタントの回答が食い違う」は回答上の症状であり、根本のソース問題ではありません。修復をどちらかのアシスタントに依頼する前に、マップ上の要件、設定、ランブック、ポリシー、配信記録を個別に読みます。

観察診断最初の対応
両方のソースは一致し、古い回答だけが異なる回答コンテキストが古い最新の読み取りから再構成する
要件は30日、設定は7日配信または実装の不一致承認済みパッケージと台帳を確認する
アダプターは1、ポリシーは2指示のバージョン不一致ポリシー変更を読んでアダプターを修正する
以前は読めたソースが拒否されたアクセス変更タスクを停止し、権限のあるレビューを依頼する
台帳は完了、ランブックは7日有効な読み戻しなしに終了配信を再開またはブロックし、調査する

**すべての不一致をモデルの問題として扱わないでください。**セッションの更新で古い会話コンテキストは修正できますが、ランブックの公開、失われた権限の回復、オーナー間の矛盾した判断の調整はできません。ツール操作を選ぶ前に、修復担当者を明確にします。

補償変更を進める #

中断の例: REQ-17には承認済みの30日という意図が記録され、配信は保留中です。設定とランブックはまだ7日です。メンテナーは未解決の実装障害を報告します。プロダクト担当は続行ではなく復元を選びます。

  1. 現在のバージョンを記録: 要件は30、設定は7、ランブックは7、配信はブロック。
  2. 保留中の提案を凍結: レビューと公開失敗の証拠を保持。
  3. 要件の補償変更を準備: 途中で追加された除外事項や注記を保持して7に戻す。
  4. オーナーのレビューを得る: 現在のソースバージョンと正確な復元文を示す。
  5. 承認済みの経路で公開: 結果の要件バージョンを読み戻す。
  6. 台帳を調整: 適用対象の公開値はすべて7、元の変更は未配信。

**補償変更は履歴の削除ではありません。**30日への変更の試み、失敗、後の復元は別々の記録として保持します。最終ソースには7と記載し、配信履歴には承認済み提案を完了できなかった理由を残します。

Recovery decision: illustrative compensation
Original proposal: PROP-042 revision 1
Observed mismatch: requirement 30, configuration/runbook 7
Owner decision: restore approved baseline intent
Review object: fixed compensation against current requirement version
Result: capture resulting revision and seven-day read-back
Original delivery: withdrawn or blocked with explanation
Limit: no runtime deletion or data restoration performed

**別の作成者が例外を加えた場合は明示的に維持します。**古いページ本文をそのまま貼り付けると、有効な途中変更を削除するおそれがあります。現状と意図したテキストを比較し、現在のバージョンに対する最小限の補償変更をレビューします。

新しい引き継ぎをテストする #

**クリーンなセッションと別のレビュアーを使います。**マップ、固定されたパッケージ、台帳、復旧判断を渡します。以前のチャットは渡しません。受信者に現在の意図、設定、運用手順、次に許可されたアクションを説明してもらいます。

Read the mapped current sources independently.
Distinguish approved intent, committed configuration, and delivery state.
Compare them with the reviewed package and ledger.
List missing reads and changed bases.
Recommend one bounded next action with its accountable role.
Do not treat this handoff as approval or publication permission.

期待する推論: 受信者はベースラインを復元済みと説明する前に、補償変更の結果を確認します。引き継ぎから「7日」と繰り返すだけなら、独立した読み取り要件は未検証です。別の要約ではなくソースの証拠を求めます。

完了した教育用一覧、合成的な中断:

記録観測状態保持する証拠次のオーナー
REQ-17v5は30日、バックアップは除外ページ履歴と最新の読み取りプロダクト
保護された設定mainのbase-001は7日コミットの読み戻しと拒否されたマージイベントリポジトリメンテナー
RUN-04v2も7日のままページの最新読み取り運用
PROP-042r1承認済み、配信はブロック固定されたレビューと台帳配信オーナー

この一覧を、以前のチャットを見せずに2人目の読み手へ渡します。読み手が4つの状態を独自に見つけ、バックアップの除外を述べ、base-001を現在の保護されたリビジョンと特定し、オーナーのレビューを受ける復旧手順を提案した場合に限り合格です。リビジョンの誤り、例外の見落とし、根拠のない再開があれば不合格とします。次の書き込み前に読み手のソース参照と修正点を記録します。

再開するか判断する #

事前確認の結果再開の判断
ソースが固定済み承認と一致する承認済みの保留手順を続ける
レビュー対象外でソースが変更された比較と再レビューのため停止する
読み取りアクセスがないアクセスレビュアーを割り当てて保留する
ポリシーが変更されたアダプターを修正し、タスク権限を再評価する
書き込み結果が不明再試行する前に保存先を読む

**復旧の合格基準を具体的にします。**一致する読み戻し、最新のレビュー対象、整合した台帳、新しい引き継ぎを必須にします。アシスタントが解決済みと言うだけで復旧を終了しません。

完了チェック: 観測した状態一覧、オーナーの判断、レビュー済みの修復、最終の読み戻し、独立した再構成を提出します。アクセスのために読み取れない場合はブロックを記録します。この証拠基準を最終課題にも適用します。

トラブルシューティングと取り消し #

revertの競合: 現状に基づいて補償変更を準備します。復元で例外が失われる: 書き込み前に関連する節全体を比較します。古い記憶が回答を支配する: 承認済みソースでやり直し、古い草案コンテキストを削除します。

復旧の取り消し: 最後に検証した状態で停止し、台帳に次の記録を追加します。元の監査イベントを消したり、保護された履歴を強制リセットしたりしません。権限の未解決事項はプロダクト担当へエスカレーションします。

演習と自己チェック #

**古い証拠、古いポリシーアダプター、一部だけの公開を作ります。**説明を付けずに記録を別のレビュアーへ渡し、修復担当者を特定してもらいます。

期待する推論: プロダクト担当は要件の調整、ポリシーオーナーはアダプターの整合、配信復旧コーディネーターは関係者間の調整を担当します。「コンテキストを更新する」だけでは、すべてのケースを修復できません。

主な参考資料 #

  • リポジトリ復旧の制御: 保護されたブランチ 。
  • ページ履歴: Confluenceのドキュメント 。
  • 指示の確認: Claude Codeのメモリ 。

次のステップ #

**両方のトラックと2人目の読み手を使って Retention Capstone を完了します。**最新ソースの読み取り、バージョンの不一致、判断オーナー、レビュー済みの復旧、読み戻し、独立した再構成を示してください。
