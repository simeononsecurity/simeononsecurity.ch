Dockerと仮想マシンを2026年に徹底比較 #

クラウドコンピューティングとアプリケーションのデプロイが進化し、Dockerコンテナと**仮想マシン（VM）**のどちらを選ぶべきかは、以前より複雑になっています。かつて「Docker対VM」の議論では両者を競合技術として扱っていました。2026年の実情は異なり、どちらも重要ですが、現代のインフラで果たす役割はそれぞれ異なります。

このガイドではDockerとVMを技術、運用、ビジネスの観点から比較し、用途に合う技術を選べるようにします。

基本を理解する #

Dockerとは #

Dockerは、アプリケーションと依存関係をコンテナと呼ばれる標準化された単位にまとめるコンテナ化プラットフォームです。Dockerの特徴は次のとおりです。

  • アプリケーションレベルの仮想化: コンテナはホストOSのカーネルを共有します。
  • 軽量な分離: OS全体のオーバーヘッドなしに、プロセスとリソースを分離します。
  • 不変のインフラ: コンテナは破棄して再作成できます。
  • 開発者に扱いやすい設定: Dockerfileによるシンプルな宣言型設定です。
  • 豊富なエコシステム: Docker Hubには1,300万以上のコンテナイメージがあります。

2026年のDocker Engine 26.xは、セキュリティ機能とリソース管理を改善し、KubernetesやDocker Swarmなどのオーケストレーターと連携します。

仮想マシン（VM）とは #

仮想マシンはハードウェアを含むコンピューターシステム全体をエミュレートし、ハイパーバイザー上で完全なOSを実行します。VMの特徴は次のとおりです。

  • ハードウェアレベルの仮想化: カーネルを含むOS全体を分離します。
  • 強い分離境界: 各VMは独自のOSを使って独立して動作します。
  • レガシー互換性: 様々なハードウェア上で任意のOSを実行できます。
  • 成熟したエコシステム: 企業向けの管理ツールが数十年にわたり整備されています。
  • 実績のある信頼性: 企業環境で長年使われてきました。

主なVM技術には、VMware vSphere 9、Microsoft Hyper-V 2025、KVM（Kernel-based Virtual Machine）、Proxmox VEがあります。2026年には性能と管理機能が向上しています。

性能比較: 2026年のベンチマーク #

リソース使用量 #

Dockerコンテナ:

  • CPUオーバーヘッド: 1%未満で、ほぼネイティブ性能。
  • メモリのオーバーヘッド: コンテナごとに10～50 MB。
  • ディスクI/O: overlay2ストレージドライバーでほぼネイティブ。
  • ネットワーク性能: ベアメタルの95～99%。
  • 起動時間: 一般的なアプリケーションで平均200 ms。

仮想マシン:

  • CPUオーバーヘッド: ハイパーバイザーにより5～10%。
  • メモリのオーバーヘッド: OS全体が必要で、VMごとに最低2～4 GB。
  • ディスクI/O: ベアメタル性能の80～95%。
  • ネットワーク性能: ベアメタルの85～95%。
  • 起動時間: 平均30～90秒。

配置密度の比較 #

一般的な64 GB RAMサーバー:

Dockerコンテナの場合:

  • ホストOS: 4 GB。
  • Docker Engine: 1 GB。
  • コンテナ用の残り容量: 59 GB。
  • コンテナの平均サイズ: 500 MB。
  • 理論上の容量: 118コンテナ。
  • 実用上の容量: 適切なリソース制限を設けて80～100コンテナ。

仮想マシンの場合:

  • ハイパーバイザー: 2 GB。
  • VM用の残り容量: 62 GB。
  • VMの平均サイズ: 4 GB。
  • 理論上の容量: 15 VM。
  • 実用上の容量: 十分な余裕を確保して10～12 VM。

Dockerの利点: コンテナが現代の開発を支える理由 #

1. シンプルさと開発者の使いやすさ #

Dockerfileのシンプルさ: Dockerfileによる宣言型設定で、アプリケーションを簡単にパッケージ化できます。

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

この1つのファイルで、アプリケーション環境全体、依存関係、実行時の設定を定義できます。

VMとの比較: VMの作成には次の作業が必要です。

  • 完全なOSを選んでインストールする（30～60分）。
  • ネットワークとストレージを設定する。
  • アプリケーションの依存関係を手動でインストールする。
  • スナップショットまたはテンプレートを作成する。
  • OSの更新とパッチを管理する。

2. 優れた移植性 #

一度作れば、どこでも実行: Dockerコンテナは次の環境で同じように動作します。

  • Windows、Mac、Linuxを使う開発者のノートPC。
  • CI/CDパイプラインサーバー。
  • テスト環境。
  • AWS、Azure、GCPなどの本番クラウド。
  • オンプレミスのデータセンター。
  • エッジデバイス。

実例: macOSで作成したコンテナは、変更せずに次の環境で実行できます。

  • Linux上のGitHub Actionsパイプライン。
  • 本番環境のAWS ECS。
  • ステージング環境のAzure Kubernetes Service。
  • ローカルのKubernetes開発クラスター。

VMでは、ハイパーバイザーごとに異なるイメージと設定が必要です。

3. 非常に速い起動時間 #

Dockerコンテナの起動時間:

  • Webアプリケーション: 200～500 ms。
  • データベースコンテナ: 1～3秒。
  • マイクロサービス: 50～200 ms。

VMの起動時間:

  • 軽量Linux VM: 10～30秒。
  • Windows Server VM: 45～90秒。
  • デスクトップVM全体: 60～120秒。

100倍を超える速度差により、次のことが可能になります。

  • 迅速なスケーリング: 負荷急増に数秒で対応。
  • 自動復旧: 障害コンテナを即座に置き換え。
  • 効率的なCI/CD: 毎日数千のテスト環境を実行。
  • 開発の高速化: 開発環境をすぐに切り替え。

4. リソース効率とコスト削減 #

Dockerの利点:

メモリの節約:

  • Docker上のNode.jsマイクロサービス100個は約50 GBのRAMを使用します。
  • 同じワークロードをVMで実行すると約400 GBのRAMが必要です。
  • 削減量: メモリ要件を87.5%削減。

ストレージの節約:

  • Dockerイメージのレイヤーは複数のコンテナ間で共有できます。
  • Ubuntuのベースイメージは50 MBで、すべてのコンテナで共有されます。
  • アプリケーションレイヤーはそれぞれ100～500 MBです。
  • 結果: レイヤー共有によってストレージを大幅に節約できます。

計算例: Pythonアプリケーション10個の場合:

  • Docker: Pythonベースイメージ1つ（300 MB）とアプリケーションレイヤー10個（各50 MB）で合計800 MB。
  • VM: Pythonを含む完全なOSイメージ10個（各3 GB）で合計30 GB。
  • 削減量: ストレージを97.3%削減。

5. マイクロサービスアーキテクチャへの対応 #

Dockerは現代のマイクロサービスの基盤です。

利点:

  • 独立したスケーリング: 需要に応じて個々のサービスを拡張できます。
  • 複数言語による開発: サービスごとに異なる言語を使えます。
  • 障害の分離: 1つのサービスの障害が他へ波及しません。
  • 継続的なデプロイ: サービスを個別に更新できます。
  • チームの自律性: 各チームがサービス全体のスタックを管理します。

6. DevOpsとCI/CDの統合 #

DockerはCI/CDパイプラインを大きく変えました。

最新のパイプライン例:

  1. Commit: 開発者がコードをpushします。
  2. Build: CIサーバーが1～3分でDockerイメージをビルドします。
  3. Test: コンテナを起動し、数秒で自動テストを実施します。
  4. Scan: イメージの各レイヤーをスキャンします。
  5. Push: コンテナレジストリにアップロードします。
  6. Deploy: インスタンスごとに数秒で本番へリリースします。
  7. Rollback: 必要に応じて以前のイメージへ即時に戻します。

VMとの比較: 従来のVMベースのパイプラインでは次の作業を行います。

  1. Commit: 開発者がコードをpushします。
  2. VMイメージのビルド: 新しいVMイメージの作成に15～30分かかります。
  3. VMのデプロイ: 新しいVMの準備に5～10分かかります。
  4. Test: VM上でテストを実行します。
  5. Rollback: 以前のVM状態の再作成に10～15分かかります。

結果: Dockerのパイプラインは10～20倍高速です。

仮想マシンの利点: VMが適する場面 #

Dockerに利点があっても、特定の用途ではVMが欠かせません。

1. より強力なセキュリティ分離 #

ハードウェアレベルの分離: VMはカーネルレベルで完全に分離します。

  • 各VMは独自のカーネルを持ちます。
  • ハイパーバイザーがハードウェアで保護された境界を設けます。
  • カーネルの脆弱性がVM間を越えて広がりません。
  • 信頼できないコードを扱うマルチテナント環境に適しています。

セキュリティ比較:

セキュリティ機能DockerVM優位な方式
カーネル分離カーネルを共有カーネルを分離VM
分離からの脱出難度Namespaceから脱出する可能性ありハイパーバイザーからの脱出はまれVM
リソース攻撃cgroupによる制限ハードウェアによる制限VM
コンプライアンス対応強化設定が必要分離機能を標準搭載VM
マルチテナント推奨されない業界標準VM

用途例: 顧客向けアプリケーションを実行する金融機関では、規制への準拠とセキュリティ保証のためにVMレベルの分離が求められることがよくあります。

2. OSの完全な制御と柔軟性 #

任意のOSを実行: VMなら次の環境を実行できます。

  • WindowsとLinuxなど、同じハードウェア上で異なるOS系列を使用。
  • Windows Server 2008やRHEL 5などの旧式OS。
  • BSDやSolarisなどの特殊なディストリビューション。
  • カスタムカーネル設定。
  • 特定のカーネルモジュールが必要なOS。

例:

  • Linuxホスト上のWindowsアプリ: Linuxハイパーバイザー上でWindows Server VMを実行。
  • レガシーシステム: 特定バージョンのOSを必要とするアプリケーションを維持。
  • カーネルのテスト: カスタムLinuxカーネルを安全にテスト。
  • 複数OS向けの開発: macOS、Windows、Linuxを同時に実行。

3. ステートフルなアプリとレガシーアプリに適する #

VMが得意とする用途:

ステートフルなアプリケーション:

  • OracleやSQL Serverなどの従来型SQLデータベース。
  • SAPやレガシーERPなどの企業向けアプリケーション。
  • ステートフルなメッセージングシステム。
  • 永続的なローカルストレージを必要とするアプリケーション。

レガシーモノリス:

  • コンテナ向けに設計されていない大規模な企業アプリケーション。
  • ファイルシステムのパスがハードコードされたアプリケーション。
  • 特定のOS設定が必要なソフトウェア。
  • ハードウェアやOSに紐づくライセンスソフトウェア。

例: SAP ERPを使う企業では:

  • 特定のカーネルパラメーターを持つWindowsまたはLinuxが必要です。
  • 特定のファイルシステムによる永続ストレージが必要です。
  • 複雑なネットワーク要件があります。
  • OSレベルのカスタマイズが必要です。
  • 解決策: 仮想マシンが現実的な選択です。

4. 実績のある企業向け管理 #

成熟したツール:

  • VMware vCenter: データセンターを包括的に管理。
  • Microsoft System Center: VMのライフサイクルを管理。
  • Red Hat Virtualization: オープンソースの企業向け仮想化。
  • Proxmox: 多機能なVM管理。

企業向け機能:

  • ライブマイグレーション: 稼働中のVMを停止せずにホスト間で移動。
  • 高可用性: ハードウェア障害時にVMを自動再起動。
  • 災害復旧: バックアップ、スナップショット、レプリケーションを利用。
  • リソース管理: CPUやメモリを高度に割り当て。
  • コンプライアンス: 監査とセキュリティ機能を標準搭載。

  • Linuxサービス。
  • AIXやSolarisなどのUnixシステム。
  • ネットワーク機器。

  • OSカーネルが異なるため、コンテナでは同じ構成を実現できません。

セキュリティの詳細比較: DockerとVM #

Dockerのセキュリティモデル #

分離の仕組み:

  • Namespaces: プロセス、ネットワーク、マウント、IPC、UTSを分離。
  • Cgroups: リソースを制限し、使用量を記録。
  • Seccomp: システムコールをフィルタリング。
  • AppArmor/SELinux: 強制アクセス制御。
  • Capabilities: 権限を細かく制御。

2026年のDockerセキュリティのベストプラクティス:

  1. rootless Dockerを使う: root以外のユーザーでコンテナを実行。
  2. 最小限のベースイメージを使う: Alpine Linuxやdistrolessなど。
  3. イメージをスキャンする: Trivy、Snyk、Clairで脆弱性を確認。
  4. イメージに署名する: Docker Content Trustで真正性を検証。
  5. Capabilitiesを制限する: 不要なLinux権限を削除。
  6. 読み取り専用ファイルシステムを使う: コンテナをread-onlyでマウント。
  7. ネットワークを分割する: 分離されたネットワークを使う。
  8. シークレットを管理する: Docker secretsまたは外部の保管庫を使う。

セキュリティリスク:

  • カーネル共有: すべてのコンテナがホストカーネルを共有。
  • 権限昇格: 設定を誤るとコンテナから脱出される可能性があります。
  • イメージの脆弱性: ベースイメージにパッチが適用されていない場合があります。
  • デーモンへの攻撃: Dockerデーモンはrootで実行されます。

VMのセキュリティモデル #

より強い分離:

  • 独立したカーネル: VMごとに別のカーネルを使用。
  • ハイパーバイザーによる強制: ハードウェアで分離を実施。
  • カーネルを共有しない: カーネルの脆弱性は1台のVM内にとどまります。
  • 成熟したセキュリティ: 数十年にわたり強化されてきました。

VMのセキュリティ対策:

  1. Type 1ハイパーバイザーを使う: VMware ESXi、KVM、Hyper-V。
  2. ハイパーバイザーを保護する: パッチを適用した状態に保つ。
  3. ネットワークを分離する: VLANとファイアウォールルールを使う。
  4. データを暗号化する: ストレージとメモリを暗号化。
  5. アクセスを管理する: 管理画面に強固な認証を設定。
  6. ゲストOSを強化する: 最小構成のOSをインストール。
  7. 定期的にパッチを適用する: ハイパーバイザーとゲストOSの両方を更新。

セキュリティ面での強み: VMは次の用途に適しています。

  • マルチテナントSaaSプラットフォーム。
  • 金融や医療などの規制対象業界。
  • 信頼できないコードの実行。
  • 高いセキュリティ要件がある環境。

  • リソースプールと上限を使用

  • リソース使用量を監視

2. 高可用性:

  • ホスト間でVMをクラスター化
  • 自動フェイルオーバーを導入
  • 共有ストレージを使用 (SAN、NAS)
  • 定期的にバックアップと復元テストを実施

3. セキュリティ:

  • ネットワークを分割 (VLAN)
  • 定期的なパッチ適用スケジュール
  • ストレージと通信を暗号化
  • アクセス制御と監査

4. パフォーマンス:

  • 準仮想化ドライバーを使用
  • 重要なVMに専用リソースを割り当て
  • 大規模VMではNUMAを考慮
  • ストレージ性能を最適化

今後の動向: 次に起きること #

コンテナの進化 #

1. Rootlessコンテナと非特権コンテナ:

  • root権限なしでセキュリティを向上
  • 規制対象の業界で採用が拡大
  • 攻撃対象領域を縮小

2. WebAssembly (Wasm) コンテナ:

  • 非常に軽量な実行環境
  • クロスプラットフォームのバイナリ形式
  • 従来型コンテナより高速な起動
  • DockerとWasmの統合が拡大

3. eBPFの統合:

  • 高度なネットワーク機能とセキュリティ
  • カーネルレベルのオブザーバビリティ
  • パフォーマンス監視を強化

4. GPUとAI/MLの高速化:

  • コンテナ間のGPU共有を改善
  • AI/MLワークロードを最適化
  • コンテナネイティブなMLプラットフォーム

VMの革新 #

1. コンフィデンシャルコンピューティング:

  • ハードウェアで暗号化されたVMメモリ
  • 機密データ向けのセキュアエンクレーブ
  • AMD SEV、Intel SGXとの統合

2. VMとコンテナのハイブリッド:

  • Kata ContainersとgVisor
  • コンテナの操作性とVMレベルの分離
  • 両技術の長所を活用

3. エッジコンピューティング:

  • 軽量ハイパーバイザー
  • マイクロVM (Firecracker)
  • エッジに最適化した仮想化

結論: 適切な選択をする #

2026年のDockerとVMの比較は、どちらの技術が「優れているか」ではなく、個々の要件にどのツールが適するかを見極めることが重要です。

Dockerを選ぶ場面:

  • 最新のマイクロサービスアプリケーションを構築する
  • リソース効率と密度を最大化する
  • 迅速なスケーリングとデプロイが必要
  • DevOpsとクラウドネイティブな手法を取り入れる
  • ステートレスなアプリケーションを実行する
  • 開発者の生産性を優先する

VMを選ぶ場面:

  • レガシーなモノリシックアプリケーションを実行する
  • 強力なセキュリティ分離が必要
  • 複数OSの環境に対応する
  • 状態を持つ従来型データベースを管理する
  • 厳格なコンプライアンス要件を満たす
  • 従来型の企業環境で運用する

両方を使う場面:

  • コンテナへ段階的に移行する
  • 混在するワークロードを実行する
  • 柔軟性と選択肢が必要
  • ハイブリッドクラウドのインフラを構築する

2026年に成果を上げている組織は、現実的なアプローチを採用しています。新しいクラウドネイティブアプリケーションや適切な既存ワークロードにはコンテナを、レガシーシステムやVMの強みが必要な用途にはVMを使います。このハイブリッド戦略により、運用効率を維持しながら、各ワークロードを個別に最適化できます。

両方の技術を理解すると、各環境に合わせてパフォーマンス、セキュリティ、コスト、運用要件のバランスを取り、根拠あるアーキテクチャ判断を下せます。
