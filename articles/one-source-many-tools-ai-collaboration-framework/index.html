Два человека задают двум инструментам ИИ один вопрос:** как долго сервис должен хранить экспорт? В этом примере IDE-агент разработчика отвечает «семь дней», ссылаясь на README.** Чат-помощник руководителя эксплуатации отвечает «тридцать дней», ссылаясь на страницу вики. Оба ответа звучат уверенно. Каждый инструмент прочитал свою копию истины.

Проблема в ответственности за источник, а не в качестве запроса. Требование в вики изменили на прошлой неделе, но README никто не обновил. Разработчик просит агента исправить задачу очистки. Агент следует старому документу и готовит аккуратный патч, возвращающий неверное поведение. Рецензенты изучают код, не видя версию требования, на которой основан ответ.

Назначьте каждому факту одно место.** Пусть каждый инструмент читает этот источник, а каждое долговременное изменение проверяет человек.** Репозиторий, вики и трекер сохраняют разные роли. Явно задайте их авторитетность и владельцев, а также общий процесс передачи информации между системами.

В этом руководстве описана модель, которую можно внедрить на этой неделе, с RAG или без него. Начните с карты проекта, версионированных инструкций, реестров доказательств и проверяемых предложений. Добавляйте поисковую инфраструктуру только тогда, когда этого требует задача поиска информации.

Первый результат это реестр источников, а не коннектор. Для каждого типа фактов укажите авторитетный источник, владельца, текущую ревизию и человека, утверждающего изменения.

Главное #

  • Назначайте авторитетность по типу информации, не сводя всё к одному приложению.
  • Считайте память и индексы поиска кэшами, а не самостоятельными источниками политики.
  • Прикладывайте версии источников к предложениям, чтобы рецензенты видели основания изменений.
  • Обеспечивайте утверждение вне запросов, с помощью контроля доступа и обязательных проверок.
  • Используйте общий процесс для разных инструментов, адаптируя его к каждому интерфейсу.

Перед началом #

Что нужно:** выберите пилотный проект с репозиторием, вики или хранилищем документов, трекером и владельцами, готовыми проверять изменения.** Если вики нет, используйте версионируемое хранилище документов. Модель ответственности не меняется.

Оценка времени:** выделите от двух до четырёх часов на первоначальную карту и шаблоны, затем проведите недельный пилот.** Сложность: средняя. Сложнее договориться об авторитетности, чем установить ещё один инструмент ИИ.

Область применения:** это предлагаемая рабочая модель команды.** Правила утверждения и соглашения об именовании являются рекомендациями, а не поведением по умолчанию, гарантированным Claude Code, Codex, Cline, Cowork, Copilot или ChatGPT. Автоматическое оглавление выше ведёт к каждому этапу внедрения.

Разные инструменты, разный контекст #

Разработчики и сотрудники без навыков программирования работают над одним проектом**, но используют разные интерфейсы.** Разработчик применяет IDE- или терминального агента. Владелец продукта работает в чат-проекте. Эксплуатация использует вики и трекер. Выбирайте интерфейс по задаче, а не по доступу к авторитетным фактам.

Контекст это материалы, доступные для текущего ответа.** Для каждой сессии проверяйте файлы репозитория, загруженные документы, историю чата, сохранённую память, ответы коннекторов и найденные фрагменты.** Сессии с разными доказательствами могут дать разные ответы даже на один вопрос.

Проблема Что происходит
Дрейф документации README повторяет устаревшее требование
Повышение статуса сводки Сводка сессии становится доказательством без исходного источника
Пересекающиеся изменения Два агента заменяют одну страницу на основе разных исходных версий
Потерянные решения Договорённость встречи не попадает в реестр решений
Нет происхождения данных Правдоподобный ответ не указывает версию страницы или коммит

Пример со сроком хранения показывает разницу.** Вики описывает утверждённое целевое поведение.** Код описывает реализованное. Ни один источник не должен молча переписывать другой. Зафиксируйте расхождение и спросите владельца, нужно ли менять реализацию или требование.

Главное: сначала договоритесь об авторитетности, затем выбирайте инструмент ИИ. Начните с общих терминов ниже.

Боковая панель: пять общих терминов #

Термин Значение в этой модели
Источник Назначенная авторитетная запись для типа информации
Кэш Производная копия для скорости или удобства
Предложение Предлагаемое изменение, ожидающее утверждения владельца
Карта проекта Индекс местоположений источников, идентификаторов и владельцев
Манифест Запись точных доказательств для ответа или предложения

Назначьте каждому факту одно место #

Один источник означает один авторитетный источник на каждый факт**, а не одну базу данных на всю организацию.** Установите такое распределение в пилоте и замените примеры реальными владельцами команды.

Тип информации Система-источник Владелец Кто записывает Как читают агенты
Код, тесты, конфигурация, схемы Репозиторий Технический сопровождающий Участники через проверяемые PR Файлы на зафиксированном коммите
Опубликованная документация и ADR Репозиторий Технический владелец Участники через тот же PR Версионируемые файлы
Требования Вики Владелец продукта Владелец или утверждённый издатель ID страницы и ревизия
Инструкции эксплуатации Вики Владелец эксплуатации Утверждённый издатель ID страницы и ревизия
Политика Вики Владелец политики Утверждённый издатель после проверки Каноническая страница и локальный адаптер
Межкомандные решения Реестр решений в вики Назначенный владелец решения Владелец после утверждения ID решения и статус
Задачи и результаты проверок Трекер Владелец задачи Люди или разрешённый приём предложений Ключ задачи и ревизия
Чаты, сводки, embeddings Только кэш Куратор сессии или индекса Инструменты и участники Только ссылка, затем проверка источника

Запись архитектурного решения (ADR)** должна находиться рядом с кодом, если она определяет архитектуру репозитория.** Межкомандное решение относится к общему реестру. Свяжите обе записи, если решение охватывает обе области. Не ведите статус утверждения в двух независимых копиях.

Локальные копии политики подчиняются канонической странице.** Тесты и схемы репозитория, напротив, являются источниками в своей области.** Авторитетность определяется картой, а не местоположением.

Кэш не заменяет источник. Если в сводке указано семь дней, а утверждённое требование говорит о тридцати, для целевого поведения используйте требование. Сохраните противоречивую сводку как доказательство дрейфа, а не как конкурирующее правило. Теперь задайте путь записи изменений.

Кэш вниз, предложение вверх #

Агенты добавляют доказательства в контекст сессии, а затем готовят предложения. Они не утверждают долговременные факты самостоятельно. Редактирование ветки задачи или отправка черновика отличается от публикации политики, слияния кода или принятия решения.

Источник -> чтение с проверкой прав -> контекст сеанса
Контекст сеанса -> предложение + базовая версия -> проверка владельцем
Одобрение владельца -> контролируемая публикация -> журнал изменений
Базовая версия изменилась -> согласовать предложение -> повторная проверка

Зафиксируйте исходную версию до запроса на проверку. Рецензенту нужны прежнее и предлагаемое значения, причина, доказательства и затронутые системы. Утверждение должно относиться к конкретной ревизии предложения, а не к постоянно меняющемуся чату.

proposal_id: PROP-042
target: wiki:REQ-17
base_version: 8
change: "Хранить экспорты тридцать дней вместо семи."
evidence:
  - "решение:DEC-12 принято"
affected_records:
  - "repo:export-service retention configuration"
  - "wiki:RUN-04 cleanup procedure"
owner_role: product-owner
status: awaiting-review

Идентификаторы выше приведены для примера. Для каждого утверждённого логического изменения внесите одну строку в журнал: ID предложения, целевые записи, прежнюю и итоговую версии, утверждающего, дату и ссылку на слияние или публикацию. Связывайте системные события аудита с этой строкой, не заменяя их исходную историю.

Решение принимают люди. Уполномоченный издатель или ограниченная автоматизация применяет утверждённую ревизию. Ограничьте права записи. Одни инструкции не разделяют подготовку и публикацию. Это же различие действует для поиска.

Общий контекст без RAG #

Карта проекта это первый поисковый индекс. Ведите по одной странице на проект с ID источников, путями репозитория, ключами трекера, областями авторитетности и владельцами. Сначала прочитайте карту, затем получите нужную запись по её ID. Используйте поиск, если ID неизвестен.

Боковая панель: пример карты проекта # 

project: export-service
map_id: MAP-01
policy:
  source_id: POL-01
  approved_version: 3
  owner_role: policy-owner
sources:
  requirements: {page_id: REQ-17, owner_role: product-owner}
  runbook: {page_id: RUN-04, owner_role: operations-owner}
  decisions: {register_id: DEC-REGISTER, owner_role: project-lead}
repository:
  key: export-service
  setup: README.md
  terms: CONTEXT.md
  decisions: docs/adr/
tracker:
  project_key: EXP
  active_task: EXP-42

Прямые коннекторы уменьшают ручное копирование. Model Context Protocol (MCP) это протокол интеграции, предоставляющий приложениям ИИ инструменты и контекст. Используйте утверждённые коннекторы к вики, трекеру и репозиторию, если они доступны. Точный запрос сокращает нерелевантные результаты, но не заменяет авторизацию и проверку актуальности. При выборе разрешений коннектора следуйте рекомендациям по безопасности MCP из списка источников.

Точный поиск требует небольшой настройки. Он даёт цитируемые доказательства без векторной базы данных. Ограничения тоже понятны: кто-то поддерживает карту, широкие вопросы требуют дополнительного поиска, а большие страницы занимают место в сессии. Получайте нужный раздел с соседними ограничениями, а не вставляйте целую инструкцию.

Для автономной работы используйте явные снимки. Записывайте экспортированную ревизию и помечайте ответы как основанные на снимке. Не публикуйте изменения, пока уполномоченный человек или коннектор не проверит актуальный источник. Затем покажите ту же политику в каждом интерфейсе.

Одна политика, разные адаптеры #

Поддерживайте одну общую политику, затем распространяйте короткие адаптеры для инструментов. Указывайте утверждённую версию политики в первой строке каждого адаптера или скопированного набора инструкций. Добавляйте ID источника и проверенный локальный снимок для сессий без коннектора.

Инструменты загружают инструкции по-разному. Codex описывает многоуровневый поиск AGENTS.md. Claude Code документирует CLAUDE.md, импорты и память проекта. Cline описывает .clinerules/ и управление правилами. Используйте официальные материалы из списка источников. Проверьте загруженные инструкции в установленной версии, не предполагая одинакового поведения по имени файла.

Боковая панель: пример заголовка AGENTS.md # 

Версия политики: v3 | Источник: wiki:POL-01 | Статус: утверждена

# Инструкции проекта

Перед задачей прочитайте карту проекта MAP-01.
Загрузите docs/policy-snapshot.md и укажите ревизию источника.
Считайте память чата и фрагменты поиска кэшами.
Прикладывайте ревизии источников к каждому фактическому предложению.
Используйте одну ветку задачи и один worktree на задачу разработки.
Не публикуйте политику, не утверждайте решения и не сливайте собственный PR.
Остановитесь при неразрешённых конфликтах источников или пересекающихся записях.
Обязательные проверки: тесты, документация, актуальность политики.
Владельцы: сопровождающий разработки, владелец продукта, владелец политики.

Инструкции чат-проекта получают тот же заголовок и процедуру. Сотрудник без навыков программирования получает снимок политики и карту проекта через утверждённые загрузки или коннекторы. Если у интерфейса нет доступа к живым источникам, человек передаёт версионированный экспорт и фиксирует ограничение.

Метка версии это утверждение, а не доказательство одинакового содержимого. Создавайте адаптеры из утверждённого снимка или сравнивайте части политики с сохранённым дайджестом. Отдельно проверяйте исключения адаптера. В пилоте ищите отключённые правила, вложенные переопределения и личные инструкции. Затем фиксируйте доказательства, использованные каждой задачей.

Запишите манифест контекста #

Манифест контекста объясняет доказательства, на которых основан ответ. Записывайте ID и ревизии страниц, ключи задач с ревизиями или временем обновления, а также полные ID коммитов репозитория. Добавляйте время получения и нужные разделы. Отмечайте недоступные записи, не заменяя их запомненной сводкой.

task: EXP-42
policy: {page_id: POL-01, version: 3}
wiki:
  - {page_id: REQ-17, version: 8, section: export-retention}
tracker:
  - {issue_key: EXP-42, revision: 5}
repository:
  commit: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  files: [README.md, config/retention.yaml]
limits:
  - "Инструкция эксплуатации не получена. Изменения не предлагаются."

Значение коммита синтетическое. В реальном манифесте замените его проверенным коммитом. Запишите время получения во время чтения. Запись, созданная до проверки, это список действий, а не доказательство.

Цитаты помогают проверке, но не создают автоматического доверия. Связывайте каждое важное утверждение с подтверждающей записью и разделом. Если источники расходятся, сохраните оба в манифесте и укажите нерешённое противоречие. Не выбирайте самую свежую дату без проверки области действия и статуса утверждения. Эта дисциплина относится и к семантическому поиску.

Общий контекст с RAG #

Генерация с дополнением извлечёнными данными (RAG) передаёт модели найденные материалы для подготовки ответа. Семантический индекс помогает находить нужные фрагменты, даже если вопрос сформулирован иначе. Обзор RAG от Microsoft описывает grounding, ограничения поиска и контроль доступа. Официальная ссылка приведена в источниках.

Используйте RAG для поиска в больших коллекциях, включая старую документацию, заметки встреч и стенограммы. Помечайте классы документов и статусы утверждения. Стенограмма исходной записи доказывает, что сказали участники, но не определяет утверждённые требования. Не превращайте разговор в политику с помощью индексации.

Правило индекса Требуемое поведение
Загружайте источники, не кэши Исключайте созданные сводки и неотслеживаемые локальные копии
Сохраняйте происхождение Храните ID источника, ревизию, раздел и статус документа для каждого фрагмента
Обновляйте после изменений Переиндексируйте правки и аннулируйте устаревшие фрагменты
Учитывайте изменения доступа Обновляйте разрешения и удаляйте отозванное или удалённое содержимое
Возвращайте цитаты Показывайте ссылки на записи рядом с найденным текстом
Проверяйте живую запись Получайте текущие доказательства перед важным предложением

В этой модели найденный фрагмент служит указателем. Его текст помогает обнаружить доказательства. Живой источник подтверждает формулировку, утверждение, исключения и доступ. Если живой поиск не удался, пометьте снимок и остановите важное действие. Это правило управления, а не утверждение обо всех реализациях RAG.

Устаревшие embeddings и нехватка контекста создают разные риски. Старый фрагмент пропускает ревизию. Даже актуальный вводит в заблуждение, если исключение находится в следующем разделе. Сохраняйте заголовки и получайте соседние ограничения перед оценкой требования.

Утечка разрешений требует отдельного теста. Проверяйте авторизацию до передачи фрагментов модели, а не после генерации ответа. Проверяйте конфиденциальные данные до индексации или внешних вызовов embedding. Учитывайте копии в журналах, запросах к модели и трассировках поиска. Локальная модель не делает удалённый коннектор локальным. Эти проверки помогут решить, нужен ли RAG в пилоте.

Выберите карту, RAG или оба варианта #

Подбирайте поиск под вопрос. Известный ID требования указывает на прямой доступ. Открытый вопрос о разрозненных исторических материалах указывает на поиск. Начинайте с карты, если проблема поиска ещё не измерена.

Боковая панель: RAG или нет? # 

Называют ли задачи обычно проект, страницу, задачу или файл?
  Да -> Достаточно ли прямого поиска для пилота?
           Да -> ТОЛЬКО КАРТА
           Нет -> ГИБРИД: карта для известных ID, RAG для поиска
  Нет -> Доказательства распределены по большой коллекции?
           Нет -> ТОЛЬКО КАРТА и встроенный поиск
           Да -> Работа исследовательская и только для чтения?
                    Да -> ТОЛЬКО RAG для поиска
                    Нет -> ГИБРИД с проверкой живых источников

Каждый вариант сохраняет владельцев, авторизацию и происхождение.
RAG-поиск всё равно проверяет источники перед долговременными действиями.

RAG-only описывает интерфейс поиска, а не разрешение пропустить управление. Используйте его для ограниченной исследовательской коллекции, где остаётся доступна прямая проверка источников. Он плохо подходит для изменений по известному ID, требующих точной проверки версии.

Гибридная модель разделяет поиск и проверку. Карта обрабатывает известные запросы. RAG находит неизвестные записи. RAG отвечает «где», источник отвечает «что». В примере срока хранения запросите REQ-17 напрямую. Для вопроса «какие прежние решения об экспорте объясняют этот лимит?» найдите записи в реестре и получите каждое нужное решение. Теперь примените часть процесса для репозитория.

Информация в репозитории #

Знания о репозитории меняются вместе с реализацией. Поддерживайте компактную структуру, чтобы агент и рецензент знали, где искать.

Файл или каталог Назначение
CONTEXT.md Термины проекта и ссылки на авторитетные записи
docs/adr/ Принятые архитектурные решения репозитория
docs/design/ Утверждённые описания поведения системы
docs/plans/ Предлагаемые планы реализации с явным статусом
AGENTS.md Проверки, границы и роли владельцев
README.md Настройка и точки входа, а не дублирование требований

Применяйте правило одного PR: меняйте код и затронутую документацию репозитория вместе. Если обновление базы знаний не требуется, попросите письменное исключение в описании PR или в согласованном месте для commit trailer.

KB-Update: none (причина: внутренний рефакторинг сохраняет документированное поведение)

Pipeline обеспечивает выполнение декларации. Обязательная проверка отклоняет изменения поведения без документации или исключения. Человек, отвечающий за документацию, проверяет исключение. Проверка путей определяет возможные изменения, но не доказывает семантическую полноту. Требуйте проверку и утверждение через защиту ветки или эквивалентное управление слиянием.

Если проверки нет в pipeline, это не проверка. Фраза «ревью документации» в инструкции даёт только рекомендацию. В пилоте отправьте намеренно неполный PR и убедитесь, что слияние блокируется.

Используйте одну задачу, одну ветку и один worktree. Официальная документация Git описывает отдельные рабочие деревья с собственным состоянием checkout. Они сокращают локальные конфликты редактирования, но не мешают двум веткам менять один файл или двум агентам обновлять одну страницу вики.

Никогда не коммитьте напрямую в ветку по умолчанию, как бы она ни называлась: main, master или иначе. Регистрируйте расхождения требования и кода в трекере. Приложите конфликтующие записи и дайте владельцам решить, какое поведение нужно, прежде чем менять одну из сторон. Применяйте подобные контроли за пределами Git.

Информация вне репозитория #

Вики нужен стандарт документации. На каждой авторитетной странице укажите цель, статус, владельца, ревизию, дату проверки и связанные ID источников. Храните предложения в черновиках с явной пометкой, что они не являются авторитетными. Не смешивайте предложенный текст с утверждённым требованием.

Безопасные обновления следуют установленной последовательности:

  1. Перечитайте текущую страницу и соседние ограничения.
  2. Сравните её версию с исходной версией предложения.
  3. Согласуйте промежуточные изменения и получите новое утверждение, если текст изменился.
  4. Запишите утверждённую ревизию с условием ожидаемой версии.
  5. Проверьте сохранённую страницу и добавьте ссылку на журнал изменений.

Повторное чтение не устраняет гонки. Если возможно, используйте условное обновление системы. Если нет, один владелец сериализует публикацию и проверяет результат. Остановитесь, если другой автор изменил основу во время проверки.

Запрет удаления относится к рабочим процессам агентов. Агенты предлагают архивирование или удаление. Уполномоченные люди применяют процедуры хранения и удаления. Не трактуйте правило как разрешение бессрочно хранить конфиденциальные данные.

Результаты трекера должны содержать доказательства, не только выводы. Запишите наблюдение, точную команду или метод проверки, изученный коммит, ожидаемое и фактическое поведение, критерии приёмки. Удалите секреты и чувствительные результаты перед добавлением. Отмечайте предложенные команды как невыполненные, пока кто-нибудь их не запустил.

Результат проверки: реализация хранения расходится с утверждённым требованием
Доказательства: REQ-17 v8 и проверенный config/retention.yaml
Команда проверки: git show HEAD:config/retention.yaml
Коммит: полный проверенный ID записан в манифесте
Приёмка: утверждённый срок совпадает с кодом, тестами и инструкцией эксплуатации
Статус: ожидается проверка владельцев продукта и разработки

Пример это шаблон результата проверки, а не измеренный результат. Заполните его фактическими данными. Свяжите обновление вики и доказательства трекера через ID предложения.

Реестр решений отделяет правила от обоснований. Записывайте вопрос, варианты, рекомендацию, компромиссы, владельца, статус утверждения и ссылку на итоговое правило. Агенты предлагают. Люди решают. Утверждённые правила попадают в политику и процедуры. Обоснование остаётся в реестре.

Сохраняйте важные факты из встреч и чатов. Отправьте предложение с исходными доказательствами и получите утверждение. До публикации помечайте договорённость как предварительную. Затем свяжите утверждённое поведение в репозитории и вики.

Свяжите две системы #

Синхронизация после слияния переносит изменения реализации наружу. Создайте задачу обновления вики со ссылками на слитый коммит, утверждённое требование и затронутую инструкцию эксплуатации. Агент готовит черновик. Владелец вики проверяет актуальную страницу и утверждает публикацию. Не закрывайте задачу, пока не проверите сохранённую ревизию.

Актуальность политики проверяется отдельно. Сравнивайте каждый адаптер репозитория и копию инструкций в чате с канонической утверждённой версией. Политика v3 находится в POL-01. В первой строке каждого AGENTS.md должна быть v3. Аудит выявляет v2, отсутствующие метки и различия содержимого при совпадающих метках.

Проверка Подтверждение выполнения
Актуальность политики Каноническая версия и сравнение дайджеста адаптера
Сверка требований Ревизия требования сравнена с кодом и тестами
Синхронизация после слияния Слитый коммит связан с опубликованной ревизией вики
Разрешение конфликтов Утверждённое владельцем решение связано с обеими записями

Сверяйтесь по расписанию или при PR. Для пилота подходит еженедельный аудит. PR, меняющий поведение, требует проверки требования до слияния. Выберите периодичность по цене дрейфа и записывайте дату последней успешной проверки.

Изменение срока до тридцати дней проходит несколько контрольных точек: продукт утверждает требование, разработчики обновляют конфигурацию и тесты, рецензенты сливают PR, эксплуатация публикует обновление инструкции. Одна строка журнала связывает полученные записи. Неудачная синхронизация вики остаётся видимой, а не скрывается за успешным слиянием. Общая передача задач сохраняет этот порядок между инструментами.

Одна процедура для каждого инструмента #

Упакуйте повторяющиеся шаги в skills или запросы с версионируемым ID процедуры. Делитесь контрактом, а не предположением об универсальном формате файла. Каждый адаптер использует поддерживаемый механизм загрузки или вызова.

Процедура Требуемый результат
Начало задачи Владелец, область, версия политики, манифест источников, резервирование записи
Lint документации Нет метаданных, дублирующий авторитет, неверные ссылки на источники
Проверка знаний Расхождения требования и кода с подтверждающими ревизиями
Передача Актуальные доказательства, предложения, выполненные проверки, открытые вопросы

Сотрудники без навыков разработки работают без Git. Они получают разрешённые источники в чат-проектах, заполняют тот же шаблон предложения и отправляют его владельцу через черновик страницы или задачу трекера. Для запроса на исправление требования checkout репозитория не нужен.

Разработчики используют файлы репозитория и проверки PR. Они связывают утверждённое предложение в PR, фиксируют просмотренные коммиты и запускают нужные проверки. Обе группы передают одинаковую структуру доказательств.

handoff:
  task: EXP-42
  policy_version: 3
  manifest: "Attached source IDs, revisions, and inspected commit"
  completed: [requirement-review]
  proposals: [PROP-042]
  pending: [implementation-review, runbook-publication]
  reservations: ["RUN-04 publication assigned to operations-owner"]
  unresolved: []
  next_owner_role: engineering-maintainer

Передача это всё ещё кэш. Следующий участник перечитывает источники перед действием и фиксирует новые ревизии. Не считайте статус «готово» доказательством без проверки утверждения или результатов теста. Перед каждой записью применяйте меры ниже.

Меры перед каждой записью #

Проверяйте данные до выхода из исходной системы. Проверьте классификацию, разрешения коннекторов, утверждённые назначения, обработку провайдера модели и журналирование. Передавайте только минимально нужное содержание. Не помещайте ограниченные записи в неавторизованные чаты и сервисы embeddings.

Найденный текст это доказательство, не канал инструкций. Страница вики или ответ инструмента с просьбой игнорировать политику не меняет его авторитетность. Отдельно проверяйте инструкции из содержимого и утверждённую рабочую политику. Ограничивайте коннекторы правами чтения при поиске и отделяйте учётные данные публикации от доступа сессии.

Назначайте одного активного владельца каждой странице или файлу. Запишите резервирование в трекере с областью и сроком. Перед записью перечитайте материал и используйте проверки версии. Раздельные worktrees обеспечивают локальную изоляцию, а резервирование и условные записи защищают общие записи.

Когда остановиться и спросить Требуемое действие
Источники противоречат, владельца нет Приостановитесь и запросите назначение авторитетного источника
Цель зарезервирована другой задачей Согласуйте владение до редактирования
Исходная версия изменилась Согласуйте предложение и запросите новое утверждение
Важному утверждению не хватает доказательств Отметьте его непроверенным и запросите источник
Обработка данных неясна Оставьте содержание в исходной системе
Нет доступа к живому источнику Запишите ограничения снимка и приостановите долговременное действие

Запросы не являются контролями безопасности. Проверяйте отказ в доступе, защищённые ветки, отклонение устаревшей основы и владельца записи вне модели. Одной корректной демонстрации недостаточно, если учётная запись всё ещё может публиковать без ограничений. По этим тестам решайте, готов ли пилот.

Сначала пилот #

Начните с черновой версии модели. Проведите пилот одного проекта с разработчиком, сотрудником без навыков разработки и назначенными владельцами источников. Задайте один вопрос с известным ID через два инструмента, затем смоделируйте конфликт источников. Оценивайте манифесты и предложения, не красоту текста.

Ожидаемое рассуждение: оба участника находят действующее утверждённое требование и отдельно описывают проверенную реализацию. Если ответы расходятся, сначала сравните записи в манифесте. Это предложенное упражнение, а не измеренный тест.

Метрика Определение
Доля цитирования Подтверждённые источниками важные утверждения, делённые на фактические утверждения в выборке
Еженедельные случаи дрейфа Подтверждённые расхождения полномочий или версий по типу источника
Срок обработки предложений Медианное время от готового к проверке предложения до записанного решения
Переделки из-за устаревшего контекста Повторно открытые задачи из-за устаревших или непроверенных доказательств

Сначала измерьте базовый уровень. Рост числа случаев дрейфа на первой неделе может означать улучшение обнаружения, а не ухудшение документации. Отслеживайте повторяемость и срок исправления наряду с общим количеством. Изучайте конфиденциальные доказательства, не копируя их в аналитические выгрузки.

Подготовьте пример репозитория при развёртывании. Добавьте синтетическую карту, адаптеры политики, манифесты, шаблоны предложений, исключения документации и исполняемые проверки. Используйте фиктивные записи вики и трекера без производственных учётных данных. Покажите отказ публикации, отклонение изменённой основы, дрейф версии политики и успешную передачу.

Репозиторий шаблонов это результат развёртывания, а не ресурс из этой статьи. Расширяйте модель после проверки результатов пилота руководством и владельцами источников. Сохраняйте исключения и нерешённые сбои в реестре решений. До расширения устраните ожидаемые проблемы ниже.

Устранение проблем общего контекста #

Признак Первая мера
Два инструмента отвечают по-разному Сравните ID источников, ревизии, область и статус утверждения
Инструкции актуальны, поведение отличается Проверьте загруженные адаптеры, переключатели правил и локальные переопределения
RAG возвращает старые требования Проверьте обновление индекса и запросите живую страницу
Правка вики стирает другую правку Требуйте условные записи или последовательную публикацию
Проверки документации принимают старый текст Добавьте проверку владельца и сверку требований
Решения остаются в чате Назначьте приём предложений и владельца реестра

Исправьте путь доказательств до переписывания запроса. Затем повторите неудачный сценарий пилота и зафиксируйте результат. Используйте чек-лист, чтобы каждую неделю повторять исправленный процесс.

Десять шагов на этой неделе #

  1. Выберите один пилотный проект и участвующих людей и инструменты.
  2. Назначьте каждому типу информации место и владельца.
  3. Опубликуйте карту проекта с ID источников и областями авторитетности.
  4. Подготовьте общую политику и получите утверждение владельца.
  5. Версионируйте каждый адаптер инструкций в первой строке и проверьте его загрузку.
  6. Требуйте манифест контекста для важных фактических ответов и предложений.
  7. Создайте канал предложений с исходными версиями и назначенными утверждающими.
  8. Обеспечьте контроль записей и правило документации в одном PR.
  9. Проверьте дрейф, конфликты и передачу на синтетических записях.
  10. Оцените метрики пилота и утвердите следующий этап развёртывания.

Назначьте каждому факту одно место, заставьте каждый инструмент читать этот источник и направляйте каждое долговременное изменение человеку.

Источники и следующие шаги #

Официальная документация описывает технические компоненты, а не организационные правила этой модели. Во время пилота проверяйте поведение установленных инструментов и разрешения коннекторов.

  • Инструкции Codex: Пользовательские инструкции с AGENTS.md , поиск и проверка инструкций.
  • Инструкции Claude Code: Как Claude запоминает ваш проект , инструкции проекта и память.
  • Инструкции Cline: Правила , правила рабочей области и управление активацией.
  • Проектирование поиска: RAG в Azure AI Search , grounding, ограничения поиска и безопасность.
  • Безопасность коннекторов: Рекомендации по безопасности MCP , авторизация и риски коннекторов.
  • Изоляция worktree: Документация Git worktree , отдельные рабочие деревья и общее состояние репозитория.

Для планирования локального вывода модели прочитайте Руководство по контексту GPU для локального ИИ . Аппаратные возможности и управление общими источниками решают разные задачи. Большое контекстное окно не устраняет конфликт авторитетности.
