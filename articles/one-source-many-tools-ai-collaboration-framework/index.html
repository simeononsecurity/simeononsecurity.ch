2人が2つのAIツールに同じ質問をします。 エクスポートをどのくらいの期間保持すべきか。この例では、開発者のIDEエージェントはREADMEを根拠に7日と答えます。運用責任者のチャットアシスタントはWikiページを根拠に30日と答えます。どちらの回答も自信ありげです。それぞれのツールが異なる情報源を読んでいます。

問題はプロンプトの質ではなく、情報源の所有者が不明なことです。 Wikiの要件は先週変更されましたが、READMEは更新されていません。開発者が保持処理の修正を依頼すると、エージェントは古い文書に従い、誤った動作を戻す整ったパッチを作ります。レビュー担当者は、回答の根拠となった要件の版を見ずにコードを確認します。

各事実の正式な置き場所を1つ決めます。 すべてのツールにその情報源を読ませ、永続的な変更は人が確認します。リポジトリ、Wiki、トラッカーはそれぞれ異なる役割を持ちます。権限と所有者を明示し、情報をシステム間で移動する共通手順を定めましょう。

このガイドは、RAGを使う場合も使わない場合も、今週から適用できるモデルを示します。 まずプロジェクトマップ、版管理された指示、証拠記録、レビュー済みの提案を整えます。検索の課題が必要とする場合に限って検索基盤を追加します。

最初に作るのはコネクターではなく、情報源の登録簿です。 情報の種類ごとに、正式な情報源、所有者、現在の版、変更の承認者を記録します。

要点 #

  • 情報の種類ごとに権限を割り当てます。 すべてを1つのアプリケーションに押し込めません。
  • メモリや検索インデックスはキャッシュとして扱います。 独立したポリシー情報源にはしません。
  • 提案に情報源の版を付けます。 レビュー担当者が変更の根拠を確認できます。
  • プロンプトの外で承認を強制します。 アクセス制御と必須レビューゲートを使います。
  • 共通手順をツール間で共有します。 実装は各インターフェースに合わせます。

始める前に #

前提条件: リポジトリ、Wikiまたは文書システム、トラッカー、変更をレビューできる所有者がいるプロジェクトを1つ選びます。Wikiがなければ版管理された文書ストアを使います。所有者モデルは変えません。

所要時間の目安: 最初のマップとテンプレートに2〜4時間、その後1週間の試行期間を確保します。難易度: 中程度です。新しいAIツールの導入より、情報源の権限を合意することの方が難しい作業です。

対象範囲: これはチーム向けの運用モデル案です。承認ルールや命名規則は推奨事項であり、Claude Code、Codex、Cline、Cowork、Copilot、ChatGPTが標準で保証する動作ではありません。上の自動目次から各実装手順に移動できます。

複数のツール、分かれたコンテキスト #

開発者と非開発者は同じプロジェクトを扱いますが、使うインターフェースは異なります。 開発者はIDEやターミナルのエージェントを使います。プロダクトオーナーはチャットプロジェクトを使います。運用担当者はWikiとトラッカーを使います。権威ある情報へのアクセスではなく、タスクに合わせてインターフェースを選びます。

コンテキストとは、現在の回答に利用できる情報です。 セッションごとにリポジトリのファイル、アップロードした文書、チャット履歴、保存メモリ、コネクターの結果、取得した抜粋を確認します。質問が同じでも、証拠が異なるセッションは一致するとは限りません。

問題見える症状
文書の陳腐化READMEが古い要件を繰り返す
要約の格上げ元の情報源がないセッション要約を証拠扱いする
重複する変更2つのエージェントが異なる基準版から同じページを置き換える
失われた決定会議での合意が決定記録に反映されない
出所の欠落もっともらしい回答にページの版やコミットが示されない

保持期間の例は両者の違いを示します。 Wikiは承認済みの目標動作を説明します。コードは実装された動作を示します。どちらも相手を黙って書き換えるべきではありません。食い違いを記録し、実装と要件のどちらを変更するか担当者に確認します。

要点: AIツールを選ぶ前に、どの情報源が正式かを決めます。以下の用語から始めてください。

用語このモデルでの意味

各事実に置き場所を1つ決める #

1つの情報源とは、事実ごとに1つの正式な情報源を設けることです。 組織全体のデータベースを1つにすることではありません。試行期間中に次の割り当てを決め、例の役割名をチームの実際の所有者に置き換えます。

情報の種類情報源となるシステム所有者書き込む人エージェントの読み方
コード、テスト、設定、スキーマリポジトリ技術メンテナーレビュー済みPRを通じた貢献者記録済みコミットのファイル
公開済みドキュメントとADRリポジトリ技術責任者同じPRを通じた貢献者版管理されたファイル
要件Wikiプロダクトオーナー所有者または承認済みの公開担当者ページIDと版
運用手順書Wiki運用責任者承認済みの公開担当者ページIDと版
ポリシーWikiポリシー責任者レビュー後に承認された公開担当者正式なページとローカルアダプター
チーム横断の決定Wikiの決定記録指名された決定責任者承認後の責任者決定IDと状態
タスクと調査結果トラッカータスク責任者人または認可された提案受付チケットキーと版
チャット、要約、埋め込みキャッシュのみセッションまたはインデックス管理者ツールと参加者参照のみ、その後に情報源を確認

アーキテクチャ決定記録（ADR） は、リポジトリ設計を規定するならコードと一緒に置きます。チーム横断の決定は共有記録に置きます。両方の範囲に及ぶ場合はリンクします。承認状態を独立した2つのコピーで管理しないでください。

ローカルのポリシーコピーは正式なポリシーページに従います。 一方、リポジトリのテストやスキーマは、それぞれの範囲における情報源です。保存場所ではなく、マップが権限を定めます。

キャッシュが情報源に優先することはありません。 要約が7日、承認済み要件が30日と示すなら、目標動作には要件を使います。矛盾する要約は競合するルールではなく、陳腐化の証拠として保存します。次に書き込み手順を定めます。

キャッシュから取り込み、提案を上げる #

エージェントは証拠をセッションコンテキストに取り込み、提案を作成します。 永続的な事実を自分で承認しません。作業ブランチを編集したり下書きを提出したりすることと、ポリシーの公開、コードのマージ、決定の承認は別です。

情報源 -> 権限を確認した読み取り -> セッションの文脈
セッションの文脈 -> 提案 + 基準版 -> 所有者のレビュー
所有者の承認 -> 制御された公開 -> 変更履歴
基準版が変更された -> 提案を照合 -> 再レビュー

レビューを依頼する前に基準版を記録します。 レビュー担当者には、以前の値、提案する値、理由、証拠、影響を受けるシステムが必要です。承認は変化し続けるチャットではなく、特定の提案版に紐付けます。

proposal_id: PROP-042
target: wiki:REQ-17
base_version: 8
change: "エクスポートを7日間ではなく30日間保持します。"
evidence:
  - "decision:DEC-12 承認済み"
affected_records:
  - "repo:export-service retention configuration"
  - "wiki:RUN-04 cleanup procedure"
owner_role: product-owner
status: awaiting-review

上の識別子は例です。 承認された論理的変更ごとに、提案ID、対象記録、変更前後の版、承認者、日時、マージまたは公開の参照先を変更ログに1行記録します。各システムの監査イベントは元の履歴を置き換えず、その行に関連付けます。

決定を担うのは人です。 認可された公開担当者または制約付き自動化が承認済みの変更を適用します。書き込み権限を制限します。指示だけで下書きと公開を分離することはできません。同じ区別は検索にも適用します。

RAGなしで共有コンテキストを作る #

プロジェクトマップを最初の検索インデックスにします。 プロジェクトごとに、情報源ID、リポジトリの場所、トラッカーキー、権限の範囲、所有者を記載したページを用意します。最初にマップを読み、IDで該当記録を取得します。IDが不明なら検索します。

サイドバー: プロジェクトマップの例 #

project: export-service
map_id: MAP-01
policy:
  source_id: POL-01
  approved_version: 3
  owner_role: policy-owner
sources:
  requirements: {page_id: REQ-17, owner_role: product-owner}
  runbook: {page_id: RUN-04, owner_role: operations-owner}
  decisions: {register_id: DEC-REGISTER, owner_role: project-lead}
repository:
  key: export-service
  setup: README.md
  terms: CONTEXT.md
  decisions: docs/adr/
tracker:
  project_key: EXP
  active_task: EXP-42

直接接続するコネクターは手作業のコピーを減らします。 Model Context Protocol（MCP）は、AIアプリケーションにツールとコンテキストを公開する統合プロトコルです。対応している場合は承認済みのWiki、トラッカー、リポジトリ用コネクターを使います。対象を絞った取得は無関係な結果を減らしますが、認可や最新性の確認に代わるものではありません。コネクター権限の設定には、参照先にあるMCPセキュリティガイダンスを使います。

正確な取得は簡単に設定できます。 ベクトルデータベースなしで引用可能な証拠を得られます。制限も明確です。マップを保守する人が必要で、広い質問には追加検索が必要になり、大きなページはセッション容量を使います。ハンドブック全体を貼るのではなく、周辺の制約とともに関連セクションを取得します。

オフライン作業では明示的なスナップショットを使います。 エクスポート版を記録し、回答がスナップショットに基づくと表示します。認可された人またはコネクターが現在の情報源を確認するまで変更を公開しません。その後、同じポリシーを各インターフェースで確認できるようにします。

1つのポリシー、異なるアダプター #

共有ポリシーは1つに保ち、ツールごとの短いアダプターを配布します。 各アダプターやコピーした指示セットの先頭行に承認済みポリシーの版を記載します。コネクターなしのセッション用に情報源IDとレビュー済みのローカルスナップショットも追加します。

ツールごとに読み込み方は異なります。 Codexは**AGENTS.mdの階層検索を説明しています。Claude CodeはCLAUDE.md、インポート、プロジェクトメモリを説明しています。Clineは.clinerules/**とルール制御を説明しています。参照先の公式説明を使います。ファイル名から同じ動作を推測せず、導入済みバージョンで読み込まれる指示を確認してください。

サイドバー: AGENTS.mdのヘッダー例 #

ポリシーのバージョン: v3 | 出典: wiki:POL-01 | 状態: 承認済み

# プロジェクトの指示

タスクを始める前にプロジェクトマップMAP-01を読みます。
docs/policy-snapshot.mdを読み込み、情報源の版を記録します。
チャットメモリと検索抜粋はキャッシュとして扱います。
事実に基づく提案には情報源の版を添付します。
開発タスクごとに1つのタスクブランチとworktreeを使います。
ポリシーを公開せず、決定を承認せず、自分のPRをマージしません。
情報源の競合が未解決、または書き込みが重複したら停止します。
必須確認: テスト、文書レビュー、ポリシーの最新性。
所有者: 開発メンテナー、プロダクトオーナー、ポリシー責任者。

チャットプロジェクトの指示にも同じヘッダーと手順を適用します。 非開発者には、承認済みのアップロードやコネクターを通じてポリシースナップショットとプロジェクトマップを提供します。インターフェースにライブアクセスがなければ、人が版付きエクスポートを渡し、その制約を記録します。

版ラベルは主張であり、内容が同じという証拠ではありません。 承認済みスナップショットからアダプターを生成するか、ポリシー部分と保存済みダイジェストを比較します。アダプター固有の例外は別にレビューします。試行期間中に無効化されたルール、入れ子の上書き、個人指示を確認します。その後、各タスクが使った証拠を記録します。

コンテキストマニフェストを記録する #

コンテキストマニフェストは回答の根拠を説明します。 ページIDと版、チケットキーとその版または更新時刻、完全なリポジトリコミットIDを記録します。取得時刻と関連セクションも含めます。利用できない記録は、記憶した要約で置き換えず、利用不可と記します。

task: EXP-42
policy: {page_id: POL-01, version: 3}
wiki:
  - {page_id: REQ-17, version: 8, section: export-retention}
tracker:
  - {issue_key: EXP-42, revision: 5}
repository:
  commit: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  files: [README.md, config/retention.yaml]
limits:
  - "運用手順書は未取得。変更は提案されていません。"

コミット値は合成例です。 実際のマニフェストでは確認したコミットに置き換えます。実際に読んだ時点で取得時刻を追加します。確認前に作成した記録はチェックリストであり、証拠ではありません。

引用は確認を助けます。 ただし、自動的な信頼を生むものではありません。重要な主張を、根拠となる記録とセクションに結び付けます。情報源が食い違う場合は両方をマニフェストに残し、未解決の差異を報告します。範囲と承認状態を確認せず、最新のタイムスタンプを選ばないでください。この証拠管理は意味検索にも適用されます。

RAGで共有コンテキストを扱う #

検索拡張生成（RAG） は、回答を作るモデルに取得した資料を渡します。意味インデックスは、質問で別の表現を使っていても関連箇所を見つけます。MicrosoftのRAG概要では、grounding、検索制約、アクセス制御を説明しています。公式情報は参照先を確認してください。

古い文書、会議メモ、文字起こしなど、大規模なコレクションの探索にはRAGを使います。 文書の分類と承認状態にラベルを付けます。元の録音から作られた文字起こしは、参加者の発言の証拠ですが、承認済み要件の権威ではありません。インデックス化によって会話をポリシーに格上げしないでください。

インデックスのルール必須の動作
キャッシュではなく情報源を取り込む生成要約と未追跡のローカルコピーを除外する
出所を維持する各チャンクに情報源ID、版、セクション、文書状態を保存する
変更時に更新する編集を再インデックスし、古いチャンクを無効にする
アクセス変更を尊重する権限を更新し、削除や取り消しの対象を除去する
引用を返す取得テキストとともに記録への参照を示す
現在の記録を確認する重要な提案の前に最新の証拠を取得する

このモデルで、取得したチャンクは参照先として機能します。 テキストは証拠を探すのに役立ちます。ライブ情報源は現在の文言、承認、例外、アクセス権を確認します。ライブ取得に失敗したらスナップショットと表示し、重要な操作を止めます。これはガバナンス上のルールであり、あらゆるRAG実装に関する主張ではありません。

古い埋め込みとコンテキスト不足は別のリスクです。 古いチャンクは改訂を見落とします。最新のチャンクでも、例外が次のセクションにあれば誤解を招きます。要件を評価する前に見出しを保ち、隣接する制約も取得します。

権限の漏えいには専用のテストが必要です。 チャンクをモデルに返す前に認可し、回答生成後に回さないでください。機密情報をインデックス化または外部埋め込みに送る前に審査します。ログ、モデル要求、取得トレースに残るコピーも考慮します。ローカルモデルを使ってもリモートコネクターはローカルになりません。これらの確認でRAGを試行に含めるべきか判断します。

マップ、RAG、または両方を選ぶ #

質問に合わせて検索方法を選びます。 既知の要件IDなら直接取得が適しています。分散した過去資料についての自由形式の質問なら検索が適しています。探索の問題が測定済みでない限り、まずマップから始めます。

サイドバー: RAGを使うべきか #

タスクでは通常、プロジェクト、ページ、issue、またはファイルを指定しますか？
  はい -> パイロットでは直接取得で十分ですか？
           はい -> マップのみ
           いいえ -> ハイブリッド: 既知IDにはマップ、探索にはRAG
  いいえ -> 証拠は大規模な集合に分散していますか？
           いいえ -> マップのみと組み込み検索
           はい -> 作業は探索的で読み取り専用ですか？
                    はい -> 探索にはRAGのみ
                    いいえ -> ライブ情報源の確認を含むハイブリッド

どの選択肢でも所有者、認可、出所を維持します。
RAGによる探索でも、永続的な操作の前に情報源を確認します。

RAG-onlyは検索インターフェースを表し、ガバナンスを省く許可ではありません。 直接の情報源を引き続き確認できる、範囲の限られた探索用コレクションで使います。正確な版確認が必要な既知IDの変更には向きません。

ハイブリッドモデルは探索と検証を分けます。 マップは既知の検索を扱い、RAGは未知の記録を探します。RAGは「どこ」を、情報源は「何」を答えます。保持期間の例では**REQ-17**を直接取得します。「過去のどのエクスポート決定がこの制限の根拠か」と尋ねる場合は記録を検索し、関連する決定を取得します。次にリポジトリ側を実践します。

リポジトリ内の情報 #

リポジトリの知識は実装に合わせて変わります。 エージェントとレビュー担当者が場所を把握できるよう、構成を簡潔にします。

ファイルまたはディレクトリ役割
CONTEXT.mdプロジェクト用語と正式な記録へのリンク
docs/adr/リポジトリの承認済みアーキテクチャ決定
docs/design/システム動作の承認済み説明
docs/plans/状態を明示した実装計画案
AGENTS.mdレビューゲート、境界、所有者の役割
README.mdセットアップと入口。要件の重複は避ける

同じPRで変更するルールを適用します。 コードと影響を受けるリポジトリ文書を同時に変更します。ナレッジベース更新が不要なら、PRの説明または合意したcommit trailer欄に例外を記載します。

KB-Update: none (理由: 内部リファクタリングは文書化済みの動作を維持する)

パイプラインが宣言を強制します。 必須チェックは、文書更新も例外もない動作変更を拒否します。文書担当者が例外をレビューします。パスに基づくチェックは候補変更を見つけますが、意味の完全性までは証明しません。ブランチ保護などを使い、チェックとレビューをマージ条件にします。

パイプラインにないゲートはゲートではありません。 指示ファイルで「ドキュメントレビュー」と述べるだけでは案内にすぎません。試行期間中に意図的に不完全なPRを出し、マージがブロックされることを確認します。

1つのタスク、1つのブランチ、1つのworktreeを使います。 Gitの公式worktree資料は、それぞれ独自のチェックアウト状態を持つ分離した作業ツリーを説明しています。別のworktreeはローカルの編集衝突を減らしますが、2つのブランチが同じファイルを変更したり、2つのエージェントが同じWikiページを編集したりすることは防ぎません。

デフォルトブランチに直接コミットしてはいけません。 main、**master**など名前は問いません。要件とコードの差はトラッカーに報告します。矛盾する記録を添付し、どちらを変更するか決める前に、所有者に意図した動作を判断してもらいます。Git以外にも同等の制御を適用します。

リポジトリ外の情報 #

Wikiには文書標準が必要です。 各正式ページに目的、状態、所有者、版、レビュー日、関連情報源IDを記載します。提案は非公式だと明示した下書き領域に置きます。提案文を承認済み要件に混ぜないでください。

安全な更新は決まった順序で行います。

  1. 再読して現在のページと周辺の制約を確認します。
  2. 比較して、提案の基準版とページの版を照合します。
  3. 調整して、途中の編集を反映し、文言が変わったら再承認を得ます。
  4. 記録して、期待版を条件に承認済みの改訂を保存します。
  5. 確認して、保存されたページを検証し、変更ログへの参照を追加します。

再読だけでは競合を防げません。 利用可能ならシステムの条件付き更新を使います。なければ1人の所有者が公開を順番に行い、結果を確認します。レビュー中に別の編集者が基準版を変えたら停止します。

削除禁止はエージェントの作業手順に適用します。 エージェントはアーカイブや削除を提案します。認可された人が保存・削除手順を実行します。この規則を機密情報の無期限保持の許可と解釈してはいけません。

トラッカーの調査結果には証拠を含めます。 観測した内容、正確なコマンドまたは確認方法、調査したコミット、期待動作、実際の動作、受け入れ基準を記録します。添付前に秘密情報や機微な出力を除去します。提案コマンドは実行されるまで未実行と記します。

調査結果: 保持処理が承認済み要件と異なる
証拠: REQ-17 v8と確認済みのconfig/retention.yaml
確認コマンド: git show HEAD:config/retention.yaml
Commit: 確認した完全なcommit IDをマニフェストに記録
受け入れ条件: 承認された期間がコード、テスト、運用手順書と一致する
状態: プロダクトと開発の責任者によるレビュー待ち

例は調査結果のテンプレートであり、実測値ではありません。 実際の確認結果を記入します。提案IDを通じてWiki更新とトラッカー証拠を関連付けます。

意思決定記録ではルールと理由を分けます。 問い、選択肢、推奨、トレードオフ、所有者、承認状態、結果のルールへの参照を保存します。エージェントは提案し、人が決めます。承認済みルールはポリシーや手順に反映し、理由は記録に残します。

会議やチャットから長期的に使う事実を取り込みます。 元の証拠を添えて提案し、承認を得ます。公開までは合意を暫定と表示します。次に、承認された動作をリポジトリとWikiの間で結び付けます。

2つのシステムをつなぐ #

マージ後の同期で実装変更を外部に伝えます。 マージ済みコミット、承認済み要件、対象の運用手順書にリンクしたWiki更新タスクを作ります。エージェントが下書きを用意し、Wiki所有者が現在のページを確認して公開を承認します。保存版を確認するまで同期タスクを開いたままにします。

ポリシーの最新性は別の監査です。 リポジトリの各アダプターやチャットの指示コピーを、正式な承認版と比較します。ポリシー**v3はPOL-01にあります。各AGENTS.mdは先頭行にv3を記載します。ラベルが一致していても、監査でv2**、ラベル欠落、内容の違いを検出します。

確認項目完了を示す証拠
ポリシーの最新性正式版とアダプターダイジェストの比較
要件の整合要件の版をコードとテストに照合
マージ後の同期マージ済みコミットを公開済みWiki版に紐付け
競合の解決所有者承認の決定を両方の対象記録に紐付け

定期的またはPR時に照合します。 試行期間では週次監査が適します。動作変更を含むPRは、マージ前に要件を確認します。陳腐化のコストに合わせて頻度を決め、最後に成功した確認日を記録します。

保持期間を30日にする変更には複数の確認点があります。 プロダクトが要件を承認し、開発が設定とテストを更新し、レビュー担当者がPRをマージし、運用が手順書を公開します。変更ログの1行に結果の記録を紐付けます。Wiki同期の失敗は成功したマージの陰に隠さず、見える状態にします。ツール間の共通引き継ぎでこの流れを保ちます。

1つの手順、すべてのツール #

繰り返し手順を、版付きの手順IDを持つスキルやプロンプトとしてまとめます。 共通契約を共有し、共通ファイル形式を想定しません。各アダプターは、そのツールがサポートする読み込みや呼び出し方法を使います。

手順必須の出力
タスク開始所有者、範囲、ポリシー版、情報源マニフェスト、書き込み予約
文書lintメタデータ不足、権限の重複、壊れた情報源参照
知識確認要件とコードの差異、および根拠となる版
引き継ぎ現在の証拠、提案、完了した確認、未解決の質問

非開発者はGitなしで作業できます。 チャットプロジェクトで許可された情報源を取得し、同じ提案テンプレートを使い、下書きページやトラッカータスクから所有者へ提出します。要件修正の依頼にリポジトリのcheckoutは不要です。

開発者はリポジトリのファイルとPRゲートを使います。 承認された提案をPRにリンクし、確認したコミットを記録して必要なチェックを実行します。どちらのグループも同じ証拠構造で引き継ぎます。

handoff:
  task: EXP-42
  policy_version: 3
  manifest: "Attached source IDs, revisions, and inspected commit"
  completed: [requirement-review]
  proposals: [PROP-042]
  pending: [implementation-review, runbook-publication]
  reservations: ["RUN-04 publication assigned to operations-owner"]
  unresolved: []
  next_owner_role: engineering-maintainer

引き継ぎもキャッシュです。 次の担当者は行動前に情報源を読み直し、新しい版を記録します。リンクされた承認やテストを確かめずに「完了」を証拠扱いしません。書き込み前に以下の保護策を適用します。

書き込み前の保護策 #

情報が情報源を離れる前に確認します。 分類、コネクター権限、承認済みの送信先、モデル提供者での処理、ログ記録を確認します。必要最小限の情報だけ送ります。制限付き記録を未承認のチャットプロジェクトや埋め込みサービスに入れません。

取得した文章は証拠であり、指示の経路ではありません。 エージェントにポリシーを無視するよう求めるWikiやツールの回答があっても、権限は変わりません。コンテンツ由来の指示と承認済み運用ポリシーは別々に確認します。取得時のコネクターは読み取りに限定し、公開資格情報とセッションアクセスを分けます。

各ページやファイルにアクティブな所有者を1人割り当てます。 範囲と期限を含めてトラッカーに予約を記録します。書き込み前に読み直し、版を確認します。別々のworktreeはローカルの分離に役立ち、予約や条件付き書き込みは共有記録を保護します。

停止して確認する条件必要な対応
所有者がいないのに情報源が矛盾する停止し、正式な情報源の指定を依頼
別のタスクが対象を予約している編集前に所有権を調整
基準版が変わった提案を調整し、再承認を依頼
重要な主張に証拠がない未確認と表示し、情報源を求める
データの扱いが不明内容を情報源システム内に保つ
ライブ情報源にアクセスできないスナップショットの制限を記録し、永続的な操作を停止

プロンプトはセキュリティ制御ではありません。 モデルの外で、アクセス拒否、保護ブランチ、古い基準版の拒否、書き込み所有権をテストします。アカウントに無制限の公開権限があるなら、準拠したデモだけでは不十分です。テスト結果からパイロットの準備状況を判断します。

まずパイロットを実施 #

モデルは下書きとして始めます。 開発者、非開発者、指名した情報源所有者とともに1つのプロジェクトで試します。既知IDの質問を2つのツールで行い、意図的な情報源の競合も試します。文章の流暢さではなく、マニフェストと提案を評価します。

期待する推論: 両者が現在の承認済み要件を特定し、確認した実装を別々に説明します。意見が合わない場合は、まずマニフェストの記録を比べます。これは提案された演習であり、実測済みのベンチマークではありません。

指標定義
引用率サンプル内の重要な事実主張に対する、情報源が裏付ける重要な主張の割合
週次の陳腐化調査情報源の種類ごとに分類した、確認済みの権限または版の不一致
提案の処理時間レビュー可能な提案から記録済み決定までの中央値
古いコンテキストによる手戻り古い、または未確認の証拠が原因で再開したタスク

目標を決める前に基準値を測ります。 初週に陳腐化の調査結果が増えても、文書が悪化したのではなく検出が改善した可能性があります。件数だけでなく、再発と解決時間も追跡します。機密の証拠を分析用エクスポートへコピーせずにレビューします。

展開時にサンプルリポジトリを用意します。 合成マップ、ポリシーアダプター、マニフェスト、提案テンプレート、文書例外、実行可能なレビュー確認を含めます。本番資格情報のない、架空のWikiやトラッカー記録を使います。公開拒否、変更された基準版の拒否、ポリシー版の陳腐化、正常な引き継ぎを実演します。

テンプレートリポジトリは展開時の成果物であり、この記事に付属するものではありません。 経営層と情報源所有者がパイロット結果をレビューした後に運用モデルを拡張します。例外と未解決の失敗は意思決定記録に残します。拡張前に、以下の予測可能な問題を修正します。

共有コンテキストのトラブルシューティング #

症状最初の修正
2つのツールで回答が異なる情報源ID、版、範囲、承認状態を比べる
指示は最新なのに動作が異なる読み込まれたアダプター、ルール切替、ローカル上書きを調べる
RAGが古い要件を返すインデックス更新を確認し、ライブページを取得
Wikiの編集が別の変更を消す条件付き書き込みまたは順次公開を要求
古い文言でも文書チェックが通る所有者レビューと要件照合を追加
決定がチャットに残る提案の受付と記録の所有者を割り当てる

プロンプトを書き換える前に、証拠の経路を直します。 次に失敗したパイロットケースをやり直し、結果を記録します。以下のチェックリストを使って、修正した手順を毎週繰り返します。

今週の10ステップ #

  1. 1つのパイロットプロジェクトと参加する人やツールを選びます。
  2. 情報の種類ごとに正式な場所と所有者を割り当てます。
  3. 情報源IDと権限範囲を示すプロジェクトマップを公開します。
  4. 共有ポリシーの案を作り、所有者のレビューを得ます。
  5. 各指示アダプターの版を先頭行に記載し、読み込みを確認します。
  6. 重要な事実回答と提案にコンテキストマニフェストを要求します。
  7. 基準版と承認者を含む提案受付経路を作ります。
  8. 書き込み制御と同一PRの文書更新ルールを強制します。
  9. 合成記録で陳腐化、競合、引き継ぎをテストします。
  10. パイロット指標を確認し、次の展開段階を承認します。

各事実に正式な場所を1つ設け、すべてのツールにそこを読ませ、永続的な変更は人を通します。

参考資料と次のステップ #

公式ドキュメントが説明するのは技術要素であり、このモデルの組織ルールではありません。 試行期間中に、インストール済みツールの動作とコネクター権限を確認します。

  • Codexの指示: AGENTS.mdを使ったカスタム指示 、指示の検索と確認について。
  • Claude Codeの指示: Claudeがプロジェクトを記憶する方法 、プロジェクト指示とメモリについて。
