長いコンテキストを使うHermesの作業なら、16GBのRTX 5060 Tiを2枚使ったQwen3.5 35Bから始めます。検証した経路はLiteLLM経由で239,153個の入力トークンを保持し、ツール、ストリーミング、画像認識、キュー処理、キャンセルを個別に通過しました。1枚で使う代替候補はQwen3.6です。RTX 3060 TiやRTX 3070のシステムではQwen3.5 2Bまたは4Bから始めます。

この選択は、エージェントが使う推論経路でモデルを実行して得たものです。長い入力の保持、ツールの往復、ストリーミング応答、画像への質問、モデルの解放を検証しました。経路に関わるモードとメモリー設定もテストしました。モデルを読み込めても、長いエージェント要求で役立つとは限らないためです。

ツールを使うエージェントには、Hermesは少なくとも64,000個のコンテキストトークンを必要とします。長いコンテキストの合格基準には、実際に処理した65,536個の入力トークンを使いました。サーバーが宣伝するコンテキスト長より、入力トークン数のほうが重要です。( Hermes Agentプロバイダーのドキュメント )

結果全体で、システムの文字は以下のハードウェア構成を表します。

D1 × RTX 2000E Ada, 16GBテスト済みの大型モデル負荷にはQwen3.5 9B、Gemma 4 12B-IT、またはGPT-OSS 20B

カードの搭載数は、毎回すべてのGPUを使ったという意味ではありません。Qwen3.5 35BとFlash Nextの試験ではシステムAの2枚を使いました。Qwen3.6は1枚で動きました。システムEで成功したQwen3.5 4Bの画像認識再試験では、8枚のプールから1枚を選び、9枚目はAI用途から除外しました。

以下の時間は、検証したモデル、実行環境、システムを組み合わせた結果です。実用可能な構成を比較しており、速度差の原因としてGPUアーキテクチャだけを切り分けたものではありません。

RTX 5060 Tiを2枚使うQwen3.5 35Bを長いコンテキスト用に選ぶ理由 #

今回の試験ではQwen3.5 35Bが最も多く入力を保持しました。Ollamaの直接実行では、実行時コンテキスト262,144個の中に248,279個の入力トークンを保持しました。別のゲートウェイ経由ストリーミング要求は239,153個を保持し、冒頭マーカーを返し、出力31トークンで148.12秒後に正常終了しました。

要求がブローカーとLiteLLMを通過したため、ゲートウェイの結果はHermesにとって重要です。別々の要求でツールの往復を完了し、赤い画像を認識し、同時送信した2件の要求に正しく回答しました。ブローカーは2件をキューに入れました。ストリーミング要求を閉じるとブローカーが解放され、60.31秒以内にモデルがアンロードされました。

段階的な直接要求では、拡張する共通プレフィックスを再利用しました。所要時間はウォーム状態での継続処理です。54.215秒という値は、新しい248Kプロンプトを処理する独立したコールド計測ではありません。

最大の直接実行段階では、2枚のGPU全体で約273億バイトが常駐しているとモデルが報告しました。カードごとのメモリピークは14,964 MiBと12,386 MiBでした。

最高温度は62°Cと63°Cで、OOMやXidの障害は記録されませんでした。設定したコンテキストには継続用として13,865トークンが残り、短いマーカー応答はそのうち31トークンを使いました。

大きな作業セットを保持することが最短の初回応答より重要なら、この経路を選びます。ツールと画像の検証はエージェントに役立つ挙動を確認し、長い入力の試験は保持を確認します。別々のワークロードです。

Qwen3.6は1枚で使う選択肢 #

Qwen3.6-35B-A3B UD-Q4_K_XLは、RTX 5060 Ti 1枚で131,000個の入力トークンを保持しました。試験中、もう1枚はアイドル状態でした。2枚を1モデルに割り当てたくない場合に有用な代替手段です。

Qwen3.6のゲートウェイ要求入力トークン出力トークン時間結果
初回の長時間リクエスト66,007167.82 s冒頭マーカーを保持
より長いリクエスト90,00011159.92 s冒頭マーカーを保持, zero cached input
より長いリクエスト119,99911250.61 s冒頭マーカーを保持, zero cached input
実行時間の上限近く131,00011287.09 s冒頭マーカーを保持, zero cached input

131,000トークンの要求は、実行時上限131,072に近づきました。エージェント用なら回答と後続のツールメッセージのために、もっと余裕を残します。上限近くでの保持結果は入力処理の証拠にはなりますが、妥当な既定入力予算ではありません。

思考を無効にするとツールを使えました。既定の思考モードはツール呼び出しの前に試験上限512トークンを使い切りました。成功したパイロットでは高速、ストリーミング、画像認識の要求も通過しました。最初の65,845トークンのコンテキスト確認には139.57秒かかりました。

同じ66K入力でQwen3.8 27Bが応答比較に勝つ #

システムAで同じ66,007トークンのマーカー課題を実行すると、Qwen3.8 27Bが最速で回答しました。検証した入力サイズ付近ではこの経路を使い、大きな作業セットにはQwen3.5 35Bを併用します。

システムAの経路入力トークン時間結果
Qwen3.8 27B66,00754.64 s冒頭マーカーを保持
Qwen3.6-35B-A3B UD-Q4_K_XL66,007167.82 s冒頭マーカーを保持
Qwen3.8-Flash-Next UD-IQ4_XS66,007164.58 s冒頭マーカーを保持
Flash Next IQ4 compatibility alias66,007213.25 sマーカーを保持

Qwen3.8 27Bの所要時間は、比較したQwen3.6やFlash Nextの約3分の1でした。検証環境で要求全体を実行した観測値であり、ハードウェアのみの比較ではありません。

高速応答、ストリーミング、ツール利用も通過しました。思考なしモードは色の全シーケンスとツール往復を完了し、思考あり試験は512トークン内でシーケンスの一部だけを返しました。

メモリー負荷のため、Flash Nextはこのシステムの既定候補としては魅力が下がります。65,847トークンのパイロットは実行時コンテキスト98,304で201.41秒かかりました。以前のコンテキスト131,072の2プロファイルは、準備完了前にメモリー上限へ達しました。

後の経路はcgroup上限54 GiBに達しました。無人運用ならメモリー余裕の大きい経路を選びます。

flash-iq2という名前の経路はFlash Next IQ4互換バックエンドを使いました。この名前はIQ2の結果を示しません。

システムCでは、ストリーミングでもGemma 4の長いプリフィル待ちは短くなりませんでした。最初のストリーム内容は277.49秒後に届き、非ストリーミングの完全な応答274.24秒より遅くなりました。前の非ストリーミング試行はタイムアウトし、その後の再試験で成功しました。初期処理に数分かかってもよい作業に限って使います。

Gemma 3 4Bは、検証を各システム単位で考える必要も示しています。システムDは65Kの想起試験2回で冒頭マーカーを見失い、そのうち1回は温度ゼロ、入力67,252トークンでの再試験でした。決定的な要求はGPUを完全に使用した状態で62.07秒後に正常終了しました。

すぐ完了し、通常のAPI応答が返っても、回答が正しいとは限りません。システムCの成功経路を使い、システムDの失敗経路はHermesの選択から外します。

思考モードでQwen3.5 0.8Bの有用性が決まる #

思考を無効にすると、Qwen3.5 0.8BはシステムCで範囲を絞った想起に使える候補になりました。小型Q8_0モデルはゲートウェイ経由で75,649個の入力トークンを65.92秒で保持しました。この結果は検証したQ8_0アーティファクトと非思考経路に限られ、他の表にある旧16Kコンテキスト構成には当てはまりません。

思考無効、条件を揃えた診断9,055217.65 s冒頭マーカー一致, no reasoning text
デフォルト思考での長時間試行600秒でタイムアウト回答未完了

同条件の診断は66.56秒から7.65秒へ、約8.7倍速くなり、生成出力は3,391トークンから21トークンへ減りました。単純な抽出やルーティングでは推論モードを明示します。既定の推論は不要な出力に処理の大半を費やしました。

短いOpenAI互換プローブはマーカーを見つけられませんでしたが、温度ゼロでの再試験は成功しました。成功した経路は非思考モードと出力上限なしの自然終了を使いました。他の3ゲートウェイも短いマーカー要求を4.22秒、4.37秒、3.85秒で処理しました。これらはルーティングを確認し、75,649トークン要求は長い入力の保持を確認します。

範囲を絞った想起と抽出にはこの経路を試します。自由形式のエージェント推論にはもっと大きいモデルを選びます。合成マーカーを1つ取り出す作業は、計画、コーディング、複数ツールの調整より限定的です。

RTX 3060 TiとRTX 3070ではQwen3.5 2Bと4Bが有力 #

8GBカードの実用的な開始候補はQwen3.5 2Bと4Bです。システムE、F、Gでテキストコンテキスト要求を実行し、65,579個を保持して30.343秒から93.753秒で完了しました。検証した4B経路はツール、ストリーミング、画像認識も通過しました。

システムEでの4B画像コンテキスト再試験は、65,637個の入力トークンを44.88秒で処理し、両方のマーカーと画像の色順を保持しました。色順を前後反転した要求も通過しました。別のカードがXid 79リンク障害を起こして再起動した後、正常な1枚を使いました。

E, RTX 3060 Ti pool65,579 tokens, 30.343 s65,579 tokens, 53.787 s65,637 tokens, 44.88 s
F, RTX 3060 Ti pool65,579 tokens, 61.282 s65,579 tokens, 93.753 s65,635 tokens, 84.749 s
G, RTX 3070 pool65,579 tokens, 76.731 s65,579 tokens, 90.807 s65,635 tokens, 87.496 s

各システムで29件の検査に合格しました。2つのRTX 3060 Tiシステム間の時間差も、要求時間だけでカードを順位付けせず、検証済みシステムプロファイルを選ぶ理由になります。

7システムすべてが推論時間後にマイニングへ戻りました。システムBの停止後回復確認は新たに承認されたシェアで成功しました。システムEの故障カードは再起動とPCIeリンク強化の後にマイニングへ復帰しましたが、AIプールからの除外は維持されました。試験時間の終わりにマイニングを戻すことと、1つの推論要求後に自動で引き渡すことは別の結果です。

モデルの読み込みだけでは適格にならない #

DeepSeek Coder V2 16Bは、検証したHermes 65K候補から外します。f16キャッシュの実行は50,477個の入力トークンを保持しましたが、65K目標の試験はVRAMガードに達しました。Q4とQ8のキャッシュ案は重みをGPUに読み込んだ後、ホストメモリー上限か長いプロンプトの低スループットにぶつかりました。

DeepSeek Coder V2のキャッシュプロファイル実行時コンテキスト観測結果評価
f1681,92050,477トークンの想起に成功、過大なリクエストは拒否短いコンテキストで有用な結果
f1673,72865K目標のプレフィルをGPU使用量15,802 MiBで停止65Kの要件を満たさない
Q4_098,304制御停止前に長いプレフィルは96.72 token/sまで低下このワークロードには不向き
Q8_077,824制御停止前に長いプレフィルは120.12 token/sまで低下このワークロードには不向き
Q4_0 / Q8_0, より大きなプロファイル163,840 / 98,304ホストメモリ保護により試験は停止したメモリ適合性はシステム全体で判断する必要がある

実務上の教訓は、送信予定の要求をベンチマークすることです。GPU常駐、短い回答、大きく設定したコンテキストだけでは、実用的な遅延で長い入力を保持できる証拠になりません。

システムAで経路別の追試を行うと、Granite 4.2 8BとGPT-OSS 20Bは改善しました。GraniteのQ6_K経路は入力キャッシュなしで66,082個を88.636秒で保持しました。GPT-OSSはブローカー修正後にツール往復を完了し、呼び出しに9.854秒、後続に9.849秒かかりました。成功した確認は以前の未完了試験と分けて扱います。

Hermesの実用性を検証した方法 #

長いプロンプトの冒頭近くに合成マーカーを置き、埋め草の後でマーカーを返すよう求めました。回答には期待した値が必要です。要求サイズはサーバー報告の入力トークン数で決めました。大きな入力後に普通に答えられても、冒頭マーカーを誤れば失敗です。

Qwen3.5 35Bの進行テストでは番号付き埋め草レコード、温度0、3,800、6,800、10,000、13,600レコードの順に使いました。各段階のプロンプトは69,429、124,179、182,579、248,279トークンでした。モデルを段階間で読み込んだままにしてプレフィックスを再利用しました。Qwen3.6の上限付近の個別確認ではキャッシュトークンがゼロでした。

0.8Bの長いプロンプトではriver stone lantern orchard circuit velvet compass marbleを8,400回繰り返し、最初の回答キーと最後の想起質問の間に置きました。ネイティブ実行はthink:false、num_ctx:131072、stream:false、keep_alive:0を使いました。OpenAI互換経路はreasoning_effort:"none"を使いました。ブローカーは非思考モードを強制しました。

ツール、画像、解放の確認 #

ツールの要求と結果返却後の回答を確認しました。簡単な試験ではadd_numbers(7, 11)を使い18を期待しました。Qwen3.5 35Bではlookup_squareを使い49を期待しました。GPT-OSSには在庫検索をさせ、返された内容を反映させました。

画像確認では赤と青の画像質問、画像順の反転、画像色と冒頭・末尾マーカーを含む長いプロンプトを使いました。Qwen3.5 35B試験では256×256の赤いPNGを使いました。要求が通る前にブローカーの画像コンテンツ変換を修正しました。システムEの4B長文画像試験では両マーカーと色順の保持が必要でした。

長い実行の前後でGPUメモリー、モデル常駐、温度、ホストメモリー負荷、OOMイベント、GPU障害を確認しました。Qwen3.5 35Bのガードは制御した中断後の解放も検査しました。後のクライアントキャンセルとキュー試験ではブローカー経路を確認しました。キュー内の2要求は検証負荷での処理を示し、独立したGPUバックエンド2つの同時稼働を示すものではありません。

性能結果の読み方 #

要求時間には長い入力の事前処理と返却された回答が含まれます。生成トークン毎秒ではありません。ストリーミングでは最初の内容までの遅延が重要で、キャッシュ済みプレフィックスの進行は別に解釈します。

システムAとCで成功した大型モデルの追試は、マイニング停止中の専用推論時間枠で行いました。要求後にモデルをアンロードしました。7システムのマイニングは試験枠の終わりに復旧しました。これは推論時間中のモデルサービスを示し、マイニングと推論の同時実行を示すものではありません。

Hermesで使うモデル構成 #

2枚のRTX 5060 TiがあるシステムではQwen3.5 35Bを高コンテキストの主経路にします。ゲートウェイ経由で239,153トークンを保持し、ツールと画像の個別試験に通り、要求後に解放されたことも確認できました。大きなコンテキストを宣伝するだけのモデルより有力です。66Kで速い応答にはQwen3.8 27B、1枚運用を優先する場合はQwen3.6を残します。

RTX 2000E Adaでは、検証済みのシステムC Gemma 3 4B経路を長文入力の応答作業に選びます。狭い想起・抽出には思考なしのQwen3.5 0.8Bを試します。4～5分の初回応答を許容できる作業なら大型Gemma、Qwen、GPT-OSS経路も候補です。システムDで失敗したGemma 3経路は除外します。

8GBのRTX 3060 TiとRTX 3070ではQwen3.5 2Bか4Bから始めます。65Kのテキスト結果と4Bの画像確認は、16GBカード2枚を毎回使わない実用的な初期構成を支えます。Flash Nextのメモリー負荷とDeepSeek Coder V2の不完全な65K動作は、検証プロファイルでの既定候補として不利です。

このモデルとシステムの選択は特定の作業を対象にしています。入力保持、ツール往復の正しさ、画像認識、確実な解放はHermesの実用性の異なる面を確認します。信頼できる構成にはエージェントが使う動作と、回答やツール通信のための十分なコンテキストが必要です。
