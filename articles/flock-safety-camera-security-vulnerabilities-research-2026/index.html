50件を超える重大なセキュリティ脆弱性が、国内最大の民間監視ネットワークを危険にさらしています

はじめに: 国家安全保障上の危機 #

2024年後半から2025年を通じて、独立系セキュリティ研究者は、米国史上法執行機関の監視技術で最も深刻なセキュリティ障害といえる問題を発見しました。Flock Safetyのカメラシステムで50件を超える重大な脆弱性が見つかりました。同社のカメラは、全国の8万件を超える導入先で、毎日1億5,000万台以上の車両を撮影し、追跡しています。

この記事では、次の資料に基づき、脆弱性を包括的に技術分析します。

  • GainSecの正式なホワイトペーパー「Examining the Security Posture of an Anti-Crime Ecosystem」（51件の指摘、22件のCVE割り当て、8件が保留中）
  • Ben Jordanによる調査報道と実地のセキュリティテスト
  • 404 Mediaによる報道、公開状態にあったカメラ映像について
  • Flock Safetyと米国上院議員の公式回答
  • National Vulnerability Database（NVD）に公開された情報
  • Distributed Denial of Secretsが公開した2026年9月のファイルシステムダンプ、Micah Leeによる詳細な技術分析、WIREDと404 Mediaの共同調査

これらのカメラが設置される理由とプライバシーへの影響については、関連記事をご覧ください: Flock Safety監視カメラ: 普及状況、プライバシー上の懸念、保護策

カメラの検出方法については、こちらをご覧ください: Flock-You検出プロジェクト: 対監視ハードウェアガイド

脆弱性の分類 #

50件を超える脆弱性は複数の分類にまたがります。

  1. 認証と認可（ハードコードされたパスワード、多要素認証の欠如）
  2. 暗号技術と暗号化（保存時および転送時にデータが暗号化されていない）
  3. ネットワークセキュリティ（露出したWi-Fiアクセスポイント、平文の認証情報）
  4. 物理セキュリティ（ボタン操作を使う攻撃、露出したUSBポート）
  5. データプライバシー（無許可のデータ収集、長期保存）
  6. システム設計（古いソフトウェア、不十分なアクセス制御）
  7. 情報漏えい（公開されたAPIキー、一般公開されたカメラ映像）

2026年9月のファイルシステムダンプ #

2026年9月、透明性を掲げる非営利団体Distributed Denial of Secretsは、稼働中のFlockカメラから取得した完全なファイルシステムイメージを公開しました。 stegan0gramと名乗る集団がカメラを支柱から取り外し、内部ストレージを複製してイメージを公開しました。404 MediaとWIREDは共同調査を行い、セキュリティ研究者のMicah Leeが内容の技術分析を公開しました。

この記事で先に紹介した調査結果は、研究者の実験機や購入した端末に基づいていました。今回のデータセットは、自治体で実際に稼働していたカメラから取得したもので、これまでに公開された中で最も強い証拠です。

カメラはネットワーク経由で侵害されたのではありません。物理的に取り外されました。

ダンプに含まれるもの #

公開されたデータには3つのパーティションイメージが含まれ、それぞれ異なる問題を示しています。

パーティションサイズ重要性

認証情報の問題が確認された #

このダンプにより、ハードコードされた認証情報が理論上の問題なのか、実運用でも使われているのかが明らかになりました。実運用されています。

FlockのバックエンドにアクセスできるAPIキーが、アプリケーションのバイナリにハードコードされています。 値はcom.flocksafety.android.common.lib内のCameraSettingsというクラスに格納されています。Flockは共有ライブラリを19個すべてのアプリに組み込んでいるため、全アプリにキーが含まれます。flock-sambucaアプリはプロビジョニング時にこのキーを使います。

認証の流れは次のとおりです。

  1. 各カメラがFlockサーバーに認証情報を要求し、MACアドレスで自身を識別
  2. FlockのOkta Auth0ログインサービスが有効期限の短いFlockAuth0Tokenを返す
  3. カメラが返された認証情報を平文で保存

Auth0のクライアントIDとクライアントシークレットは、暗号化されていない/persistパーティションにある、工場出荷時リセット後も残るファイルに保存されています。保護されていないため、攻撃者はまずpersistパーティションを取得します。

プラットフォーム全体でハードコードされた秘密情報については、 重大な脆弱性#4 で説明します。

錠前の横に置かれた暗号化キー #

Flockは、カメラを端末上の暗号化で保護していると説明しています。ダンプは実際の実装を明らかにしました。

18 GBのmediaパーティションは暗号化コンテナ内にあります。復号キーは同じパーティションにあり、拡張子.keyのファイルとして保存されています。stegan0gramはキーを復元し、コンテナのロックを解除して内容を読み取りました。鍵をふたに貼り付けた箱のように、画像は暗号化されています。

復元されたログからカメラの位置も判明しました。GPS座標はログに155回記録され、半径約100メートルの範囲に集中していました。これは支柱に固定された受信機で通常起こる誤差です。座標はミルウォーキー郊外のウィスコンシン州ウォーワトサを示しており、カメラはN Mayfair Roadに設置されていました。Micah LeeはGoogle Street Viewとログを照合し、シリアル番号とMACアドレスから個別の機器を特定しました。

暗号文の隣にキーを保存していれば、保存時の暗号化に意味はありません。

Flockの説明 #

Flockの回答は、GainSecによる以前の調査結果への立場を繰り返すものでした。広報担当者は次のように述べました。

「Flockはセキュリティを重視し、セキュリティ研究者が潜在的な脆弱性を直接報告できる公開の脆弱性開示ポリシーを設けています。当社はこのプロセスを通じた報告を受けていません。提供された情報は限られており、主張を評価する詳細が不足しています。」

この回答は経緯と整合しません。カメラのOSの脆弱性は2018年と2021年に公開修正されていました。認証情報の保管とキー管理の基準は、カメラの出荷よりずっと前から変わっていません。10年分の公開された脆弱性履歴の確認に、外部からの報告は必要ありません。

Flockは、カメラの撤去と分析は違法だとも述べました。現行法ではそのとおりですが、機器の入手方法にかかわらず、セキュリティ上の調査結果は変わりません。

以前の調査より重要な理由 #

GainSecのホワイトペーパーは、合法的に入手した機器について51件の問題を記録しました。Flockは深刻度に異議を唱え、物理的な近接が必要だと主張しました。

このダンプによって、その留保は解消されます。運用中のカメラには、インフラの認証情報が平文で含まれ、保護対象データの隣にキーが置かれ、8年間セキュリティ更新を受けていないOSが搭載されていました。エクスプロイトは不要でした。必要だったのはレンチだけです。

Bravoは正反対の例です。 Android 13を搭載した最新の計算機で、カメラ映像にAI推論を適用しています。必要と判断すれば最新ソフトウェアを出荷できることを示しています。

重大な脆弱性#1: ボタン操作で起動する無線アクセスポイント #

CVE-2025-59403 #

深刻度: 重大 (CVSS 9.8)

攻撃方法 #

発見された中でも特に深刻な脆弱性により、Flock Safetyカメラへ物理的にアクセスできる人なら誰でも、60秒以内に完全な制御を得られます。

手順1: Falcon/Sparrowカメラ背面のボタンを3回押す 手順2: デバイスがオープンなWi-Fiアクセスポイントを作成 手順3: Wi-Fiネットワークに接続（ハードコードされたパスワードはGainSecのホワイトペーパーに記載） 手順4: ADB（Android Debug Bridge）を有効にするコマンドを送信 手順5: ADBで接続し、rootシェルを取得

技術的な詳細 #

デバイス: Flock Safety Falcon/Sparrow ALPRカメラ
ハードウェア: Android Things 8.0/8.1（2021年にサポート終了）
攻撃経路: ボタンを物理的に押す一連の操作
認証: ハードコードされたWiFiパスワード（全デバイス共通）
影響: デバイスの完全な侵害、データの持ち出し、マルウェアのインストール

可能になること #

シェルにアクセスされると、攻撃者は次の操作を実行できます。

  • 保存されている画像をすべて抽出（車両だけでなく人物も含む）
  • デバイス上の証拠を変更または削除
  • 再起動後も残る永続的なマルウェアをインストール
  • なりすまし用にデバイスのIDを複製
  • 映像ストリームを傍受して変更
  • DDoS攻撃用ボットネットのクライアントとしてデバイスを利用
  • 周辺デバイスのWi-Fi認証情報を取得（ハニーポット攻撃）
  • カメラを無効化、またはサービス拒否を起こす

実演 #

セキュリティ研究者のBen JordanはYouTubeでこの攻撃を実演し、次の内容を示しました。

  • 30秒未満でWi-Fiアクセスポイントに接続
  • 合計60秒未満でrootシェルを取得
  • ファイルシステム、保存画像、システムメモリへ完全にアクセス
  • 任意のAndroidアプリをインストール

実演からの引用:

「このアクセスポイントのパスワードは[REDACTED]で、すべて小文字です。試したカメラはすべて同じハードコードされたパスワードでした。次にADBを有効にするコマンドを送れば……おそらく30秒もかからず、デバイスのシェルを完全に取得して全面的にアクセスできます。」

ベンダーの対応 #

Flock Safetyは当初、脆弱性はクラウドに接続されていないデバイスだけに影響すると主張し、 「トラックから盗まれ、接続前のiPhone」 にたとえました。

この主張は否定されました。 研究者はクラウド接続済みのデバイス、同じ脆弱性がある複数モデルのカメラ、異なる入手元のデバイスで再現しました。いずれも同じ欠陥を示しました。

重大な脆弱性#3: 実行時の暗号化がない #

CVE-2025-47824とCVE-2025-59407 #

深刻度: 高から重大 (CVSS 2.0〜9.8)

Flock Safetyの主張と実態 #

Flock Safetyのウェブサイトの説明:

「データと映像はライフサイクル全体を通じて暗号化されています」

独立研究者の調査結果（GainSecとBen Jordan）:

「調査で復号や解読をしたものはありません。すべて実行時に暗号化されていませんでした」

宣伝文句と技術的な実態の差は決定的です。

暗号化されていないデータ #

研究者がデバイスを調査したところ、次のデータが暗号化されていませんでした。

  1. 保存された動画と画像
  2. ナンバープレートデータとメタデータ
  3. Wi-Fi認証情報とAPIキー
  4. 検出記録を含むデータベースファイル
  5. ネットワークトラフィック（脆弱性#6を参照）
  6. 機微情報を含むシステムログ

データ保存期間の矛盾 #

Flock Safetyの説明: データは7日後に自動削除される 研究結果: デバイスの製造時に撮影された画像が見つかった（数カ月から数年前）

GainSecホワイトペーパーからの抜粋:

「7日より古い画像が見つかりました。実際、デバイスを製造した工場でカメラが反応した際に撮影された画像が保存されていました。」

つまり、説明されているプライバシーポリシーはデバイス上で適用されていません。

プライバシーへの影響 #

この暗号化の欠如により、次の問題が生じます。

  • デバイスの物理的な盗難が即時のデータ侵害につながる
  • ネットワーク傍受で平文データが露出する
  • 内部関係者が容易にデータを持ち出せる
  • 暗号化されていないデータには令状による保護が適用されない可能性がある
  • 複数の規制（HIPAA、CCPAなど）への準拠違反につながる

重大な脆弱性#4: システム全体にハードコードされた認証情報 #

CVE-2025-47818、CVE-2025-47821、CVE-2025-47823、CVE-2025-59407、CVE-2025-59409 #

深刻度: 重大 (最大CVSS 9.8)

ハードコードされた秘密情報の分類 #

セキュリティ研究者は多数のハードコードされた認証情報を発見しました。

1. Wi-Fiアクセスポイントのパスワード #

  • Falcon/Sparrow全機種で共通のパスワード
  • ユーザーや管理者が変更できない
  • 研究者に知られており、ホワイトペーパーで公開（該当箇所は伏字）
  • CVE-2025-59409で確認: FalconおよびSparrowの量産ファームウェア（ビルドOPM1.171019.026）に開発用Wi-Fi認証情報が平文で保存

2. APIキーとトークン #

  • ファームウェアとアプリケーションコードにハードコード
  • 複数サービスのバックエンドにアクセスできる
  • Android APKのリバースエンジニアリングで発見
  • 2026年9月のダンプで確認: バックエンドAPIキーがcom.flocksafety.android.common.lib内のCameraSettingsにハードコードされ、端末上のFlock製アプリ19個すべてに組み込まれている
  • Auth0のクライアントIDとシークレットが、暗号化されていない/persistパーティションのflock/auth0/auth0_credに保存。工場出荷時リセット後も残る場所
  • カメラがMACアドレスを使ってFlockのOkta Auth0サービスで認証した後、返された認証情報は平文で保存される

3. データベース認証情報 #

  • パスワード保護されていないSQLiteデータベース
  • 設定ファイル内のMySQL/PostgreSQL認証情報
  • ローカルシェルからのデータベースへの直接アクセス

4. 暗号鍵ストア #

  • CVE-2025-59407で確認: DetectionProcessingアプリはJavaキーストアとハードコードされたパスワードを一緒に含み、キーストアに秘密鍵を保存
  • 深刻度: 重大 (CVSS 9.8)。保護するはずのバイナリと鍵素材が一緒に配布されるため

5. Wi-Fiネットワーク名 #

  • 優先ネットワークの一覧がファームウェアにハードコード
  • 不正アクセスポイント攻撃が可能（脆弱性#6を参照）

6. クラウドサービス認証情報 #

  • AWS/Azureトークンをコードに埋め込み
  • サードパーティAPIキー（ArcGIS、地図サービス）
  • ローテーションされないOAuthトークン

攻撃シナリオ: 偽のネットワーク #

ハードコードされたWi-Fiネットワーク名を使い、研究者は次の攻撃を実演しました。

  1. 攻撃者がハードコードされたSSIDと同じ偽のWi-Fiネットワークを用意
  2. カメラが自動接続（ハードコードされたネットワークを優先）
  3. 攻撃者が中間者攻撃ですべてのネットワーク通信を傍受
  4. トラフィックから平文の認証情報を抽出
  5. 攻撃者がバックエンドシステムにアクセス

カメラへの物理アクセスは不要です。 Wi-Fiの通信範囲内にいるだけで十分です。

重大な脆弱性#5: 多要素認証の欠如 #

組織のポリシー上の問題 #

深刻度: 高（組織的な問題）

明らかになった事実 #

一部の法執行機関では、Flock Safetyが2FA/MFAを必須にしていません。その機関は、毎日1億5,000万台の車両の追跡データにアクセスしています。

セキュリティ研究者の発言:

「初めてこれを知ったとき、信じられませんでした。Disney Plusにログインするときのセキュリティ手続きですら、機密情報や、ほぼすべての人の位置情報にアクセスする警察署には負担が大きすぎるということです。」

重要な理由 #

MFA/2FAがなければ:

  • パスワードを1つ盗まれるだけでシステム全体にアクセスされる
  • フィッシング攻撃が非常に効果的になる
  • 他の侵害で得た情報を使うクレデンシャルスタッフィングが機能する
  • 内部関係者による脅威を実行しやすくなる
  • 盗難デバイスからすぐにアクセスされる

比較 #

機微性が低いシステムのセキュリティ要件:

  • Disney+: 2FAを利用可能
  • Gmail: 新規アカウントでは2FAが初期設定
  • 銀行: 法律により2FAを必須化
  • ソーシャルメディア: 2FAが標準

毎日1億5,000万台以上の車両を追跡するシステムのセキュリティ要件:

  • Flock Safety: 2FAは任意（一部の機関は使っていない）

米国上院議員の対応 #

この調査結果は、FTC調査を求めたWyden上院議員の書簡で特に取り上げられ、Flock Safetyが次の状態を招いた証拠とされました。

「ハッカーや外国のスパイに、米国民の機微な個人情報を不必要に盗まれる危険にさらした」

簡単な解決策 #

USB/NFCセキュリティキーは10〜25ドルで、次の利点があります。

  • フィッシング耐性のある認証
  • 追加のアプリやコードが不要
  • FIDO2/WebAuthn標準に準拠
  • 簡単な操作（差し込む、またはデバイスをタップ）

法執行機関の職員にとって「面倒すぎる」のであれば、国家規模の監視システムにアクセスさせるべきではありません。

重大な脆弱性#6: 平文のネットワーク通信 #

識別子の割り当て待ち #

深刻度: 高（研究者はCVSS 7.8と推定）

この分類にCVE識別子は割り当てられていません。 最も近い割り当て済みの記録であるCVE-2025-59406には、平文通信を示すCWE-319分類があります。ただし、これは通信の傍受ではなく、埋め込まれたAuth0シークレットを対象とします。この節の調査結果は、上記の研究報告に基づいています。

脆弱性 #

カメラはネットワーク（LTEまたはWi-Fi）への接続時に、十分な暗号化を行わずデータを送信します。

影響を受ける通信:

  • ナンバープレート画像とテキスト
  • 検出メタデータ
  • システムログ
  • 設定データ
  • 認証情報（一部）

攻撃経路#1: 不正なWi-Fiネットワーク #

研究者は次の手順を実演しました。

  1. カメラからSIMカードを取り外すまたはハードコードされたSSIDを使う偽ネットワークを作る
  2. カメラが不正なWi-Fiに接続
  3. Wiresharkなどのパケット解析ツールで通信を取得
  4. NetworkMinerやUnbloなどで解析
  5. 平文の認証情報や機微データを抽出

GainSecの調査からの引用:

「あるカメラから送信されるpcapデータをしばらく取得し、WiresharkとUnbloで解析しました……すると、実際に平文の認証情報がデータに含まれていました。」

攻撃経路#2: IMSIキャッチャー / Stingray #

より高度な攻撃では物理的な近接も必要ありません。

  1. IMSIキャッチャー（自作Stingray装置）または業務用SDRを使う
  2. 携帯基地局になりすましてLTE接続を乗っ取る
  3. カメラが不正な基地局に接続
  4. 中間者攻撃で通信をすべて傍受
  5. 認証情報、画像、メタデータを抽出

物理アクセスは不要です。 数百フィート離れた場所から実行できます。

現代のTempest攻撃の可能性 #

平文通信により、次のようなTempest型攻撃も可能になります。

  • カメラのRF放射を取得できる
  • 映像ストリームを遠隔から再構成できる
  • 冷戦時代のCIAの手法に似ている
  • 現代のSDR機器により一般の愛好家も実行できる

重大な脆弱性#7: 公開状態のカメラ映像 #

2026年1月の発見 #

深刻度: 重大 (CVSS 10.0 - システム全体の露出)

発見内容 #

2026年1月、Ben Jordanと404 Mediaは、簡単なGoogle検索で次の情報を見つけられることを発見しました。

  • 完全に露出したFlock Safetyの管理画面が60件以上
  • ユーザー名とパスワード不要
  • ライブ映像と過去30日分の録画
  • カメラを完全に制御するパネルへのアクセス

アクセス可能だった情報 #

公開された管理画面から、誰でも次の操作が可能でした。

  • ライブ映像を見る
  • 30日分の録画を確認する

重大な脆弱性#8: 無許可のデータ収集 #

公開声明との矛盾 #

深刻度: 高（プライバシーと法的影響）

Flock Safetyの主張 #

公式ウェブサイトの説明:

「Flock Safetyは人のデータを取得・記録せず、車両だけを対象としています」

独立研究者の調査結果 #

カメラの実際の動作:

  1. 動体検知はあらゆる動きでカメラを起動し、車両だけに限定しない
  2. AIが画像内のナンバープレートを検索
  3. プレートが見つからない場合も、画像は削除されず保存される
  4. 別のフォルダーにプレートがない画像を保存
  5. 人、歩行者、自転車利用者も撮影・保存

「車両だけ」という主張は事実ではありません。カメラの前を通る人の画像も保存します。

検証された観察 #

研究者は、カメラが次のものを撮影することを確認しました。

  • カメラの前を歩く人（画像を保存）
  • レンズに向かって手を振る様子（画像を保存）
  • カメラの近くで机や物を動かす様子（画像を保存）
  • 製造施設で働く工場作業員（数カ月保存）

GainSecの発言:

「私がカメラの前に移動すると、レーダーモジュールがカメラモジュールを起動して私を撮影しました。その後、端末内のAIはナンバープレートを探しましたが見つからず、それでも画像を別フォルダーに保存しました。」

法的影響 #

この無許可のデータ収集は、次の問題につながる可能性があります。

  • 表明されたプライバシーポリシーへの違反（欺瞞的な慣行）
  • 都市が「車両のみ」を指定していれば調達契約に違反
  • GDPR/CCPAの違反（EU市民、カリフォルニア州居住者）
  • 同意契約を無効化
  • 虚偽広告に関する訴訟で企業が責任を問われる

監視範囲の拡大 #

Condor PTZカメラ（2025〜2026年導入）は、人を追跡するように明確に設計されています。

  • AIによる人物検出
  • 顔への自動ズーム
  • 移動する人を追尾
  • オプトアウト手段がない
  • 公園、トレイル、交通施設に頻繁に導入

これは「ナンバープレートリーダー」から一般の人々を監視する仕組みへの大幅な拡大です。ポリシー変更も、新しい契約も、一般への通知もありません。

重大な脆弱性#9: Rubber Ducky攻撃に悪用できる露出したUSBポート #

物理アクセスによる攻撃 #

深刻度: 高（物理アクセスが必要）

脆弱性 #

Bravo計算機と一部のカメラ機種には、次の問題があります。

  • 外部に露出したUSB-Cポート
  • 物理的な保護がない（筐体の封印など）
  • USBデバイスの自動実行
  • 認証が不要

Rubber Ducky / BadUSB攻撃 #

BadUSBデバイス（価格5〜15ドル）は:

  • システムにUSBキーボードとして認識される
  • プログラム済みのスクリプト（ペイロード）を実行する
  • 接続すると自動的に動作する
  • ユーザー操作を必要としない

攻撃シナリオ #

GainSecは次の攻撃を実演しました。

  1. 設置済みのFlock端末に近づく
  2. 露出したポートへBadUSBデバイスを接続
  3. デバイスがペイロード（スクリプト）を実行
  4. ペイロードが永続的なマルウェアをインストール
  5. 攻撃者はその場を離れる
  6. マルウェアがLTE/Wi-Fi経由で管理サーバーに接続

所要時間: 30秒未満

ペイロードで可能な操作 #

自動スクリプトで次の操作が可能です。

  • ボタンを押さずに無線アクセスポイントを有効化
  • リモートアクセス用のバックドアを設置
  • リモートサーバーへデータを持ち出す
  • 映像や証拠を改ざんする
  • カメラを無効化、またはDoSを引き起こす
  • DDoS攻撃用ボットネットに参加させる
  • 他のシステムから認証情報を取得する

重要な理由 #

8万台を超えるカメラは、郊外や農村に近い場所の視界が限られた場所に設置されていることが多く:

  • 物理アクセスを得やすい
  • 警備員や継続的な監視がない
  • 一般的なホースクランプで固定
  • 地上から約7フィートに設置されていることが多い（踏み台で届く高さ）

Ben Jordanの発言:

「これらのカメラは難攻不落の要塞ではありません。7フィートの高さにホースクランプで固定された、プラスチック製のAndroidカメラと計算機です。」

重大な脆弱性#10: 公開されたAPIキー #

OSINT研究者による発見 #

深刻度: 重大 (CVSS 9.5)

発見内容 #

2025年、OSINT研究者Joshua Michaelが次の内容を発見しました。

  • Google検索演算子で見つかった露出したFlock Safetyデモサイト
  • 閲覧可能な5,000行のソースコード
  • コードに埋め込まれた有効なAPIキー
  • 50を超える非公開地理空間データレイヤーへのアクセス

APIキーが許可したアクセス #

露出したArcGIS APIキーは、次の情報へのアクセスを可能にしました。

1. 登録情報

  • 顧客名
  • メールアドレス
  • 拠点ごとのカメラ台数
  • ファイル添付機能

2. 複数の警察組織のパトカー位置情報

  • 警察車両のリアルタイムGPS追跡
  • コロラド州オーロラの導入環境
  • キャロルトン警察署
  • 国家安全保障上のリスク

3. 警察官の個人情報

  • 氏名と電話番号
  • メールアドレス
  • 予定されている巡回区域
  • 所属する管轄区域

4. テキサス州ダラスの要注意車両データベース

  • フラグ付き車両の6,000件の記録
  • ナンバープレートとフラグの理由
  • 検出場所とタイムスタンプ
  • 車両を撮影したカメラID
  • 5カ月分の移動追跡記録

Joshua Michaelの発言:

「誰でもGoogleでこの地図を見つけ、5カ月分の移動パターンを追跡できました。理由の欄には単に『容疑者』と書かれた人がいて、多くの記録では理由が記載されていないか空欄でした。」

攻撃対象領域 #

露出したAPIキーにより、次のことが可能になります。

  • 特定の車両をストーキングする
  • 自宅住所や巡回パターンを露出させ、警察官の安全を脅かす
  • 警察がいる場所・いない場所を明らかにし、作戦上の安全を損なう
  • 犯罪を通報した人を追跡して証人を脅迫する
  • 組織犯罪による犯罪情報の収集

情報侵害の背景: Flax Typhoon #

この発見の数週間前、セキュリティ研究者のAlexa FemininaとJames Zhangによると、中国政府が支援するハッカー集団Flax TyphoonがArcGISを侵害しました。

InfoSecurity Magazineからの引用:

「ハッカーは、災害復旧、緊急事態管理、その他重要な機能に使われる正規の公開ArcGISアプリケーションを標的にしたとされています。」

つまり敵対的な国家が、 警察車両の位置、警察官の身元、監視カメラの設置場所、緊急対応のパターンにアクセスできた可能性があります。

その他の脆弱性（50件以上の概要） #

脆弱性#11〜#51 #

GainSecのホワイトペーパーは、次のような追加の41件の問題を記録しています。

システム設計の欠陥:

  • 本番ファームウェアでデバッグモードが有効
  • 安全でない起動処理によりブートローダーを侵害可能
  • キー保存用のセキュアエレメントやTPMがない
  • 予測可能なファームウェア更新方式

認証の問題:

  • セッショントークンの有効期限がない
  • IPアドレスによるアクセス制限がない
  • デバイス群で認証情報を共有
  • 証明書ピンニングがない

ネットワークセキュリティ:

  • デバッグサービスのポートが開放
  • 一部の端末でTelnetが有効
  • 弱い認証情報を持つFTPサーバー
  • DNSリバインディングの脆弱性

プライバシーとデータ保存:

  • 宣言された期間を超えて画像を保存
  • メタデータが削除されない
  • 顔認識データを収集
  • 車両以外の位置も追跡

物理セキュリティ:

  • 筐体を簡単に分解できる
  • シリアルインターフェースが露出
  • JTAGデバッグポートにアクセス可能
  • 改ざん検知シールがない

暗号技術の欠陥:

  • 弱い乱数生成
  • 暗号化キーがハードコード
  • ハッシュチェーンでMD5を引き続き使用
  • 証明書検証が無効

情報漏えい:

  • 詳細なエラーメッセージが内部情報を漏らす
  • Webサーバーでディレクトリ一覧を有効化
  • ソースコードコメントに認証情報
  • 設定バックアップを誰でも閲覧可能

  • 8件のCVEがMITREの割り当て待ち

Flock Safetyの対応 #

公式声明 #

2025年11月のブログ投稿:

「Flockはセキュリティの継続的な改善に取り組んでいます……報告書に記載された脆弱性のいずれも、お客様が公共の安全を実現する能力に影響しません。」

主張: 脆弱性の悪用には物理アクセスと「深い知識」が必要

反証:

  • 露出したカメラ映像の発見に必要なのはGoogle検索だけ
  • 無線攻撃に必要なのは近くにいることだけ
  • APIキーの露出は完全にリモートから利用可能
  • 開示後、ハードコードされたパスワードは広く知られる状態

調査用デバイスへの反論 #

Flockは当初、研究対象のデバイスは次の状態だと主張しました。

「クラウドに接続されていない……接続前のトラックから盗まれたiPhoneのようなもの」

この説明は誤りだと証明されました。 研究者はクラウド接続済みのデバイスをテストし、同じ結果を得ました。一般公開されたカメラにも同じ脆弱性があり、404 Mediaは本番カメラ60台以上の露出を発見しました。

研究者への対応 #

GainSecによると、責任ある開示の試みは次の結果を招きました。

  • 開示を封じるNDA付きバグ報奨金制度
  • 修正に関する確認がない
  • 90日間の期間前に広報声明を公開
  • 報道発表で研究者に言及しない
  • 動画公開から48時間以内に研究者が職を失う

Ben Jordanは次のことを報告しました。

  • 自宅への警察の訪問
  • 自宅を撮影する私立探偵と疑われる人物
  • 近隣住民による嫌がらせ
  • Flock Safetyからの差し止め要求

Benの発言:

「セキュリティの脆弱性を調査した結果や罰だとは思いません。倫理的かつ透明に調査したことへの結果や罰だと考えています。」

導入の継続 #

こうした状況にもかかわらず、Flock Safetyは:

  • 脆弱なデバイスを販売し続ける
  • 根本原因に対処するファームウェア更新を提供しない
  • サポートが2021年に終了したAndroid Things 8.xを使い続ける
  • 法執行機関にMFAを義務付けない

技術分析: 現実の攻撃シナリオ #

シナリオ1: 国家による監視 #

脅威主体: 外国の情報機関

目的: 政府関係者の追跡

手法:

  1. IMSIキャッチャーを使い、カメラのLTE通信を傍受
  2. 通信から平文の認証情報を抽出
  3. 侵害されたAPIキー（または以前露出したArcGISレイヤー）を使ってバックエンドにアクセス
  4. 政府施設に登録された車両をデータベースで検索
  5. 政府関係者や軍関係者の移動を追跡

実行時間: 数日（インフラの準備後） 検出される可能性: 低い（暗号化されたC2が正規通信を模倣）

シナリオ2: 組織犯罪による対監視 #

脅威主体: 麻薬密売組織

目的: 警察の巡回パターンを特定

手法:

  1. BadUSBデバイスを購入（15ドル）
  2. 活動地域のカメラへ車で移動
  3. 露出したUSBポートにBadUSBを接続（30秒）
  4. ペイロードがカメラを無効化、または映像を変更
  5. 代わりに、警察車両の位置をリモートサーバーへ持ち出すことも可能

実行時間: カメラ1台あたり30秒 検出される可能性: 低い（正規のデバイス操作に見える）

シナリオ3: ストーカー / ドメスティックバイオレンス #

脅威主体: 暴力的な元パートナー

目的: 被害者の行動追跡

手法:

  1. 被害者のナンバープレートを入手（公開情報）
  2. Googleで公開状態のFlockカメラ管理画面を検索（2026年1月の脆弱性）
  3. 30日分の映像で車両の出現を検索
  4. 公開データベース（勤務先住所、自宅など）と照合
  5. 日常の行動と時刻を割り出す

実行時間: 数分〜数時間 検出される可能性: なし（認証ログが存在しない）

シナリオ4: 証拠の改ざん #

脅威主体: 刑事事件の被告

目的: 裁判前に証拠を破壊

手法:

  1. 令状の証拠開示からカメラ位置を知る
  2. カメラに物理的にアクセス（ボタン操作）
  3. rootシェルを取得
  4. 証拠フォルダーに移動
  5. 特定の画像・動画を削除、またはタイムスタンプを変更

実行時間: 5分未満 検出される可能性: 低い（弁護側がアクセスする前にカメラをフォレンジック調査しない限り）

シナリオ5: プライバシー活動家 / ジャーナリスト #

脅威主体: 透明性を求める活動家

目的: 過剰な監視を記録

手法:

  1. 検出デバイスを使用（ Flock-Youハードウェアガイド を参照）
  2. 地域内のカメラ位置を地図化
  3. 映像ポリシーについてFOIA請求
  4. 市議会に脆弱性を実演
  5. 撤去や監督を求める

実行時間: 継続的 検出される可能性: 高い（公開活動）

倫理上の考慮事項 #

責任ある開示の経緯 #

セキュリティコミュニティは、責任ある開示のベストプラクティスに従いました。

標準的な手順:

  1. 脆弱性を発見
  2. ベンダーに90日前までに非公開で通知
  3. ベンダーがパッチを開発・配布
  4. パッチ公開後、または90日後（早い方）に情報を公開
  5. 防御に役立つ詳細な解説を公開

実際の経緯:

  1. GainSecが脆弱性を発見（2024年後半）
  2. Flock Safetyに繰り返し連絡（2025年2月以降）
  3. FlockはNDA付きバグ報奨金制度を提示（開示を抑制）
  4. 研究者に触れず、Flockが期限前に広報声明を公開
  5. パッチ導入に関する確認なし
  6. GainSecは90日間の期間後に公開開示
  7. Ben Jordanと404 Mediaが本番システムで独立検証

研究者への報復 #

GainSecとBen Jordanは次のことを報告しました。

  • 失職または雇用上の問題
  • 自宅への警察訪問
  • 自宅や敷地の監視疑惑
  • 近隣住民による嫌がらせ
  • 差し止め要求
  • ソーシャルメディア上の攻撃（FlockのCEOは研究者を「テロリスト」と呼んだ）

セキュリティ研究を萎縮させる影響:

  • 脆弱性開示をためらわせる
  • 重大なセキュリティ修正を遅らせる
  • 公共の安全を損なう
  • セキュリティコミュニティの倫理規範に違反

公益 #

研究者は次の行動により公益に貢献しました。

  • 責任ある開示手順に従う
  • 公開前にベンダーへ先に通知する
  • 悪用を可能にする機微情報を伏せる
  • 実務者へ防御の指針を提供する

業界全体:

  2. 有資格の第三者による独立テスト
  3. 監査結果を公開
  4. セキュリティ障害に対するベンダー責任
  5. 標準準拠（NIST、ISOなど）

  1. 調達契約にセキュリティ要件を盛り込む
  2. 導入済みシステムを定期監査
  3. 全利用者にMFAを義務化
  4. インシデント対応計画を整備
  5. 監視プログラムについて地域社会へ説明

  2. 影響を受ける当事者への脆弱性開示を義務化
  3. セキュリティ研究者に対する内部告発者保護
  4. プライバシー侵害への民事救済
  5. 監視システムの監督制度

より大きな問題 #

この事例が示すのはFlock Safetyだけの問題ではありません。次の状況を象徴しています。

  • 成長をセキュリティより優先する監視業界
  • 技術的専門性が不足した政府調達
  • 検証されず、異議を唱えられないベンダーの主張
  • 公共の安全と一致しない金銭的な動機
  • 新技術の監督における規制の空白

独立したセキュリティ検証なしにFlockと契約するすべての都市は、住民に代わってこうしたリスクを受け入れています。
