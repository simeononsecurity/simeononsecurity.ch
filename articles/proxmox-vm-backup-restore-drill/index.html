সবুজ ব্যাকআপ টাস্ক বোঝায় Proxmox একটি ব্যাকআপ লিখেছে। অতিথি সিস্টেম চালু হয় কি না, ডেটা হালনাগাদ কি না, বা প্রধান সার্ভিস কাজ করে কি না, টাস্কটি তা দেখায় না। নতুন VM ID দিয়ে বিচ্ছিন্ন নেটওয়ার্কে একটি কপি পুনরুদ্ধার করুন। কোনো বিভ্রাট পরীক্ষায় বাধ্য করার আগেই ফলাফল আপনাকে পুনরুদ্ধারের প্রমাণ দেয়।

এই মহড়ায় একটি Proxmox VE ভার্চুয়াল মেশিন পরীক্ষা করা হয়। কনটেইনারের ব্যাকআপ নিয়ম আলাদা, বিশেষ করে bind mount ও device mount-এর ক্ষেত্রে। সাইটের হোমল্যাব ব্যাকআপ পুনরুদ্ধার মহড়া আরও বিস্তৃত ফাইল পুনরুদ্ধার নিয়ে আলোচনা করে। এখানে আপনি একটি Proxmox VM ব্যাকআপ ও তার কাজের চাপ পরীক্ষা করবেন।

গেস্ট হলো ভার্চুয়াল মেশিনের ভেতরে চলা অপারেটিং সিস্টেম। Bind mount ও device mount গেস্টকে হোস্টের রিসোর্স দেখায়। এই রিসোর্স আলাদা পুনরুদ্ধার পরিকল্পনা দিয়ে পরীক্ষা করুন।

মূল বিষয় #

  • আগে সাফল্য নির্ধারণ করুন: একটি ডেটা আইটেম, একটি সার্ভিস পরীক্ষা এবং গ্রহণযোগ্য পুনরুদ্ধার সময় ঠিক করুন।
  • কভারেজ দেখুন: VM ব্যাকআপ No backup চিহ্নিত ডিস্ক বাদ দেয় এবং বাইরের সার্ভিস বা বাদ পড়া ডেটা পুনরায় তৈরি করতে পারে না।
  • আলাদাভাবে পুনরুদ্ধার করুন: অব্যবহৃত VM ID নিন এবং পুনরুদ্ধার করা নেটওয়ার্ক উৎপাদন নেটওয়ার্ক থেকে বিচ্ছিন্ন রাখুন।
  • প্রমাণ লিখে রাখুন: ব্যাকআপের বয়স, পুনরুদ্ধারের সময়, বুট, ডিস্কের উপস্থিতি এবং বাস্তব অ্যাপ পরীক্ষা মাপুন।

শুরু করার আগে #

এমন VM বেছে নিন যার ব্যাকআপ নিরাপদে পরীক্ষা করা যায়। আপনার Proxmox প্রশাসক প্রবেশাধিকার, ফাইল স্টোরেজ বা Proxmox Backup Server (PBS)-এ সম্পূর্ণ ব্যাকআপ, দ্বিতীয় VM-এর জন্য পর্যাপ্ত জায়গা এবং একটি বিচ্ছিন্ন bridge বা সংযোগ বিচ্ছিন্ন নেটওয়ার্ক ডিভাইস দরকার। বিচ্ছিন্ন bridge হলো Proxmox ভার্চুয়াল নেটওয়ার্ক, যার উৎপাদন LAN-এ যাওয়ার কোনো route নেই। এমন bridge না থাকলে সংযোগ বিচ্ছিন্ন adapter বা test VLAN ব্যবহার করুন। উৎপাদন VM চালু রাখুন। অন্য কোনো গেস্ট IDটি ব্যবহার করছে কি না দেখে নতুন VM ID, যেমন 920, সংরক্ষণ করুন। সম্পূর্ণ restore ও কাজের চাপের পরীক্ষার জন্য পর্যাপ্ত সময় রাখুন।

পুনরুদ্ধারের আগে পাসের শর্ত লিখুন। ফাইল সার্ভারের জন্য একটি সাম্প্রতিক ফাইল এবং প্রত্যাশিত checksum বা বিষয়বস্তু বেছে নিন। ডেটাবেসের জন্য নিরাপদ read-only query এবং ব্যাকআপের আগে লেখা একটি record বেছে নিন। ওয়েব সার্ভিসের জন্য স্থানীয় health check ও প্রতিনিধিত্বমূলক পৃষ্ঠা নিন। গ্রহণযোগ্য সর্বশেষ ডেটার সময়, আপনার recovery point objective (RPO), এবং সার্ভিস ফেরাতে অনুমোদিত সময়, আপনার recovery time objective (RTO) লিখে রাখুন। শুধু বুট স্ক্রিন এই পরীক্ষাগুলো পূরণ করে না।

নথিভুক্ত বিষয়প্রমাণের উদাহরণ

পুনরুদ্ধারের লক্ষ্যঅব্যবহৃত VM ID, লক্ষ্য স্টোরেজ, বিচ্ছিন্ন bridge
কাজের চাপের পরীক্ষালগইন, volume mount এবং অ্যাপ থেকে পড়া
সময়সীমাrestore ও সার্ভিস পরীক্ষার শুরু এবং শেষের সময়

নাম, IP ঠিকানা, MAC ঠিকানা, নির্ধারিত কাজ এবং বাইরের ইন্টিগ্রেশন যাচাই করার আগে পুনরুদ্ধার করা গেস্টকে উৎপাদন নেটওয়ার্কে যুক্ত করবেন না। কপি করা পরিচয় চলমান VM-এর সঙ্গে দ্বন্দ্ব তৈরি করতে পারে অথবা একই কাজ দুবার পাঠাতে পারে।

ব্যাকআপে কী আছে দেখুন #

সংস্করণের পরিধি: নিবন্ধ প্রস্তুতের সময় এই উদাহরণগুলো চালানো হয়নি। পরীক্ষা শুরুর আগে pveversion --verbose-এর আউটপুট লিখুন। ইনস্টল করা Proxmox VE রিলিজের সঙ্গে মেলে এমন নথি ব্যবহার করুন। পরীক্ষার নথিতে storage backend, guest type এবং command output লিখুন।

Proxmox node-এ নিচের read-only কমান্ড উৎস VM-এর কনফিগারেশন দেখায়। 120-এর জায়গায় উৎস VM ID দিন:

qm config 120

প্রতিটি ভার্চুয়াল ডিস্ক ও তার ব্যাকআপ সেটিং লিখুন। Proxmox-এর VM ডিস্ক ডকুমেন্টেশন বলে No backup বিকল্প VM ব্যাকআপ থেকে ডিস্ক বাদ দেয়। অ্যাপের ডেটা বাদ দেওয়া ডিস্ক, host mount, সরাসরি পাস করা হার্ডওয়্যার বা দূরবর্তী সার্ভিসে আছে কি না যাচাই করুন। সেগুলোর আলাদা পুনরুদ্ধার পদ্ধতি লিখুন। VM বুট পরীক্ষা বাদ দেওয়া ডেটা সুরক্ষিত আছে প্রমাণ করে না।

সর্বশেষ ব্যাকআপের timestamp, আকার, task log এবং storage location যাচাই করুন। Proxmox ইন্টারফেসে ব্যাকআপ স্টোরেজের Backups দৃশ্য বা VM-এর Backup ট্যাব খুলুন। নিশ্চিত করুন কাজটি ত্রুটি ছাড়া শেষ হয়েছে। Proxmox-এর ব্যাকআপ ডকুমেন্টেশন সাধারণ ব্যাকআপ ফাইল এবং PBS storage-এর পার্থক্য দেখায়। PBS deduplicated chunk ও metadata রাখে।

ব্যাকআপ মোডVM-এর আচরণএই মহড়ায় সিদ্ধান্ত
Snapshotকম downtime-এ চলমান VM-এর ব্যাকআপ নেয়। গেস্টের লেখা সামান্য consistency ঝুঁকি তৈরি করে।কাজের চাপ এই recovery point সহ্য করলে নিয়মিত পরীক্ষার জন্য উপযুক্ত।
Stopব্যাকআপ শুরুতে গেস্ট বন্ধ করে এবং সবচেয়ে বেশি consistency দেয়।কাজের চাপ clean shutdown চাইলে এবং downtime গ্রহণযোগ্য হলে ব্যবহার করুন।
Suspendsnapshot mode-এর আগে গেস্ট স্থগিত করে; সাধারণ consistency সুবিধা ছাড়াই downtime বাড়ায়।snapshot-এর ওপর উন্নতি ভেবে suspend-কে ডিফল্ট করবেন না।

এই মোডগুলোর সুবিধা-অসুবিধা Proxmox backup mode reference -এ আছে। QEMU guest agent হলো গেস্টের ভেতরের সার্ভিস, যা Proxmox-কে filesystem freeze ও thaw-এর মতো কাজের অনুরোধ করতে দেয়। চালু ও সুস্থ guest agent-সহ গেস্ট snapshot backup-এর সময় এই কাজগুলো সমর্থন করে। Filesystem freeze consistency বাড়ায়, কিন্তু database-নির্দিষ্ট recovery check-এর বিকল্প নয়। নির্ধারিত কাজ আপনার পছন্দের সেটিং ব্যবহার করছে ধরে না নিয়ে প্রকৃত mode ও agent-এর অবস্থা লিখুন।

একটি পুনরুদ্ধার পয়েন্ট তৈরি বা বেছে নিন #

মহড়ায় নিয়মিত পুনরুদ্ধার পরীক্ষা করলে সাম্প্রতিক সফল নির্ধারিত ব্যাকআপ নিন। একবারের নতুন ব্যাকআপ লাগলে VM-এর Backup ট্যাব খুলুন, Backup now নির্বাচন করুন, লক্ষ্য storage ও mode ঠিক করুন এবং task log-এ সফলতা না আসা পর্যন্ত অপেক্ষা করুন। Proxmox shell থেকে এই উদাহরণে 120 VM-কে backup-nfs নামের storage ID-তে snapshot mode-এ ব্যাকআপ করা হয়:

vzdump 120 --storage backup-nfs --mode snapshot

দুটি ID-ই নিজের মান দিয়ে বদলান। সংরক্ষণব্যবস্থা ব্যাকআপ গ্রহণ করে এবং যথেষ্ট জায়গা আছে নিশ্চিত হওয়ার পরই কমান্ড চালান। Proxmox-এর vzdump নির্দেশিকা মোড ও স্টোরেজের বিকল্প ব্যাখ্যা করে। কমান্ড শেষ হলে কাজের লগ দেখুন। ফাইলের নাম নতুন দেখালেই পুরোনো ব্যাকআপকে বর্তমান পুনরুদ্ধার বিন্দু মনে করবেন না।

লক্ষ্য PBS হলে নির্বাচিত ডেটাস্টোরের যাচাই কাজ চালান বা পর্যালোচনা করুন। PBS-এর যাচাই-সংক্রান্ত নথি ব্যাকআপ ডেটার অখণ্ডতা যাচাই ও নিয়মিত পরীক্ষা নির্ধারণের পদ্ধতি জানায়। যাচাই ক্ষতিগ্রস্ত ব্যাকআপ অংশ খুঁজে পায়। যাচাই সফল হলেও পুনরুদ্ধার করা OS, application বা বাইরের নির্ভরতা কাজ করবে প্রমাণ হয় না। ভালো যাচাই ফলের পরও পুনরুদ্ধার মহড়া চালিয়ে যান।

বিচ্ছিন্ন VM-এ পুনরুদ্ধার করুন #

Proxmox ইন্টারফেসে storage-এর Backups দৃশ্য থেকে ব্যাকআপ বেছে Restore নির্বাচন করুন। অব্যবহৃত VM ID এবং লক্ষ্য storage দিন। Start after restore বন্ধ রাখুন। নতুন MAC address তৈরির বিকল্প দেখুন। অফিসিয়াল qmrestore synopsis অনন্য VM ID, storage নির্বাচন, এলোমেলো Ethernet address-এর জন্য --unique এবং পুনরুদ্ধার করা VM না চালু করার default আচরণ নির্ধারণ করে।

ফাইলভিত্তিক vzdump archive-এর জন্য এই shell command একই ধরন দেখায়। নিজের পরিবেশের archive path, নতুন VM ID এবং storage ID বসান:

qmrestore /path/to/vzdump-qemu-120-2026_10_11-02_00_00.vma.zst 920 --storage local-lvm --unique 1

Proxmox-এর restore বিবরণ বলে target storage না দিলে restore মূল storage ব্যবহার করার চেষ্টা করে। test node-এ পুরোনো storage না থাকলে --storage দিন। মহড়ায় --force ব্যবহার করবেন না। এটি বিদ্যমান VM overwrite করার অনুমতি দেয়, কিন্তু এই পদ্ধতিতে অব্যবহৃত ID লাগে। PBS backup-ও Proxmox interface দিয়ে restore হয়। PBS snapshot-এর storage entry বেছে নিন, সেটিকে স্থানীয় .vma.zst ফাইল হিসেবে ধরবেন না।

প্রথম boot-এর আগে প্রতিটি পুনরুদ্ধার করা network interface দেখুন, secondary ও passthrough interface-সহ। MAC address নেটওয়ার্ক ইন্টারফেস শনাক্ত করে। DNS নামকে ঠিকানায় রূপান্তর করে। DHCP নেটওয়ার্ক সেটিং বরাদ্দ করে। VLAN ভাগ করা hardware-এর ওপর চলা যৌক্তিক নেটওয়ার্ক। Virtual TPM গেস্টের নিরাপত্তা অবস্থা রাখে। সব interface বিচ্ছিন্ন করুন অথবা শুধু বিচ্ছিন্ন test segment-এ যুক্ত করুন। কোনো production route, DNS path, DHCP service, management network বা external integration যেন পৌঁছানো না যায় নিশ্চিত করুন। কাজের চাপের অন্য test service দরকার হলে বিচ্ছিন্ন network-এ তার test copy দিন। উৎসের সঙ্গে disk mapping, firmware, virtual TPM-এর শর্ত এবং বিশেষ device তুলনা করুন। বাইরের disk, passthrough device ও VM-এর বাইরে রাখা secret-এর আলাদা পরিকল্পনা দরকার।

গেস্ট ও কাজের চাপ পরীক্ষা করুন #

পুনরুদ্ধার করা VM চালু করে আগে তার console ব্যবহার করুন। OS boot হয়, প্রত্যাশিত volume mount হয়, ঘড়ির সময় সঠিক এবং application শুরু হয় নিশ্চিত করুন। তারপর আগে লেখা পাসের শর্ত চালান। পরিচিত ডেটা আইটেমের মান ও timestamp ব্যাকআপের আগের মানের সঙ্গে তুলনা করুন। Login prompt বা চলমান process একা প্রমাণ করে না যে সার্ভিসে সঠিক ডেটা আছে।

পরীক্ষাপাসের শর্ত
Bootগেস্ট repair mode বা বারবার recovery prompt ছাড়া স্বাভাবিক login-এ পৌঁছায়।
Diskব্যাকআপে থাকা প্রতিটি disk দেখা যায়, mount হয় এবং প্রত্যাশিত ডেটা রাখে।
Serviceপ্রতিনিধিত্বমূলক স্থানীয় request বা read সফল হয়।
পুনরুদ্ধার বিন্দুপুনরুদ্ধার করা ডেটা নথিভুক্ত RPO মেনে চলে।
পুনরুদ্ধারের সময়পুনরুদ্ধার, বুট ও সার্ভিস যাচাই নথিভুক্ত RTO-তে শেষ হয়।
Isolationproduction address, job বা integration-এ duplicate traffic যায় না।

নির্ধারিত task, notification hook, backup agent ও application credential দেখার সময় পুনরুদ্ধার করা গেস্ট বিচ্ছিন্ন রাখুন। প্রকৃত customer-কে বার্তা পাঠায় বা production service-এ লেখে এমন পরীক্ষা চালাবেন না। পরীক্ষা ব্যর্থ হলে নির্দিষ্ট ধাপটি লিখুন। Backup integrity failure, VM boot failure, missing data ও application failure আলাদা করুন। প্রতিটির সমাধান আলাদা।

ব্যর্থতার ধরননিশ্চিত করার প্রমাণপ্রথম সংশোধনপুনরায় পরীক্ষা
ব্যাকআপের অখণ্ডতাverification বা restore task ক্ষতিগ্রস্ত ডেটা জানায়অন্য যাচাইকৃত recovery point নিন এবং storage health দেখুনverification ও restore পুনরাবৃত্তি করুন
VM bootconsole firmware, disk বা recovery error দেখায়firmware, disk mapping ও boot order উৎসের সঙ্গে মেলানবিচ্ছিন্ন copy boot করে console-এর ফল লিখুন
ডেটা অনুপস্থিতপ্রত্যাশিত file, volume বা database record নেইবাদ পড়া disk, mount, snapshot ও বাইরের dependency দেখুনচিহ্নিত file বা data check আবার করুন
অ্যাপ্লিকেশনগেস্ট boot হলেও service check ব্যর্থservice log, credential, dependency ও recovery step দেখুনএকই local health check ও workload test চালান

Proxmox PBS backup-এর জন্য একটি ফাইল পুনরুদ্ধার সমর্থন করে। কাজের চাপের জন্য একক ফাইল পুনরুদ্ধার দরকার হলে সেই পথ পরীক্ষা করুন। পুনরুদ্ধার করা ফাইল পূর্ণ VM boot ও service test-এর বিকল্প নয়। Proxmox PBS থেকে live restore-ও দেয়। নথিতে বলা হয়েছে live restore ব্যর্থ হলে VM অনির্ধারিত অবস্থায় থাকে। তাই পরিকল্পিত এই মহড়ায় স্বাভাবিক, সম্পূর্ণ restore ব্যবহার করুন।

ফল নথিভুক্ত করে মহড়া শেষ করুন #

উৎস VM ID, backup storage, backup timestamp, mode, নতুন VM ID, target storage, network isolation, restore শুরুর ও শেষের সময়, application test, data timestamp এবং ব্যর্থ check লিখুন। মাপা recovery point ও সময় লক্ষ্যের সঙ্গে তুলনা করুন। ব্যর্থতা তখনই কার্যকর প্রমাণ, যখন আপনি backup plan বদলে মহড়া পুনরাবৃত্তি করেন।

পরীক্ষা শেষে পুনরুদ্ধার করা VM বন্ধ করুন। ফল সংরক্ষণের পরেই test copy মুছুন এবং production VM প্রত্যাশামতো চলছে নিশ্চিত করুন। স্বাভাবিক retention policy মেনে backup রাখুন। একটি মহড়া পাশ করানোর জন্য retention বদলাবেন না।

স্টোরেজ, গেস্ট বা ব্যাকআপ কনফিগারেশনে বড় পরিবর্তনের পর পরীক্ষা পুনরাবৃত্তি করুন। গুরুত্বপূর্ণ VM-গুলো ঘুরিয়ে পরীক্ষা করুন, বাদ পড়া disk বা বাইরের নির্ভরতা-সহ গেস্টও রাখুন। Hyper-V থেকে Proxmox-এ স্থানান্তর নির্দেশিকা উৎস VM বন্ধ করার আগে এই পুনরুদ্ধার প্রমাণ ব্যবহার করে। ব্যবহারযোগ্য ব্যাকআপের পরিচিত পুনরুদ্ধার পথ, পরীক্ষিত কাজের চাপ এবং মাপা পুনরুদ্ধার বিন্দু থাকে।

পরবর্তী ধাপ #

স্টোরেজ, গেস্ট বা ব্যাকআপ বদলানোর পর মহড়া পুনরাবৃত্তি করুন। ফাইল পুনরুদ্ধারের জন্য হোমল্যাব ব্যাকআপ পুনরুদ্ধার মহড়া দেখুন।
