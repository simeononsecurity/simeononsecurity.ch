自托管 Hindsight：本地智能体记忆与私有模型路由

**我们的 Hindsight 记忆服务运行在我们控制的硬件上。**记忆引擎、数据库、嵌入模型和重排序器在同一个自托管部署中运行。Hindsight 将生成请求发送到私有网关。已检查的共享 Qwen 后端和经过测试的页面刷新路由使用本地模型服务器，无需订阅托管推理服务。

本文描述的是一个实际运行的部署。**自托管不等于离线。**VPN 使用外部协调服务，软件镜像和模型权重也需要下载。这里的结论只涉及记忆处理和模型推理，不涵盖我们的设备或其他智能体工具发起的所有网络连接。

要点 #

  • **Hindsight 负责记忆工作流。**Docker 容器提供 API、工作进程和控制平面，记忆库数据存放在持久卷中。
  • **小型检索模型留在本地。**嵌入和重排序在 Hindsight 进程内通过 CPU 运行。
  • **Qwen 负责文本生成。**Retain、Reflect 和 Consolidation 请求私有别名 Qwen3.5-4B，并关闭推理、限制输出。已检查的后端在本地提供服务。
  • **耗时较长的页面刷新使用 GPU。**另一个模型别名为后台请求租用一张显卡，请求完成后再释放显卡。
  • **网关隐藏物理部署位置。**Hindsight 选择模型别名，私有路由服务选择模型服务端点。

先明确边界，再选择模型 #

**Hindsight 是记忆引擎，不是模型服务器。**完整的 Docker 镜像包含本地嵌入和重排序模型，但语言模型生成需要一个端点。 Hindsight 安装指南 说明了这种分工，并将本地 llama.cpp、Ollama 和 vLLM 服务器列为托管服务商的替代方案。

**记忆 API 留在私有网络中。**Web 控制平面只绑定本地接口。持久卷保存嵌入式数据库，因此重新创建容器不会丢失记忆库。身份验证保护 API，不同记忆库分别保存项目上下文。

**生成网关提供稳定的模型名称。**Hindsight 通过 VPN 向私有网关发送兼容 OpenAI 格式的请求。网关将请求转发到本地模型服务端点。已检查的 Qwen 路由连接到映射至本地 CPU 服务器的 LiteLLM 部署。 LiteLLM 路由文档 介绍了这种模型别名模式。兼容 OpenAI 的同类路由器也能承担相同职责。

打开完整请求路径图 。

**系统仍然存在内部 API。**Hindsight 使用兼容 OpenAI 的格式调用私有网关。已检查的模型路由在本地运行推理。我们没有审计网关的所有故障转移规则，因此在将本地处理视为每个请求的保证之前，需要先检查网关策略。

为每项记忆任务分配合适的计算资源 #

Hindsight 的各项操作承担不同工作。Retain 从新材料中提取事实。Recall 查找相关记忆。Reflect 检索内容并撰写综合回答。Consolidation 合并相关事实。后台的 knowledge-page refresh 会从记忆库重新生成动态摘要。

操作模型位置原因
Retain通过私有网关使用 Qwen3.5-4B在本地提取结构化内容，并限制输出预算
Recall本地 CPU 嵌入和重排序搜索不需要调用生成 API
Reflect通过私有网关使用 Qwen3.5-4B检索记忆后还需要生成综合内容
Consolidation通过私有网关使用 Qwen3.5-4B小批次可限制较长的结构化回复
Knowledge-page refresh专用本地 GPU Qwen 路由大型后台综合任务超过了 CPU 路由的时间上限

小型检索任务留在 CPU 上，仅为经过测量的长任务分配 GPU 推理。

Hindsight 容器使用 BAAI/bge-small-en-v1.5 生成嵌入，使用 hindsight-ai/hs-rerank-1 执行重排序。启动日志确认两者都在本地 CPU 上运行。 Hindsight 模型参考 介绍了本地模型选项和可选的决策模型路径。

我们保留了现有嵌入模型，因为更改嵌入空间需要重新生成已存储的向量。重排序器已经在本地运行，因此使用托管重排序服务会增加新的数据边界，却无法解决观察到的生成超时。一次本地 hs-decide-1-flash 试运行生成了一个正确的 Reflect 回答，但耗时接近测试上限。合成的 Consolidation 数据没有测试决策路径。因此，决策模型没有纳入生产路由。

为缓慢的后台任务分配 GPU #

**常规模型名称与刷新模型名称不同。**Retain、Reflect 和 Consolidation 使用共享的 Qwen 别名。后台页面刷新使用特定节点的 GPU 别名，并限制为一次并发语言模型调用。这样，长时间维护任务一次最多占用一张 GPU。

**按请求预留资源可限制 GPU 使用。**收到请求后，GPU 池启动模型工作进程。控制器预留一张显卡、处理请求、停止工作进程，然后释放预留资源。图中省略了物理主机清单。

打开完整 GPU 租用周期图 。

这种分工源于一次经过测量的失败。**一次以 CPU 为主的页面刷新触及了一小时上限。**将后台刷新任务路由到本地 GPU 池后，一次恢复运行中的五个失败页面在约两到六分钟内完成。这些数字只描述那些页面和设置，并非通用的 Qwen 吞吐量基准。

修正默认值和超时 #

**Hindsight 之前的输出限制不适用于我们的本地路由器。**路由器最多接受 8,192 个输出 token，如果请求未指定限制，则采用 256 token 的上限。之前 Retain 设置的 64,000 token 上限触发了 HTTP 400。每批八条事实的 Consolidation 任务因输出长度限制而停止，Reflect 也需要显式上限，避免触发路由器的 256 token 默认值。

**我们为每种任务明确设置了限制。**这些记忆操作关闭了 Qwen 推理。现在 Hindsight 总共允许四个并发 LLM 调用，其中后台页面刷新最多占用一个调用。全局 LLM 超时为 1,800 秒，模型最多重试一次。

工作负载输出或批次上限调用和操作限制
Retain8,192 个输出 token每次调用的全局超时为 1,800 秒
Reflect4,096 个输出 token每次调用 900 秒，单次操作 3,600 秒
Consolidation4,096 个输出 token，每次调用四条事实每次调用 900 秒，单次操作 14,400 秒
Page refresh一次并发模型调用每次调用 900 秒，专用 GPU 路由

这些数值描述的是 2026 年 11 月部署中的本地路由器设置。

**调用超时和操作总时限约束的是不同阶段。**一些有效的 Qwen 调用超过了之前的 300 秒调用超时。较长的操作时限允许多次调用组成的工作，而每次调用的 900 秒上限仍限制单次尝试。

在恢复运行中，多个 Retain 任务以 1,042 到 2,076 个输出 token完成。两次 Consolidation 运行分别完成了 41 项中的 41 项和 30 项中的 30 项。之后一次页面刷新超时，因此我们采用了上文所述的独立 GPU 路由。这些恢复结果不能证明长期可靠性。

这种设计有哪些取舍？ #

**无需支付托管模型费用，不等于零成本。**该部署使用自有硬件、电力、存储、维护时间，以及页面刷新时的 GPU 时间。每种部署选择都在处理能力、延迟和运维简便性之间取舍。

选择优点代价
优先使用 CPU 生成保留 GPU 可用性一次测试的页面刷新触及了一小时上限
使用 GPU 刷新页面一次运行中五个页面约两到六分钟完成占用 GPU 资源并依赖专用路由
嵌入式数据库保持部署紧凑缩小故障域，并要求测试备份

如果测得的 CPU 延迟超过维护时限，再使用 GPU 刷新路由。

Hindsight 安装指南 建议在较大型的生产部署中单独使用 PostgreSQL。随着记忆库增长，我们的嵌入式数据库需要经过测试的备份和恢复流程。

**私有推理取决于请求路径。**检查所选的 Hindsight 服务提供方、网关中的模型映射、故障转移规则、本地模型进程、日志保留策略和网络出口流量。Hindsight 跟踪 ID 有助于关联请求，Docker 会轮换容器日志。但这些措施都无法证明后续请求始终在本地处理。网关审计可补足端到端证据。

建议 #

**从本地检索模型和明确的生成限制开始。**在自有计算设备上运行 Hindsight 及其嵌入和重排序模型。通过 VPN 将生成请求路由到兼容 OpenAI 的私有网关。先测量每项操作，再分配 CPU 或 GPU 资源，并将 GPU 路由留给 CPU 延迟超过维护时限的后台任务。

在将部署视为私有且有韧性之前，请检查每条网关故障转移规则并测试记忆库恢复。 本地 AI 隐私边界指南 提供了起步检查清单。

结论 #

**此部署在自有硬件上保存 Hindsight 记忆和已检查的推理路径，无需订阅托管推理服务。**CPU 检索、受限的 Qwen 调用和单次调用的 GPU 页面刷新路由分别处理不同工作负载。恢复运行在这些设置下完成了 Retain、Consolidation 和页面刷新任务。接下来需要全面审计网关故障转移规则、测试备份，并延长可靠性观察时间。
