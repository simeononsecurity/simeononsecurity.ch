Tailscale がリレーを使う理由: 直接接続、DERP、ピアリレー

Tailscale がリレーを使うのは、デバイス間で直接接続を確立できていない場合です。起動時に短時間 DERP 接続になるのは正常です。リレー経由が続く場合は、多くの場合、デバイス間の経路に影響するネットワークアドレス変換 (NAT) やファイアウォールの条件が関係します。直接接続、DERP、ピアリレーのいずれでも、WireGuard のエンドツーエンド暗号化は維持されます。 Tailscale の接続タイプ

要点 #

  • 経路を見分ける: 直接接続、DERP、ピアリレーを区別します。
  • 証拠を集める: 両端で対象ピアへのプローブとネットワークチェックを実行します。
  • パターンを分析する: デバイスの組み合わせとネットワーク条件を比較します。
  • 変更を選ぶ: 測定したワークロードと再テストの結果に基づいて判断します。

始める前に #

前提条件: Tailscale に登録済みでオンラインのデバイスが2台あり、Tailscale のコマンドラインインターフェイス、つまり CLI を使えるターミナルが必要です。管理者アクセスが必要になるのは、調査の結果として設定を変更する場合だけです。

所要時間の目安: 基本チェックに5分、その後、比較演習に15～20分。難易度: 状況の観察は初級、ネットワーク変更は中級です。最初に、バックアップが遅い、ターミナルの応答が遅れるなど、問題を具体的に定義してください。

直接接続、DERP、ピアリレー #

tailnet は Tailscale のネットワークです。デバイスは UDP による直接接続を試み、直接経路が使えない場合はリレーを利用できます。Tailscale は接続オプションを定期的に再確認します。 接続の確立

経路通信経路一般的な意味
直接接続2台のデバイス間通常、パフォーマンス面で優先される経路
DERP リレーTailscale のリレーインフラストラクチャ経由直接アクセスに失敗した場合に中継点を追加
ピアリレーtailnet 内で設定したデバイス経由自分で管理する別のリレー経路

DERP のパフォーマンスは、追加される経路や共有サービスの容量にも左右されます。Tailscale は DERP リソースを公平に共有するためのスループット制限を公開しています。ファイル転送時間を予測できるような、あらゆる環境に当てはまるリレー速度はありません。 Tailscale のパフォーマンス問題を解決する

接続ネゴシエーションを理解する #

NAT トラバーサルとは、アドレス変換を行う機器を越えて利用可能な経路を確立するプロセスです。Tailscale は DERP 経由で通信を始め、同時に直接経路をネゴシエートします。直接接続に失敗した場合、利用可能な設定済みピアリレーが別の選択肢になります。Tailscale は時間の経過に伴って接続オプションを再確認します。 接続の確立

ハード NATは、NAT トラバーサルを難しくするマッピング動作を指します。両端の条件が関係します。異なるルーターの背後にある2台のデバイスは、両方のネットワークがプライベートアドレスを使っていても、同じように動作するとは限りません。 デバイスの接続性

持ち歩くノートパソコンでは、自宅の Wi-Fi からホテルのネットワークへ移動した後、ホームサーバーへの経路が変わることがあります。観察時に使ったネットワークを記録してください。昨日の直接接続は、今日の経路を示す証拠にはなりません。

現在の接続を確認する #

home-server を、対象ピアの Tailscale 名またはアドレスに置き換えます。

tailscale ping home-server
tailscale status
tailscale netcheck

tailscale ping は指定したピアへの接続を確認します。tailscale status はピアと接続の詳細を一覧表示します。tailscale netcheck はコマンドを実行したデバイスのネットワーク状況を報告します。各コマンドの詳細は Tailscale CLI リファレンス を参照してください。

出力の表示意味
direct対象ピアへの通信は直接経路を使っています
relay対象ピアへの通信は DERP を使っています
peer-relay通信は設定済みのピアリレーを使っています
最初の DERP pongリレー経由が続いていると判断する前に、その後の結果を確認してください

これらの表示は 接続タイプのドキュメント に基づいています。先に通信を発生させてから、確認したいピアを調べてください。上記のコマンドは例であり、ベンチマークで記録した結果ではありません。

経路の変化を読み取る #

次の例示シーケンスでは、接続の切り替わりに注目できるよう、アドレスと時間を省略しています。

最初の応答:      DERP 経由
後の応答:        直接エンドポイント経由
その後の status: direct

解釈: この観察ではネゴシエーションに成功しています。最初の応答だけで判断していたら、誤った診断になっていたでしょう。その後の応答と status でもリレー経由が続く場合は、このデバイスの組み合わせとテスト期間でリレー接続が継続していると記録します。

プローブで確認できる範囲: Tailscale ping が成功すれば、そのプローブについてピアとの接続を確認できます。ダッシュボード、ファイルサービス、SSH デーモンがアプリケーション通信を受け付けることまでは証明できません。問題が解決したと判断する前に、障害が発生しているアプリケーションも別にテストしてください。

netcheck で分かること #

両方のデバイスで tailscale netcheck を実行します。 次のフィールドを デバイス接続性のリファレンス と照らし合わせます。

フィールド判断の手がかり
UDPプローブが外向き UDP 接続を確認したか
MappingVariesByDestIP外部マッピングが変化する場合、NAT トラバーサルが難しい可能性があります
IPv6デバイスが利用可能な IPv6 接続を持つか
PortMappingサポート対象のポートマッピング方式を利用できるか

1つのフィールドだけでは断定できません。 マッピング方式を利用できても、特定のピアへの経路が機能する証拠にはなりません。リレー表示から原因となったルーターを特定することもできません。両端と実際の ping 結果を比較してください。

キャリア NATも関係します。上流のアドレス変換を管理できない場合があるためです。詳細は T-Mobile Home Internet のポートフォワーディング解説 を参照してください。キャリア NAT の背後にある接続がすべて同じように動作すると決めつけないでください。

3組のデバイスを比較する #

可能であれば、3台目の登録済みデバイスを使って証拠を増やします。以下は仮定上のパターンであり、測定結果ではありません。

デバイスの組み合わせ観察された経路
ノートパソコンからホームサーバーDERP
ノートパソコンから別のサーバー直接接続
ホームサーバーから別のサーバーDERP

作業仮説: ホームサーバーが関係する2つの経路でリレーが続いたため、まずホームサーバーのネットワークを調査します。これは手がかりであり、証明ではありません。接続ネゴシエーションは組み合わせごとに行われ、比較対象のサーバーにも独自のネットワーク条件があります。

次の観察: 3台すべてで netcheck の出力を集め、別の管理下にあるネットワークからノートパソコンとホームサーバー間のテストを繰り返します。経路が変化したら、どのネットワークを変えたか正確に記録してください。テストする前に特定のファイアウォール設定が原因だと判断しないでください。

演習: ノートパソコンとホームサーバーは直接接続しているのに、ファイル転送が遅い状態です。この観察ではリレーが原因という説明は当てはまりません。リレー設定を変更する前に、基盤となるアップロード接続、サーバー負荷、ストレージ、アプリケーションの動作を確認してください。

対象を絞った変更を選ぶ #

まず、管理下にある別のネットワークで比較テストを行います。同じピアが直接接続できれば、元のネットワーク経路に関する有用な証拠になります。関係のない DNS やアプリケーション設定を変える前に、UDP の制限と NAT の構成を確認してください。

変更する変数を1つに絞り、同じ確認をやり直して同じワークロードを測定します。転送方向、ファイルサイズ、経過時間、接続タイプを記録してください。これにより、経路の改善と、サーバーやストレージ負荷の変化を区別できます。

ファイアウォールの変更は、プラットフォーム固有のガイダンスと収集した証拠に基づいてください。アプリケーションポートをインターネットに公開しても、それだけで Tailscale の通信経路が改善するわけではありません。必要な通信と管理対象のネットワークに変更を限定してください。 Tailscale のファイアウォールガイダンス

観察結果検討する変更
UDP プローブが失敗するこのネットワークの外向き UDP 制限を確認する
宛先ごとにマッピングが異なる管理している機器の NAT 動作を確認する
直接接続なのにアプリケーションが遅いホスト、基盤の接続、ワークロードを調べる
リレーは動作し、利用上の問題もない現状を維持し、基準値を記録する

リレー表示だけを消す目的で設定を変更するより、測定で確認できる改善を優先してください。

ピアリレーを評価する #

ピアリレーには、適切なホスト、到達可能な UDP ポート、使用を許可するアクセス方針が必要です。リレーと参加するクライアントの両方で Tailscale 1.86 以降が必要です。デバイスを割り当てる前に、サポートされているホストプラットフォームを確認してください。 ピアリレーの要件

配置によって有用性が決まります。 同じ到達不能なネットワーク境界の内側にあるデバイスは、リレーポートに到達できるようになるまで、ほかのピアの助けにはなりません。

保守の負担: 誰かがリレーをオンラインに保ち、更新し、十分な性能を確保する必要があります。管理作業がたまにしかなく、遅延も許容できるなら、その負担と測定した効果を比較してください。大容量転送を繰り返す場合は、採用前に候補のリレー経由でワークロードを測定します。

共有トラフィックの影響を確認する #

サブネットルーターや出口ノードが複数のワークロードを DERP 経由で処理する場合、集約トラフィックに注意してください。Tailscale は、リレー経由の大量トラフィックが、同じ接続を共有する低遅延が必要な通信を遅らせる状況を説明しています。 ハード NAT の問題を解決する

比較演習: 大容量バックアップの前、実行中、完了後に、対話型セッションを観察します。対象のエンドポイントを固定し、毎回経路を記録してください。転送中に遅延が発生すれば共有負荷の調査を検討できますが、原因を特定したことにはなりません。

観察結果から次のテストを選びます。 リンクの飽和とホスト負荷を確認します。そのうえで、トポロジーが許せば、直接経路の評価や低遅延が必要なサービスの分離を検討してください。DNS の症状だけを根拠に DNS 設定の誤りと決めつけないでください。

リレーは出口ノードですか？ #

出口ノードは、クライアントの一般的なインターネット通信を tailnet 内の指定デバイス経由でルーティングします。リレーは Tailscale のピア間で通信を中継します。出口ノードを選んでも、そのノードまで直接接続できるとは限りません。 出口ノードのドキュメント

診断記録を作成する #

実際の問題について、変更前後の短い記録を保存します。

日付と Tailscale のバージョン:
送信元と宛先のデバイス:
各デバイスで使ったネットワーク:
接続の初期経路と安定後の経路:
両端の netcheck の結果:
ワークロード、方向、経過時間:
テストした変更1つ:
再テストの結果:
変更を維持するか戻すかの判断:

完了条件: 記録によって、具体的な症状、観察結果、仮説、測定済みの再テストが結び付いていること。「リレーが消えた」だけでは、アプリケーションがまだ遅い場合に不十分です。「DERP 経由でもバックアップが時間要件を満たす」は、要件が明確なら有効な結果です。

tailscale netcheck は判定ではなく証拠として使ってください。 このコマンドが示すのは1台のデバイスから見たネットワークです。安定後の経路は、デバイスの組み合わせとワークロードによって決まります。ファイアウォールや NAT の設定を変更する前に、両端のデバイス、最後の tailscale status の行、アプリケーションの測定値を記録してください。

次の手順 #

重要なピアへの経路を記録し、ネットワーク設定を変える前にワークロードをテストしてください。調整インフラストラクチャの運用者については、 Tailscale と Headscale の比較 を参照してください。
