Linux Containers（LXC）内のDockerは、インフラのオーバーヘッドを抑える一方で、アプリケーションのランタイムとProxmoxホストとの相互作用を増やします。家庭で使うDockerサービスには、Debianの**仮想マシン（VM）**が実用的な出発点です。ゲストカーネルを分離し、トラブルシューティング時に再現する環境を簡素化できます。この記事では、提供された動画と関連するインシデント報告を確認し、文書化された障害と移行計画を紹介します。

要点 #

  • 障害の種類を区別する: Dockerの起動エラー、停止したVM、応答しない物理ホストでは、調査方法が異なります。
  • 根拠を評価する: 移行後の安定は復旧判断を支えますが、元の原因を証明するものではありません。
  • 最新の文書を確認する: OCIイメージのネイティブ対応とLXC内のDockerは、異なる導入経路です。
  • 永続データを保護する: ProxmoxのバックアップやComposeファイルだけでは、すべてのアプリケーションデータが保護されるとは限りません。
  • 復旧計画をテストする: 古い構成を廃止する前に、復元、再起動後の動作、サービスの可用性を測定します。

始める前に #

難易度: 中級。対象読者: 入れ子のDockerとVM内のDockerを比較するProxmox管理者。診断例を使う前に、Composeプロジェクト、コンテナのマウント、Linuxシェルのプロンプトを認識できる必要があります。

所要時間の目安: インベントリと根拠の収集に30〜60分を見込みます。移行時間は、データベースのサイズ、ストレージのスループット、ハードウェアへのアクセス、選択する停止時間によって異なります。以下は文書化された手順と説明用の推論であり、この記事のために実施したラボのベンチマークではありません。

要件重要な理由
ホストコンソールへのアクセスネットワーク障害とホスト全体の停止を区別できます
最新のバックアップ構成を変更する前の復旧手段になります
コンテナとVMのIDホスト上のコマンドを対象のワークロードに向けます
アプリケーションデータの一覧ボリューム、バインドマウント、データベース、外部依存関係を特定します
独立したテスト環境本番環境で書き込み先を二重化せずに移行を試せます

元の動画を見る #

元の動画: Proxmox: The Hidden Danger of Running Docker Inside LXC 。Proxmox x Kubernetes x Homelab x Backupが2026年9月15日に公開しました。中心となる問いは、リソースを節約する構成にどれだけの運用上の不確実性が伴うかです。

根拠の範囲: 動画はインシデントを紹介し、教訓を提案しています。以下では、所有者の観察、文書化されたソフトウェアの動作、そこから導かれる推奨事項を分けて扱います。

インシデントから分かること #

元の報告には、Intel Core i3-13100とBIOSTAR H610MHPを搭載したホストが記載されています。所有者は、管理アクセスとLXCサービスに影響する断続的なフリーズを報告しました。接続したディスプレイは応答を停止しましたが、報告にはsyslogの出力が続いていたと明記されています。ログがまったく残らなかったとするより、具体的な状況です。 Proxmoxフォーラムの元の報告

所有者は後に、移行後に改善したと報告しました。8月3日の追記では、DockerワークロードをDebian仮想マシンに移し、Dockerを実行するLXCを停止したと説明しています。追記時点で、その後のフリーズは報告されていません。動画は16日間の安定期間に言及しています。どちらの記述も、制御された再現試験や特定の故障部品の特定を示すものではありません。 同じスレッド内の所有者の追記

観察事項裏付けられること証明されないこと
初期の長い稼働期間以前のワークロードとソフトウェアの組み合わせが動作していたその後のすべての更新後も信頼できること
ホストとサービスが停止障害が単一アプリケーションを超えているDockerが根本原因であること
移行の後に改善運用上有効な回避策どの相互作用の変更がきっかけを取り除いたか
16日間の安定限られた観察期間2〜3週間ごとに起きる障害パターンが解消したこと

観察期間には注意が必要です。16日は、再発間隔の14〜21日の範囲内です。以前の障害間隔を数回分、同程度のワークロード、通常のメンテナンスを含む長い観察期間であれば、確信度は高まります。それでも、制御された因果関係の証明にはなりません。

運用上の成功と根本原因の証明は別の結果です。家庭で信頼しているサービスを復旧することは、移行の正当な理由です。より強い根拠で仕組みが明らかになるまでは、結果を「観察された信頼性の改善」と説明します。

カーネルの境界を把握する #

LXC内のDocker:
アプリケーション -> Dockerランタイム -> LXCの名前空間とポリシー
                         -> Proxmoxホストカーネル -> 物理ハードウェア

VM内のDocker:
アプリケーション -> Dockerランタイム -> ゲストLinuxカーネル
                         -> 仮想ハードウェア / KVM-QEMU
                         -> Proxmoxホストカーネル -> 物理ハードウェア

LXCはホストのカーネルを使います。名前空間、コントロールグループ、ケーパビリティ、seccomp、セキュリティプロファイルはプロセスを制限しますが、独立したカーネルを提供しません。LXC内にDockerを加えると、同じホストカーネルを使うワークロードにコンテナ管理の層がもう一つ加わります。 LXCのアーキテクチャと隔離機能

VMにはゲストカーネルがあります。ゲストカーネルの障害は通常そのVMに影響し、Proxmoxは他のゲストの管理を続けます。VMも物理ホスト、ハイパーバイザー、ストレージ、ネットワークに依存します。ハードウェア障害やホストカーネルの欠陥は共有依存のままです。

境界LXC内のDockerVM内のDocker
アプリケーションが使うカーネルProxmoxホストのカーネルゲストカーネル
Dockerランタイム環境外側のコンテナのポリシーで制限一般的なゲストOS内にインストール
ゲストカーネルの更新ホストカーネルに連動ゲスト内で管理
物理ホストの停止依存するワークロードが停止依存するワークロードが停止

VMは一部の障害伝播を抑えますが、すべてではありません。LXC内のアプリケーションプロセスがクラッシュしても、Proxmoxが自動的に停止するわけではありません。一方、すべての家庭内サービスを1台のDocker VMに入れると、同じゲストOSとメンテナンス予定に依存します。

より広い概念上の比較は Dockerコンテナと仮想マシン を参照してください。ここではProxmox内のDockerの配置と、それに伴うトラブルシューティングの境界を扱います。

サポートを具体的に定義する #

**「サポート対象外」**という表現には、対象のコンポーネントとバージョンが必要です。ベンダー推奨の構成、文書化された機能、ディストリビューションによる保守、契約上のサポート権を区別します。入れ子の構成が動作しても、すべての組み合わせが同程度にテストされているとは限りません。VMの推奨も、メンテナーが入れ子に関連するすべてのバグを拒否するという意味ではありません。

Proxmoxの最新ドキュメントでは、重要な区別も示されています。コンテナツールキットのソースは、**Open Container Initiative（OCI）**アプリケーションイメージのサポートを技術プレビューとして説明し、イメージをLXCフレームワークに変換します。隔離とライブマイグレーションを重視する要件では、QEMU VM内のコンテナも推奨しています。この仕組みへのOCIイメージのインポートは、LXCゲストにDocker EngineをインストールしてComposeを実行することとは異なります。 Proxmoxコンテナツールキットのドキュメント

構成確認する項目
従来型のLXCゲストOSテンプレートとアプリケーションは、文書化されたコンテナの制限に適合するか
LXC内にDockerを入れ子にする構成どのカーネル、ランタイム、セキュリティポリシー、ストレージの組み合わせがテスト済みか
OCIイメージのネイティブインポートインストール済みProxmoxのバージョンは、文書化された機能と必要な動作を提供するか
Debian VM内のDockerゲストのリリースはDockerのインストール要件を満たすか

DockerはDebian向けのインストール手順を公開しています。ゲストOSでは、サポート対象のリリース一覧とリポジトリの手順を使ってください。古い手順が現行でも正しいと決めつけず、導入したバージョンを記録します。これは文書化されたインストール基準であり、稼働率の保証や自動的な有償サポート契約ではありません。 DebianでのDocker Engine

確認済みの入れ子構成の障害 #

2025年のrunc/AppArmor互換性問題は検証可能な例です。runcのメンテナーは、AppArmorプロファイルが設定された外側のコンテナ内で、ファイル記述子を再オープンする際の障害を文書化しました。AppArmorが**/proc/sysへのアクセスを/sys**へのアクセスと誤認し、ポリシーで拒否しました。 runcの課題4968

影響を受けた起動処理では、次のエラーが報告されました。

open sysctl net.ipv4.ip_unprivileged_port_start file: reopen fd 8: permission denied

記録された障害はコンテナの起動を妨げました。フォーラムで報告されたホストのフリーズを説明するものではありません。issueには、この問題に対するProxmoxの修正として**lxc-pve 6.0.5-2**が記録されています。対応する上流のLXC変更は2025年11月20日にマージされました。これらは過去の修正記録であり、現行システムでパッケージを固定する推奨ではありません。 メンテナーによる修正の概要 、 マージ済みのLXC変更

教訓は依存関係の調整です。ランタイムのセキュリティ変更が外側のコンテナのポリシーと相互作用し、修正には別の層の変更が必要でした。AppArmorを恒久的に無効にしたり、古く脆弱なランタイムを残したりせず、使用中のリリース向けに保守された適切なパッケージ更新を適用してください。

要点: このインシデントは、入れ子のコンテナに実際の互換性問題があり、メンテナーが対応したことを示しています。LXC全般の不安定さや、別のホスト停止の原因を証明するものではありません。

実際のコストを比較する #

実際のワークロードを使って効率を測ります。同等の条件で、ホストのメモリ負荷、CPU需要、ストレージ遅延、アプリケーション応答時間、復旧の手間を比較します。VMに割り当てたRAM、ゲストの空きメモリ、ホストの常駐メモリは別々の測定値です。

主張される節約収集する測定値追加で記録するコスト
メモリオーバーヘッドの削減同じワークロードにおけるホストのメモリ使用量と負荷入れ子の制限管理と競合の診断にかかる時間
導入の高速化データ復元後にサービスが利用可能になるまでの時間更新失敗後の再構築にかかる時間
ハードウェア共有の簡素化必要なデバイス、権限、アプリケーションの正常動作ホストドライバーへの依存と移行の制約
バックアップの簡素化必要なデータをすべて正常に復元できること外部マウントとアプリケーションの整合性

Dockerでは、制限を設定しない限り、既定でCPUとメモリを無制限に使用します。LXCでは外側のコンテナが独自の制限を追加します。VMではゲストへの割り当てが別の容量境界になります。ゲストOS、Docker、キャッシュ、アプリケーションのピーク需要にも容量が必要です。 Dockerのリソース制限

ハードウェアアクセスはワークロードの要件です。ホストのグラフィックデバイスをコンテナと共有する方法と、PCIデバイスをVMに割り当てる方法では、ドライバーや隔離の設定が異なります。選ぶ前に、対象デバイスとアプリケーションの要件を具体化してください。ハードウェアデコードを必要とするメディア処理なら、一般的なHTTPヘルスチェックに加えて、移行後にデコードが成功することを試験します。

一律のオーバーヘッド値を避けます。この記事では固定のRAM増加量や性能比を示しません。そうした値には、統制されたワークロード、構成、測定方法が必要です。以下の判断記録には、自分で比較した結果を記載してください。

層ごとに根拠を集める #

管理者シェルでProxmoxホストから始めます。調査対象のLXC IDに合わせて**101**を置き換えます。

pveversion -v
uname -r
pct config 101
journalctl --list-boots
journalctl -k -b -1 --no-pager

**pveversion -vは、インストール済みProxmoxコンポーネントのバージョンを記録します。pct configは外側のコンテナの構成を記録します。journalctlでは、-kがカーネルメッセージ、-b -1が前回の起動、--no-pager**が通常の端末出力を選びます。前回起動時のメッセージには、ジャーナルデータの保存が必要です。 Proxmoxツールキット 、 systemd journalctlリファレンス

次に、デーモンを実行するLXCまたはVM内でDockerホストを調べます。

docker version
docker info
docker compose version
docker ps -a
docker stats --no-stream

両方の環境を記録します。コンテナイメージのタグだけでは、Docker、containerd、runc、ホストカーネル、セキュリティポリシー、ストレージバックエンドの情報は分かりません。インシデントの時刻、最近の更新、ローカルホストコンソールの応答を記録します。診断情報を公開する前に、認証情報と非公開のアプリケーション情報を削除してください。

特定のワークロードを調べるには、コンテナ名を指定して**app**を置き換えます。

docker inspect --format '{{json .State}}' app
docker inspect --format '{{.RestartCount}}' app
docker inspect --format '{{json .Mounts}}' app

**docker inspect**は、指定したコンテナの状態、再起動回数、マウント情報を表示します。再起動回数はログと照合する手がかりであり、ホスト障害の証明ではありません。コンテナを再作成すると履歴も新しくなります。 docker inspectリファレンス

リソース負荷と停止を区別する #

問題が発生している間、ホスト上のLinuxリソース負荷情報を取得します。

cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io

Pressure Stall Information（PSI）は、リソース待ちでタスクが失った時間を報告します。someとfullは異なる停止条件を示し、avg10、avg60、**avg300**は最近の期間を要約します。メモリ負荷とメモリ使用量は別です。大きなキャッシュだけでは不足を示しません。 Linux PSIドキュメント

根拠有用な解釈次の確認
1つのコンテナが繰り返し終了するアプリケーションまたはコンテナランタイムの障害終了状態、サービスログ、再起動ポリシー
SSHは失敗するがコンソールは動作するネットワークまたは管理経路の障害リンク状態、NICドライバー、ブリッジ、ファイアウォール
負荷中にMemory PSIが上昇するメモリ競合によりタスクが時間を失う制限、回収動作、OOM記録、ワークロードの増加
ストレージ要求が停止するI/O依存関係が処理を遅らせているデバイス状態、ストレージログ、遅延、キュー
Watchdogがロックアップを報告するカーネル検出器が定義済みの停止条件を検知した完全なトレース、カーネルバージョン、再現可能なトリガー
最後のログがない有用な出力が届く前に記録が終わった再発前に永続または外部の記録を設定

Linuxロックアップの報告には技術的な意味があります。カーネルのWatchdogはsoft lockupとhard lockupを区別します。ブラウザーのタイムアウトはどちらも証明しません。Watchdogの報告がないことも、ホストが正常だった証明にはなりません。 Linuxロックアップ検出のドキュメント

ファームウェアや電源状態の変更は実験です。以前の設定、変更理由、観察期間を記録してください。CPUアイドル状態を無効にすると、電力と熱の動作が変わります。別のマシンの報告だけでは、同じ設定を一律に推奨できません。

有用なログを保存する #

永続ジャーナリングは、再起動後も根拠を保持できる可能性を高めます。journaldの設定ファイルには次の項目を指定します。

[Journal]
Storage=persistent

**Storage=persistentは、利用可能な場合にジャーナルをディスクへ保存する設定です。保持期間とディスク容量を設定し、journalctl --list-boots**に以前の起動が表示されることを確認します。永続ログでも、障害前にホストが書き込みを完了できることが前提です。 systemd journaldの設定

外部からの監視は別の視点を加えます。別のマシンからサービスを監視し、時刻を記録します。障害が起きるProxmoxホスト上の監視は同じ停止中に消えるため、ダウンタイムとテレメトリー欠落を区別しにくくなります。

説明用の試験: 別のシステムから軽量なHTTPチェックを定期実行し、失敗とホスト到達性、ローカルコンソールの状態を比較します。ホストが応答する状態でのアプリケーションのタイムアウトと、アプリケーション、管理経路、コンソールの同時停止では、調査が異なります。これは診断設計であり、元のインシデントで観察された結果ではありません。

管理された移行を計画する #

まずリスクの低いComposeプロジェクトを1つ選びます。Dockerのインストール文書にあるリリースでDebian VMを準備し、バックアップとリソース割り当てを設定します。移行先がテストに合格するまで、ロールバック用に元の構成を残します。 DockerのDebian向けインストール手順

作業ディレクトリでComposeプロジェクトを一覧化します。

docker compose config --quiet
docker compose config --images
docker compose config --volumes

**--quietは出力せずに構成を検証します。--imagesは参照されるイメージ、--volumes**は名前付きボリュームを一覧表示します。このコマンドではアプリケーションデータはエクスポートされず、バインドマウントの完全な一覧も得られません。Composeファイルと各コンテナのマウントも確認してください。 Docker Compose configリファレンス

データまたは依存関係移行時の作業
Compose定義プロジェクトファイルを移し、検証済みの構成を保持する
シークレットと環境設定選択したシークレット管理手順で必要な値を再設定する
名前付きボリュームアプリケーションと整合する手順で内容をバックアップし復元する
バインドマウントのパス元のデータを移行または再接続し、所有者を確認する
データベース対応するバックアップと復元、または書き込みを停止したコピー手順を使う
デバイスと共有領域アクセスを再設定し、アプリケーションの動作をテストする
ポートとDNS移行先アドレスを準備し、切り替えを計画する

ボリュームはコンテナより長く存続しますが、自動では移行されません。Composeファイルはリソース名とサービスを定義します。Dockerのボリューム文書には、永続データのバックアップと復元が別々に記載されています。プロジェクトを再作成するだけでデータが復元されると考えてはいけません。 Dockerボリュームのライフサイクルとバックアップ

Proxmoxバックアップの対象範囲も別に確認してください。文書上、コンテナのバックアップにはデバイスやバインドマウントの内容が含まれません。LXCのルートファイルシステムのバックアップが成功しても、内部で公開したすべてのディレクトリが保護されるとは限りません。 Proxmoxバックアップのドキュメント

コピー前にストレージを確認する #

各Dockerホストで実際のDockerストレージ設定を確認します。

docker info
findmnt -T /var/lib/docker

**findmntは指定したパスを含むファイルシステムを示します。デーモンが別のデータルートを使う場合は/var/lib/docker**を置き換え、必要に応じてcontainerdのストレージパスも確認します。Dockerの文書ではcontainerdイメージストアと従来のストレージドライバーを区別し、バックエンドごとの要件を説明しています。 Dockerストレージバックエンドの選択

選択したバックエンドの手順に沿って、**イメージを再作成し、アプリケーションデータを復元します。**稼働中のDockerデータディレクトリを異なるストレージ構成間でコピーすると、メタデータ、マウント状態、整合性に関する追加の前提が必要です。停止したアプリケーションのデータボリュームをバックアップする操作とは異なります。

ロールバックを用意して切り替える #

  1. 復元をリハーサルする: 必要に応じて、別のアドレスとテストデータを使ってVM上で試します。
  2. 本番の書き込みを停止する: 合意した停止時間に最終的な整合性のあるバックアップを取得します。
  3. 復元して検証する: アプリケーションデータ、権限、認証情報、必要なハードウェアアクセスを確認します。
  4. サービスの経路を切り替える: 移行先がアプリケーション固有の確認項目に合格してから行います。
  5. 元の環境を停止したままにする: その構成と復旧データは保持します。
  6. 切り替え後のロールバックを文書化する: 古いシステムを再起動する前に、切り替え後の書き込みデータの扱いを決めます。

同じデータベースストレージに対する2つの同時書き込み元を避けます。切り替え後に本番データが追加された場合、ロールバックではその書き込みを保持するか、意図的に破棄する計画が必要です。古いコンテナを再起動するだけでは、分岐したデータ履歴は統合されません。

稼働時間だけでなくテストする #

受け入れテストはサービスの目的に合わせます。コンテナが正常な状態でも、確認できるのはプロセスが動いていることだけです。データ、ネットワーク、依存関係、復旧動作も必要です。

テスト保存する根拠
アプリケーションの機能実際のトランザクション、クエリ、メディア処理の成功
データの完全性期待されるレコード、ファイル、権限、最近の変更
ゲストの再起動手作業の修復なしにサービスが復帰する
バックアップからの復元復元したコピーが同じ機能テストに合格する
代表的な負荷遅延、CPU、メモリ負荷、ストレージの動作
メンテナンスのリハーサルテスト済みの更新と実行可能な復旧手順
長期の観察以前の障害間隔を複数回含む可用性記録

判断例: カメラサービスと実験用ダウンローダーが現在、1つの入れ子構成を共有しています。両方を1台のVMに移すとカーネルの分離は改善しますが、ゲストのメンテナンス境界は共有されたままです。カメラの可用性を優先する場合は、メンテナンスグループとリソース制限を分けることを検討し、ダウンローダーの更新中に録画が続くかテストします。

想定される考え方: 分離したいサービスの依存関係に合わせて配置を選びます。同じ物理サーバー上の2台のVMは、電源、ストレージ、ホストカーネルを共有します。サーバーの停止にも耐える必要があるなら、独立したシステムを追加するか、許容可能な手動の代替手順が必要です。

判断記録を作成する #

測定した根拠を使って構成を選び、見直す時期を定めます。

サービスと家庭への影響:
現在のホスト / カーネル / LXC / Dockerのバージョン:
必要なGPU、デバイス、ネットワークへのアクセス:
測定したメモリ、CPU、ストレージ、レイテンシ:
既知の障害の兆候と再発間隔:
バックアップ範囲と復元成功の証拠:
選択した構成と理由:
許容される停止時間と復旧目標:
切り替えと切り替え後のデータ復元手順:
受け入れテストと監視期間:
構成の再検討が必要となる条件:

LXC内のDockerを意図的に選ぶのは、その利点が統合作業に見合い、復旧経路をテスト済みの場合です。通常のDockerゲスト環境と独立したゲストカーネルでサービス運用が簡素になるならVMを選びます。どちらの判断も、バックアップ、監視、ホストの保守の代わりにはなりません。

移行前に変更を審査する #

移行を管理された変更として扱い、元のインシデント原因の証明と混同しません。切り替え前に、コンテナ設定、イメージのダイジェスト、バインドマウントのパス、環境キー、デバイス割り当て、最後に成功した復元を記録します。切り替え後は同じサービス確認とリソース測定を比較します。新しい環境が受け入れ期間を通過するまで、古いワークロードは停止したままにします。

移行後にインシデントが再発した場合は、両方の配置でホストカーネル、ストレージ、メモリ負荷、デバイスアクセス、Dockerのバージョンを比較します。比較によって調査範囲を絞れます。関連する変数が制御された場合に限り、移行の成功を因果関係の実験として扱えます。

関連する作業には、アップグレード計画用の Proxmox VEアップグレードガイド と、ワークロードの保護用の DockerとKubernetesのセキュリティガイド を参照してください。構成の選択、アップグレードの実施、インシデントの診断は、それぞれの根拠を持つ別の判断として扱います。
