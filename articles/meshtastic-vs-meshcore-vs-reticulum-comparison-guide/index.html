简短结论 #

**这三个项目解决的并不是同一个问题。**Meshtastic 和 MeshCore 是采用不同路由理念的 LoRa 网状网络系统。Reticulum 的范围更广，它是与传输方式无关的网络层，可同时运行在 LoRa、分组无线电、Wi-Fi、以太网、串行链路和互联网之上。

**正确的问题不是“哪个最好”，**而是“哪种架构适合我要构建的网络？”

Meshtastic 适合临时组网和移动用户。 MeshCore 适合经过规划的固定基础设施。 **Reticulum 适合需要连接不同传输方式或独立网络的场景。**构建一个区域 LoRa 网状网络时，大多数人只需要前两者之一。

先确定要构建的网络 #

比较协议之前，先写下网络要完成的任务。对多数社区和应急通信部署，以下目标很实用：

  • 免许可运行，任何人无需业余无线电执照即可参与
  • 低成本硬件，社区有能力大规模部署
  • 低功耗，最好可由太阳能或电池供电
  • 远距离通信，不依赖蜂窝网络或互联网
  • 脱离基础设施运行，不依赖电网、ISP 或运营商
  • 非无线电专家也能轻松设置和使用
  • 适合社区部署，而不是只供一位运营者在地下室使用
  • 节点数量超过少数几个后仍可扩展
  • 基础设施故障时仍有用，例如蜂窝基站和互联网中断
  • 可靠送达比刷新距离纪录更重要

阅读后文时记住这份清单。下面会按这些要求评估每项架构取舍。

Meshtastic #

Meshtastic 是这里最成熟、部署最广泛的选择。它很好地满足了普通用户的许多需求。

  • 成熟的生态系统，多年持续活跃开发
  • 庞大的用户社区、活跃的 Discord 和完善的文档
  • 广泛支持硬件，包括 LILYGO、Heltec、RAK 和 Seeed 板卡
  • 优秀的 iOS 和 Android 移动应用
  • 入门简单，首次设置不到 20 分钟
  • 很好地支持便携和移动用户，适合不可预测地加入或离开网状网络的人
  • GPS 和遥测功能，以及围绕这些功能发展起来的生态
  • 许多城市已有部署，加入现有网络比从零建设容易

如需详细比较 Meshtastic 与 MeshCore 的路由、硬件兼容性和设置过程，请参阅** MeshCore 与 Meshtastic 对比指南 **。本文重点讨论大规模部署最重要的架构问题：受控泛洪和跳数上限。

受控泛洪和跳数上限为何重要 #

Meshtastic 广播使用受控泛洪。一个节点发送消息后，所有收到消息的节点都会按配置的跳数上限重新广播数据包。节点无需了解网络拓扑。新节点无需配置即可加入，故障节点也会被自动绕过，因为泛洪会找到其他路径。

默认跳数上限是 3，最大为 7。不要把问题说成“Meshtastic 最多只能走七跳”。真正的问题是提高这个数字会带来什么代价。

每增加一跳，消息覆盖范围内的所有节点都要再次广播。转发增加会导致：

  • 每条消息占用更多空中时间
  • 更多重复传输，因为每个听到重播的节点都会再次发送
  • 共享信道竞争加剧
  • 碰撞风险上升，更多无线设备在同一时段发送
  • 接收并转发消息的每个节点耗电更多
  • 留给实际消息流量的信道容量减少

LoRa 容量受空中占用时间和区域占空比限制，而不是受节点数限制。十个频繁发送 GPS 和遥测数据的活跃节点就可能占满信道，五十个安静的传感器节点则可能毫无影响。因此，高跳数上限的密集网络会比相同节点数、较低上限且遥测间隔受控的网络更快退化。Meshtastic 2.6 改进了直接消息传递：发现路由后切换到下一跳路由，因此点对点流量不再泛洪整个跳数范围。广播消息仍然会泛洪。

对徒步俱乐部规模的小型或中型网络，这通常不是问题。对于覆盖一座城市或多个城镇的区域网络，它会成为核心设计限制。

MeshCore #

**MeshCore 采用了不同的架构思路：**它不把每台设备都视为平等的消息传播参与者，而是建立有规划的基础设施层，并将流量路由到该层。

节点角色 #

MeshCore 部署将节点划分为不同角色，而不是让所有节点构成一个扁平网络：

  • 伴随节点或客户端节点配有与手机或笔记本配对的 LoRa 无线电，并在附近有基础设施时通过它通信
  • 中继器专门在客户端与其他基础设施之间转发流量，承担大部分路由工作
  • 聊天室服务器是可选组件，用来保存群组对话，并在客户端重新连接时交付存储的消息

系统先发现路由，然后让流量沿发现的路径前往目的地，而不是向所有附近节点扩散。信道占用量取决于活跃对话，而非节点总数。这与 Meshtastic 的泛洪模型有明显不同的增长方式。

为什么适合固定基础设施 #

*这是支持 MeshCore 的核心理由。*Meshtastic 的泛洪模型确实适合临时和移动网络：无需规划，无需维护基础设施，也能妥善应对节点的加入和离开。当用户有意部署基础设施时，MeshCore 的路由模型更有优势。

由已知的高处中继器组成的网络，可以有计划地设计覆盖范围，而不是依赖某一天恰好互相在范围内的节点。这对以下场景很重要：

  • 供电可靠的永久屋顶节点
  • 通信塔和现有通信设施
  • 无人值守地点的太阳能中继器
  • 山地或高处中继站
  • 由多个群体共享的社区基础设施
  • 覆盖范围超过单一社区的区域网络
  • 应急通信，可预测的覆盖范围比灵活性更重要

这与射频基础知识相符：**规划合理的基础设施之间建立可靠链路，比一味提高天线增益、发射功率或理论距离更重要。**使用专用中继器的协议，会让你从认真进行射频选址中受益。泛洪协议对此的收益较小，因为无论节点放在哪里，它们的作用都大致相同。

移动节点的说法及其代价 #

一种常见建议是：“Meshtastic 更适合移动节点，MeshCore 更适合固定节点，所以用户用 Meshtastic，骨干网用 MeshCore。”

纸面上听起来很吸引人。实际上，混用两者并不会自动获得双方的优点，因为**Meshtastic 和 MeshCore 使用不同的路由和网络架构，彼此不能交换消息。**连接它们需要在不兼容的系统间增加转换层，而不是简单拼合各自的优点。

建立桥接后，你需要维护：

  • 两个独立网络，各有自己的拓扑和行为
  • 两种互不共享状态的路由模型
  • 需要持续开发和维护的转换层
  • 用于运行桥接的额外基础设施
  • 两套固件生态的额外配置
  • 更多故障点，桥接本身可能独立于任一网状网络发生故障
  • 更复杂的排障，消息可能在任一网络或桥接处丢失

采用这种设计之前，直接问自己：**新增的复杂性解决了单个调优良好的网状协议无法解决的问题吗？**通常，正确配置的 MeshCore 加上少量适合移动用户的伴随节点，或者 Meshtastic 加上几个位置合适、跳数上限较高的中继器，就能带来大部分实际好处，无需把两个网络粘在一起。

Reticulum #

Reticulum 值得单独归类，而不是当作“第三种 LoRa 网状方案”，因为它本身并非 LoRa 网状协议。它的核心特点是与传输方式无关。

Reticulum 是基于密码学的网络协议栈。它不使用源地址，因此数据包不包含发起地点信息。每个地址都是自主的：生成后数秒到数分钟内即可在全球范围内访问；即使物理迁移到网络的另一部分，仍可访问。所有通信默认使用临时密钥和前向保密进行加密。Reticulum 会丢弃未加密的数据包，而不是交付它们。它不需要内核驱动，可在任何运行 Python 3 的系统用户空间运行，包括 Raspberry Pi Zero。

Reticulum 支持的接口包括：

  • LoRa，使用兼容 RNode 的硬件。RNode 是开放的 LoRa 收发器设计，可自行制作、刷写到常见板卡或购买成品
  • 分组无线电，通过任何运行 KISS 模式的 TNC，适合 VHF 和 UHF 业余无线电
  • Wi-Fi 和有线以太网，无需路由器或 DHCP 服务器即可自动发现对等节点
  • 串行链路，用于设备间直接连接
  • 现有 IP 网络上的 TCP 和 UDP，包括互联网
  • I2P 网络，以及可通过 Python 桥接的其他自定义接口

Reticulum 上层可以运行 LXMF 等应用，它是一种容忍延迟的消息协议；也可以使用 Sideband、NomadNet 和社区开发的 MeshChat 客户端。这些工具为 Reticulum 网络提供消息和浏览功能，类似 Meshtastic 和 MeshCore 开箱即用的功能。

Reticulum 适用的场景 #

在混合传输方式的网络中，Reticulum 的价值很明显，例如：

LoRa 网状网络、Reticulum 节点、IP 链路、Reticulum 节点、无线电网络

Reticulum 在这里完成了 Meshtastic 和 MeshCore 都做不到的事情：把两个独立的通信系统连接为一个可寻址网络。这是具体的实际需求，不是通用升级。适合的场景包括：

  • 连接地理位置分散且没有直接无线电链路的网络
  • 连接不同的物理传输方式，例如一端是 LoRa 网状网络，另一端是分组无线电网络
  • 无线电到 IP 网关，在现场无线网络与互联网之间传递流量
  • 实验与研究网络，传输方式的灵活组合比部署简单更重要
  • 单一传输方式无法满足全部需求、必须拼接各部分的网络

Reticulum 会增加不必要复杂性的场景 #

如果所有人都使用兼容的 LoRa 硬件，实际目标又是一个区域 LoRa 网状网络，添加 Reticulum 收益很小，却要付出实际代价。网络协议栈每增加一层，就会增加：

  • 配置工作，需要正确设置并在各节点间保持一致
  • 软件维护，需要安装、更新和排障
  • 硬件需求，某些接口桥接方式下还要添置设备
  • 排障范围，消息无法送达时要检查更多环节
  • 运维人员的知识要求，还要理解第三种网络模型

*只有当传输独立性解决了真实需求时才使用 Reticulum，而不是因为它支持更多接口类型。*单一 LoRa 网状网络的跳数上限问题，应通过调整 Meshtastic 或 MeshCore 来解决。这不是传输独立性问题，Reticulum 也不会改变这一点。

先建好一个健康的网状网络，再考虑三个割裂的网络 #

如果一个协议已经符合需求，就先建好一个健康的网络，不要用桥接拼接多个小网络。上文多数选择都应遵循“先建一个网”的原则。

在社区网络中，**现有用户之间的互操作性往往比架构灵活性更重要。**规模大、运行正常的单协议网络，实际价值通常高于三个技术上有趣、但彼此割裂且只能部分通信的网络。

现有 Meshtastic 网络也很重要 #

**不要仅仅因为 MeshCore 在固定基础设施方面有架构优势，就否定 Meshtastic。**如果一个城市已有几十或数百个 Meshtastic 节点，这些节点代表真实基础设施和真实社区。迁移成本不会出现在规格表对比中：

  • 已安装硬件需要重新刷写固件或更换
  • 现有用户已经会操作该网络
  • 社区经验已经围绕当前部署积累
  • 已部署的中继器和选址，包括来之不易的屋顶或塔台位置
  • 网络运营者积累的配置经验
  • 用户已经收听的既有信道
  • 学习第二套系统的培训成本

协议选择**既是工程问题，也是社区采纳问题。**纸面上更好的架构不一定胜出，尤其是它要求一个正常运行的社区从头开始时。

区域网络的问题 #

考虑一个假设的多城市部署：

城市 A、中继器、中继器、乡村中继、中继器、城市 B、中继器、城市 C

设想网络扩展时各种架构如何应对。跳数上限为 7 的泛洪网络很难可靠覆盖这样的链路，因为每一跳都会增加空中占用时间，路径上的每个活跃节点都会增加信道竞争。MeshCore 这样的结构化中继架构就是为这种形态设计的：中继点已知、位置经过规划，路由随活跃对话增长，而不是随节点总数增长。

在这种场景下，跳数上限、空中占用预算、路由行为和基础设施设计不再是理论问题，而会直接决定网络能否端到端工作。达到一定地理规模后，Meshtastic 和 MeshCore 的架构差异就不再只是学术话题。

射频条件仍比协议重要 #

**再聪明的路由软件也无法创造物理上不存在的射频路径。**在把覆盖问题归咎于协议之前，先检查基础条件：

  • 天线高出障碍物的安装高度
  • 链路两端之间的视距
  • 菲涅耳区净空，它不同于肉眼视距
  • 廉价或过长同轴电缆造成的馈线损耗
  • 天线质量及其与使用频段的匹配程度
  • 接收地点的噪声底
  • 节点之间的地形
  • 节点位置以及实际可行的改进空间
  • 链路余量，即接收信号与最低解码信号之间的差值

*在良好桅杆上正确放置的 2 dBi 天线，常常胜过放在地下室窗边、位置不佳的高增益天线。*协议决定网络如何使用现有链路，不能创造物理条件不支持的链路。

可靠性优先于最大距离 #

**不要根据链路偶尔达到的最远距离设计网络。**要按稳定工作的链路设计。

对社区或应急通信网络来说，**15 英里处稳定送达，比偶尔能传到 40 英里、其余时间经常失败的链路更有实际价值。**应依靠可靠基础设施建立重叠覆盖，而不是追逐距离纪录。这条原则适用于所有协议。

如何选择 #

**适合选 Meshtastic 的情况：**你看重成熟生态、易于采用、便携和移动用户支持，以及与现有 Meshtastic 社区兼容。对大多数从零开始的人来说，它是合适的默认选择。

**MeshCore 更有吸引力的情况：**你正计划建设持久的 LoRa 基础设施，并希望用专用中继器搭建更大、更有结构的网络。与泛洪设计相比，它能更直接地发挥规划和中继器选址的作用。

**适合选 Reticulum 的情况：**需求超出一个 LoRa 网状网络，需要把不同传输方式或独立网络接入同一个可寻址系统。

如果要建设免许可、低功耗、远距离、主要依靠固定中继器的社区基础设施网络，优先考虑 MeshCore。*如果当地已有健康运行的 Meshtastic 网络，替换它所带来的收益必须足以抵偿社区分裂的代价。*只有在单一网状协议或物理传输方式无法满足需求时才引入 Reticulum，而不是因为它能做更多事情。
