Microsoft SOCホームラボ：2026年にサイバーセキュリティ経験を積む

セキュリティオペレーションセンター（SOC）のホームラボでは、アラートを調査し、証拠を説明し、防御策の変更を試せます。小規模なMicrosoft環境を構築し、テレメトリを収集して各調査を記録します。目指す成果は、証拠で裏付けた再現可能な調査です。

このガイドは、Mad Hatのサイバーセキュリティ職業紹介動画と提供されたCyber Rangeランブックのラボ構成を発展させます。製品要件にはMicrosoftの資料を使い、構築、検知、検証を測定可能な作業に分けます。

要点 #

  • 小さく始める： 最初の演習には、管理対象Windowsクライアント1台とテスト用ID 1つで十分です。
  • テレメトリを確認する： デバイスやポータルが表示されても、ログ到着の証明にはなりません。
  • 調査を完了する： きっかけ、証拠、対応、再テストを記録します。
  • 費用を管理する： ライセンス、保持データ、ネットワーク、コンピューティングを分けて追跡します。
  • 経験を正確に説明する： 履歴書にはラボプロジェクトとして記載します。

始める前に #

前提知識： Windows管理とネットワークの基礎、仮想マシンの基本知識が必要です。専用のMicrosoft Entraテナントとラボ専用のAzureサブスクリプションを使います。本番ID、個人ファイル、勤務先のシステムを演習に含めないでください。

所要時間の目安： 初期構築に週末程度、その後は調査ごとに集中したセッションを計画します。これは計画上の目安です。試用申請、クォータ、サービス準備状況により実時間は変わります。難易度： 中級。

管理者アカウントと権限のないテストユーザーを分けます。アクセス制御を試す前に緊急アクセスを確立し、動作を確認します。構築作業には必要な権限を割り当て、日常の調査には低い権限のアカウントを使います。

コンポーネントラボでの役割
Sentinel接続したログソースを扱うセキュリティ情報イベント管理（SIEM）
Defender XDRライセンス対象のMicrosoftセキュリティサービス間の相関と調査
Defender for Endpoint登録済みデバイスのエンドポイント検知・対応（EDR）
Intuneデバイス登録とエンドポイントセキュリティポリシー管理
Entra IDID、サインイン記録、アクセス方針の評価
Defender for ServersDefender for Cloudによるサーバー保護

まずライセンスを確認 #

Microsoft 365 E5は幅広いラボを構成する選択肢の1つですが、利用可否は参加ユーザーに割り当てたサービスプランとライセンスによります。Office 365 E5とMicrosoft 365 E5は別の製品です。管理者1人のライセンスだけでは、すべてのテストユーザーやワークロードの対象範囲を確認できません。サブスクリプションを選ぶ前に Defender XDRの前提条件 を確認してください。

DefenderポータルのSentinelはE5やDefender XDRがなくても利用できます。XDRを追加すると、別途ライセンスと構成の要件が生じます。インシデント一覧が空でも、E5ライセンスがない証拠にはなりません。Microsoftの Sentinelオンボード資料 では両方の構成を説明しています。

サーバー保護には別のライセンス経路があります。Defender for Serversは対応するサーバーワークロードでDefender for Endpointと連携します。WindowsクライアントOSには適切なクライアントライセンスが必要です。Azure VMなら自動的にサーバーライセンスの対象になると考えないでください。 Defender for Endpoint連携の資料 を確認してください。

試用の計画： 自分のアカウントで利用資格、期限、更新設定、対象サービスを確認します。動画で紹介された試用期間や固定の月額費用を前提に予算を組まないでください。

支出計画を立てる #

Azureの予算は通知を送りますが、しきい値に達しても利用を停止しません。コスト報告にも遅延があります。早めにアラートを設定し、各セッション後に費用を確認します。 Microsoftの予算設定ガイド を参照してください。

費用項目計画時の質問
ユーザーライセンスどのユーザーにどのサービスプランが必要か。試用期間はいつ終わるか。
コンピューティング各演習に何時間のVM稼働が必要か。
ストレージ停止後も残るディスクやスナップショットはどれか。
ログ収集どのテーブルを取り込み、どのくらい保持するか。
ネットワーク有料Bastion、パブリックIP、外部向けサービスを含むか。
サーバー保護有料Defenderプランを有効にするワークロードはどれか。

設計の選択： クライアント1台から始めます。サーバーのテレメトリが必要な演習でサーバーを追加します。クライアント4台と複数サーバーは、調査の練習に役立つ前に管理負担と費用を増やします。

ネットワークを構築する #

推奨構成： Azureリソースを**rg-soc-lab**のような分かりやすいリソースグループにまとめます。クライアント用とサーバー用のサブネットを分け、ネットワークセキュリティグループの規則を明示し、管理アクセスにはプライベート経路を使います。サブネットを分けるだけではワークロード間通信を遮断できません。

専用のAzure Bastionを展開する場合はSKU要件に従います。現在の展開では、予約名**AzureBastionSubnetと/26**以上のサブネットが必要です。Developer SKUは展開方法が異なります。設計を選ぶ前に Bastionの構成設定 を確認してください。

RDPとSSHをインターネットに公開しないでください。選んだ管理経路に通信を制限します。登録とセキュリティテレメトリに必要な外向き接続は許可します。

検証： ワークロードを導入する前に、プライベート管理アクセスを確立し、有効なネットワーク規則を確認します。後で意図的に脆弱なアプリを追加する場合は、演習用ネットワーク内に置き、テストマシンからのアクセスに制限します。

Sentinelとログを接続する #

ポータルの設定： Log Analyticsワークスペースを作成し、Sentinelを有効にします。Defenderポータルにワークスペースがない場合は、System > Settings > Microsoft Sentinel > Connect a workspaceを開きます。 オンボードの前提条件 を参照し、テナントとAzure、Entraの必要なロールを確認してください。

ログ収集は別の手順です。 Entraで診断設定を構成し、必要なアクティビティカテゴリを同じワークスペースに送ります。対話型サインインと監査イベントから始めます。 Entraログ連携ガイド に権限と送信先の説明があります。

現在のSentinelの手順では、Microsoft Defenderポータルからも接続できます。テーブルが空の場合は、意図したプライマリワークスペースか、テストIDと同じテナントか、アカウントに必要なロールがあるかを確認します。ポータルに表示されるだけではデータ取り込みの証明になりません。 DefenderポータルでのSentinelオンボード

SigninLogs
| where TimeGenerated > ago(24h)
| where UserPrincipalName =~ "soc-test@YOUR-TENANT.onmicrosoft.com"
| project TimeGenerated, UserPrincipalName, AppDisplayName,
          IPAddress, ResultType, ConditionalAccessStatus, CorrelationId
| order by TimeGenerated desc

新しいテストサインインを発生させた後、ワークスペースのLogs画面で**Kusto Query Language（KQL）**の例を実行します。サンプルのユーザープリンシパル名をラボのユーザーに置き換えてください。列は SigninLogsテーブルのスキーマ に基づいています。

期待する結果： テストアカウントとサインイン時刻に一致する行です。行がない場合は、期間、ID、収集設定、送信先、取り込み遅延を確認します。テーブルがない場合は、検知の問題より先に収集またはワークスペースの問題を調べます。

最初のエンドポイントを登録する #

Intune登録とEDRオンボードは別々の確認項目です。IntuneとDefender for Endpointを接続し、対応するWindowsクライアントを登録し、ラボグループにEDRオンボードポリシーを割り当てます。Entraへの登録だけでは、どちらも完了したことになりません。

IntuneでEndpoint security > Defender for Endpointを確認します。接続できない場合は、Defenderのエンドポイント詳細機能でIntune連携を有効にします。 IntuneとDefenderの連携ガイド でプラットフォームごとの手順を確認してください。

確認項目収集する証拠
登録Intuneにクライアントが表示され、最近チェックインしている
ポリシー割り当て対象デバイスグループにオンボードポリシーが適用されている
センサーの報告Defenderにオンボード状態と最近のテレメトリが表示される
検知テスト文書化されたテストが想定したセキュリティ信号を生成する

**サーバーの場合は、**選んだDefender for Serversプランとエンドポイント連携を有効にし、センサーの展開と報告を確認します。Defender for Cloudのインベントリにはオンボード完了前でもマシンが表示されます。インベントリにあるだけでは不十分です。 リソースの検出とオンボードのガイダンス を参照してください。

テストアラートを調査する #

ラボのエンドポイントでMicrosoftが文書化したEDR検知テストから始めます。 最新のテスト手順 に従い、プラットフォーム要件とトラブルシューティングを確認します。アラートキューを開く前に実行時刻を記録します。

生成されたアラートを調査演習として扱います。製品のタイトルは出発点です。何が起きたかを確認し、証拠に基づいて判断してください。

  1. トリアージ： アラートの発生元、デバイス、アカウント、イベント時刻を特定します。
  2. 確認： プロセスツリー、コマンドライン、ファイル情報、取得可能なネットワーク活動を調べます。
  3. 範囲の確認： テストIDや他のラボデバイスに関連する活動を探します。
  4. 評価： 証拠が計画した演習に一致するか、無関係なイベントかを説明します。
  5. 対応： 選んだ対応、その影響、復旧手順を記録します。演習で必要な場合に限り、サポートされた隔離を実施します。
  6. 再テスト： 制御を変更した後、関連テストを繰り返し、証拠を比較します。

存在しない結果を作らないでください。 アラートが届かない場合は実行記録を残して収集を調査します。想定イベントの前に制御がテストを阻止した場合は、その防止結果を記録します。

ID制御をテストする #

**中間者型フィッシング（AiTM）**では、攻撃者が制御する中継者がサインインの流れに入ります。提供されたランブックでは、このシナリオを強い認証の理由として使っています。最初のID演習では、権限のない自分のアカウントでポリシーの動作を直接テストします。

正規のサインインと認証の詳細を記録します。リスク信号を解釈する前に、Microsoftの Entraリスク検知リファレンス を確認します。検知の前提条件と処理は信号ごとに異なります。新しいIPアドレスやサインイン失敗だけでAiTMアラートが出るとは限りません。

**パスキー（FIDO2）**は、正規サービスに結び付いた資格情報を使い、中継ログインページに入力する再利用可能なコードを避けます。パイロットグループに適切なパスキープロファイルを有効にし、ポリシー適用前に認証方法を登録します。対応する認証器と制約は パスキー設定ガイド で確認します。

Conditional Access演習： ラボのパイロットグループだけを対象にするポリシーを作成し、緊急アクセスアカウントを除外して、Require authentication strength > Phishing-resistant MFA strengthを選択します。まずReport-onlyで影響を確認し、その後有効にします。これはMicrosoftの 管理者ポリシー例 を小規模なテストグループ向けに適用したものです。

テスト収集する証拠
Report-onlyポリシー提案されたポリシーの評価を示すサインイン記録
強制ポリシー、弱い方式新しい認証でアクセス前により強い方式が求められる
強制ポリシー、登録済みパスキー必要な強度を満たしたサインイン成功

比較ごとに新しい認証を使い、ポリシーの詳細を確認します。既存セッションがあると比較が複雑になります。証明できる範囲： この演習で検証するのは認証要件です。エンドポイント侵害や既存セッション窃取を含むあらゆる攻撃への保護を証明するものではありません。

ポートフォリオの証拠を書く #

有用なポートフォリオ項目では、別の分析者が確認できる形で判断を説明します。簡潔な構成説明、収集の前提条件、イベント時系列、対応の理由を含めます。

演習：
日付とUTC時間帯：
ラボの範囲と前提条件：
トリガーと期待する信号：
観測したアラートまたは防止結果：
証拠とクエリ：
影響を受けたIDとデバイス：
判断と理由：
対応と復旧：
制御の変更と再テスト：
制約とフォローアップ：

各欄を自分の観察結果で埋めます。スクリーンショットやクエリ結果を公開する前に、エクスポートをサニタイズ： 資格情報、セッション情報、個人情報、不要な識別子を削除します。

履歴書の例：「Microsoftセキュリティラボを構築し、IDログをSentinelに接続し、エンドポイントのテストアラートを調査し、Conditional Accessを検証した。」これらを完了した場合に限って使います。実際の日付と範囲を添えて、プロジェクトまたは実習経験に記載します。

ラボは自主的な練習を示します。本番SOC業務には、事業への影響、エスカレーション、サービス基準、他チームとの調整もあります。練習した内容と経験していない内容を説明します。

トラブルシューティング #

症状最初の確認項目
Defenderにワークスペースがない同じテナントか、Sentinelが有効か、必要なオンボードロールがあるか
SigninLogsがない、または空診断カテゴリ、送信先ワークスペース、新しいイベント、期間
Intuneにクライアントがない登録の前提条件と登録状態
デバイスは見えるがテレメトリがない実際のオンボード状態、センサーの状態、外向き接続
オンボードポリシーが未適用割り当て範囲、デバイスのプラットフォーム、最近のチェックイン
IDリスクアラートがない信号の前提条件と記録済み活動。検知が確実だと思い込まない
予期しないアクセス許可Report-only状態、除外、リソース範囲、既存セッション
停止後も料金が発生割り当て状態とコンピューティング以外で課金されるリソース

トラブルシューティングの順番： イベントが発生した証拠を確認し、収集の動作を確かめてから検知ロジックを調べます。各失敗と修正をプロジェクトノートに記録します。

ラボを停止または削除する #

割り当て解除はVMのコンピューティング割り当てを解放します。ゲストOSをシャットダウンしただけでは解除は保証されません。Azureに表示される電源状態を確認し、Microsoftの VM状態と課金の資料 を参照します。

保持中のリソースも確認が必要です。ディスク、スナップショット、ネットワークサービス、ログ保持、ユーザーサブスクリプションには別々のライフサイクルがあります。試用期限の前に通知を設定し、削除後の使用状況レポートも確認します。

ラボのリソースグループを削除する前に、保持したい証拠をエクスポートして内容を確認します。リソースグループの削除は破壊的な操作で、含まれるリソースが削除されます。テナントユーザー、Intuneポリシー、Conditional Accessポリシー、サブスクリプション、サブスクリプションレベルのセキュリティ設定は別途クリーンアップが必要な場合があります。

次のステップ #

別のワークロードを追加する前に、記録を残した調査を1つ完了します。その後、明確なテスト条件を持つサーバー、ID演習、検知ルールを追加します。追加要素から学べることと費用を記録します。

インフラ演習には ITホームラボガイド を、学んだ作業の紹介には IT履歴書ガイド を使います。構築、証拠、クリーンアップまで説明できる規模に次のプロジェクトを保ちます。
