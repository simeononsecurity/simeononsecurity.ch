ਮੁੱਖ ਗੱਲਾਂ #

  • ਪਹਿਲਾਂ ਬੈਕਿੰਗ ਸਟੋਰੇਜ ਚੁਣੋ। ਵਰਚੁਅਲ ਡਿਸਕ ਦਾ ਦੱਸਿਆ ਆਕਾਰ ਹੋਸਟ ਉੱਤੇ ਦਿੱਤੀ ਥਾਂ ਤੋਂ ਸਿਰਫ਼ ਉਦੋਂ ਵੱਖਰਾ ਹੁੰਦਾ ਹੈ ਜਦੋਂ ਇਮੇਜ ਫਾਰਮੈਟ ਜਾਂ ਬੈਕਐਂਡ ਪਤਲੀ ਵੰਡ ਸਹਾਇਕ ਹੋਵੇ।
  • VM ਲਈ discard ਚਾਲੂ ਕਰੋ, ਫਿਰ ਗੈਸਟ ਵਿੱਚ trim ਚਲਾਓ। Windows ReTrim ਅਤੇ Linux fstrim ਵਰਚੁਅਲ ਡਿਸਕ ਰਾਹੀਂ ਨਾ ਵਰਤੇ ਬਲਾਕਾਂ ਲਈ ਬੇਨਤੀਆਂ ਭੇਜਦੇ ਹਨ।
  • ਸਨੈਪਸ਼ਾਟਾਂ ਅਤੇ ਬੈਕਅੱਪਾਂ ਦੀ ਵੱਖ-ਵੱਖ ਜਾਂਚ ਕਰੋ। ਪੁਰਾਣੇ ਬਲਾਕ ਉਦੋਂ ਤੱਕ ਦਿੱਤੇ ਰਹਿੰਦੇ ਹਨ ਜਦੋਂ ਤੱਕ ਕੋਈ ਸਨੈਪਸ਼ਾਟ ਉਹਨਾਂ ਦਾ ਹਵਾਲਾ ਦਿੰਦਾ ਹੈ। ਬੈਕਅੱਪ ਫ਼ਾਈਲਾਂ ਅਤੇ PBS ਡਾਟਾ ਖੰਡ ਦੀ ਆਪਣੀ retention ਨੀਤੀ ਹੁੰਦੀ ਹੈ।
  • LXC ਮਾਊਂਟ ਨੂੰ ਕਿਸਮ ਅਨੁਸਾਰ ਦੇਖੋ। ਪ੍ਰਬੰਧਿਤ rootfs ਅਤੇ ਮਾਊਂਟ-point ਵਾਲਿਊਮ, bind ਮਾਊਂਟ ਅਤੇ device ਮਾਊਂਟ ਦੀ ਮਾਲਕੀ ਅਤੇ ਬੈਕਅੱਪ ਵਿਹਾਰ ਵੱਖਰਾ ਹੁੰਦਾ ਹੈ।

ਸ਼ੁਰੂ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ #

ਤੁਹਾਨੂੰ Proxmox VE 9 ਦਾ ਪ੍ਰਸ਼ਾਸਕ ਪਹੁੰਚ, ਪ੍ਰਭਾਵਿਤ ਹਰ ਗੈਸਟ ਦਾ ਜਾਂਚਿਆ ਬੈਕਅੱਪ ਅਤੇ ਕਾਰਵਾਈ ਲਈ ਪੂਲ ਵਿੱਚ ਕਾਫ਼ੀ ਖਾਲੀ ਥਾਂ ਚਾਹੀਦੀ ਹੈ। ਸੈਟਿੰਗਾਂ ਬਦਲਣ ਤੋਂ ਪਹਿਲਾਂ ਗੈਸਟ ID, ਡਿਸਕ ਬੱਸ, ਵਾਲਿਊਮ ID, ਸਟੋਰੇਜ ID, ਸਨੈਪਸ਼ਾਟ ਅਤੇ ਮੌਜੂਦਾ ਵਰਤੋਂ ਲਿਖੋ। ਰਿਕਵਰੀ ਦੀ ਜਾਂਚ ਲਈ VM ਮੁੜ-ਬਹਾਲੀ ਅਭਿਆਸ ਵਰਤੋ।

ਅੰਦਾਜ਼ੀ ਸਮਾਂ: ਹਰ ਗੈਸਟ ਲਈ 20 ਤੋਂ 60 ਮਿੰਟ, ਨਾਲ ਵੱਡੇ trim ਜਾਂ ਸਫ਼ਾਈ ਕੰਮ ਦਾ ਵਾਧੂ ਸਮਾਂ। ਮੁਸ਼ਕਲ: ਦਰਮਿਆਨੀ। ਘੱਟ ਜੋਖਮ ਵਾਲੀ ਇੱਕ VM ਨਾਲ ਸ਼ੁਰੂ ਕਰੋ ਅਤੇ ਪਹਿਲਾਂ ਤੇ ਬਾਅਦ ਦੀ ਸਟੋਰੇਜ ਵਰਤੋਂ ਦੀ ਤੁਲਨਾ ਕਰੋ।

ਚੇਤਾਵਨੀ: ਭਰਿਆ ਪਤਲਾ ਪੂਲ ਗੈਸਟਾਂ ਵਿੱਚ I/O ਗਲਤੀਆਂ ਪੈਦਾ ਕਰਦਾ ਹੈ ਅਤੇ ਫ਼ਾਈਲ ਸਿਸਟਮ ਨੂੰ ਨੁਕਸਾਨ ਪਹੁੰਚਾ ਸਕਦਾ ਹੈ। ਪੂਲ ਦੀ ਖਾਲੀ ਡਾਟਾ ਅਤੇ ਮੈਟਾਡੇਟਾ ਥਾਂ ਦੀ ਨਿਗਰਾਨੀ ਤੋਂ ਬਿਨਾਂ ਸਮਰੱਥਾ ਤੋਂ ਵੱਧ ਥਾਂ ਨਾ ਦਿਓ। Proxmox ਸਟੋਰੇਜ ਦਸਤਾਵੇਜ਼

ਅਲਾਟਮੈਂਟ ਲੜੀ ਦੀ ਜਾਂਚ ਕਰੋ #

ਮਿਟਾਉਣਾ, discard ਅਤੇ ਥਾਂ ਵਾਪਸ ਲੈਣਾ ਵੱਖਰੀਆਂ ਪਰਤਾਂ ਉੱਤੇ ਹੁੰਦਾ ਹੈ। ਗੈਸਟ ਫ਼ਾਈਲ ਮਿਟਾ ਕੇ ਫ਼ਾਈਲ ਸਿਸਟਮ ਬਲਾਕਾਂ ਨੂੰ ਖਾਲੀ ਨਿਸ਼ਾਨ ਲਗਾਉਂਦਾ ਹੈ। ਫ਼ਾਈਲ ਸਿਸਟਮ ਉਹਨਾਂ ਬਲਾਕਾਂ ਲਈ TRIM ਜਾਂ UNMAP ਭੇਜਦਾ ਹੈ। ਵਰਚੁਅਲ ਡਿਸਕ ਉੱਤੇ discard ਚਾਲੂ ਹੋਵੇ ਤਾਂ QEMU ਬੇਨਤੀ ਅੱਗੇ ਭੇਜਦਾ ਹੈ। ਫਾਰਮੈਟ ਅਤੇ ਪੂਲ ਸਹਾਇਕ ਹੋਣ ਉੱਤੇ ਬੈਕਐਂਡ ਭੌਤਿਕ ਅਲਾਟਮੈਂਟ ਛੱਡਦਾ ਹੈ। Proxmox VM ਡਿਸਕ ਦਸਤਾਵੇਜ਼

ਪਰਤਕੀ ਜਾਂਚਣਾ ਹੈਲਾਭਦਾਇਕ ਸਬੂਤ
ਗੈਸਟ ਫ਼ਾਈਲਾਂਫ਼ਾਈਲ ਸਿਸਟਮ ਦੀ ਖਾਲੀ ਥਾਂWindows ਵਾਲਿਊਮ ਵਿਸ਼ੇਸ਼ਤਾਵਾਂ ਜਾਂ Linux df -h
ਵਰਚੁਅਲ ਡਿਸਕਬੱਸ, discard, SSD ਦੀ ਨਕਲ, ਇਮੇਜ ਫਾਰਮੈਟVM ਦਾ Hardware ਟੈਬ ਜਾਂ qm config VMID
PVE ਵਾਲਿਊਮਮਾਲਕ ਅਤੇ ਕੌਂਫਿਗਰ ਆਕਾਰਸਟੋਰੇਜ ਦਾ Content ਟੈਬ ਜਾਂ pvesm list STORAGE_ID
ਸਟੋਰੇਜ ਪੂਲਖਾਲੀ ਡਾਟਾ, ਮੈਟਾਡੇਟਾ ਅਤੇ ਰੋਕੇ ਬਲਾਕpvesm status ਅਤੇ ਬੈਕਐਂਡ ਦੇ ਖ਼ਾਸ ਟੂਲ

100 GiB ਦੀ ਵਰਚੁਅਲ ਡਿਸਕ ਸਮਰੱਥਾ ਹੱਦ ਹੈ, 100 GiB ਅਲਾਟ ਹੋਣ ਦੀ ਗਾਰੰਟੀ ਨਹੀਂ। ਇਸੇ ਤਰ੍ਹਾਂ ਗੈਸਟ ਵੱਲੋਂ 20 GiB ਵਰਤੋਂ ਦਿਖਾਉਣਾ ਇਹ ਸਾਬਤ ਨਹੀਂ ਕਰਦਾ ਕਿ ਹੋਸਟ ਵੀ 20 GiB ਵਰਤਦਾ ਹੈ। ਮੈਟਾਡੇਟਾ, ਸਨੈਪਸ਼ਾਟ, ਬੈਕਅੱਪ ਕਾਪੀਆਂ ਅਤੇ ਪਹਿਲਾਂ ਲਿਖੇ ਬਲਾਕ ਅੰਕੜਾ ਬਦਲਦੇ ਹਨ। Proxmox ਸਟੋਰੇਜ ਦਸਤਾਵੇਜ਼

ਡਿਸਕ ਫਾਰਮੈਟਾਂ ਦੀ ਤੁਲਨਾ ਕਰੋ #

ਸਟੋਰੇਜ ਬੈਕਐਂਡ ਨਿਰਧਾਰਤ ਕਰਦਾ ਹੈ ਕਿ Proxmox ਕਿਹੜੇ ਇਮੇਜ ਫਾਰਮੈਟ ਦਿੰਦਾ ਹੈ। ZFS zvol ਅਤੇ Ceph RBD ਵਰਚੁਅਲ raw ਡਿਸਕਾਂ ਵਰਤਦੇ ਹਨ। LVM ਆਮ ਤੌਰ ਉੱਤੇ raw ਵਰਤਦਾ ਹੈ, ਹੇਠਾਂ ਦੱਸੀ Proxmox VE 9 ਵਾਲਿਊਮ-chain ਛੋਟ ਤੋਂ ਇਲਾਵਾ। directory ਅਤੇ NFS ਵਰਗੇ ਫ਼ਾਈਲ ਬੈਕਐਂਡ raw ਜਾਂ qcow2 ਸਹਾਇਕ ਕਰਦੇ ਹਨ। Raw ਇਕੱਲਾ ਪਤਲਾ ਅਲਾਟਮੈਂਟ ਜਾਂ ਸਨੈਪਸ਼ਾਟ ਨਹੀਂ ਦਿੰਦਾ। ਇਹ ਗੁਣ ਹੇਠਲੀ ਸਟੋਰੇਜ ਨੂੰ ਦੇਣੇ ਪੈਂਦੇ ਹਨ। Qcow2 ਇਮੇਜ ਪਰਤ ਉੱਤੇ copy-on-write ਅਲਾਟਮੈਂਟ ਅਤੇ ਸਨੈਪਸ਼ਾਟ ਦਿੰਦਾ ਹੈ। Proxmox VM ਡਿਸਕ ਦਸਤਾਵੇਜ਼

ਫਾਰਮੈਟਅਲਾਟਮੈਂਟ ਤਰੀਕਾਥਾਂ ਦਾ ਸਮਝੌਤਾ
ਫ਼ਾਈਲ ਸਟੋਰੇਜ ਉੱਤੇ qcow2ਲਿਖਣ ਵੇਲੇ qcow2 clusters ਅਲਾਟ ਕਰਦਾ ਹੈਇਮੇਜ ਮੈਟਾਡੇਟਾ ਅਤੇ ਸਨੈਪਸ਼ਾਟ ਲੜੀਆਂ ਥਾਂ ਲੈਂਦੀਆਂ ਹਨ
ਫ਼ਾਈਲ ਸਟੋਰੇਜ ਉੱਤੇ raw ਫ਼ਾਈਲਸਹਾਇਕ ਹੋਵੇ ਤਾਂ ਫ਼ਾਈਲ ਸਿਸਟਮ ਦਾ sparse-ਫ਼ਾਈਲ ਵਿਹਾਰRaw ਇਕੱਲਾ ਪਤਲੀ ਵੰਡ ਜਾਂ ਸਨੈਪਸ਼ਾਟ ਨਹੀਂ ਦਿੰਦਾ
Raw ਬਲਾਕ ਵਾਲਿਊਮਪਤਲੀ ਵੰਡ ਵਾਲਾ LVM, ZFS, Ceph RBD ਜਾਂ ਹੋਰ ਬੈਕਿੰਗ ਸਟੋਰੇਜਪੂਲ ਅਲਾਟਮੈਂਟ ਅਤੇ ਸਨੈਪਸ਼ਾਟ ਬੈਕਐਂਡ ਉੱਤੇ ਨਿਰਭਰ ਹਨ

Proxmox VE 9 ਮੋਟਾ LVM ਵਿੱਚ ਸਨੈਪਸ਼ਾਟ ਦਾ ਖ਼ਾਸ ਮੋਡ ਹੈ। snapshot-as-volume-chain ਮੋਟਾ LVM ਤਰਕਸੰਗਤ ਵਾਲਿਊਮ ਵਿਚਕਾਰ qcow2 ਦਾ ਆਧਾਰ ਸੰਬੰਧ ਵਰਤਦਾ ਹੈ। ਇਹ qcow2 ਦੇ ਅੰਦਰੂਨੀ ਸਨੈਪਸ਼ਾਟ ਨਹੀਂ ਵਰਤਦਾ। ਇਹ ਚੋਣ ਸਿਰਫ਼ ਨਵੀਆਂ VM ਡਿਸਕਾਂ ਉੱਤੇ ਅਸਰ ਕਰਦੀ ਹੈ ਅਤੇ ਮੌਜੂਦਾ Proxmox ਦਸਤਾਵੇਜ਼ ਵਿੱਚ ਤਕਨੀਕੀ preview ਹੈ। PVE ਹਰ ਸਨੈਪਸ਼ਾਟ ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਅਲਾਟ ਦਿਖਾਉਂਦਾ ਹੈ। SAN ਦੀ ਅਸਲ ਅਲਾਟਮੈਂਟ ਸਿਰਫ਼ ਉਦੋਂ ਘੱਟ ਹੁੰਦੀ ਹੈ ਜਦੋਂ ਬੈਕਿੰਗ ਸਟੋਰੇਜ ਪਤਲੀ ਵੰਡ ਅਤੇ discard ਸਹਾਇਕ ਕਰੇ। Proxmox LVM ਸਟੋਰੇਜ ਦਸਤਾਵੇਜ਼

Drive ਦੀਆਂ ਹੋਰ ਚੋਣਾਂ ਵਿਹਾਰ ਦੱਸਦੀਆਂ ਹਨ, ਥਾਂ ਵਾਪਸੀ ਨਹੀਂ। format ਕਈ ਇਮੇਜ ਫਾਰਮੈਟਾਂ ਵਾਲੇ backend ਉੱਤੇ ਡਿਸਕ ਅਲਾਟ ਕਰਦੇ ਸਮੇਂ ਲਾਗੂ ਹੁੰਦਾ ਹੈ। size ਵਰਚੁਅਲ ਸਮਰੱਥਾ ਹੈ, ਅਲਾਟ bytes ਨਹੀਂ। ro=1 ਡਿਸਕ ਨੂੰ ਸਿਰਫ਼ ਪੜ੍ਹਨਯੋਗ ਕਰਦਾ ਹੈ। snapshot=1 QEMU ਦਾ ਆਰਜ਼ੀ ਸਨੈਪਸ਼ਾਟ ਮੋਡ ਚਾਲੂ ਕਰਦਾ ਹੈ, ਜੋ VM ਬੰਦ ਹੋਣ ਤੇ ਡਿਸਕ ਬਦਲਾਅ ਛੱਡ ਦਿੰਦਾ ਹੈ। ਇਹ Proxmox VM ਸਨੈਪਸ਼ਾਟ ਵਿੱਚ ਡਿਸਕ ਸ਼ਾਮਲ ਕਰਨ ਵਾਲੀ ਚੋਣ ਨਹੀਂ। ਸਥਾਈ ਡਾਟੇ ਲਈ ਇਸ ਤੋਂ ਬਚੋ। backup=0 ਜਾਂ replicate=0 ਵਰਤਣ ਤੋਂ ਪਹਿਲਾਂ ਮੁੜ-ਬਹਾਲੀ ਕਵਰੇਜ ਜਾਂਚੋ। Proxmox VM ਡਿਸਕ ਚੋਣਾਂ

ਮੌਜੂਦਾ drive ਉੱਤੇ ਛੋਟੀ qm set --scsi0 ਲਾਈਨ ਨਾ ਚਿਪਕਾਓ। qm config VMID ਵੇਖੋ ਅਤੇ ਸੋਧਦੇ ਸਮੇਂ ਪੂਰਾ ਵਾਲਿਊਮ ID ਅਤੇ ਮੌਜੂਦਾ ਚੋਣਾਂ ਰੱਖੋ। ਛੋਟੀ ਡਰਾਈਵ ਵੰਡ ਦੂਜੀਆਂ ਡਿਸਕ ਸੈਟਿੰਗਾਂ ਹਟਾ ਸਕਦੀ ਹੈ। ਹਰ ਬਦਲਾਅ ਪਿੱਛੋਂ ਇੰਟਰਫੇਸ ਵਿੱਚ ਸੇਵ ਕੀਤੀਆਂ ਚੋਣਾਂ ਜਾਂਚੋ।

qm config 100
pvesm status

100 ਉਦਾਹਰਨ VM ID ਹੈ। ਮੌਜੂਦਾ VM ਉੱਤੇ ਨਵੀਂ 64 GiB SCSI ਡਿਸਕ ਲਈ, ਜਿਸਦਾ controller VirtIO SCSI ਸਿੰਗਲ ਹੈ ਅਤੇ ਗੈਸਟ ਕੋਲ ਲੋੜੀਂਦਾ ਡਰਾਈਵਰ ਹੈ, ਇਹ ਕਮਾਂਡ ਅਲਾਟਮੈਂਟ syntax ਦਿਖਾਉਂਦੀ ਹੈ। VM ID ਅਤੇ ਸਟੋਰੇਜ ID ਆਪਣੇ ਮੁੱਲਾਂ ਨਾਲ ਬਦਲੋ।

qm set 100 --scsi0 local-lvm:64,discard=on,ssd=1,iothread=1

ਉਦਾਹਰਨ ਵਰਤਣ ਤੋਂ ਪਹਿਲਾਂ ਜਾਂਚੋ ਕਿ scsi0 ਪਹਿਲਾਂ ਹੀ ਮੌਜੂਦ ਤਾਂ ਨਹੀਂ। ਇਹ ਕਮਾਂਡ ਉਸ slot ਨੂੰ ਬਦਲਦੀ ਹੈ। ਮੌਜੂਦਾ ਡਿਸਕ ਲਈ ਜੇ ਸਹੀ ਵਿਕਲਪ ਲੜੀ ਬਚਾਉਣਾ ਸੌਖਾ ਹੋਵੇ ਤਾਂ ਇੰਟਰਫੇਸ ਵਰਤੋ। Proxmox qm ਕਮਾਂਡ ਹਵਾਲਾ ਵੇਖੋ।

ਗੈਸਟ ਸਿਸਟਮ ਦੀਆਂ ਫ਼ਾਈਲਾਂ ਸਾਫ਼ ਕਰੋ #

ਪਹਿਲਾਂ ਗੈਸਟ ਫ਼ਾਈਲਾਂ ਖਾਲੀ ਕਰੋ। Windows ਸਟੋਰੇਜ ਸੈਟਿੰਗਾਂ, ਅਸਥਾਈ ਫ਼ਾਈਲਾਂ, ਪੁਰਾਣੇ installers, ਐਪਲੀਕੇਸ਼ਨ ਕੈਸ਼ ਅਤੇ ਰੱਦੀਦਾਨ ਜਾਂਚੋ। Database ਅਤੇ container runtime ਨੂੰ ਉਹਨਾਂ ਦੇ ਆਪਣੇ ਇੰਟਰਫੇਸ ਰਾਹੀਂ ਸਾਫ਼ ਕਰੋ। ਸਿਰਫ਼ ਅਲਾਟਮੈਂਟ ਘਟਾਉਣ ਲਈ ਸਰਗਰਮ ਐਪਲੀਕੇਸ਼ਨ ਦਾ ਡਾਟਾ ਮਿਟਾਉਣ ਨਾਲ ਡਾਟਾ ਗੁਆਚ ਸਕਦਾ ਹੈ।

ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਵਾਲਿਊਮ discard-ਸਹਾਇਕ ਵਰਚੁਅਲ ਡਿਸਕ ਵਰਤਦਾ ਹੈ, ਫਿਰ Windows VM ਵਿੱਚ ਉੱਚੇ ਅਧਿਕਾਰਾਂ ਵਾਲਾ PowerShell ਸੈਸ਼ਨ ਖੋਲ੍ਹੋ:

fsutil behavior query DisableDeleteNotify
Optimize-Volume -DriveLetter C -ReTrim -Verbose

DisableDeleteNotify = 0 ਦੱਸਦਾ ਹੈ ਕਿ Windows ਨੇ ਰਿਪੋਰਟ ਕੀਤੇ ਫ਼ਾਈਲ ਸਿਸਟਮ ਲਈ ਮਿਟਾਉਣ ਦੀਆਂ ਸੂਚਨਾਵਾਂ ਚਾਲੂ ਕੀਤੀਆਂ ਹਨ। ReTrim ਮੌਜੂਦਾ ਖਾਲੀ ਵਾਲਿਊਮ ਖੇਤਰਾਂ ਲਈ trim ਬੇਨਤੀਆਂ ਮੁੜ ਭੇਜਦਾ ਹੈ। ਕਮਾਂਡ ਸਫਲ ਹੋਣਾ ਇਹ ਪੁਸ਼ਟੀ ਕਰਦਾ ਹੈ ਕਿ ਗੈਸਟ ਨੇ ਕਾਰਵਾਈ ਭੇਜੀ, ਨਾ ਕਿ ਹੋਸਟ ਨੂੰ ਕਿੰਨੇ bytes ਵਾਪਸ ਮਿਲੇ। ਕੰਮ ਮੁੱਕਣ ਪਿੱਛੋਂ ਹੋਸਟ ਜਾਂਚੋ। Microsoft Optimize-Volume ਹਵਾਲਾ ਅਤੇ Proxmox VM ਡਿਸਕ ਦਸਤਾਵੇਜ਼

QEMU ਗੈਸਟ ਏਜੰਟ ਨੂੰ TRIM ਨਾ ਸਮਝੋ। Agent ਗੈਸਟ ਕੰਟਰੋਲ ਅਤੇ ਬੈਕਅੱਪ consistency ਗੁਣ ਦਿੰਦਾ ਹੈ। ਫ਼ਾਈਲ ਸਿਸਟਮ ਦੀਆਂ ਮਿਟਾਉਣ ਦੀਆਂ ਸੂਚਨਾਵਾਂ ਵਰਚੁਅਲ ਡਿਸਕ ਰਾਹੀਂ ਜਾਂਦੀਆਂ ਹਨ। ਸਿਰਫ਼ agent ਇੰਸਟਾਲ ਕਰਨ ਨਾਲ ਬਲਾਕ ਵਾਪਸ ਨਹੀਂ ਮਿਲਦੇ। Proxmox VM ਗੈਸਟ ਏਜੰਟ ਦਸਤਾਵੇਜ਼

ਫ਼ਾਈਲ ਸਿਸਟਮ ਦੇ ਖਾਲੀ ਬਲਾਕ ਦਰਜ ਕਰੋ #

Trim ਤੋਂ ਪਹਿਲਾਂ ਬਲਾਕ ਰਾਹ ਅਤੇ ਫ਼ਾਈਲ ਸਿਸਟਮ ਜਾਂਚੋ। ਆਧੁਨਿਕ distribution ਅਕਸਰ fstrim.timer ਨੂੰ ਨਿਯਮਿਤ ਚਲਾਉਂਦੀ ਹੈ। ਇਸਦਾ status ਵੇਖੋ, ਫਿਰ ਬੇਲੋੜਾ ਗੈਸਟ ਡਾਟਾ ਮਿਟਾਉਣ ਤੋਂ ਬਾਅਦ mounted ਫ਼ਾਈਲ ਸਿਸਟਮਾਂ ਉੱਤੇ trim ਚਲਾਓ।

lsblk -D
systemctl status fstrim.timer
sudo fstrim -av

lsblk -D ਦਿਸਦੇ ਬਲਾਕ devices ਲਈ discard ਬਾਰੀਕੀ ਅਤੇ limits ਦੱਸਦਾ ਹੈ। fstrim -av ਸਹਾਇਕ mounted ਫ਼ਾਈਲ ਸਿਸਟਮਾਂ ਨੂੰ trim ਕਰਦਾ ਅਤੇ ਭੇਜੇ ranges ਦੱਸਦਾ ਹੈ। ਭੇਜੇ bytes ਪੂਲ ਨੂੰ ਵਾਪਸ ਆਏ bytes ਦੇ ਬਰਾਬਰ ਨਹੀਂ। Encrypted, LVM, RAID ਅਤੇ ਹੋਰ ਪਰਤਦਾਰ ਡਿਵਾਈਸ ਦੀ ਹਰ ਪਰਤ ਨੂੰ discard ਸਹਾਇਤਾ ਚਾਹੀਦੀ ਹੈ। Red Hat ਨਾ ਵਰਤੇ ਬਲਾਕਾਂ ਬਾਰੇ ਰਹਿਨੁਮਾਈ

ਤੈਅਸ਼ੁਦਾ trim ਜਾਂ ਸੋਚੀ-ਸਮਝੀ ਚਾਲੂ discard ਨੀਤੀ ਵਰਤੋ। ਸਟੋਰੇਜ ਰਸਤਾ ਜਾਂਚਣ ਦੀ ਥਾਂ ਹਰ ਫ਼ਾਈਲ ਸਿਸਟਮ ਉੱਤੇ ਲਗਾਤਾਰ discard ਚਾਲੂ ਨਾ ਕਰੋ। ਗੈਸਟ ਵਿੱਚ trim ਪਿੱਛੋਂ PVE ਵਾਲਿਊਮ ਅਤੇ ਪੂਲ ਵੇਖੋ। ਜੇ ਮਿਟਾਏ records ਹਾਲੇ ਫ਼ਾਈਲਾਂ ਵਿੱਚ ਥਾਂ ਲੈਂਦੇ ਹਨ, ਤਾਂ database ਜਾਂ service ਦੀ ਆਪਣੀ compact ਕਰਨ ਦੀ ਨੀਤੀ ਜਾਂਚੋ।

ਕੰਟੇਨਰ ਸਟੋਰੇਜ ਦੇ ਨਿਯਮ ਵੱਖਰੇ ਜਾਂਚੋ #

LXC ਦੇ root ਫ਼ਾਈਲ ਸਿਸਟਮ ਲਈ VM ਵਾਲੀ emulated ਡਿਸਕ ਬੱਸ ਨਹੀਂ ਹੁੰਦੀ। pct config CTID ਨਾਲ ਸ਼ੁਰੂ ਕਰੋ ਅਤੇ ਹਰ rootfs ਤੇ mpN entry ਪਛਾਣੋ। Proxmox ਸਟੋਰੇਜ-backed ਮਾਊਂਟ, bind ਮਾਊਂਟ ਅਤੇ device ਮਾਊਂਟ ਵੱਖ ਕਰਦਾ ਹੈ। ਕੰਟੇਨਰ ਵਿੱਚ ਦਿਸਦਾ ਰਾਹ ਇਹ ਨਹੀਂ ਦੱਸਦਾ ਕਿ ਬਲਾਕਾਂ ਦਾ ਮਾਲਕ ਕਿਹੜਾ ਹੋਸਟ ਵਾਲਿਊਮ ਹੈ। Proxmox ਕੰਟੇਨਰ ਮਾਊਂਟ ਪੁਆਇੰਟ

pct config 101
pct exec 101 -- df -h
pvesm status

ਪ੍ਰਬੰਧਿਤ rootfs ਜਾਂ ਮਾਊਂਟ ਬਿੰਦੂ ਲਈ ਕੰਟੇਨਰ ਜਾਂ ਉਸਦੀ application ਵਿੱਚੋਂ ਫ਼ਾਈਲਾਂ ਮਿਟਾਓ, ਫਿਰ ਹੋਸਟ ਉੱਤੇ ਬੈਕਿੰਗ ਵਾਲਿਊਮ ਅਤੇ ਸਨੈਪਸ਼ਾਟ ਜਾਂਚੋ। CT ਉੱਤੇ VM ਦੇ qm discard ਕਮਾਂਡ ਨਾ ਚਲਾਓ। ZFS ਉਪ-ਵਾਲਿਊਮ ਉੱਤੇ ਸਨੈਪਸ਼ਾਟ ਮਿਟਾਏ ਬਲਾਕ ਰੋਕਦੇ ਹਨ। directory ਅਤੇ ਪਤਲੀ ਵੰਡ ਵਾਲਾ LVM ਉੱਤੇ ਸੰਰਚਿਤ CT ਆਕਾਰ ਦੀ ਥਾਂ ਅਸਲ ਬੈਕਐਂਡ ਅਲਾਟਮੈਂਟ ਵੇਖੋ।

ਜੇ ਬੈਕਿੰਗ ਸਟੋਰੇਜ discard ਸਹਾਇਕ ਕਰਦੀ ਹੈ, ਤਾਂ CT ਦੀ ਸਫ਼ਾਈ ਪਿੱਛੋਂ Proxmox ਹੋਸਟ ਉੱਤੇ pct fstrim ਚਲਾਓ। Proxmox CT rootfs ਅਤੇ ਯੋਗ ਪ੍ਰਬੰਧਿਤ ਮਾਊਂਟ ਬਿੰਦੂ ਨੂੰ trim ਕਰਦਾ ਹੈ। ਇਹ bind ਮਾਊਂਟ ਅਤੇ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਵਾਲਾ ਮਾਊਂਟ points ਛੱਡ ਦਿੰਦਾ ਹੈ। ਸਿਰਫ਼ rootfs trim ਕਰਨ ਲਈ --ignore-mountpoints ਵਰਤੋ। ਪਹਿਲਾਂ ਤੇ ਬਾਅਦ ਦੀ ਸਟੋਰੇਜ ਵਰਤੋਂ ਤੁਲਨਾ ਕਰੋ। Proxmox pct fstrim ਹਵਾਲਾ

pct fstrim 101
pct fstrim 101 --ignore-mountpoints 1

ਇਹ ਕਮਾਂਡ ਉਦਾਹਰਨ CT ID 101 ਲਈ ਵੱਖਰੇ ਦਾਇਰੇ ਦਿਖਾਉਂਦੀਆਂ ਹਨ। ਆਪਣੇ ਸਟੋਰੇਜ ਲੇਆਉਟ ਵਾਲਾ ਇੱਕ ਦਾਇਰਾ ਚਲਾਓ। ਸਫਲ trim ਨਾਲ ਬਰਾਬਰ bytes ਵਾਪਸ ਮਿਲਣ ਦੀ ਗਾਰੰਟੀ ਨਹੀਂ, ਜੇ ਸਨੈਪਸ਼ਾਟ ਪੁਰਾਣੇ ਬਲਾਕ ਰੋਕਦੇ ਹੋਣ।

Proxmox bind ਮਾਊਂਟ ਅਤੇ device ਮਾਊਂਟ ਦਾ ਪ੍ਰਬੰਧ ਨਹੀਂ ਕਰਦਾ। ਉਹਨਾਂ ਦਾ ਸਰੋਤ ਡਾਟਾ ਹੋਸਟ ਜਾਂ ਬਾਹਰੀ ਯੰਤਰ ਉੱਤੇ ਰਹਿੰਦਾ ਹੈ। ਕੰਟੇਨਰ ਦੇ vzdump ਬੈਕਅੱਪ ਉਹਨਾਂ ਦੀ ਸਮੱਗਰੀ ਛੱਡ ਦਿੰਦੇ ਹਨ। ਵਾਧੂ ਸਟੋਰੇਜ-backed ਮਾਊਂਟ ਬਿੰਦੂ ਵੀ ਮੂਲ ਰੂਪ ਵਿੱਚ ਬਾਹਰ ਰਹਿੰਦੇ ਹਨ, ਜਦ ਤੱਕ backup ਵਿਕਲਪ ਉਹਨਾਂ ਨੂੰ ਸ਼ਾਮਲ ਨਾ ਕਰੇ। ਸਫ਼ਾਈ ਤੋਂ ਪਹਿਲਾਂ ਅਸਲ ਬੈਕਅੱਪ ਨੀਤੀ ਜਾਂਚੋ। Proxmox ਬੈਕਅੱਪ ਦਸਤਾਵੇਜ਼

Nested Docker ਲਈ Docker ਸਫ਼ਾਈ ਕਮਾਂਡ ਚਲਾਉਣ ਤੋਂ ਪਹਿਲਾਂ ਅਸਲ ਸਟੋਰੇਜ ਮਾਲਕ ਵਿੱਚ ਚਿੱਤਰ layers, ਵਾਲਿਊਮ ਅਤੇ logs ਜਾਂਚੋ। LXC ਵਿੱਚ Docker ਭਰੋਸੇਯੋਗਤਾ ਗਾਈਡ ਮਾਊਂਟ ਅਤੇ ਬੈਕਅੱਪ ਦੀਆਂ ਹੱਦਾਂ ਦੱਸਦੀ ਹੈ। Container ਚਿੱਤਰ ਮਿਟਾਉਣ ਨਾਲ ਸਥਾਈ ਵਾਲਿਊਮ ਮੂਲ ਰੂਪ ਵਿੱਚ ਨਹੀਂ ਮਿਟਦਾ।

ਹੋਸਟ ਨੂੰ ਸਹੀ ਤਰ੍ਹਾਂ ਮਾਪੋ #

ਸਫ਼ਾਈ ਤੋਂ ਪਹਿਲਾਂ ਅਤੇ ਬਾਅਦ ਇੱਕੋ ਜਿਹੇ ਮਾਪ ਦਰਜ ਕਰੋ। ਪੂਲ ਦੀ ਖਾਲੀ ਥਾਂ ਅੰਤਿਮ ਸਮਰੱਥਾ ਸੰਕੇਤ ਹੈ। ਵਧੇਰੇ ਵਰਤੋਂ ਵਾਲੇ ਗੈਸਟ ਨੂੰ ਲੱਭਣ ਲਈ ਵਾਲਿਊਮ ਪੱਧਰ ਦੇ ਅੰਕੜੇ ਵਰਤੋ।

pvesm status
pvesm list local-lvm
qm config 100
pct config 101

pvesm list ਪ੍ਰਬੰਧਿਤ ਵਾਲਿਊਮ ਅਤੇ ਸੰਰਚਿਤ ਆਕਾਰ ਦੀ ਸੂਚੀ ਦਿੰਦਾ ਹੈ। ਇਹ ਪਤਲੀ ਸਟੋਰੇਜ ਵਿੱਚ ਅਲਾਟ bytes ਨਹੀਂ ਮਾਪਦਾ। Directory ਸਟੋਰੇਜ ਲਈ ਸਹੀ mounted ਰਾਹ ਅਤੇ ਜਾਣੀ ਇਮੇਜ ਫ਼ਾਈਲ ਵੇਖੋ। Datacenter > ਸਟੋਰੇਜ ਅਤੇ VM config ਵਾਲੇ paths ਪਾਓ।

du -h /var/lib/vz/images/100/vm-100-disk-0.qcow2
ls -lh /var/lib/vz/images/100/vm-100-disk-0.qcow2

ਬੰਦ VM ਲਈ ਫ਼ਾਈਲ ਬਦਲੇ ਬਿਨਾਂ ਇਮੇਜ ਦੀ ਵਰਚੁਅਲ ਸਮਰੱਥਾ ਅਤੇ ਹੋਸਟ ਅਲਾਟਮੈਂਟ ਦੀ ਤੁਲਨਾ ਕਰੋ:

qemu-img info /var/lib/vz/images/100/vm-100-disk-0.qcow2

ਪਤਲੀ ਵੰਡ ਵਾਲਾ LVM ਲਈ ਪੂਲ ਦੇ ਡਾਟਾ ਅਤੇ ਮੈਟਾਡੇਟਾ ਵੇਖੋ:

lvs -a -o lv_name,vg_name,lv_size,data_percent,metadata_percent,segtype

ZFS ਲਈ ਸਰਗਰਮ dataset ਡਾਟਾ ਅਤੇ ਸਨੈਪਸ਼ਾਟ ਵੱਲੋਂ ਰੋਕੇ ਡਾਟਾ ਵੱਖ ਵੇਖੋ:

zpool list
zfs list -o name,used,available,referenced,usedbysnapshots -r POOL_OR_DATASET
zfs list -t snapshot -o name,used,referenced,written -r DATASET

usedbysnapshots dataset ਦੇ ਸਾਰੇ ਸਨੈਪਸ਼ਾਟ ਵੱਲੋਂ ਰੋਕੇ ਬਲਾਕ ਦੱਸਦਾ ਹੈ। ਸਨੈਪਸ਼ਾਟ used ਅੰਕ ਜੋੜੇ ਨਹੀਂ ਜਾ ਸਕਦੇ, ਕਿਉਂਕਿ ਸਨੈਪਸ਼ਾਟ ਬਲਾਕ ਸਾਂਝੇ ਕਰਦੇ ਹਨ। ਮਿਟਾਈ ਫ਼ਾਈਲ ਨਾਲ ਪੂਲ ਵਰਤੋਂ ਉਹਨਾਂ ਸਾਰੇ ਸਨੈਪਸ਼ਾਟ ਦੇ expire ਜਾਂ ਨੀਤੀ ਮੁਤਾਬਕ ਮਿਟਣ ਤੱਕ ਬਦਲਣੀ ਲਾਜ਼ਮੀ ਨਹੀਂ, ਜੋ ਉਸਦੇ ਬਲਾਕਾਂ ਦਾ ਹਵਾਲਾ ਦਿੰਦੇ ਹਨ। OpenZFS ਸਨੈਪਸ਼ਾਟ ਅਤੇ clones

Ceph RBD ਲਈ Ceph ਕਮਾਂਡ ਚਲਾਉਣ ਤੋਂ ਪਹਿਲਾਂ Proxmox ਵਾਲਿਊਮ ID ਨੂੰ map ਕਰੋ। qm config VMID ਵਿੱਚ STORAGE_ID:IMAGE ਦਿਸਦਾ ਹੈ। Datacenter > ਸਟੋਰੇਜ ਵਿੱਚ RBD ਐਂਟਰੀ ਖੋਲ੍ਹ ਕੇ ਪੂਲ ਅਤੇ ਚੋਣਵੇਂ namespace ਲੱਭੋ। ਸਟੋਰੇਜ ID ਦਾ ਪੂਲ name ਨਾਲ ਮਿਲਣਾ ਲਾਜ਼ਮੀ ਨਹੀਂ। ਪੂਲ ਅਤੇ ਚਿੱਤਰ ਮੁੱਲਾਂ ਨਾਲ POOL/IMAGE ਬਣਾਓ। ਇਹ ਕਮਾਂਡ ਨਿਰਧਾਰਤ Ceph ਕਲੱਸਟਰ ਲਈ configured client ਅਤੇ ਠੀਕ credentials ਨਾਲ ਚਲਾਓ। Proxmox RBD ਸਟੋਰੇਜ ਦਸਤਾਵੇਜ਼

ceph df
rbd du POOL/IMAGE
rbd snap ls POOL/IMAGE

rbd du ਚਿੱਤਰ ਦੀ provisioned ਅਤੇ ਅਸਲ ਵਰਤੋਂ, ਜੁੜੇ ਸਨੈਪਸ਼ਾਟ ਸਮੇਤ, ਦੱਸਦਾ ਹੈ। fast-diff ਚਿੱਤਰ ਵਿਸ਼ੇਸ਼ਤਾ ਨਾ ਹੋਵੇ ਤਾਂ ਇਹ ਸੰਭਾਵੀ objects ਲਈ OSDs ਤੋਂ ਪੁੱਛਦਾ ਹੈ ਅਤੇ ਵੱਧ ਕੰਮ ਕਰਦਾ ਹੈ। ceph df ਪੂਲ ਅਤੇ cluster ਸਮਰੱਥਾ ਦਿਖਾਉਂਦਾ ਹੈ। Replication, ਇਰੇਜ਼ਰ ਕੋਡਿੰਗ ਅਤੇ ਸਨੈਪਸ਼ਾਟ ਕਲੱਸਟਰ ਦੀ raw ਵਰਤੋਂ ਵਰਤੋਂ ਬਦਲਦੇ ਹਨ, ਇਸ ਲਈ ਚਿੱਤਰ ਅਤੇ ਪੂਲ bytes ਵੱਖਰੇ ਹੁੰਦੇ ਹਨ। Ceph RBD ਕਮਾਂਡ ਹਵਾਲਾ ਅਤੇ Ceph ਪੂਲ ਵਰਤੋਂ ਰਹਿਨੁਮਾਈ

ਜੇ RBD ਸਟੋਰੇਜ namespace ਵਰਤਦੀ ਹੈ, ਤਾਂ ਹਰ rbd ਕਮਾਂਡ ਵਿੱਚ --namespace NAMESPACE ਜੋੜੋ। Proxmox ਸਟੋਰੇਜ entry ਵਿੱਚ configured namespace ਵਰਤੋ, Proxmox ਸਟੋਰੇਜ ID ਨਹੀਂ।

ਸਨੈਪਸ਼ਾਟਾਂ ਅਤੇ ਬੈਕਅੱਪਾਂ ਦਾ ਹਿਸਾਬ ਰੱਖੋ #

ਸਨੈਪਸ਼ਾਟ ਬਲਾਕਾਂ ਦੇ ਪੁਰਾਣੇ ਰੂਪ ਸੰਭਾਲਦੇ ਹਨ। Trim ਪਿੱਛੋਂ ਵਰਤੋਂ ਨਾ ਘਟੇ ਤਾਂ VM ਜਾਂ CT ਦਾ ਸਨੈਪਸ਼ਾਟ ਟੈਬ ਅਤੇ ਬੈਕਐਂਡ ਦੀ ਸਨੈਪਸ਼ਾਟ ਸੂਚੀ ਵੇਖੋ। ਮਿਟਾਉਣ ਤੋਂ ਪਹਿਲਾਂ ਮਾਲਕੀ ਅਤੇ ਨਿਰਭਰਤਾਵਾਂ ਜਾਂਚੋ। ਬੈਕਅੱਪ ਵੱਖਰੀ ਕਾਪੀ ਹੈ ਅਤੇ ਬੈਕਅੱਪ ਸਟੋਰੇਜ ਦੀ retention ਅਨੁਸਾਰ ਚੱਲਦਾ ਹੈ, ਗੈਸਟ ਦੇ ਮੌਜੂਦਾ df ਅਨੁਸਾਰ ਨਹੀਂ।

PBS ਵਿੱਚ ਡੁਪਲੀਕੇਟ ਡਾਟਾ ਹਟਾਉਣਾ ਹਿਸਾਬ ਬਦਲਦੀ ਹੈ। Datastore ਵਿੱਚ ਬੈਕਅੱਪਾਂ ਵੱਲੋਂ ਸਾਂਝੇ chunks ਹੁੰਦੇ ਹਨ। Pruning ਬੈਕਅੱਪ ਸਨੈਪਸ਼ਾਟ ਮੈਟਾਡੇਟਾ ਹਟਾਉਂਦਾ ਹੈ। ਫਿਰ ਉਡੀਕ ਸਮਾਂ ਪਿੱਛੋਂ ਬੇਕਾਰ ਡਾਟਾ ਸਫ਼ਾਈ ਬਿਨਾਂ ਹਵਾਲੇ ਵਾਲੇ chunks ਹਟਾਉਂਦੀ ਹੈ। ਬੈਕਅੱਪ ਥਾਂ ਵਾਪਸ ਮਿਲਣ ਦਾ ਦਾਅਵਾ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਦੋਵੇਂ ਕੰਮ ਜਾਂਚੋ। PBS ਰੱਖ-ਰਖਾਅ ਦਸਤਾਵੇਜ਼

ਚੇਤਾਵਨੀ: Proxmox-ਪ੍ਰਬੰਧਿਤ ਵਾਲਿਊਮ ਫ਼ਾਈਲ, zvol ਜਾਂ ਸਨੈਪਸ਼ਾਟ ਨੂੰ ਸਿਰਫ਼ ਨਾਮ ਵੇਖ ਕੇ ਕਦੇ ਨਾ ਮਿਟਾਓ। ਪਹਿਲਾਂ ਗੈਸਟ ਅਤੇ retention ਨੀਤੀ ਪਛਾਣੋ। ਸਟੋਰੇਜ ਸਫ਼ਾਈ ਵਿੱਚ ਬੈਕਅੱਪ ਅਤੇ ਵਾਪਸੀ ਦਾ ਰਸਤਾ ਬਚਣਾ ਚਾਹੀਦਾ ਹੈ।

VM ਬੰਦ ਕਰਕੇ ਡਿਸਕ ਚਿੱਤਰ ਮੁੜ ਬਣਾਓ #

ਬੰਦ ਹਾਲਤ ਵਿੱਚ conversion ਸਿਰਫ਼ ਉਦੋਂ ਵਰਤੋ ਜਦੋਂ ਆਮ ਗੈਸਟ trim ਅਤੇ ਬੈਕਐਂਡ ਰਸਤਾ qcow2 ਅਲਾਟਮੈਂਟ ਸਮੱਸਿਆ ਹੱਲ ਨਾ ਕਰਨ। VM ਬੰਦ ਕਰੋ, ਬੈਕਅੱਪ ਪੱਕਾ ਕਰੋ, ਸਾਰੇ ਸਨੈਪਸ਼ਾਟ ਅਤੇ backing-chain ਸੰਬੰਧ ਪਛਾਣੋ ਅਤੇ ਵੱਖਰੀ ਮੰਜ਼ਿਲ ਚਿੱਤਰ ਲਿਖੋ। QEMU ਦੂਜੇ ਪ੍ਰਕਿਰਿਆ ਵੱਲੋਂ ਵਰਤੀ ਜਾ ਰਹੀ ਇਮੇਜ ਬਦਲਣ ਤੋਂ ਸਾਵਧਾਨ ਕਰਦਾ ਹੈ। QEMU qemu-img ਦਸਤਾਵੇਜ਼

ਜੇ ਡਿਸਕ ਉੱਤੇ ਸਨੈਪਸ਼ਾਟ ਹੋਣ ਜਾਂ ਪ੍ਰਬੰਧਿਤ ਬਲਾਕ ਸਟੋਰੇਜ ਉੱਤੇ ਹੋਵੇ, ਤਾਂ Proxmox-ਪ੍ਰਬੰਧਿਤ move ਜਾਂ ਬੈਕਅੱਪ ਅਤੇ ਮੁੜ-ਬਹਾਲੀ ਤਰੀਕਾ ਚੁਣੋ। PVE-owned ਚਿੱਤਰ ਉੱਤੇ ਇਕੱਲਾ qemu-img convert VM config, ਵਾਲਿਊਮ ਮਾਲਕੀ ਜਾਂ ਸਨੈਪਸ਼ਾਟ references ਆਪਣੇ ਆਪ ਨਹੀਂ ਬਦਲਦਾ। ਮਿਟਾਈਆਂ ਫ਼ਾਈਲਾਂ ਵਾਪਸ ਲੈਣ ਲਈ qemu-img resize --shrink ਨਾ ਵਰਤੋ। ਗੈਸਟ ਨੂੰ ਦਿਸਦੀ ਸਮਰੱਥਾ ਘਟਾਉਣ ਨਾਲ ਡਾਟਾ ਕੱਟਿਆ ਜਾ ਸਕਦਾ ਹੈ ਜੇ partitions ਅਤੇ ਫ਼ਾਈਲ ਸਿਸਟਮ ਪਹਿਲਾਂ ਛੋਟੇ ਨਾ ਕੀਤੇ ਹੋਣ।

ਥਾਂ ਵਾਪਸ ਨਾ ਮਿਲੇ ਤਾਂ ਨਿਪਟਾਰਾ ਕਰੋ #

ਲੱਛਣਸੰਭਾਵੀ ਜਾਂਚਅਗਲਾ ਕਦਮ
ਗੈਸਟ df ਘਟੇ, ਹੋਸਟ ਨਾ ਬਦਲੇVM discard ਨਿਸ਼ਾਨ, ਗੈਸਟ trim, ਸਨੈਪਸ਼ਾਟਪੂਰਾ discard ਰਸਤਾ ਅਤੇ ਰੋਕੇ ਸਨੈਪਸ਼ਾਟ ਜਾਂਚੋ।
fstrim ਅਸਮਰਥਿਤ ਦੱਸੇਗੈਸਟ ਡਿਸਕ ਬੱਸ, stacked ਬਲਾਕ devices, ਬੈਕਐਂਡlsblk -D, ਗੈਸਟ kernel ਅਤੇ ਵਿਚਕਾਰਲੀ ਹਰ ਪਰਤ ਵੇਖੋ।
Windows ReTrim ਮੁੱਕੇ, ਹੋਸਟ ਨਾ ਬਦਲੇਬੈਕਐਂਡ ਅਲਾਟਮੈਂਟ, ਸਨੈਪਸ਼ਾਟ, ਸਰਵਰ ਹਿਸਾਬਵਾਲਿਊਮ ਅਤੇ ਪੂਲ ਦੀ ਤੁਲਨਾ ਕਰੋ। ਪੱਕਾ ਕਰੋ ਕਿ ਡਿਸਕ ਪਤਲੀ ਸਟੋਰੇਜ ਵਰਤਦੀ ਹੈ।
ls -lh ਅਤੇ du -h ਵੱਖਰੇ ਹੋਣSparse ਜਾਂ qcow2 ਫ਼ਾਈਲਅਲਾਟ ਫ਼ਾਈਲ ਸਿਸਟਮ ਬਲਾਕਾਂ ਲਈ du ਵਰਤੋ।
LVM ਪਤਲਾ ਪੂਲ ਭਰਿਆ ਰਹੇਡਾਟਾ, ਮੈਟਾਡੇਟਾ, ਸਨੈਪਸ਼ਾਟਕੁਝ ਹਟਾਉਣ ਤੋਂ ਪਹਿਲਾਂ lvs ਅਤੇ PVE ਸਨੈਪਸ਼ਾਟ ਵੇਖੋ।
ZFS ਪੂਲ ਭਰਿਆ ਰਹੇਸਨੈਪਸ਼ਾਟ-held ਬਲਾਕ ਅਤੇ ਰਿਜ਼ਰਵੇਸ਼ਨusedbysnapshots, zvol ਸੈਟਿੰਗਾਂ ਅਤੇ ਪੂਲ ਸਮਰੱਥਾ ਜਾਂਚੋ।
CT df ਅਤੇ ਪੂਲ ਨਾ ਮਿਲਣBind ਮਾਊਂਟ, ਮਾਊਂਟ ਬਿੰਦੂ, ਸਨੈਪਸ਼ਾਟrootfs ਅਤੇ ਹਰ mpN ਨੂੰ ਹੋਸਟ ਉੱਤੇ ਉਸਦੇ ਮਾਲਕ ਨਾਲ ਜੋੜੋ।

Background ਕੰਮ ਮੁੱਕਣ ਪਿੱਛੋਂ ਮੁੜ ਜਾਂਚੋ। Trim, ਸਨੈਪਸ਼ਾਟ ਮਿਟਾਉਣ ਜਾਂ backend ਬੇਕਾਰ ਡਾਟਾ ਸਫ਼ਾਈ ਪਿੱਛੋਂ ਸਟੋਰੇਜ ਹਿਸਾਬ ਦੇਰ ਨਾਲ ਬਦਲ ਸਕਦਾ ਹੈ। ਮਾਪੀ ਪੂਲ ਖਾਲੀ ਥਾਂ ਦੀ ਸ਼ੁਰੂਆਤੀ ਮੁੱਲ ਨਾਲ ਤੁਲਨਾ ਕਰੋ। ਸਿਰਫ਼ ਗੈਸਟ ਕਮਾਂਡ ਦੇ ਨਿਕਾਸ ਕੋਡ ਤੋਂ ਸਫਲਤਾ ਨਾ ਮੰਨੋ।

ਅਗਲੇ ਕਦਮ #

ਹਰ ਗੈਸਟ ਲਈ ਸਟੋਰੇਜ ਰਿਕਾਰਡ ਬਣਾਓ: ਵਰਚੁਅਲ ਆਕਾਰ, ਅਲਾਟ bytes, ਬੈਕਐਂਡ, ਬੱਸ, discard ਨਿਸ਼ਾਨ, ਸਨੈਪਸ਼ਾਟ ਗਿਣਤੀ, ਬੈਕਅੱਪ ਕਵਰੇਜ ਅਤੇ ਪੂਲ ਦੀ ਖਾਲੀ ਥਾਂ। ਇੱਕ VM ਚੁਣੋ, ਸਹਾਇਕ discard ਰਸਤਾ ਚਾਲੂ ਕਰੋ, ਗੈਸਟ ਵਿੱਚ trim ਚਲਾਓ ਅਤੇ ਦਰਜ ਮੁੱਲਾਂ ਦੀ ਤੁਲਨਾ ਕਰੋ। ਪਹਿਲੀ VM ਦਾ ਨਤੀਜਾ ਬੈਕਐਂਡ ਦੇ ਉਮੀਦਵਾਰ ਵਿਹਾਰ ਨਾਲ ਮਿਲੇ ਤਾਂ ਹੀ ਦੁਹਰਾਓ।

ਵਿਆਪਕ ਰਿਕਵਰੀ ਯੋਜਨਾ ਲਈ Proxmox ਬੈਕਅੱਪ ਅਤੇ ਮੁੜ-ਬਹਾਲੀ drill ਅਤੇ Proxmox VE 8 ਤੋਂ 9 ਅਪਗ੍ਰੇਡ ਗਾਈਡ ਵੇਖੋ।
