バックアップジョブが成功と報告しても、使えるファイルを復元できるとは限りません。**復元訓練**では、稼働中のファイルを置き換えずに、保存済みバックアップから使えるデータまでの手順を確認します。このガイドではResticを使ったファイル単位の例を示し、ラボの変更後に繰り返し使える記録を用意します。

<!--more-->

Resticはバックアッププログラムです。**リポジトリ**はバックアップデータを保持する保護された保存領域です。**スナップショット**は保存されたバックアップ時点です。

## 要点

- **目標を選ぶ:** 復旧するファイルやサービスを選び、許容できる復旧時点と時間を決めます。
- **別の場所に復元する:** 空のテスト先を使い、稼働中のデータを上書きしないようにします。
- **結果を確認する:** 復元したファイルを開き、可能ならアプリケーションデータも検証し、経過時間を測ります。
- **失敗を記録する:** スナップショットID、欠落項目、権限、修復内容を復旧計画に記録します。

## 開始前の準備

動作するバックアップリポジトリ、そのパスワードまたはキー、十分な空き容量がある復元先、バックアップとテスト先への読み取り権限が必要です。この例ではResticがインストールされ、リポジトリに最近のファイルバックアップがあることを前提とします。Resticの[クイックスタート](https://restic.readthedocs.io/en/stable/010_introduction.html)では、リポジトリの作成と最初のバックアップを説明しています。サイトの[3-2-1バックアップガイド](/articles/what-is-the-3-2-1-backup-rule-and-why-you-should-use-it/)ではコピーの配置を扱います。[Homelabの概要](/articles/what-is-a-homelab-and-should-you-have-one/)には簡単なバックアップテストのチェックリストがあります。

この訓練では1つのスナップショット内のファイルを確認します。データベース、仮想マシン、アプリケーションには個別の復旧手順も必要です。復元したサービスの起動が稼働中のサービスに影響する場合、テストシステムを隔離してください。ファイルのコピーに成功しても、すべてのサービスが起動する証明にはなりません。

> **警告:** 最初のテストでは稼働中のパスに復元しないでください。別のファイルシステムまたはテストホスト上に空のテストディレクトリを使います。スクリーンショット、チケット、シェル履歴にリポジトリのパスワードを残さないでください。

## 復旧目標を決める

障害後に必要なものを書き出します。**目標復旧時点 (RPO)** は、中断後にデータを復旧する必要がある時点です。許容できる最大データ損失を表します。**目標復旧時間 (RTO)** は、サービスが停止してよい時間です。NISTは[緊急時対応計画ガイド](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-34r1.pdf)で両方を定義しています。データの変更頻度と、自分のハードウェアでの復元時間に基づいて目標を決めます。

| 項目 | 目標例 | 記録内容 |
|---|---|---|
| **家族の書類** | 最新の夜間バックアップ | 最新スナップショットの時刻と開いたファイル |
| **家庭内サービスの設定** | 最後に正常動作した変更 | 設定のバージョンと必要なシークレット |
| **ネットワーク接続ストレージ (NAS) のメディアライブラリ** | 週次バックアップ | サンプル再生と復元時間 |

上記は例であり、測定結果ではありません。復旧計画にはバックアップの保存場所と、許可された担当者がリポジトリのパスワードまたは暗号化キーを取得する方法を記録します。秘密の値を計画や訓練記録に書かないでください。障害が発生するホストとは独立した保護経路にシークレットを保存します。リポジトリが残っていても唯一のパスワードを失えば復旧できません。

この訓練で**重要なファイルセット**を1つ選びます。最新スナップショットに含まれるはずの小さなファイルを加えます。サービスの場合は、起動に必要な設定、データベースのエクスポート、証明書、アプリケーションのバージョンも列挙します。実行中のデータベースをファイル単位でコピーする前に、バックアップ方法が一貫性のあるアプリケーションデータを取得することを確認してください。

## スナップショットを探す

復元訓練で許可された方法でリポジトリにアクセスします。Resticはバックアップデータの読み取りや変更時に、一時的なリポジトリロックを使用します。以下のコマンドはリポジトリがこのロックを許可していることを前提とします。稼働中のソースとテスト先を分けます。`/path/to/repository`を実際のResticリポジトリのパスに置き換え、スナップショットを一覧表示します。

```bash
restic -r /path/to/repository snapshots
```

設定済みのシークレット管理方法でパスワードを渡していない場合、Resticはリポジトリのパスワードを要求します。[スナップショット一覧](https://restic.readthedocs.io/en/stable/010_introduction.html)にはID、日付、ホスト、ソースパスが表示されます。テストするスナップショットのIDとタイムスタンプを記録し、RPOと比較します。直近のジョブログだけでは不十分です。必要なスナップショットが想定より古い可能性があります。

必要なスナップショットが見つからない場合は訓練を中止し、バックアップスケジュール、ソース選択、リポジトリパスを調査します。古いスナップショットを黙って選び、復旧目標を達成したと報告しないでください。

## 空のテスト先に復元する

スナップショットを保存できる十分な空き容量のあるテスト用ファイルシステムに、**空の復元先ディレクトリ**を作成します。元のソース、マウント済みの本番共有、保持したいデータがある既存フォルダーをResticの復元先にしないでください。実行前に`SNAPSHOT_ID`と2つの例示パスを置き換えます。

```bash
restic -r /path/to/repository restore SNAPSHOT_ID \
  --target /path/to/empty-restore-drill
```

Resticの[復元ガイド](https://restic.readthedocs.io/en/stable/050_restore.html)では、スナップショットIDと`--target`パスを説明しています。復元後のディレクトリツリーには、復元先の下にソースパスが保持されます。結果を判定する前に実際のファイルを探してください。少量だけ必要な場合は、文書化されている[復元対象の包含フィルター](https://restic.readthedocs.io/en/stable/050_restore.html)を使用し、除外したものを記録します。訓練で`--delete`を使わないでください。Resticによると、このオプションはスナップショットにない復元先のファイルを削除します。

復元が始まったら計時を始めます。必要なファイルが存在し、使用できる状態になったら止めます。コマンドが最初に進捗を表示した時点ではありません。リポジトリの場所、ネットワーク接続、データ量、テストホストを記録します。これらは後の復旧時間に影響します。

> **期待する結果:** 選んだスナップショットが稼働中のソースを変更せず、別の復元先に戻ること。

## データとサービスを検証する

通常そのファイルを開くアプリケーションで、復元したファイルをいくつか開きます。最近のファイル、古いファイル、入れ子のディレクトリにあるファイルを含めます。バックアップ前に記録したサイズやチェックサムがあれば比較します。Linuxでは所有者と権限も確認します。テストアカウントが読めても、サービスアカウントでは使えない場合があります。

サービスは隔離されたテストインスタンスに復元します。設定、必要なシークレット、データベースの整合性、起動、代表的なユーザー操作を確認します。データベースやシークレットがないファイル復元は、サービス全体の復旧ではありません。制御された切り替え計画がない限り、テストインスタンスを稼働中のデータベースや本番アドレスに接続しないでください。

サンプルの復元後、Resticのリポジトリ検査を実行します。

```bash
restic -r /path/to/repository check
```

リポジトリ全体のデータを読み取るには、メンテナンス時間に`check --read-data`を使用します。Resticは、全リポジトリを読み込み、リモートバックエンドから大量のデータをダウンロードする可能性があると警告しています。[Resticのトラブルシューティングガイド](https://restic.readthedocs.io/en/stable/077_troubleshooting.html)には検査方法とコストが記載されています。エラーのない検査は安心材料になりますが、復元ファイルを開いたりサービスを起動したりする確認の代わりにはなりません。

```bash
restic -r /path/to/repository check --read-data
```

スナップショットの経過時間をRPOと比較し、測定した復旧時間をRTOと比較します。どちらかの目標を満たさなければ、Resticがエラーなしで終了しても訓練は失敗です。バックアップ頻度、保存場所、帯域幅、復旧手順を調整して再テストします。

## 復元記録を残す

毎回の訓練後に短い記録を作成します。NISTの[バックアップ管理策 SP 800-53](https://csrc.nist.gov/CSRC/media/Projects/risk-management/800-53%20Downloads/800-53r5/SP_800-53_v5_1-derived-OSCAL.pdf)では、サンプルシステム機能の復元を復旧テストの方法として挙げています。繰り返し使える記録があれば計画の改善状況を確認できます。

| 項目 | 記録する結果 |
|---|---|
| **日付と実施者** | 実施日と担当者 |
| **リポジトリとスナップショット** | 場所、ID、タイムスタンプ、ソースパス |
| **復旧目標** | テストしたファイルやサービス、およびRPOとRTO |
| **測定結果** | スナップショットの経過時間、復元時間、ファイルまたはサービスの確認結果 |
| **失敗内容** | データ欠落、キーへのアクセス、権限、ネットワーク、起動の問題 |
| **次の対応** | 担当者、修正内容、次回テスト日 |

リポジトリのパスワード、復旧キー、機密ファイルの内容を記録に書かないでください。保護されたシークレットストアに保存し、障害中に許可された担当者が取得する方法を記録します。

## トラブルシューティング

- **パスワードがない:** 独立したキー保管経路を確認します。故障したホストから自身のキーを取得できると思い込まないでください。
- **スナップショットが古い:** スケジュール、ジョブ失敗、ソースパス、対象ホストが別のリポジトリに保存していないかを確認します。
- **復元が遅い:** ストレージの読み取り速度、ネットワーク接続、データ量を測ります。重要なデータの小さなセットを試し、RTOまたは復旧設計を見直します。
- **ファイルはあるがサービスが失敗する:** データベースのエクスポート、アプリケーションのバージョン、所有者、権限、証明書、シークレットの不足を確認します。
- **リポジトリ検査でエラーが出る:** 出力を保存し、可能ならリポジトリのコピーも保持します。修復を試す前に、Resticの[破損調査ガイド](https://restic.readthedocs.io/en/stable/077_troubleshooting.html)に従います。
- **テストで稼働データを変更した:** テストサービスを停止し、本番データを確認して、隔離計画を修正してから再度訓練します。

## 次のステップ

バックアップソフト、ストレージ、暗号化キー、重要なサービスを変更した後に訓練を繰り返します。異なるファイルセットとサービス全体の復旧を順番に試します。[3-2-1計画](/articles/what-is-the-3-2-1-backup-rule-and-why-you-should-use-it/)に従って独立したバックアップコピーを保管します。元のホストが使えなくなったときに繰り返せる、測定済みの復元手順を作ることが目標です。
