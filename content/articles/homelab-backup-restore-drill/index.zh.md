备份任务报告成功，并不能证明你能恢复可用文件。**恢复演练**会检查从已存储备份到可用数据的整个流程，同时避免替换正在使用的文件。本指南使用 Restic 展示文件级恢复，并提供一份可在实验环境变更后重复填写的记录。

<!--more-->

Restic 是备份程序。**仓库**是保存备份数据的受保护存储区。**快照**是保存的一个备份时间点。

## 重点

- **设定目标：** 选择需要恢复的文件或服务，并确定可接受的恢复时间点和耗时。
- **单独恢复：** 使用空的测试目标，避免演练覆盖现有数据。
- **检查结果：** 打开恢复的文件，在可行时验证应用数据，并记录耗时。
- **记录问题：** 在恢复计划中记录快照 ID、缺失项目、权限和修复措施。

## 开始前

你需要一个可用的备份仓库、仓库密码或密钥、空间充足的目标位置，以及读取备份和测试位置的权限。本示例假设已安装 Restic，且仓库中有近期文件备份。Restic 的[快速入门](https://restic.readthedocs.io/en/stable/010_introduction.html)介绍如何创建仓库和首次备份。本站的[3-2-1 备份指南](/articles/what-is-the-3-2-1-backup-rule-and-why-you-should-use-it/)介绍备份副本的存放位置。[Homelab 概述](/articles/what-is-a-homelab-and-should-you-have-one/)包含简短的备份测试清单。

本演练只检查一个快照中的文件。数据库、虚拟机或应用也需要各自的恢复步骤。如果启动恢复的服务可能影响线上服务，请隔离测试系统。文件复制成功不代表所有服务都能启动。

> **警告：** 首次测试时，不要恢复到正在使用的路径。请在独立文件系统或测试主机上使用空目录。不要在屏幕截图、工单或 shell 历史中暴露仓库密码。

## 定义恢复目标

记录故障后需要恢复的内容。**恢复点目标 (RPO)** 是中断后必须恢复数据的时间点，也表示可接受的最大数据丢失量。**恢复时间目标 (RTO)** 是服务最多可以中断多久。NIST 在其[应急规划指南](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-34r1.pdf)中定义了这两个概念。目标应考虑数据变化频率，以及当前硬件上的恢复耗时。

| 项目 | 示例目标 | 记录内容 |
|---|---|---|
| **家庭文件** | 最近一次夜间备份 | 最新快照时间和已打开的文件 |
| **家庭服务配置** | 最近一次已知可用的变更 | 配置版本和所需机密 |
| **网络附加存储 (NAS) 媒体库** | 每周备份 | 样本播放情况和恢复时间 |

以上目标仅为示例，并非测量结果。在恢复计划中记录备份存放位置，以及授权人员如何获取仓库密码或加密密钥。不要把机密值写进计划或演练记录。通过独立于故障主机的受保护渠道保存机密。仓库仍在，但唯一密码丢失时，数据无法恢复。

为本次演练选择一个**关键文件集**，并加入一个确定应存在于最新快照中的小文件。对于服务，还要列出启动所需的配置、数据库导出、证书和应用版本。依赖运行中数据库的文件级副本之前，先确认备份方法能捕获一致的应用数据。

## 查找快照

使用已获准用于恢复演练的仓库访问方式。Restic 在读取或修改备份数据时会临时锁定仓库。以下命令假设仓库允许该锁操作。将在线源和测试目标分开。把 `/path/to/repository` 替换为实际的 Restic 仓库路径，然后列出快照：

```bash
restic -r /path/to/repository snapshots
```

如果尚未通过配置好的机密管理方式提供密码，Restic 会提示输入仓库密码。[快照列表](https://restic.readthedocs.io/en/stable/010_introduction.html)显示 ID、日期、主机和源路径。记录要测试的快照 ID 和时间戳，并将其与 RPO 比较。近期任务日志不能替代此检查，因为所需快照可能比预想的旧。

如果找不到预期快照，请停止演练并调查备份计划、源选择和仓库路径。不要悄悄改用更旧的快照，再报告恢复目标已达成。

## 恢复到空目标

在有足够空间的测试文件系统上创建一个**空目标目录**。不要把原始源路径、已挂载的生产共享目录或包含需保留数据的现有文件夹用作 Restic 目标。运行命令前，替换 `SNAPSHOT_ID` 和两个示例路径：

```bash
restic -r /path/to/repository restore SNAPSHOT_ID \
  --target /path/to/empty-restore-drill
```

Restic 的[恢复指南](https://restic.readthedocs.io/en/stable/050_restore.html)说明快照 ID 和 `--target` 路径。恢复后的目录树会在目标目录下保留源路径，因此评估结果前要找到实际文件。如果只需恢复少量内容，请使用文档中的[恢复包含筛选器](https://restic.readthedocs.io/en/stable/050_restore.html)，并记录排除了什么。演练时不要使用 `--delete`。Restic 说明此选项会删除目标中快照不存在的文件。

恢复开始时启动计时器。等所需文件均已存在且可用时再停止，不要在命令首次显示进度时停止。记录仓库位置、网络连接、数据量和测试主机，因为这些条件会影响后续恢复。

> **预期结果：** 选定快照恢复到独立目标，且不更改在线源数据。

## 验证数据和服务恢复

用平时读取这些文件的应用打开几个恢复的文件，包括近期文件、较早的文件和嵌套目录中的文件。如果备份前记录过大小或校验和，请进行比对。在 Linux 上检查所有者和权限，因为测试账户可读的文件对服务账户仍可能不可用。

恢复服务时，应使用隔离的测试实例。检查配置、必需机密、数据库一致性、启动过程和一项典型用户操作。缺少数据库或机密的文件恢复不算完整的服务恢复。没有受控切换计划时，绝不要让测试实例连接在线数据库或生产地址。

恢复样本后，运行 Restic 仓库检查：

```bash
restic -r /path/to/repository check
```

要完整读取仓库数据，可在维护窗口使用 `check --read-data`。Restic 警告此命令会读取整个仓库，并可能从远程后端下载大量数据。[Restic 故障排查指南](https://restic.readthedocs.io/en/stable/077_troubleshooting.html)说明了检查方式和成本。检查通过能增加信心，但不能替代打开恢复文件或启动服务。

```bash
restic -r /path/to/repository check --read-data
```

将快照年龄与 RPO 比较，将实测恢复耗时与 RTO 比较。如果任一目标未达成，演练就算失败，即使 Restic 没有报错。调整备份频率、存储位置、带宽或恢复步骤，然后重新测试。

## 保存恢复记录

每次演练后都写一份简短记录。NIST 的[备份控制 SP 800-53](https://csrc.nist.gov/CSRC/media/Projects/risk-management/800-53%20Downloads/800-53r5/SP_800-53_v5_1-derived-OSCAL.pdf)将恢复抽样系统功能列为一种恢复测试方法。使用可重复的记录有助于判断计划是否改进。

| 字段 | 填写内容 |
|---|---|
| **日期和操作员** | 演练时间和执行人员 |
| **仓库和快照** | 位置、ID、时间戳和源路径 |
| **恢复目标** | 测试的文件或服务，以及 RPO 和 RTO |
| **测量结果** | 快照年龄、恢复时间、文件或服务检查结果 |
| **失败情况** | 数据缺失、密钥访问、权限、网络或启动问题 |
| **后续措施** | 负责人、修复措施和下次测试日期 |

不要在记录中填写仓库密码、恢复密钥或敏感文件内容。将它们保存在受保护的机密存储中，并记录授权人员如何在中断期间取用。

## 故障排查

- **无法取得密码：** 检查独立的密钥托管渠道。不要假设故障主机仍可用于取回自己的密钥。
- **快照太旧：** 检查计划、失败任务、源路径，以及预期主机是否备份到了另一仓库。
- **恢复太慢：** 测量存储读取速度、网络连接和数据量。先测试更小的关键子集，再调整 RTO 或恢复设计。
- **文件存在但服务失败：** 检查数据库导出、应用版本、所有者、权限、证书和缺失的机密。
- **仓库检查报告错误：** 保存输出，并尽可能保留仓库副本。尝试修复前，按照 Restic 的[损坏排查指南](https://restic.readthedocs.io/en/stable/077_troubleshooting.html)处理。
- **测试更改了在线数据：** 停止测试服务，检查生产数据，并在重新演练前修改隔离计划。

## 后续步骤

更换备份软件、存储、加密密钥或关键服务后，重新执行演练。之后轮流测试不同文件集和完整服务恢复。按照你的[3-2-1 计划](/articles/what-is-the-3-2-1-backup-rule-and-why-you-should-use-it/)保留独立备份。目标是获得可测量、可重复的恢复流程，以便原主机失效后仍可使用。
