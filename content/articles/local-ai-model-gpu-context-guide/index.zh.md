**最适合本地编码的模型，是能够将足够多的项目内容保留在内存中，并以足够快的速度读取，从而持续发挥作用的模型。**模型大小仍然重要，但如果模型只有在把数据转移到系统内存后才能装下，它通常不如较小且上下文窗口稳定的模型好用。

*模型和内存预算要一起选。不要先按排行榜挑模型，再硬把它塞进不合适的硬件。*

本指南关注编码代理，而不是简短的自动补全提示。代理会先读取文件、工具输出、编译器错误和测试结果，再编写修复。这些输入会占用上下文，而上下文会改变硬件选择。

## 为什么模型排行榜不够用

模型排行榜通常会把参数量对应到 GPU 显存数值。这个捷径适合做初步估算，但编码代理开始读取真实代码库后，它就不再够用了。

模型权重是首次分配的内存。**KV 缓存**则会逐渐增长。它保存当前上下文中的注意力键和值，避免运行时在每生成一个令牌后都重新计算整个提示词。

| 内存用途 | 保存内容 | 重要原因 |
|---|---|---|
| **模型权重** | 量化后的参数 | 一次性加载需求 |
| **KV 缓存** | 当前上下文中的信息 | 随提示词和对话增长 |
| **运行时缓冲区** | 临时计算空间 | 随后端和批次大小变化 |
| **代理指令** | 系统提示和工具定义 | 项目文件到达前就占用上下文 |

**模型文件能装进显卡，并不代表代理就能正常使用。**运行时还需要为缓存、临时缓冲区、工具定义和下一条回复留出空间。

## 上下文才是真正的预算

编码代理消耗的上下文不止源文件。系统指令、工具架构、目录清单、shell 输出、编译器消息、测试结果和先前的对话轮次也都占用预算。

三个带有详细工具定义的 MCP 连接，可能在代理打开项目文件之前就消耗数千个令牌。默认上下文较小时，留给代码的空间就很少。代理仍然会回复，但在多步修复中会缺少必要的工作集。

Ollama 的[运行时常见问题](https://docs.ollama.com/faq)列出的默认上下文长度为 4,096 个令牌。`OLLAMA_CONTEXT_LENGTH` 设置可更改默认值，而 `OLLAMA_NUM_PARALLEL` 会随并发请求数量增加所需内存。将本地基准测试与单请求结果比较前，先记录这两个值。

```bash
OLLAMA_CONTEXT_LENGTH=32768 OLLAMA_NUM_PARALLEL=1 ollama serve
```

这个示例为一个活动请求设置 32K 的默认上下文。它不会为项目文件预留 32K 个令牌。指令、工具定义、输入和输出仍然共用同一个窗口。

### 简单的上下文记录

比较 GPU 前，记录以下数值：

- **项目规模：** 常见任务涉及的文件数和大致源代码行数。
- **工具开销：** 系统提示、MCP 架构、shell 工具和编辑器指令。
- **错误信息负载：** 常见编译器和测试输出的长度。
- **目标上下文：** 希望在不截断的情况下保留的最大提示词。
- **回复预留空间：** 为计划中的补丁和说明留出的空间。

将结果作为工作负载规格。一次只编辑一个文件的开发者，与让代理在大型代码库中追踪 API 的开发者，需要的内存并不相同。

## KV 缓存会改变模型排序

参数量相近的两个模型，其上下文成本往往不同。每一层都让缓存持续增长的稠密模型，通常比采用混合注意力设计的模型需要更多内存。

参考资料讨论的一款 27B 编码模型只在有限数量的层中使用完整注意力，其他层则使用固定大小的摘要。据报告，在 128K 上下文下，其缓存成本低于 9GB。同等大小、每一层都采用完整增长型注意力的模型，据报在相同上下文长度下需要超过 21GB。

这些数值对应特定模型架构和运行时设置。应把它们当作检查架构的理由，而非通用内存公式。

| 模型行为 | 对上下文的影响 | 对硬件的影响 |
|---|---|---|
| **每一层都使用完整注意力** | 缓存大幅增长 | 长提示词需要更多内存 |
| **混合或滑动注意力** | 某些层的缓存增长较少 | 相同模型大小下可留出更多上下文空间 |
| **混合专家模型** | 每个令牌激活的参数较少 | 每个令牌计算量较低，但仍要存储全部权重 |
| **长上下文扩展** | 工作窗口更大 | 需要更多缓存内存和提示词处理时间 |

**购买内存前，先查看模型架构。**单看参数量会掩盖长时间编码会话的成本。

## 按 GPU 显存档位选择

### 4 到 8 GB

小型稠密模型仍是实用选择。它们能装进显卡、响应快，适合自动补全、简短说明和范围较小的文件修改。

更大的模型通过 CPU 卸载也许能生成文本，但响应时间往往会成为瓶颈。编码代理需要反复读取文件和调用工具。即使模型技术上能够运行，速度只有每秒四个令牌也会让每次修复都变成漫长等待。

混合专家模型提供了另一种途径。较小的激活部分可减少计算压力，而完整权重集仍有一部分驻留在系统内存中。这种方式适合内存充足且传输路径较快的系统。

| 工作负载 | 建议方向 |
|---|---|
| **自动补全** | 配合短提示词的小型稠密模型 |
| **单文件修改** | 支持工具调用的小型指令模型 |
| **全代码库代理** | 先租用更大的 GPU，或先增加系统内存 |
| **NDA 约束下的私有代码** | 使用本地模型，但接受较小范围或较慢运行 |

**在这个档位，先购买系统内存，再考虑追求大模型。**稳定的小模型胜过大部分时间都在总线上搬运数据的大模型。

### 12 到 16 GB

这个档位让 27B 编码模型成为可能，但量化选择非常关键。标准 4 位版本约为 17GB，运行时开销加入后无法装进 16GB 显卡。

3 位版本约为 13GB，能为上下文留出更多空间。12GB 显卡会让选择转向 2 位版本或更小的混合专家模型。质量取决于具体量化器和校准流程，因此即使位数相同，不同上传版本的编码效果也常有差别。

下载量化模型前，请检查以下项目：

- **量化器作者和发行说明**
- **校准数据和评估结果**
- **分词器兼容性**
- **工具调用测试**
- **该量化版本支持的上下文长度**
- **Ollama、llama.cpp 或所选前端的运行时支持**

**不要把“2 位”或“3 位”当成完整的质量描述。**打包方法和校准记录同样重要。

### 24 到 32 GB

对于 27B 编码模型来说，这是最灵活的范围。24GB 显卡通常能装下 4 位版本并保留可用上下文，但完整的 128K 窗口可能会超出剩余内存。32GB 显卡能给运行时留出更多缓存和临时分配空间。

这个范围也更容易证明自购硬件的合理性。一张 GPU 就能处理工作负载，不用处理双卡拆分的复杂性。与多 GPU 系统相比，整机功耗更低，软件支持也更容易测试。

| 容量 | 实用定位 |
|---|---|
| **24GB** | 性能强的 4 位模型，但要测量上下文限制 |
| **32GB** | 上下文空间更充裕的 4 位或 6 位 27B 模型 |
| **48GB** | 提高精度或扩大缓存，无需更换核心模型 |

**对于频繁进行的私有编码工作，24GB 到 32GB 是合理的自购区间。**它避免了最差的卸载表现，也不用把数据中心硬件塞进桌面机箱。

### 48 GB 及以上

内存增加不代表一定要换模型。同一个 27B 模型可能在 48GB 显卡上以 8 位精度运行，同时使用更大的缓存、减少妥协。改进来自更稳定的运行、更大的上下文空间和更高的输出质量，而不是推理能力升了一个档次。

达到 128GB 后，选择会有所不同。此时可以运行大得多的混合专家模型，但提示词处理会成为重要因素。模型生成速度可能很快，却需要很长时间才能读取大型代码库或新返回的工具结果。

**对于大模型，请分别测量预填充速度和解码速度。**读提示词很慢，即使之后回答很快，在代理工作流中仍然会显得慢。

## 解码速度只是测试的一半

**解码速度**衡量每秒生成的令牌数。它回答“模型写得有多快？”**预填充速度**衡量提示词处理速度。它回答“模型读得有多快？”

代理大部分时间都在读取。每次工具调用都会加入新文本。长源文件、堆栈跟踪或测试日志会在下一条回复开始前进入提示词。

| 指标 | 用户体验 |
|---|---|
| **每秒解码令牌数** | 处理完成后，答案出现的速度 |
| **每秒提示词令牌数** | 代理在答案开始前需要等待多久 |
| **首令牌耗时** | 提示词处理和初始化的总延迟 |
| **上下文保留量** | 任务期间还可用的项目状态 |

**用自己的提示词规模做基准测试。**短小的合成提示词会掩盖代码库工作中最重要的开销。

## 先尝试免费的运行时设置

升级硬件不是提升性能的第一步。打开购物页面前，先测试运行时设置。

### 多令牌预测

部分模型与后端组合支持预测多个后续令牌，再通过一次处理来验证。这个功能通常通过运行时标志或兼容的草稿模型设置启用。

参考资料中报告的测试显示，这项功能在某些高端显卡上能带来显著提升。实际效果会随模型文件、后端、驱动和显卡而变化。Apple Metal 路径在转换时可能无法保留所需功能。

### 推理等级

默认启用最高推理等级的模型，在返回结果前会花更多时间进行内部处理。对于代码修复，中等推理等级往往更均衡，尤其是任务已经包含清晰的错误信息和明确的目标文件时。

可以用一个简单的测试矩阵：

1. 分别用低、中、高推理等级运行同一个错误修复任务。
2. 记录首令牌耗时、总耗时、补丁是否成功以及测试结果。
3. 使用简短提示词和接近真实代码库规模的提示词重复测试。
4. 选择能完成任务效果最好的设置，而不是令牌速率最高的设置。

**中等推理等级搭配兼容的多令牌预测路径，是一个很好的起点。**设为默认值前，请在自己的代码上验证质量。

## 本地硬件还是租赁 GPU？

偶尔使用时，租赁计算资源更划算。你只需为活动会话付费，不用全年购买、散热、更新和供电。

如果工作频繁、涉及私密数据或需要离线运行，自购硬件更合适。它也能减少排队时间，并为可重复测试提供稳定环境。

| 情况 | 更适合的首选方案 |
|---|---|
| **每月只有几次会话** | 租用 GPU 或使用 API |
| **每天处理私有代码** | 购买受支持的 24GB 到 32GB 系统 |
| **大型代码库且经常重新加载** | 先租用，再测量预填充速度 |
| **代码不能离开单位** | 自购满足上下文目标的最小系统 |
| **试用新模型** | 购买硬件前先租用 |

用实际运行小时数计算回本时间，不要按日历小时计算。将电费、存储、散热、维护和维持运行时可用所需的时间都算进去。

**为偶尔试验而购买高端 GPU 属于兴趣开销。**每天用于私密工作的 24GB 到 32GB 系统，经济理由更充分。

## 更合理的购买清单

比较模型和 GPU 时，按以下顺序操作：

1. **定义任务。**自动补全、单文件修复、代码库代理，还是长上下文分析。
2. **测量提示词。**统计常见系统指令、工具架构、文件和测试输出。
3. **检查缓存行为。**查找架构说明和上下文内存测量结果。
4. **选择量化版本。**查看具体上传版本的质量结果，不要只看位数。
5. **测试预填充和解码。**使用自己代码库里的提示词。
6. **调整推理等级。**比较多个推理等级下的任务完成时间。
7. **检查隐私和维护。**确认源代码会传到哪里，以及由谁维护后端。
8. **比较租赁成本。**根据预计活动小时数计算，并在自购系统估算中加入电费。

## 最终建议

**显存低于 12GB 时，运行更小的模型，或搭配足够系统内存使用混合专家模型。**不要硬塞 27B 稠密模型，让系统大部分时间都在卸载数据。

**显存为 12GB 到 16GB 时，重点考虑量化质量和可控的上下文目标。**经过充分测试、支持工具调用的 2 位或 3 位版本，比始终无法顺利装入的 4 位文件更实用。

**显存为 24GB 到 32GB 时，27B 编码模型适合作为日常私有工作的实用默认选择。**不要假设宣传的完整上下文窗口都可用，先测量上下文用量和提示词速度。

**显存达到 48GB 及以上时，先把额外内存用于精度、缓存空间和稳定运行，再考虑更大的模型。**模型达到 128GB 级别后，提示词读取速度和租赁经济性比原始容量更值得关注。

模型名称只是起点。真正有用的问题是，模型、运行时、工具和缓存各自占用内存后，还能留下多少项目上下文。
