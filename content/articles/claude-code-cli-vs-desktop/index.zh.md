**Claude Code CLI 和 Desktop** 提供了引导 Anthropic 编码代理的两种方式。CLI 适合 Shell 工作流和程序化调用。Desktop 适合可见的项目工作区，能够在会话旁查看文件变化和审查结果。

**本文比较桌面编码工作区。** Anthropic 的[桌面快速入门](https://code.claude.com/docs/en/desktop-quickstart)将其描述为 Code 标签页。普通聊天和其他桌面工作流不在范围内。检查仓库访问权限和配置时，这一区别很重要。

## 主要结论

- **脚本、管道输入和终端中心的工作使用 CLI。**
- **图形化监督、附件和 diff 审查使用 Desktop。**
- **共享配置减少重复。** 但会话行为和可用控制项不同。
- **移动会话需要受支持的交接。** 不能只把 prompt 复制到新聊天中。

**范围和日期：** 官方文档于 2026 年 10 月 10 日检查。这是功能和工作流比较，不是编码基准测试。你需要可测试的仓库和获批准的账户路径。小规模试用预留 45 至 60 分钟。

## 相同引擎，不同控制项

**Anthropic 将 Desktop 描述为带有 GUI 的同一底层引擎。** [桌面参考](https://code.claude.com/docs/en/desktop)说明了共享配置和项目记忆，同时区分客户端功能。基础相同，并不表示每个 CLI 选项都有对应的 Desktop 按钮。

| 活动 | CLI | Desktop Code 工作区 |
|---|---|---|
| **交互式工作** | 终端会话 | 带项目窗格的图形会话 |
| **脚本调用** | Print 模式和管道输入 | 此工作流使用 CLI |
| **变更审查** | 终端或编辑器工作流 | 集成式可视化 diff |
| **任务组织** | 终端会话和 CLI 控制项 | 会话侧栏和工作区布局 |
| **重复工作** | 外部调度器或 CI | Desktop 计划任务 |
| **项目规则** | 仓库和用户配置 | 带界面特定行为的共享设置 |

**根据监督成本选择。** Shell 密集型故障调查和可视化应用修改对界面的要求不同。两者都不能证明模型更强。

## 终端工作和脚本

```bash
claude -p "Explain the failing test and propose a fix. Do not edit files."
```

**Print 模式不运行普通的交互式会话。** Anthropic 的 [CLI 参考](https://code.claude.com/docs/en/cli-reference)说明了这组命令、管道输入和恢复选项。根据调查内容匹配工具权限。上面的 prompt 不能替代只读策略。

**当输入输出契约稳定时使用脚本。** 例子包括计划报告、范围有限的仓库检查，或生成审查材料的 CI 步骤。定义失败条件并保存证据。不要只因为代理的最终消息看起来完整就批准补丁。

**决策仍未确定时保持交互式工作。** 如果任务需要选择 API 设计或解决矛盾需求，带有明确检查点的终端会话通常比无界面包装器需要更少的自动化代码。

## Desktop 审查和计划任务

**Desktop 提供编码工作区，无需单独安装 CLI。** 快速入门介绍项目选择、模型选择和图形化接受变更。使用跨越源文件、测试和配置文件的补丁进行评估，让审查涉及多个窗格。

**计划工作是 Desktop 的独立功能。** Anthropic 的[计划任务文档](https://code.claude.com/docs/en/desktop-scheduled-tasks)说明了重复任务和运行要求。依赖每日工作流前，检查计划任务在哪里运行，以及哪些条件必须持续可用。

**审查聚合后的补丁。** 单个编辑批准不能显示变更文件之间的全部交互。运行结束后检查最终 diff，并独立执行验收检查。

## 设置和权限

**设置有范围和优先级。** Anthropic 的[设置参考](https://code.claude.com/docs/en/settings)区分托管、用户、项目和本地配置。诊断客户端差异前，先验证实际生效的配置。项目规则不一定覆盖组织策略。

**权限模式会改变交互。** 使用匹配的策略比较两个客户端，再单独测试首选策略。更少的批准提示不代表无条件的优势。关键问题是允许的操作是否符合任务和环境。

| 配置检查 | 原因 |
|---|---|
| **项目文件夹** | 加载预期代码和项目规则 |
| **账户路径** | 决定访问和计费上下文 |
| **所选模型** | 避免混淆界面变化和模型变化 |
| **权限策略** | 控制哪些操作继续执行 |
| **运行环境** | 决定可用命令和测试 |

**把规范的项目指令保存在仓库中。** 记录构建命令、排除文件和验收标准。编辑前要求代理识别这些约束。发现不一致时，先解决配置问题，再比较行为。

## 移动会话

```text
/desktop
```

**文档中的 CLI 到 Desktop 交接会保存会话并退出 CLI。** 桌面参考将此命令限制为受支持的 macOS 和 x64 Windows 订阅会话。API 密钥和第三方提供商会话没有相同的交接路径。依赖此功能前检查已安装版本和账户。

**把交接视为受控转换。** 完成或停止活动操作，确认当前分支并检查待处理变更。打开目标界面后验证仓库，并询问下一步计划。第一项实现仍在运行时，不要对同一文件启动第二项实现。

**共享文件不等于共享会话。** 两个客户端打开同一个 checkout 时都能看到文件系统变化，但新会话没有原会话的推理和约束。需要可移植交接时，在仓库中保存简短的任务记录。

## 通过小规模试用选择

**使用有明显症状的错误。** 提供复现、预期行为和代理必须保留的文件。从同一基础修订开始，在匹配的模型和权限设置下分别试用。

| 试用阶段 | 观察内容 |
|---|---|
| **上下文** | 附加日志、文件和截图的工作量 |
| **实现** | 中断和澄清需求 |
| **审查** | 检查每个变更文件的难易程度 |
| **修正** | 被拒绝方法的回应 |
| **完成** | 独立测试结果和干净 diff |

**脚本和终端上下文占主导时优先选择 CLI。** **可见项目状态和图形审查能够降低摩擦时优先选择 Desktop。** 在两类需求之间切换时，有意识地使用两者。

## 故障排查和后续步骤

**如果 Desktop 缺少 CLI 中的命令，** 查阅功能比较，不要先假设安装失败。如果命令只能在终端工作，比较执行环境和 runtime 发现情况。如果交接不可用，检查平台和认证资格。
