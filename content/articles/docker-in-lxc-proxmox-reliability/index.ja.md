**Linux Containers（LXC）内のDocker**は、インフラのオーバーヘッドを抑える一方で、アプリケーションのランタイムとProxmoxホストとの相互作用を増やします。家庭で使うDockerサービスには、Debianの**仮想マシン（VM）**が実用的な出発点です。ゲストカーネルを分離し、トラブルシューティング時に再現する環境を簡素化できます。この記事では、提供された動画と関連するインシデント報告を確認し、文書化された障害と移行計画を紹介します。

<!--more-->

## 要点

- **障害の種類を区別する:** Dockerの起動エラー、停止したVM、応答しない物理ホストでは、調査方法が異なります。
- **根拠を評価する:** 移行後の安定は復旧判断を支えますが、元の原因を証明するものではありません。
- **最新の文書を確認する:** OCIイメージのネイティブ対応とLXC内のDockerは、異なる導入経路です。
- **永続データを保護する:** ProxmoxのバックアップやComposeファイルだけでは、すべてのアプリケーションデータが保護されるとは限りません。
- **復旧計画をテストする:** 古い構成を廃止する前に、復元、再起動後の動作、サービスの可用性を測定します。

## 始める前に

**難易度:** 中級。**対象読者:** 入れ子のDockerとVM内のDockerを比較するProxmox管理者。診断例を使う前に、Composeプロジェクト、コンテナのマウント、Linuxシェルのプロンプトを認識できる必要があります。

**所要時間の目安:** インベントリと根拠の収集に30〜60分を見込みます。移行時間は、データベースのサイズ、ストレージのスループット、ハードウェアへのアクセス、選択する停止時間によって異なります。以下は文書化された手順と説明用の推論であり、この記事のために実施したラボのベンチマークではありません。

| 要件 | 重要な理由 |
|---|---|
| **ホストコンソールへのアクセス** | ネットワーク障害とホスト全体の停止を区別できます |
| **最新のバックアップ** | 構成を変更する前の復旧手段になります |
| **コンテナとVMのID** | ホスト上のコマンドを対象のワークロードに向けます |
| **アプリケーションデータの一覧** | ボリューム、バインドマウント、データベース、外部依存関係を特定します |
| **独立したテスト環境** | 本番環境で書き込み先を二重化せずに移行を試せます |

## インシデントから分かること

元の報告には、**Intel Core i3-13100とBIOSTAR H610MHPを搭載したホスト**が記載されています。所有者は、管理アクセスとLXCサービスに影響する断続的なフリーズを報告しました。接続したディスプレイは応答を停止しましたが、報告にはsyslogの出力が続いていたと明記されています。ログがまったく残らなかったとするより、具体的な状況です。[Proxmoxフォーラムの元の報告](https://forum.proxmox.com/threads/pve-host-freezes-every-2-3-weeks.185009/)

所有者は後に、**移行後に改善した**と報告しました。8月3日の追記では、DockerワークロードをDebian仮想マシンに移し、Dockerを実行するLXCを停止したと説明しています。追記時点で、その後のフリーズは報告されていません。動画は16日間の安定期間に言及しています。どちらの記述も、制御された再現試験や特定の故障部品の特定を示すものではありません。[同じスレッド内の所有者の追記](https://forum.proxmox.com/threads/pve-host-freezes-every-2-3-weeks.185009/)

| 観察事項 | 裏付けられること | 証明されないこと |
|---|---|---|
| **初期の長い稼働期間** | 以前のワークロードとソフトウェアの組み合わせが動作していた | その後のすべての更新後も信頼できること |
| **ホストとサービスが停止** | 障害が単一アプリケーションを超えている | Dockerが根本原因であること |
| **移行の後に改善** | 運用上有効な回避策 | どの相互作用の変更がきっかけを取り除いたか |
| **16日間の安定** | 限られた観察期間 | 2〜3週間ごとに起きる障害パターンが解消したこと |

**観察期間**には注意が必要です。16日は、再発間隔の14〜21日の範囲内です。以前の障害間隔を数回分、同程度のワークロード、通常のメンテナンスを含む長い観察期間であれば、確信度は高まります。それでも、制御された因果関係の証明にはなりません。

**運用上の成功と根本原因の証明**は別の結果です。家庭で信頼しているサービスを復旧することは、移行の正当な理由です。より強い根拠で仕組みが明らかになるまでは、結果を「観察された信頼性の改善」と説明します。

## カーネルの境界を把握する

```text
Docker inside LXC:
Application -> Docker runtime -> LXC namespaces and policy
            -> Proxmox host kernel -> physical hardware

Docker inside a VM:
Application -> Docker runtime -> guest Linux kernel
            -> virtual hardware / KVM-QEMU
            -> Proxmox host kernel -> physical hardware
```

**LXC**はホストのカーネルを使います。名前空間、コントロールグループ、ケーパビリティ、seccomp、セキュリティプロファイルはプロセスを制限しますが、独立したカーネルを提供しません。LXC内にDockerを加えると、同じホストカーネルを使うワークロードにコンテナ管理の層がもう一つ加わります。[LXCのアーキテクチャと隔離機能](https://linuxcontainers.org/lxc/introduction/)

**VM**にはゲストカーネルがあります。ゲストカーネルの障害は通常そのVMに影響し、Proxmoxは他のゲストの管理を続けます。VMも物理ホスト、ハイパーバイザー、ストレージ、ネットワークに依存します。ハードウェア障害やホストカーネルの欠陥は共有依存のままです。

| 境界 | LXC内のDocker | VM内のDocker |
|---|---|---|
| **アプリケーションが使うカーネル** | Proxmoxホストのカーネル | ゲストカーネル |
| **Dockerランタイム環境** | 外側のコンテナのポリシーで制限 | 一般的なゲストOS内にインストール |
| **ゲストカーネルの更新** | ホストカーネルに連動 | ゲスト内で管理 |
| **物理ホストの停止** | 依存するワークロードが停止 | 依存するワークロードが停止 |

VMは**一部の障害伝播を抑えます**が、すべてではありません。LXC内のアプリケーションプロセスがクラッシュしても、Proxmoxが自動的に停止するわけではありません。一方、すべての家庭内サービスを1台のDocker VMに入れると、同じゲストOSとメンテナンス予定に依存します。

**より広い概念上の比較**は[Dockerコンテナと仮想マシン](/articles/docker-vs-vms/)を参照してください。ここではProxmox内のDockerの配置と、それに伴うトラブルシューティングの境界を扱います。

## サポートを具体的に定義する

**「サポート対象外」**という表現には、対象のコンポーネントとバージョンが必要です。ベンダー推奨の構成、文書化された機能、ディストリビューションによる保守、契約上のサポート権を区別します。入れ子の構成が動作しても、すべての組み合わせが同程度にテストされているとは限りません。VMの推奨も、メンテナーが入れ子に関連するすべてのバグを拒否するという意味ではありません。

**Proxmoxの最新ドキュメント**では、重要な区別も示されています。コンテナツールキットのソースは、**Open Container Initiative（OCI）**アプリケーションイメージのサポートを技術プレビューとして説明し、イメージをLXCフレームワークに変換します。隔離とライブマイグレーションを重視する要件では、QEMU VM内のコンテナも推奨しています。この仕組みへのOCIイメージのインポートは、LXCゲストにDocker EngineをインストールしてComposeを実行することとは異なります。[Proxmoxコンテナツールキットのドキュメント](https://github.com/proxmox/pve-docs/blob/master/pct.adoc)

| 構成 | 確認する項目 |
|---|---|
| **従来型のLXCゲスト** | OSテンプレートとアプリケーションは、文書化されたコンテナの制限に適合するか |
| **LXC内にDockerを入れ子にする構成** | どのカーネル、ランタイム、セキュリティポリシー、ストレージの組み合わせがテスト済みか |
| **OCIイメージのネイティブインポート** | インストール済みProxmoxのバージョンは、文書化された機能と必要な動作を提供するか |
| **Debian VM内のDocker** | ゲストのリリースはDockerのインストール要件を満たすか |

Dockerは**Debian向けのインストール手順**を公開しています。ゲストOSでは、サポート対象のリリース一覧とリポジトリの手順を使ってください。古い手順が現行でも正しいと決めつけず、導入したバージョンを記録します。これは文書化されたインストール基準であり、稼働率の保証や自動的な有償サポート契約ではありません。[DebianでのDocker Engine](https://docs.docker.com/engine/install/debian/)

## 確認済みの入れ子構成の障害

**2025年のrunc/AppArmor互換性問題**は検証可能な例です。runcのメンテナーは、AppArmorプロファイルが設定された外側のコンテナ内で、ファイル記述子を再オープンする際の障害を文書化しました。AppArmorが**`/proc/sys`**へのアクセスを**`/sys`**へのアクセスと誤認し、ポリシーで拒否しました。[runc issue 4968](https://github.com/opencontainers/runc/issues/4968)

**影響を受けた起動処理**では、次のエラーが報告されました。

```text
open sysctl net.ipv4.ip_unprivileged_port_start file: reopen fd 8: permission denied
```

記録された障害は**コンテナの起動**を妨げました。フォーラムで報告されたホストのフリーズを説明するものではありません。issueには、この問題に対するProxmoxの修正として**`lxc-pve 6.0.5-2`**が記録されています。対応する上流のLXC変更は2025年11月20日にマージされました。*これらは過去の修正記録であり、現行システムでパッケージを固定する推奨ではありません。*[メンテナーによる修正の概要](https://github.com/opencontainers/runc/issues/4968)、[マージ済みのLXC変更](https://github.com/lxc/lxc/pull/4609)

教訓は**依存関係の調整**です。ランタイムのセキュリティ変更が外側のコンテナのポリシーと相互作用し、修正には別の層の変更が必要でした。AppArmorを恒久的に無効にしたり、古く脆弱なランタイムを残したりせず、使用中のリリース向けに保守された適切なパッケージ更新を適用してください。

> **要点:** このインシデントは、入れ子のコンテナに実際の互換性問題があり、メンテナーが対応したことを示しています。LXC全般の不安定さや、別のホスト停止の原因を証明するものではありません。

## 実際のコストを比較する

**実際のワークロード**を使って効率を測ります。同等の条件で、ホストのメモリ負荷、CPU需要、ストレージ遅延、アプリケーション応答時間、復旧の手間を比較します。VMに割り当てたRAM、ゲストの空きメモリ、ホストの常駐メモリは別々の測定値です。

| 主張される節約 | 収集する測定値 | 追加で記録するコスト |
|---|---|---|
| **メモリオーバーヘッドの削減** | 同じワークロードにおけるホストのメモリ使用量と負荷 | 入れ子の制限管理と競合の診断にかかる時間 |
| **導入の高速化** | データ復元後にサービスが利用可能になるまでの時間 | 更新失敗後の再構築にかかる時間 |
| **ハードウェア共有の簡素化** | 必要なデバイス、権限、アプリケーションの正常動作 | ホストドライバーへの依存と移行の制約 |
| **バックアップの簡素化** | 必要なデータをすべて正常に復元できること | 外部マウントとアプリケーションの整合性 |

Dockerでは、制限を設定しない限り、既定で**CPUとメモリを無制限に使用**します。LXCでは外側のコンテナが独自の制限を追加します。VMではゲストへの割り当てが別の容量境界になります。ゲストOS、Docker、キャッシュ、アプリケーションのピーク需要にも容量が必要です。[Dockerのリソース制限](https://docs.docker.com/engine/containers/resource_constraints/)

**ハードウェアアクセス**はワークロードの要件です。ホストのグラフィックデバイスをコンテナと共有する方法と、PCIデバイスをVMに割り当てる方法では、ドライバーや隔離の設定が異なります。選ぶ前に、対象デバイスとアプリケーションの要件を具体化してください。ハードウェアデコードを必要とするメディア処理なら、一般的なHTTPヘルスチェックに加えて、移行後にデコードが成功することを試験します。

**一律のオーバーヘッド値**を避けます。この記事では固定のRAM増加量や性能比を示しません。そうした値には、統制されたワークロード、構成、測定方法が必要です。以下の判断記録には、自分で比較した結果を記載してください。

## 層ごとに根拠を集める

管理者シェルで**Proxmoxホストから始めます**。調査対象のLXC IDに合わせて**`101`**を置き換えます。

```bash
pveversion -v
uname -r
pct config 101
journalctl --list-boots
journalctl -k -b -1 --no-pager
```

**`pveversion -v`**は、インストール済みProxmoxコンポーネントのバージョンを記録します。**`pct config`**は外側のコンテナの構成を記録します。**`journalctl`**では、**`-k`**がカーネルメッセージ、**`-b -1`**が前回の起動、**`--no-pager`**が通常の端末出力を選びます。前回起動時のメッセージには、ジャーナルデータの保存が必要です。[Proxmoxツールキット](https://github.com/proxmox/pve-docs/blob/master/pct.adoc)、[systemd journalctlリファレンス](https://github.com/systemd/systemd/blob/main/man/journalctl.xml)

**次に、デーモンを実行するLXCまたはVM内でDockerホストを調べます。**

```bash
docker version
docker info
docker compose version
docker ps -a
docker stats --no-stream
```

**両方の環境**を記録します。コンテナイメージのタグだけでは、Docker、containerd、runc、ホストカーネル、セキュリティポリシー、ストレージバックエンドの情報は分かりません。インシデントの時刻、最近の更新、ローカルホストコンソールの応答を記録します。診断情報を公開する前に、認証情報と非公開のアプリケーション情報を削除してください。

**特定のワークロードを調べる**には、コンテナ名を指定して**`app`**を置き換えます。

```bash
docker inspect --format '{{json .State}}' app
docker inspect --format '{{.RestartCount}}' app
docker inspect --format '{{json .Mounts}}' app
```

**`docker inspect`**は、指定したコンテナの状態、再起動回数、マウント情報を表示します。再起動回数はログと照合する手がかりであり、ホスト障害の証明ではありません。コンテナを再作成すると履歴も新しくなります。[docker inspectリファレンス](https://docs.docker.com/reference/cli/docker/inspect/)

## リソース負荷と停止を区別する

問題が発生している間、**ホスト上のLinuxリソース負荷情報を取得します。**

```bash
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
```

**Pressure Stall Information（PSI）**は、リソース待ちでタスクが失った時間を報告します。**`some`**と**`full`**は異なる停止条件を示し、**`avg10`**、**`avg60`**、**`avg300`**は最近の期間を要約します。メモリ負荷とメモリ使用量は別です。大きなキャッシュだけでは不足を示しません。[Linux PSIドキュメント](https://docs.kernel.org/accounting/psi.html)

| 根拠 | 有用な解釈 | 次の確認 |
|---|---|---|
| **1つのコンテナが繰り返し終了する** | アプリケーションまたはコンテナランタイムの障害 | 終了状態、サービスログ、再起動ポリシー |
| **SSHは失敗するがコンソールは動作する** | ネットワークまたは管理経路の障害 | リンク状態、NICドライバー、ブリッジ、ファイアウォール |
| **負荷中にMemory PSIが上昇する** | メモリ競合によりタスクが時間を失う | 制限、回収動作、OOM記録、ワークロードの増加 |
| **ストレージ要求が停止する** | I/O依存関係が処理を遅らせている | デバイス状態、ストレージログ、遅延、キュー |
| **Watchdogがロックアップを報告する** | カーネル検出器が定義済みの停止条件を検知した | 完全なトレース、カーネルバージョン、再現可能なトリガー |
| **最後のログがない** | 有用な出力が届く前に記録が終わった | 再発前に永続または外部の記録を設定 |

**Linuxロックアップの報告**には技術的な意味があります。カーネルのWatchdogはsoft lockupとhard lockupを区別します。ブラウザーのタイムアウトはどちらも証明しません。Watchdogの報告がないことも、ホストが正常だった証明にはなりません。[Linuxロックアップ検出のドキュメント](https://docs.kernel.org/admin-guide/lockup-watchdogs.html)

**ファームウェアや電源状態の変更**は実験です。以前の設定、変更理由、観察期間を記録してください。CPUアイドル状態を無効にすると、電力と熱の動作が変わります。別のマシンの報告だけでは、同じ設定を一律に推奨できません。

## 有用なログを保存する

**永続ジャーナリング**は、再起動後も根拠を保持できる可能性を高めます。journaldの設定ファイルには次の項目を指定します。

```ini
[Journal]
Storage=persistent
```

**`Storage=persistent`**は、利用可能な場合にジャーナルをディスクへ保存する設定です。保持期間とディスク容量を設定し、**`journalctl --list-boots`**に以前の起動が表示されることを確認します。永続ログでも、障害前にホストが書き込みを完了できることが前提です。[systemd journaldの設定](https://github.com/systemd/systemd/blob/main/man/journald.conf.xml)

**外部からの監視**は別の視点を加えます。別のマシンからサービスを監視し、時刻を記録します。障害が起きるProxmoxホスト上の監視は同じ停止中に消えるため、ダウンタイムとテレメトリー欠落を区別しにくくなります。

**説明用の試験:** 別のシステムから軽量なHTTPチェックを定期実行し、失敗とホスト到達性、ローカルコンソールの状態を比較します。ホストが応答する状態でのアプリケーションのタイムアウトと、アプリケーション、管理経路、コンソールの同時停止では、調査が異なります。これは診断設計であり、元のインシデントで観察された結果ではありません。

## 管理された移行を計画する

まず**リスクの低いComposeプロジェクトを1つ**選びます。Dockerのインストール文書にあるリリースでDebian VMを準備し、バックアップとリソース割り当てを設定します。移行先がテストに合格するまで、ロールバック用に元の構成を残します。[DockerのDebian向けインストール手順](https://docs.docker.com/engine/install/debian/)

作業ディレクトリで**Composeプロジェクトを一覧化します。**

```bash
docker compose config --quiet
docker compose config --images
docker compose config --volumes
```

**`--quiet`**は出力せずに構成を検証します。**`--images`**は参照されるイメージ、**`--volumes`**は名前付きボリュームを一覧表示します。このコマンドではアプリケーションデータはエクスポートされず、バインドマウントの完全な一覧も得られません。Composeファイルと各コンテナのマウントも確認してください。[Docker Compose configリファレンス](https://docs.docker.com/reference/cli/docker/compose/config/)

| データまたは依存関係 | 移行時の作業 |
|---|---|
| **Compose定義** | プロジェクトファイルを移し、検証済みの構成を保持する |
| **シークレットと環境設定** | 選択したシークレット管理手順で必要な値を再設定する |
| **名前付きボリューム** | アプリケーションと整合する手順で内容をバックアップし復元する |
| **バインドマウントのパス** | 元のデータを移行または再接続し、所有者を確認する |
| **データベース** | 対応するバックアップと復元、または書き込みを停止したコピー手順を使う |
| **デバイスと共有領域** | アクセスを再設定し、アプリケーションの動作をテストする |
| **ポートとDNS** | 移行先アドレスを準備し、切り替えを計画する |

**ボリューム**はコンテナより長く存続しますが、自動では移行されません。Composeファイルはリソース名とサービスを定義します。Dockerのボリューム文書には、永続データのバックアップと復元が別々に記載されています。プロジェクトを再作成するだけでデータが復元されると考えてはいけません。[Dockerボリュームのライフサイクルとバックアップ](https://docs.docker.com/engine/storage/volumes/)

**Proxmoxバックアップの対象範囲**も別に確認してください。文書上、コンテナのバックアップにはデバイスやバインドマウントの内容が含まれません。LXCのルートファイルシステムのバックアップが成功しても、内部で公開したすべてのディレクトリが保護されるとは限りません。[Proxmoxバックアップのドキュメント](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc)

### コピー前にストレージを確認する

各Dockerホストで**実際のDockerストレージ設定を確認します。**

```bash
docker info
findmnt -T /var/lib/docker
```

**`findmnt`**は指定したパスを含むファイルシステムを示します。デーモンが別のデータルートを使う場合は**`/var/lib/docker`**を置き換え、必要に応じてcontainerdのストレージパスも確認します。Dockerの文書ではcontainerdイメージストアと従来のストレージドライバーを区別し、バックエンドごとの要件を説明しています。[Dockerストレージバックエンドの選択](https://docs.docker.com/engine/storage/drivers/select-storage-driver/)

選択したバックエンドの手順に沿って、**イメージを再作成し、アプリケーションデータを復元します。**稼働中のDockerデータディレクトリを異なるストレージ構成間でコピーすると、メタデータ、マウント状態、整合性に関する追加の前提が必要です。停止したアプリケーションのデータボリュームをバックアップする操作とは異なります。

### ロールバックを用意して切り替える

1. **復元をリハーサルする:** 必要に応じて、別のアドレスとテストデータを使ってVM上で試します。
2. **本番の書き込みを停止する:** 合意した停止時間に最終的な整合性のあるバックアップを取得します。
3. **復元して検証する:** アプリケーションデータ、権限、認証情報、必要なハードウェアアクセスを確認します。
4. **サービスの経路を切り替える:** 移行先がアプリケーション固有の確認項目に合格してから行います。
5. **元の環境を停止したままにする:** その構成と復旧データは保持します。
6. **切り替え後のロールバックを文書化する:** 古いシステムを再起動する前に、切り替え後の書き込みデータの扱いを決めます。

同じデータベースストレージに対する**2つの同時書き込み元**を避けます。切り替え後に本番データが追加された場合、ロールバックではその書き込みを保持するか、意図的に破棄する計画が必要です。古いコンテナを再起動するだけでは、分岐したデータ履歴は統合されません。

## 稼働時間だけでなくテストする

**受け入れテスト**はサービスの目的に合わせます。コンテナが正常な状態でも、確認できるのはプロセスが動いていることだけです。データ、ネットワーク、依存関係、復旧動作も必要です。

| テスト | 保存する根拠 |
|---|---|
| **アプリケーションの機能** | 実際のトランザクション、クエリ、メディア処理の成功 |
| **データの完全性** | 期待されるレコード、ファイル、権限、最近の変更 |
| **ゲストの再起動** | 手作業の修復なしにサービスが復帰する |
| **バックアップからの復元** | 復元したコピーが同じ機能テストに合格する |
| **代表的な負荷** | 遅延、CPU、メモリ負荷、ストレージの動作 |
| **メンテナンスのリハーサル** | テスト済みの更新と実行可能な復旧手順 |
| **長期の観察** | 以前の障害間隔を複数回含む可用性記録 |

**判断例:** カメラサービスと実験用ダウンローダーが現在、1つの入れ子構成を共有しています。両方を1台のVMに移すとカーネルの分離は改善しますが、ゲストのメンテナンス境界は共有されたままです。カメラの可用性を優先する場合は、メンテナンスグループとリソース制限を分けることを検討し、ダウンローダーの更新中に録画が続くかテストします。

**想定される考え方:** 分離したいサービスの依存関係に合わせて配置を選びます。同じ物理サーバー上の2台のVMは、電源、ストレージ、ホストカーネルを共有します。サーバーの停止にも耐える必要があるなら、独立したシステムを追加するか、許容可能な手動の代替手順が必要です。

## 判断記録を作成する

測定した根拠を使って構成を選び、見直す時期を定めます。

```text
Service and household impact:
Current host / kernel / LXC / Docker versions:
Required GPU, device, and network access:
Measured memory, CPU, storage, and latency:
Known failure signature and recurrence interval:
Backup coverage and successful restore evidence:
Chosen deployment and reason:
Permitted outage window and recovery target:
Cutover and post-cutover data rollback procedure:
Acceptance tests and observation period:
Condition requiring another architecture review:
```

**LXC内のDockerを意図的に選ぶ**のは、その利点が統合作業に見合い、復旧経路をテスト済みの場合です。通常のDockerゲスト環境と独立したゲストカーネルでサービス運用が簡素になるならVMを選びます。どちらの判断も、バックアップ、監視、ホストの保守の代わりにはなりません。

## 移行前に変更を審査する

移行を**管理された変更**として扱い、元のインシデント原因の証明と混同しません。切り替え前に、コンテナ設定、イメージのダイジェスト、バインドマウントのパス、環境キー、デバイス割り当て、最後に成功した復元を記録します。切り替え後は同じサービス確認とリソース測定を比較します。新しい環境が受け入れ期間を通過するまで、古いワークロードは停止したままにします。

移行後にインシデントが再発した場合は、両方の配置でホストカーネル、ストレージ、メモリ負荷、デバイスアクセス、Dockerのバージョンを比較します。比較によって調査範囲を絞れます。関連する変数が制御された場合に限り、移行の成功を因果関係の実験として扱えます。
