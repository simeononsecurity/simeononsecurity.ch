**Open WebUI v0.12.4-এ এমন নিরাপত্তা সংশোধন রয়েছে, যেগুলোর বিস্তারিত রক্ষণাবেক্ষণকারীরা এখনও জানাননি।** রিলিজ নোটে দ্রুত ডিপ্লয়মেন্ট আপডেট করার পরামর্শ দেওয়া হয়েছে এবং CVE নির্ধারণের পর নিরাপত্তা পরামর্শ প্রকাশের কথা বলা হয়েছে। নিচে চ্যাট শেয়ারিং ও অনুমতি সম্পর্কে যেসব পরিবর্তনের নাম আছে, সেগুলো রিলিজ নোটে দৃশ্যমান বিষয়। এগুলো অপ্রকাশিত নিরাপত্তা সংশোধনের সম্পূর্ণ তালিকা নয়। [Open WebUI v0.12.4 রিলিজ নোট](https://github.com/open-webui/open-webui/releases/tag/v0.12.4)

<!--more-->

## মূল বিষয়

- **আগে ব্যাকআপ নিন।** অ্যাপ্লিকেশন পরিবর্তনের আগে ডেটা ভলিউম বা ডেটাবেস এবং আপলোডের পুনরুদ্ধারযোগ্য কপি রাখুন।
- **অফিশিয়াল রিলিজ নির্দিষ্ট করুন।** সাধারণ Docker ইমেজের জন্য `ghcr.io/open-webui/open-webui:v0.12.4` এবং pip-এর জন্য `open-webui==0.12.4` ব্যবহার করুন।
- **আসল ব্যবহারকারীর ভূমিকা দিয়ে অনুমতি পরীক্ষা করুন।** বোতাম লুকানো থাকলেই API-তে অনুমোদন পরীক্ষা হয়, এমন প্রমাণ হয় না।
- **অ্যাক্সেস ব্যক্তিগত রাখুন।** অ্যাপ্লিকেশনে প্রমাণীকরণ বাধ্যতামূলক করুন এবং VPN বা প্রমাণীকৃত রিভার্স প্রক্সি দিয়ে নেটওয়ার্ক অ্যাক্সেস সীমিত করুন।

## আপগ্রেডের আগে

**পূর্বশর্ত:** বর্তমান ইনস্টল পদ্ধতি, কনটেইনার ইমেজের ধরন, স্থায়ী ডেটার অবস্থান, বাহ্যিক ডেটাবেস, রিভার্স প্রক্সি এবং প্রমাণীকরণ প্রদানকারী শনাক্ত করুন। রক্ষণাবেক্ষণের সময় নির্ধারণ করুন এবং বর্তমান কনটেইনার কনফিগারেশন বা সার্ভিস সংজ্ঞা সংরক্ষণ করুন। আলাদা ইনস্ট্যান্সে পুনরুদ্ধারের মহড়ার জন্য সময় রাখুন। নিচের কমান্ডগুলো সরবরাহকারীর নথিভুক্ত পদ্ধতির নমুনা, যা এই নির্দিষ্ট সংস্করণের জন্য মানিয়ে নেওয়া হয়েছে। এই গাইডের জন্য বাস্তবে আপগ্রেড চালিয়ে এগুলো পাওয়া যায়নি। [Open WebUI আপডেট করা](https://docs.openwebui.com/getting-started/updating/)

1. **স্টোরেজের তালিকা করুন।** সাধারণ Docker সেটআপে `open-webui` `/app/backend/data`-এ মাউন্ট হয়। বাইন্ড মাউন্ট, বাহ্যিক ডেটাবেস, অবজেক্ট স্টোরেজ এবং কাস্টম পরিবেশ ভেরিয়েবল লিখে রাখুন। pip ব্যবহার করলে পরিবেশ বদলানোর আগে সক্রিয় অ্যাপ ডেটা ডিরেক্টরি এবং ডেটাবেস খুঁজে নিন। চ্যাট রপ্তানিকে পূর্ণাঙ্গ ব্যাকআপ ভাববেন না।
2. **লেখা বন্ধ রেখে ব্যাকআপ নিন।** অ্যাপ্লিকেশন বন্ধ করুন অথবা ডেটাবেসের সামঞ্জস্যপূর্ণ স্ন্যাপশট নিন। তারপর ভলিউম, বাহ্যিক ডেটাবেস এবং আপলোড আলাদা স্টোরেজে কপি করুন। সরবরাহকারী Docker ভলিউম আর্কাইভ করার পদ্ধতি নথিভুক্ত করেছে। ভলিউমের নাম এবং ব্যাকআপের পথ আপনার ডিপ্লয়মেন্ট অনুযায়ী বদলান। আর্কাইভ খোলে কি না যাচাই করুন এবং তার ওপর নির্ভর করার আগে আলাদা ইনস্ট্যান্সে পুনরুদ্ধারের মহড়া দিন। [ব্যাকআপ ও পুনরুদ্ধার](https://docs.openwebui.com/getting-started/updating/#backup--restore)
3. **রিলিজ নোট ও মাইগ্রেশন নির্দেশনা পড়ুন।** v0.12.4 নোটে অপেক্ষমাণ নিরাপত্তা সংশোধন বা প্রভাবিত সংস্করণের সীমা উল্লেখ করা হয়নি। এসব সংশোধনের জন্য CVE নির্ধারণ করবেন না এবং v0.12.4-এর আগের প্রতিটি সংস্করণ কোনো নির্দিষ্ট ত্রুটিতে আক্রান্ত, এমন ধারণা করবেন না। আপডেট গাইডে একমুখী ডেটাবেস মাইগ্রেশন এবং ভিন্ন সংস্করণের রেপ্লিকা নিয়ে সতর্ক করা হয়েছে। একাধিক worker বা replica একই ডেটাবেস ব্যবহার করলে একসঙ্গে থামান এবং [একাধিক replica-র মাইগ্রেশন পদ্ধতি](https://docs.openwebui.com/troubleshooting/multi-replica/#updates-and-migrations) অনুসরণ করুন। রোলব্যাকের জন্য আপগ্রেডের আগের ডেটাবেস ব্যাকআপ লাগতে পারে।

## ইনস্টল করা প্যাকেজ আপডেট করুন

**Docker, নির্দিষ্ট ট্যাগের জন্য মানিয়ে নেওয়া সরবরাহকারীর পদ্ধতি:** ব্যাকআপের পর অফিশিয়াল সাধারণ ইমেজ টানুন এবং একই স্থায়ী ভলিউম, কনফিগারেশন ও `WEBUI_SECRET_KEY` দিয়ে কনটেইনার পুনরায় তৈরি করুন। উদাহরণটি ডিফল্ট নামের ভলিউম এবং একই হোস্টে যুক্ত proxy upstream ধরে নেয়। আসল কী শেলের ইতিহাসে পেস্ট করবেন না। বিদ্যমান সুরক্ষিত পরিবেশ ব্যবস্থা বা secret-management পদ্ধতিতে কী সরবরাহ করুন। বর্তমান ডিপ্লয়মেন্টের GPU, Ollama, কাস্টম নেটওয়ার্ক, ডেটাবেস এবং অন্যান্য বিকল্প অক্ষুণ্ণ রাখুন। [Open WebUI আপডেট করা](https://docs.openwebui.com/getting-started/updating/) · [অফিশিয়াল ইমেজ ট্যাগ](https://docs.openwebui.com/getting-started/quick-start/)

```bash
docker pull ghcr.io/open-webui/open-webui:v0.12.4
docker rm -f open-webui
docker run -d --name open-webui --restart always \
  -p 127.0.0.1:3000:8080 \
  -v open-webui:/app/backend/data \
  --env-file ./open-webui.env \
  ghcr.io/open-webui/open-webui:v0.12.4
```

**চালানোর আগে `./open-webui.env` পরীক্ষা করুন:** ফাইলটি আগে থেকেই থাকতে হবে, সীমাবদ্ধ অনুমতি থাকতে হবে এবং তাতে বর্তমান `WEBUI_SECRET_KEY` ও দরকারি কনফিগারেশন থাকতে হবে। loopback binding একই হোস্টের proxy-র জন্য, অন্য মেশিনের proxy-র জন্য নয়। Compose ব্যবহার করলে শুধু সার্ভিসের ইমেজটি নির্দিষ্ট ট্যাগে বদলান। তারপর চলমান প্রকল্পে `docker compose pull open-webui` এবং `docker compose up -d open-webui` চালান। একই ভলিউম ও পরিবেশ কনফিগারেশন রাখুন। এগুলো প্রস্তাবিত কমান্ড, আপনার ডিপ্লয়মেন্টের পরীক্ষিত মাইগ্রেশন নয়।

**pip, নির্দিষ্ট সংস্করণের জন্য সরবরাহকারীর আপডেট পদ্ধতি:** বর্তমান ভার্চুয়াল পরিবেশে সার্ভিস বন্ধ করুন, প্যাকেজের নির্দিষ্ট সংস্করণ ইনস্টল করুন এবং একই ডেটা ডিরেক্টরি ও পরিবেশ দিয়ে পুনরায় চালু করুন। দ্বিতীয় Python পরিবেশ বা নতুন খালি ডেটাবেস তৈরি করবেন না। সরবরাহকারীর সাধারণ আপডেট নির্দেশ `pip install -U open-webui` ব্যবহার করে। নিচের সংস্করণ সীমা এই চেকলিস্টকে v0.12.4-এ নির্দিষ্ট করে। [Open WebUI আপডেট করা](https://docs.openwebui.com/getting-started/updating/) · [দ্রুত শুরু](https://docs.openwebui.com/getting-started/quick-start/)

```bash
python -m pip install --upgrade 'open-webui==0.12.4'
python -m pip show open-webui
```

**শুধু ইনস্টল করা সফটওয়্যার নয়, চলমান সার্ভিস যাচাই করুন।** `docker logs open-webui` অথবা pip সার্ভিসের লগে চালুর সময়ের সংস্করণ দেখুন এবং সাইন ইন করার পর অ্যাপ্লিকেশনে দেখানো সংস্করণের সঙ্গে তুলনা করুন। সরবরাহকারীর আপডেট গাইড কনটেইনার লগ দেখা ও লগইন পৃষ্ঠা খোলার পরামর্শ দেয়। ইন্টারফেসে পুরোনো সম্পদ দেখালে ব্রাউজার জোর করে রিফ্রেশ করুন। চালুর সময় মাইগ্রেশন ত্রুটি জানালে কারণ নির্ণয় না হওয়া পর্যন্ত সার্ভিস বন্ধ রাখুন। পুনরুদ্ধারের শর্ত না দেখে মাইগ্রেট করা ডেটাবেসে পুরোনো বাইনারি চালাবেন না। [আপডেট-পরবর্তী পরীক্ষা](https://docs.openwebui.com/getting-started/updating/)

## পুনরায় চালুর পর অ্যাক্সেস পরীক্ষা করুন

**সরবরাহকারীর বর্ণিত আচরণ:** v0.12.4-এ **Allow Chat Export** অনুমতি নেই এমন ব্যবহারকারীদের কাছ থেকে ফোল্ডার রপ্তানি, আর্কাইভ করা চ্যাট রপ্তানি এবং চ্যাট কপি করার কাজ লুকানো হয়। সংশ্লিষ্ট শেয়ারিং অনুমতি নেই এমন ব্যবহারকারীদের কাছ থেকে মডেল, prompt, tool, knowledge, skill, note এবং folder-এর অ্যাক্সেস নিয়ন্ত্রণও লুকানো হয়। শেয়ার করা ফোল্ডারের দর্শক মালিক চ্যাট আর্কাইভ করার পর লাইভ চ্যাট আপডেট পান না। শেয়ার করা লিংকের দর্শক মালিক সব চ্যাটের শেয়ার বন্ধ করার পর লাইভ আপডেট পান না। নিয়ন্ত্রণ লুকানো UI-এর আচরণ, কোনো অনির্দিষ্ট দুর্বলতার সার্ভার-পক্ষের সমাধানের প্রমাণ নয়। [রিলিজ নোট](https://github.com/open-webui/open-webui/releases/tag/v0.12.4)

**অপারেটরের জন্য প্রস্তাবিত যাচাই:** রপ্তানি ও শেয়ারিং অনুমতি নেই এমন পরীক্ষামূলক অ্যাকাউন্ট দিয়ে দেখুন নামযুক্ত কাজগুলো অনুপস্থিত কি না। অনুমতিপ্রাপ্ত অ্যাকাউন্ট দিয়ে দেখুন প্রত্যাশিত কাজগুলো এখনও চলে কি না। শেয়ার করা ফোল্ডারে সংবেদনশীল তথ্যবিহীন একটি পরীক্ষামূলক চ্যাট বানান, অন্য অ্যাকাউন্ট থেকে দেখুন, মালিক হিসেবে আর্কাইভ করুন এবং নিশ্চিত করুন যে দর্শক নতুন আপডেট পাওয়া বন্ধ করেছেন। শেয়ার করা লিংক ও **Unshare All Chats** দিয়েও পুনরাবৃত্তি করুন। সংরক্ষিত অনুমতি ও পুরোনো লিংক আবার পরীক্ষা করুন। আর্কাইভ করা বিষয়বস্তু বা আগের কপি মুছে গেছে, এমন ধরে নেবেন না।

| পর্যালোচনার ক্ষেত্র | যা যাচাই করবেন |
|---|---|
| **ভূমিকা ও গ্রুপ** | পুরোনো সদস্য ও প্রশাসক বরাদ্দ সরান। নতুন অনুমোদিত ব্যবহারকারী ও সীমাবদ্ধ ব্যবহারকারীর কার্যকর অনুমতি পরীক্ষা করুন। |
| **মডেল ও টুল** | প্রতিটি মডেলের অ্যাক্সেস অনুমতি, যুক্ত টুল, টুল তৈরির অধিকার এবং প্রদানকারীর পরিচয়পত্র দেখুন। প্রশাসক নয় এমন অ্যাকাউন্টে পরীক্ষা করুন। |
| **জ্ঞান ও ফাইল** | জ্ঞানভান্ডারের সহযোগী, রিসোর্স অনুমতি, সংযুক্তি এবং শেয়ারিং সেটিং দেখুন। যার অ্যাক্সেস প্রত্যাহার করা হয়েছে সেই অ্যাকাউন্ট পরীক্ষা করুন। |
| **চ্যাট ও রপ্তানি** | শেয়ার করা ফোল্ডার, লিংক, আর্কাইভ করা চ্যাট এবং Allow Chat Export বরাদ্দ পর্যালোচনা করুন। অপ্রয়োজনীয় লিংক বাতিল করুন। |

এই ইনভেন্টরি পরীক্ষা **অপারেটরের সুপারিশ**, v0.12.4-এর নতুন নিশ্চয়তা নয়। সরবরাহকারীর [হার্ডেনিং নির্দেশিকা](https://docs.openwebui.com/getting-started/advanced-topics/hardening/) স্তরভিত্তিক ভূমিকা, গ্রুপ, প্রতি-রিসোর্স অনুমতি, ওয়ার্কস্পেস অনুমতি, API কী এবং নেটওয়ার্কে অবস্থান ব্যাখ্যা করে।

## অ্যাকাউন্ট ও নেটওয়ার্কের ঘাটতি পূরণ করুন

- **নিবন্ধন, সরবরাহকারীর সেটিং:** প্রশাসক বা পরিচয় প্রদানকারী অ্যাকাউন্ট তৈরি করলে উন্মুক্ত নিবন্ধন বন্ধ করুন। [হার্ডেনিং নির্দেশিকা](https://docs.openwebui.com/getting-started/advanced-topics/hardening/) ধরে `ENABLE_SIGNUP` এবং স্থায়ী অ্যাডমিন সেটিং পরীক্ষা করুন। নতুন অ্যাকাউন্ট অনুমোদনে কঠোর নিয়ম রাখুন।
- **API কী, অপারেটরের পর্যালোচনা:** জারি করা কী-এর তালিকা করুন, অব্যবহৃত কী মুছুন এবং কী তৈরি ও endpoint অ্যাক্সেসকে প্রয়োজনীয় ভূমিকা ও পথের মধ্যে সীমিত করুন। সরবরাহকারীর নির্দেশিকা অনুযায়ী, একটি কী তার নির্মাতার অনুমতিতে কাজ করে। নিবন্ধের উদাহরণ ও অ্যাপ্লিকেশন লগে কী রাখবেন না।
- **অ্যাডমিন, অপারেটরের পর্যালোচনা:** পরিত্যক্ত অ্যাডমিন অ্যাকাউন্ট সরান, শক্তিশালী সাইন-ইন নিয়ন্ত্রণ বাধ্যতামূলক করুন, MFA পাওয়া যায় কি না দেখুন এবং অপ্রত্যাশিত অ্যাকাউন্ট পরিবর্তন তদন্ত করুন। অতিরিক্ত অ্যাডমিন বন্ধ করার আগে অ্যাকাউন্ট পুনরুদ্ধার পদ্ধতি পরীক্ষা করুন।
- **নেটওয়ার্ক সীমা, সরবরাহকারীর নির্দেশনা:** সার্ভিসকে VPN, অ্যাক্সেস প্রক্সি বা প্রমাণীকরণ ও IP অনুমোদন তালিকাযুক্ত রিভার্স প্রক্সির পেছনে রাখুন। প্রমাণীকরণ ছাড়া প্রকাশ্যে দেবেন না। নেটওয়ার্কে পৌঁছানো যায় এমন সার্ভিসে `WEBUI_AUTH=False` এড়িয়ে চলুন। নিজস্ব প্রমাণীকরণহীন রিভার্স প্রক্সি অ্যাপ্লিকেশন সাইন-ইনের বিকল্প নয়। [Open WebUI সুরক্ষিত করুন](https://docs.openwebui.com/getting-started/advanced-topics/hardening/)

**পরিধি:** এই চেকলিস্ট অফিসিয়াল Open WebUI রিলিজ এবং নথিভুক্ত সাধারণ ইনস্টল পদ্ধতির জন্য। এটি fork, derivative image বা তৃতীয় পক্ষের প্যাকেজ যাচাই করে না। v0.12.4 নোটে সক্রিয় শোষণের দাবি নেই। পরবর্তী প্রকাশ এবং তাদের নিজস্ব প্রভাবিত ও সংশোধিত সংস্করণ জানতে [প্রকল্পের নিরাপত্তা পরামর্শ](https://github.com/open-webui/open-webui/security/advisories) দেখুন। আগের কোনো পরামর্শের সংশোধন v0.12.4-কে দেবেন না, যদি না তার সংস্করণসীমা পড়েন।
