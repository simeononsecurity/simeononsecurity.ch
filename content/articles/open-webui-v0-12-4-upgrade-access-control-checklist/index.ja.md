**Open WebUI v0.12.4 には、メンテナーがまだ詳細を列挙していないセキュリティ修正が含まれています。**リリースノートは早急な更新を推奨し、CVE の割り当て後にアドバイザリーを公開するとしています。以下で名前を挙げるチャット共有と権限の変更は、リリースノートで確認できる項目です。未公開のセキュリティ修正をすべて示すものではありません。[Open WebUI v0.12.4 リリースノート](https://github.com/open-webui/open-webui/releases/tag/v0.12.4)

<!--more-->

## 要点

- **最初にバックアップします。**アプリケーションを変更する前に、データボリュームまたはデータベースとアップロードの復元可能なコピーを保管します。
- **公式リリースのバージョンを固定します。**標準 Docker イメージには `ghcr.io/open-webui/open-webui:v0.12.4`、pip には `open-webui==0.12.4` を使用します。
- **実際のユーザーロールで権限をテストします。**ボタンが非表示でも、API 側で認可チェックが行われている証明にはなりません。
- **アクセスを非公開に保ちます。**アプリケーション認証を必須にし、VPN または認証済みリバースプロキシでネットワークアクセスを制限します。

## アップグレード前

**前提条件：**現在のインストール方法、コンテナーイメージの種類、永続データの保存場所、外部データベース、リバースプロキシ、認証プロバイダーを特定します。停止時間を計画し、現在のコンテナー設定またはサービス定義を保存します。別のインスタンスで復元をリハーサルする時間も確保します。以下のコマンドは、ベンダーが文書化した手順例を、この固定バージョン向けに調整したものです。このガイド用に実際のアップグレードを実施した結果ではありません。[Open WebUI の更新](https://docs.openwebui.com/getting-started/updating/)

1. **ストレージを一覧にします。**標準 Docker 設定では、`open-webui` は `/app/backend/data` にマウントされます。バインドマウント、外部データベース、オブジェクトストレージ、カスタム環境変数を記録します。pip では、環境を変更する前にアクティブなアプリケーションデータディレクトリとデータベースを特定します。チャットのエクスポートが完全なバックアップだと考えないでください。
2. **書き込みを停止してからバックアップします。**アプリケーションを停止するか、整合性のあるデータベーススナップショットを使います。その後、ボリューム、外部データベース、アップロードを別のストレージにコピーします。ベンダーは Docker ボリュームのアーカイブ方法を説明しています。ボリューム名とバックアップ先は、実際のデプロイに合わせてください。アーカイブを開けることを確認し、別インスタンスで復元を試してから信頼します。[バックアップと復元](https://docs.openwebui.com/getting-started/updating/#backup--restore)
3. **リリースノートと移行ガイダンスを読みます。**v0.12.4 のノートには保留中のセキュリティ修正一覧も対象バージョン範囲もありません。これらの修正に CVE を割り当てたり、v0.12.4 より前のすべてのバージョンが特定の欠陥の影響を受けると推測したりしないでください。更新ガイドは、一方向のデータベース移行と、異なるバージョンのレプリカ混在に注意を促しています。複数のワーカーまたはレプリカがデータベースを共有する場合、同時に停止し、[複数レプリカの移行手順](https://docs.openwebui.com/troubleshooting/multi-replica/#updates-and-migrations)に従います。ロールバックにはアップグレード前のデータベースバックアップが必要になる場合があります。

## インストール済みパッケージを更新する

**Docker、固定タグ向けに調整したベンダー手順：**バックアップ後、公式標準イメージを取得し、同じ永続ボリューム、設定、`WEBUI_SECRET_KEY` を使ってコンテナーを作り直します。この例は、既定の名前付きボリュームと、同じホストにバインドされたプロキシの上流を想定しています。実際のキーをシェル履歴に貼り付けないでください。既存の保護された環境設定またはシークレット管理機構で渡します。現在のデプロイの GPU、Ollama、カスタムネットワーク、データベースなどの設定を維持します。[Open WebUI の更新](https://docs.openwebui.com/getting-started/updating/) · [公式イメージタグ](https://docs.openwebui.com/getting-started/quick-start/)

```bash
docker pull ghcr.io/open-webui/open-webui:v0.12.4
docker rm -f open-webui
docker run -d --name open-webui --restart always \
  -p 127.0.0.1:3000:8080 \
  -v open-webui:/app/backend/data \
  --env-file ./open-webui.env \
  ghcr.io/open-webui/open-webui:v0.12.4
```

**実行前に `./open-webui.env` を確認します。**ファイルがすでに存在し、アクセス権が制限され、既存の `WEBUI_SECRET_KEY` と必要な設定が含まれている必要があります。ループバックへのバインドは同じホスト上のプロキシ向けで、別マシンのプロキシ向けではありません。Compose ではサービスイメージだけを固定タグに変更し、既存プロジェクト内で `docker compose pull open-webui` と `docker compose up -d open-webui` を実行します。同じボリュームと環境設定を維持します。これは推奨コマンドであり、あなたのデプロイで検証済みの移行手順ではありません。

**pip、固定バージョンを使うベンダー手順：**既存の仮想環境でサービスを停止し、指定バージョンのパッケージをインストールして、同じデータディレクトリと環境で再起動します。2つ目の Python 環境や空のデータベースを作らないでください。ベンダーの一般的な更新方法は `pip install -U open-webui` です。次のバージョン指定により、このチェックリストは v0.12.4 に固定されます。[Open WebUI の更新](https://docs.openwebui.com/getting-started/updating/) · [クイックスタート](https://docs.openwebui.com/getting-started/quick-start/)

```bash
python -m pip install --upgrade 'open-webui==0.12.4'
python -m pip show open-webui
```

**インストール済みの成果物だけでなく、稼働中のサービスを確認します。**`docker logs open-webui` または pip サービスのログで起動時のバージョンを確認し、ログイン後にアプリケーションが表示するバージョンと比べます。ベンダーの更新ガイドは、コンテナーのログ確認とログインページの読み込みを推奨しています。画面に古いリソースが表示されたら、ブラウザーを強制更新します。起動時に移行エラーが出たら、原因を診断するまでサービスを利用不可のままにします。復元要件を確認せず、移行済みデータベースに古いバイナリーを戻さないでください。[更新後の確認](https://docs.openwebui.com/getting-started/updating/)

## 再起動後にアクセスを確認する

**ベンダーが説明する動作：**v0.12.4 では、**Allow Chat Export** の権限がないユーザーに対して、フォルダーのエクスポート、アーカイブ済みチャットのエクスポート、チャットのコピーが非表示になります。また、対応する共有権限を持たないユーザーには、モデル、プロンプト、ツール、ナレッジ、スキル、ノート、フォルダーのアクセス制御も表示されません。共有フォルダーの閲覧者は、所有者がチャットをアーカイブすると、そのチャットのライブ更新を受け取らなくなります。共有リンクの閲覧者も、所有者がすべてのチャットの共有を解除すると、ライブ更新を受け取らなくなります。コントロールが非表示になるのは UI の動作であり、特定されていない脆弱性がサーバー側で修正された証拠ではありません。[リリースノート](https://github.com/open-webui/open-webui/releases/tag/v0.12.4)

**推奨する運用者の確認：**エクスポート権限と共有権限がないテストアカウントで、該当する操作が表示されないことを確認します。許可されたアカウントで、必要な操作が引き続き動くことを確認します。共有フォルダーに機密情報のないテストチャットを作成し、別のアカウントから表示し、所有者としてアーカイブして、閲覧者に新しい更新が届かなくなることを確かめます。共有リンクと **Unshare All Chats** でも繰り返します。保存済みの権限付与と古いリンクを再確認します。アーカイブ済みの内容や過去のコピーが削除されたと考えないでください。

| 確認領域 | 確認する内容 |
|---|---|
| **ロールとグループ** | 古いメンバーと管理者の割り当てを削除します。新たに承認したユーザーと制限対象ユーザーの実効権限を確認します。 |
| **モデルとツール** | 各モデルのアクセス権、関連付けられたツール、ツール作成権限、プロバイダー認証情報を確認します。非管理者アカウントでテストします。 |
| **ナレッジとファイル** | ナレッジベースの共同作業者、リソース権限、添付ファイル、共有設定を確認します。アクセスを取り消したアカウントも確認します。 |
| **チャットとエクスポート** | 共有フォルダー、共有リンク、アーカイブ済みチャット、Allow Chat Export の割り当てを確認します。不要なリンクを取り消します。 |

これらの棚卸しは**運用者への推奨事項**であり、v0.12.4 が新たに保証する内容ではありません。ベンダーの[ハードニングガイド](https://docs.openwebui.com/getting-started/advanced-topics/hardening/)では、階層的なロール、グループ、リソース単位の権限、ワークスペース権限、API キー、ネットワーク上の配置について説明しています。

## アカウントとネットワークの不足を解消する

- **サインアップ、ベンダー設定：**管理者または ID プロバイダーがアカウントを作成する場合は、オープンサインアップを無効にします。[ハードニングガイド](https://docs.openwebui.com/getting-started/advanced-topics/hardening/)を参照し、`ENABLE_SIGNUP` と永続化された管理者設定を確認します。新規アカウントの承認ルールを厳しく保ちます。
- **API キー、運用者の確認：**発行済みキーを一覧にし、未使用のキーを削除して、キーの作成とエンドポイントへのアクセスを必要なロールおよびルートに制限します。ベンダーのガイドによると、キーは作成者の権限で動作します。記事の例やアプリケーションログにキーを含めないでください。
- **管理者、運用者の確認：**使われていない管理者アカウントを削除し、強いログイン制御を適用し、MFA の利用可否を確認し、予期しないアカウント変更を調査します。冗長な管理者を無効にする前に、アカウント復旧手順をテストします。
- **ネットワーク境界、ベンダーの指針：**認証と IP 許可リストを備えた VPN、アクセスプロキシ、またはリバースプロキシの背後にサービスを置きます。認証なしで公開しないでください。到達可能なサービスで `WEBUI_AUTH=False` を使わないでください。独自の認証を持たないリバースプロキシだけでは、アプリケーションへのログインの代わりになりません。[Open WebUI の保護](https://docs.openwebui.com/getting-started/advanced-topics/hardening/)

**対象範囲：**このチェックリストの対象は、公式 Open WebUI リリースと文書化された標準インストール方法です。フォーク、派生イメージ、サードパーティーパッケージは検証しません。v0.12.4 のノートは、脆弱性の悪用が進行中とは述べていません。後続の公表情報と、それぞれの影響バージョンおよび修正バージョンについては、[プロジェクトのセキュリティアドバイザリー](https://github.com/open-webui/open-webui/security/advisories)を確認してください。以前のアドバイザリーの修正を v0.12.4 に帰属させる前に、そのバージョン範囲を読んでください。
