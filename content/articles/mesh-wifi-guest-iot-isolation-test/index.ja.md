Wi-Fi名を分けても、どの機器同士が通信できるかは分かりません。メッシュシステムでは、**ゲストネットワーク**、**IoTネットワーク**、**無線クライアント分離**が別々の制御として扱われる場合があります。このガイドでは、メーカーのラベルが実際のポリシーを示すと決めつけず、自分の機器で通信経路をテストします。

<!--more-->

## 要点

- **先に接続先が動作することを確認する:** 遮断経路を試す前に、メインネットワークから既知のサービスへ接続します。
- **境界ごとにテストする:** ゲストからメイン、IoTからメイン、ゲスト同士のアクセスは、それぞれ別の問いに答えます。
- **構成を記録する:** モデル、ファームウェア、ルーターモードかアクセスポイントモードか、接続先のメッシュノードが結果の解釈に影響します。
- **変更後に再テストする:** 結果が有効なのは、テストした機器、サービス、アドレスファミリー、構成の範囲です。

## 始める前に

約20分を見込んでください。メイン、ゲスト、IoTの各Wi-Fiに接続できるノートPCが必要です。また、NASのWeb画面など、**開いていることが分かっているTCPサービス**をメインネットワーク上の信頼できる機器で稼働させます。TCPサービスとは、NASのWebページで使うポート443のような番号付きポートで待ち受けるネットワークサービスです。自分が所有または管理するサービスを使います。ローカルアドレスとポートを控え、公開しないでください。テスト中はサービスを稼働させておきます。

メッシュのモデル、ファームウェアのバージョン、動作モード、ゲストアクセス、IoTアクセス、共有デバイス、クライアント分離の設定を記録します。Wi-Fiを切り替えるたびに、ノートPCの接続先名を確認します。通常のポリシーで許される場合は、このローカル経路のテスト中にVPNまたはプロキシを切断し、終了後に戻します。VPNはテスト対象の経路を変えます。

> **警告:** 自分の機器、または管理許可を得た機器だけをテストしてください。ルーターのログイン画面はメインネットワーク上のホストの代わりになりません。ゲートウェイへのアクセスには別のルールが適用されます。

**ローカルエリアネットワーク（LAN）**は自宅のプライベートネットワークです。**IoT**（モノのインターネット）には、カメラ、スピーカー、スマートプラグなどが含まれます。**クライアント分離**は、同じWi-Fi上の機器同士の直接通信を遮断します。

## 境界を決める

設定を変える前に、求める結果を決めます。インターネットアクセスとローカルアクセスは別の結果です。

| 経路 | 確認すること | 期待する結果の例 |
|---|---|---|
| **ゲストからメインLAN** | PCやNASへ到達できるか | 例外を設定していなければ遮断 |
| **IoTからメインLAN** | プライベート機器へ到達できるか | 製品とポリシーによる |
| **ゲスト同士** | 2台のゲスト機器が通信できるか | クライアント分離設定による |
| **ゲストから共有機器** | 共有プリンターやディスプレイを使えるか | 意図した場合のみ許可 |
| **ゲストからインターネット** | 通常の公開サイトへアクセスできるか | ゲストポリシーに含まれる場合は許可 |

これらは別々のテストです。TP-Linkの[Decoデバイス分離ガイド](https://www.tp-link.com/us/support/faq/3968/)によると、分離された機器はインターネットや他の分離機器との通信を維持しますが、メインネットワークの機器にはアクセスできません。ASUSの[AP分離ガイド](https://www.asus.com/us/support/faq/1044821/)は無線ピア間の制御を説明し、上流の有線ルーターを通る経路は対象外としています。**1つの経路が遮断されても、ほかの境界まで機能している証拠にはなりません。**

## メッシュ設定を確認する

テストする境界を制御する機能を探します。メニュー名と利用可否はモデルやファームウェアによって異なります。

| メッシュ設定 | 確認内容 |
|---|---|
| **TP-Link Decoのゲストネットワーク** | [ルーターモードではゲストをメインから分離します](https://www.tp-link.com/us/support/faq/1460/)。アクセスポイントモードでは **Allow Local Access** を確認します。 |
| **ASUSのゲストプロファイル** | 対応プロファイルでは [Access Intranet](https://www.asus.com/uk/support/faq/1009857/) がメインネットワークへのアクセスを制御します。 |
| **Google NestのゲストWi-Fi** | プリンターやディスプレイを隠す想定なら、先に[共有デバイス](https://support.google.com/googlehome/answer/6327302?hl=en)の一覧を確認します。 |
| **IoTネットワークまたはデバイス分離** | 製品に個別の分離設定があるか確認します。IoT用Wi-Fi名だけではアクセスルールは決まりません。 |

Decoの[デバイス分離](https://www.tp-link.com/us/support/faq/3968/)には、メインユニットとサテライトの対応が必要です。テスト用ノートPCを接続しているノードを記録します。機能が見つからない場合は、他の所有者のアプリ画面と同じだと考えず、正確なモデルとファームウェアの文書を確認します。

## 正常系の確認を行う

Windowsのテスト用ノートPCを**メインWi-Fi**に接続します。選んだサービスがこのノートPCから動作することを確認します。PowerShellを使う場合は、プロンプトが表示されたらメインネットワーク上のホストのアドレスと既知の開放TCPポートを入力します。

```powershell
$targetAddress = Read-Host "Main-network test host address"
$targetPort = [int](Read-Host "Known open TCP port")
Test-NetConnection -ComputerName $targetAddress -Port $targetPort
```

Microsoftの[Test-NetConnectionの説明](https://learn.microsoft.com/powershell/module/nettcpip/test-netconnection)では、`-ComputerName`と`-Port`は特定のホストとTCPサービスを指定する引数です。`TcpTestSucceeded`を記録します。まずここで`True`を確認します。その後に出た`False`を解釈してください。メインネットワークのテストが失敗した場合は、サービス、アドレス、ホストファイアウォール、ノートPCの設定を確認します。まずメインネットワークのテストを直します。

スマートフォンや別のOSを使う場合は、同じ既知のサービスをブラウザーまたはアプリで開きます。Wi-Fiを切り替えても、同じサービスと接続先アドレスを使います。機器の検出一覧は強い証拠になりません。検出トラフィックと直接のTCPアクセスでは経路が異なります。

## ゲストとIoTのアクセスをテストする

同じノートPCを**ゲストWi-Fi**に接続します。Wi-Fi名を確認し、ゲストポリシーにインターネットアクセスが含まれる場合は公開サイトを開きます。同じ`Test-NetConnection`コマンドを再実行します。`$targetAddress`と`$targetPort`は変更しません。結果を記録します。

メインネットワークへ戻り、サービスが引き続き`True`を返すことを確認します。メインネットワークのテストが失敗した場合、ゲストの失敗は判断材料になりません。次に、システムがノートPCの接続を許可する場合は同じ端末を**IoT Wi-Fi**につなぎ、テストを繰り返します。IoTの結果がゲストと同じだと決めつけないでください。IoTからメインへの接続に成功した場合、この構成では選んだローカルTCPサービスへIoTネットワークから到達できたことを示します。

ゲスト同士の分離を確認する場合は、ゲストネットワーク上で自分が管理する2台の機器を使います。一方から、もう一方の既知のサービスをテストします。ゲストからメインへのアクセスとは別に記録します。共有プリンターやディスプレイを使える想定なら、その例外もテストします。スマート機器をクラウド経由で操作できても、直接のローカル経路がある証拠にはなりません。

各メッシュノードの近くで、ゲストからメインへのテストを繰り返します。アプリが接続ノードを表示する場合は確認します。**IPv6**は128ビットのアドレスを使う新しいインターネットプロトコルのアドレスファミリーです。メインホストがIPv6に対応し、正常系の確認がIPv6で成功する場合は、ゲストとIoTのWi-Fiからも同じアドレスファミリーでテストします。IPv4だけのテストではIPv6経路を確認できません。

## 結果の食い違いを解釈する

| 観察結果 | 次の確認 |
|---|---|
| **メインとゲストの両方で失敗** | 接続先サービス、アドレス、ポート、ホストファイアウォールを確認します。分離は証明されていません。 |
| **メインとゲストの両方で成功** | ゲストのローカルアクセス、共有機器の例外、ルーターモードとアクセスポイントモードを確認します。 |
| **メインは成功、ゲストは失敗** | この接続先とTCP経路の結果を記録します。ポリシーで必要なほかの経路もテストします。 |
| **ゲストは遮断、IoTは成功** | IoTのSSIDが、対応する分離ルールのない互換用ネットワークではないか確認します。 |
| **ゲストからメインは遮断、ゲスト同士は成功** | 無線クライアント分離を別に確認します。 |

**ping**が失敗してもTCPの結果は分かりません。ホストファイアウォールがpingを遮断しながら、選んだサービスを許可する場合があります。TCPテストが失敗しても範囲は限定的です。他のポート、機器、IPv6、共有機器の例外については分かりません。結果の食い違いがあれば、設定したルールを確認し、条件をそろえて再テストします。

## 修正して結果を記録する

一度に変更する制御は1つにします。アクセスポイントモードのDecoでは **Allow Local Access** を確認します。ASUSのゲストプロファイルでは **Access Intranet** を確認します。Google Nest Wifiでは意図しない項目を **Shared devices** から削除します。スマートホームのローカル制御が必要なら、例外を追加する前に、どの機器がどのサービスへ接続する必要があるか決めます。**VLAN**は共有ハードウェア上に構成する論理ネットワークです。一般向けメッシュに必要なアクセスルールがない場合は、サイトの[VLANセグメント化計画](/articles/homelab-vlan-segmentation-plan/)を参照してください。

メッシュのモデル、ファームウェア、動作モード、ノード、Wi-Fi名、送信元機器、接続先サービス、アドレスファミリー、期待結果、実際の結果、変更した設定1つを記録します。プライベートアドレスやネットワークパスワードは公開しないでください。ファームウェア更新、ノード変更、ルーターモードとアクセスポイントモードの切り替え後に、同じテストを繰り返します。

機器を選んでいる段階なら、[メッシュWi-Fi購入ガイド](/articles/best-wifi-mesh-system-for-consumers/)で機能を比較します。その後、この手順で設置したネットワークを確認します。**ラベルやアプリの切り替え項目は仕様の主張です。正常系の確認と条件をそろえた再テストにより、必要な経路の証拠を得られます。**

## 次のステップ

ファームウェア、ノード、動作モードを変更した後に分離テストを繰り返します。メッシュの制御で必要な境界を実現できない場合は、[VLANセグメント化計画](/articles/homelab-vlan-segmentation-plan/)を確認してください。
