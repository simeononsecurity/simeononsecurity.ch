仮想プライベートネットワーク（VPN）の接続アイコンだけでは、ブラウザーのすべてのリクエストが同じ経路を通るとは限りません。**パブリックIP**、**ドメインネームシステム（DNS）リゾルバー**、**WebRTCアドレス**を個別にテストしてください。それぞれの結果は異なる問いに答えます。このガイドでは、再現可能な確認手順と予期しない結果の調査方法を説明します。

<!--more-->

## 要点

- **2つの状態を比較する:** VPN接続の前後で同じテストを記録します。
- **結果を個別に読む:** パブリックIPが変わっても、DNSクエリの送信先は分かりません。
- **WebRTC候補を確認する:** 想定した経路の外にあるパブリックアドレスを探します。プライベートアドレスは別の意味を持ちます。
- **設定は一度に1つ変更する:** VPN、ブラウザー、DNSの設定を変えるたびに再テストします。

## 始める前に

保護したいブラウザーとネットワーク接続を使います。VPNがデバイス全体を対象にするのか、選択したアプリだけを対象にするのか確認します。VPNがスプリットトンネルを使う場合は、テストするブラウザーがトンネル内にあるか記録してください。比較できるように、VPNクライアントのDNSポリシーも確認します。

**スプリットトンネル**では、選択したアプリをVPN経由で送り、ほかのアプリは通常のネットワークを使います。

この手順では、[BrowserLeaks IP](https://browserleaks.com/ip)、[DNS](https://browserleaks.com/dns)、[WebRTC](https://browserleaks.com/webrtc)のページを使います。アクセス時にサービスへ接続元アドレスが伝わります。テストの説明によると、DNSテストはブラウザーに50個のランダムな名前を解決させます。管理対象または制限付きネットワークでは、許可なく外部テストを実行しないでください。テストサイトに認証情報、内部ホスト名、非公開の閲覧記録を入力しないでください。

> **注意:** 正確なIPアドレスを公開スクリーンショットやサポート投稿に載せないでください。アドレスが想定したISPまたはVPN経路と一致するか記録します。実際の値は承認済みのサポート窓口だけで共有してください。

## 各テストで分かること

| 確認項目 | 比較する内容 | 結果からは分からないこと |
|---|---|---|
| **パブリックIP** | 通常のウェブサイトに見えるアドレス | DNSを処理したリゾルバー |
| **DNSリゾルバー** | 新しい名前解決で観測されたサーバー | 各アプリがDNSを送る先 |
| **WebRTC** | ローカルとパブリックの接続候補 | 後の通話で使われる候補 |

パブリックIPのページは、ウェブリクエストに使われたアドレスを報告します。DNSページは新しい名前解決を実行し、処理したリゾルバーを示します。WebRTC（Web Real-Time Communication）は、ブラウザーアプリがピア接続を確立するための技術です。WebRTCページは、接続時に公開されるアドレスを調べます。**ICE候補**は、ピア接続に使える可能性があるネットワークアドレスです。**VPN出口**は、VPNを出た後の通信に使われるパブリックアドレスです。[RFC 8828](https://datatracker.ietf.org/doc/html/rfc8828)では、特にスプリットトンネルやプロキシを使う場合に、WebRTC候補に通常のウェブリクエストとは異なるアドレスが含まれる理由を説明しています。

VPN事業者のDNSサーバー、VPN内で別に選択したリゾルバー、ブラウザーで選んだ暗号化リゾルバーは、テスト結果に異なる名前を表示します。リゾルバー名だけで漏えいとは判断できません。意図したポリシーと照らし合わせてください。

## 基準値を記録する

トンネルを使わない基準値を取得できる場合に限り、VPNを切断します。通常のブラウザープロファイルで3つのテストページを開きます。DNSテストを実行し、結果を待ちます。正確なアドレスを公開せずに、次の項目を記録します。

| 項目 | 基準メモ |
|---|---|
| **ブラウザーとバージョン** | 名前、バージョン、関連するプライバシー拡張機能 |
| **ネットワーク** | 自宅Wi-Fi、モバイルホットスポット、または承認済みの別のネットワーク |
| **パブリックIPv4とIPv6** | それぞれが通常の接続に属するか |
| **DNS結果** | 表示されたリゾルバー名または運営者 |
| **WebRTC結果** | 表示されたパブリック、プライベート、`.local`候補 |

VPNを切断できない場合は、想定したVPN経路から始め、トンネルなしの基準値は取得不可と記録します。位置ラベルや地図から通常のISPアドレスを推測しないでください。位置データベースが実際のネットワーク事業者と異なることがあります。

## VPN接続後にテストを繰り返す

VPNに接続し、クライアントがトンネルの動作を示していることを確認します。**同じブラウザープロファイル**で各テストページを再読み込みします。新しい名前解決を行うため、DNSテストも再実行します。サービスが表示する場合はIPv4とIPv6の両方を記録します。

次の順に結果を比較します。

1. **パブリックIP:** ウェブリクエストには、VPN出口または意図して設定した経路に一致するアドレスが表示されるはずです。ブラウザーがトンネル内にある想定なのに通常のISPアドレスが表示された場合、ルーティングに問題があります。
2. **DNS:** 表示された各リゾルバーをVPNとブラウザーのDNS設定と比較します。想定したトンネル外のISPリゾルバーは調査してください。ブラウザーで第三者のリゾルバーを意図して選択した場合、その名前が表示されるのは想定どおりです。
3. **WebRTC:** パブリックWebRTC候補をVPN出口および基準値のパブリックIPと比較します。ブラウザーのすべての通信をVPN経由にする想定なのに、通常のISPアドレスがWebRTCだけに現れる場合は調査が必要です。
4. **プライベートアドレス:** [RFC 1918のプライベート範囲](https://www.rfc-editor.org/rfc/rfc1918)内のアドレスや`.local`候補は、ISPのパブリックアドレスとは異なります。ローカル情報を記録し、サイトに知らせる必要があるか判断します。

[WebRTC IP処理標準](https://datatracker.ietf.org/doc/html/rfc8828)では、ICE候補の検出によりアプリが別のパブリックまたはプライベートアドレスを知る仕組みを説明しています。Chromiumの[mDNSホスト候補の設計](https://groups.google.com/a/chromium.org/g/blink-dev/c/z5hSy6Rf_aE/m/aGND030cAgAJ)は、一部のプライベートアドレスを`.local`名に置き換えます。JavaScript、API、テストサーバーが動作しなかった場合、WebRTCの空欄結果は**判断不能**です。空欄だけでは保護が完全だと証明できません。

> **想定する結果:** ブラウザーの通常のウェブリクエストとパブリックWebRTC候補が選択した経路を使います。DNS結果は記録したVPNまたはブラウザーのリゾルバーポリシーと一致します。

## DNSの不一致を調べる

まずブラウザーが独自のリゾルバーを選んでいないか確認します。[FirefoxのDNS over HTTPS設定](https://support.mozilla.org/en-US/kb/dns-over-https)には有効状態と保護レベルが表示されます。標準保護は状況によってシステムリゾルバーに切り替わり、ネットワークの通知を考慮します。強化保護とカスタム保護は、選択したプロバイダーとバックアップ動作を使います。最大保護は安全な名前解決に失敗した場合に警告します。トグルだけでなく、状態と例外リストを確認してください。

[ChromeのセキュアDNSガイド](https://support.google.com/chrome/answer/10468685?co=GENIE.Platform%3DDesktop&hl=en)では、自動モードとカスタムプロバイダーを説明しています。安全な名前解決に失敗すると、自動モードは暗号化されていない問い合わせに切り替わります。カスタムプロバイダーは、既定で非暗号化モードに切り替わりません。管理対象デバイスや保護者による使用制限でこの設定が制限されることがあります。管理ポリシーを変更する前に、現在のブラウザー画面を確認してください。

ブラウザーのリゾルバーが原因でなければ、VPNクライアントのDNS設定、スプリットトンネルのアプリ一覧、OSのリゾルバー、IPv6経路を比較します。1項目だけ変更し、DNSテストを繰り返します。ブラウザーのDNSテストで分かるのは、そのブラウザーの名前解決経路です。ほかのアプリの名前解決方法は分かりません。ネットワークで[DNSフィルタリング](/articles/nextdns-vs-adguard-ad-blocker-comparison/)を使っている場合は、意図してブロックするドメインと許可するドメインを1つずつテストします。広告が表示されないことをリゾルバー経路の証拠とみなさないでください。

## WebRTCの不一致を調べる

ブラウザーがVPNトンネルの対象外になっていないか、想定経路の外にあるプロキシを使っていないか確認します。経路を修正して再テストします。曖昧な結果が1つ出ただけで、最初にIPv6やWebRTCを無効にしないでください。[WebRTC標準](https://datatracker.ietf.org/doc/html/rfc8828)は、アドレスの露出と直接通話の性能のトレードオフを説明しています。候補の制限やプロキシの強制は、ビデオ通話やほかのピア接続に影響します。

ブラウザーまたはVPNにWebRTC IP処理の説明付き設定がある場合は、現在の説明を読み、通話の使い方に合ったポリシーを選びます。パブリック候補を再テストしてください。ローカルアドレスだけではISPのパブリックアドレスがVPN外へ出たとは判断できません。VPNのHTTPアドレスと異なるISPのパブリックアドレスが表示されれば、より強い兆候です。

## テスト記録を残す

| 項目 | 記録する結果 |
|---|---|
| **日付とブラウザー** | バージョン、プロファイル、拡張機能、ネットワーク |
| **想定経路** | デバイス全体のVPN、スプリットトンネル、ブラウザープロキシ |
| **前後の結果** | パブリックIPの事業者、DNS事業者、パブリックWebRTC候補 |
| **不一致** | 想定したポリシーと異なった結果 |
| **変更した設定** | 変更内容と理由 |
| **再テスト** | 新しい結果と残る不確実性 |

ブラウザー、VPN、ネットワークの設定を変更した後は、再度テストします。問題のない結果が当てはまるのは、テストしたブラウザー、プロファイル、ネットワーク、時点だけです。匿名性を証明したり、すべてのアプリを対象にしたりするものではありません。ブラウザーを選んでいる段階なら、まず[プライバシーブラウザーの比較](/articles/best-privacy-browsers-librewolf-brave-firefox-tor/)で機能を確認し、自分の環境でこのテストを行ってください。
