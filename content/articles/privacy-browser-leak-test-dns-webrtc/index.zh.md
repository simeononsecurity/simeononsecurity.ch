虚拟专用网络（VPN）的连接图标无法证明浏览器的每个请求都经过同一路径。请分别测试你的**公网 IP**、**域名系统（DNS）解析器**和**WebRTC 地址**。每项结果回答的问题都不同。本指南提供可重复的检查方法，并说明如何调查异常结果。

<!--more-->

## 要点

- **比较两种状态：**记录连接 VPN 前后的相同测试结果。
- **分别解读结果：**公网 IP 发生变化，并不能说明 DNS 查询发往何处。
- **检查 WebRTC 候选地址：**留意不属于预期路径的公网地址。私有地址代表不同情况。
- **每次只改一项设置：**每次调整 VPN、浏览器或 DNS 后重新测试。

## 开始之前

使用你打算保护的浏览器和网络连接。确认 VPN 应覆盖整个设备，还是只覆盖选定的应用。如果 VPN 使用分流，请记录测试浏览器是否经过隧道。准备好 VPN 客户端的 DNS 策略以便对照。

**VPN 分流**会让部分应用经过 VPN，其他应用使用普通网络。

本流程使用 [BrowserLeaks IP](https://browserleaks.com/ip)、[DNS](https://browserleaks.com/dns) 和 [WebRTC](https://browserleaks.com/webrtc) 页面。访问时，该服务会看到你的连接地址。根据测试说明，DNS 测试会要求浏览器解析 50 个随机名称。未经批准，不要在受管理或受限的网络上运行外部测试。不要在测试网站输入凭据、内部主机名或私人浏览记录。

> **警告：**不要在公开截图或支持帖子中暴露准确的 IP 地址。记录地址是否符合预期的 ISP 或 VPN 路径。仅通过获批的支持渠道分享实际值。

## 每项测试展示什么

| 检查项 | 比较内容 | 结果无法证明的内容 |
|---|---|---|
| **公网 IP** | 普通网站看到的地址 | 哪个解析器处理了 DNS |
| **DNS 解析器** | 新名称查询过程中观察到的服务器 | 每个应用把 DNS 发往何处 |
| **WebRTC** | 本地和公网连接候选地址 | 后续通话会使用哪个候选地址 |

公网 IP 页面会报告其 Web 请求使用的地址。DNS 页面会发起新的查询，并报告处理这些查询的解析器。WebRTC 是 Web Real-Time Communication 的简称，它让浏览器应用建立对等连接。WebRTC 页面会检查这些连接暴露的地址。**ICE 候选地址**是对等连接可能使用的网络地址。**VPN 出口**是流量离开 VPN 后使用的公网地址。[RFC 8828](https://datatracker.ietf.org/doc/html/rfc8828) 说明了为什么 WebRTC 连接候选地址有时会包含普通 Web 请求未显示的地址，尤其是在分流或使用代理时。

VPN 提供商的 DNS 服务器、在 VPN 内另行选择的解析器，或浏览器选定的加密解析器，都会在测试中显示不同名称。仅凭解析器名称无法判断是否泄漏。请将名称与预期策略对照。

## 记录基准状态

只有在当前情况允许未经过隧道的基准测试时，才断开 VPN。在普通浏览器配置文件中打开三个测试页面。运行 DNS 测试并等待结果。不要公开准确地址，记录以下内容：

| 字段 | 基准记录 |
|---|---|
| **浏览器和版本** | 名称、版本及相关隐私扩展 |
| **网络** | 家用 Wi-Fi、移动热点或其他获批网络 |
| **公网 IPv4 和 IPv6** | 每个地址是否属于普通连接 |
| **DNS 结果** | 显示的解析器名称或运营方 |
| **WebRTC 结果** | 显示的公网、私有或 `.local` 候选地址 |

如果无法断开 VPN，请从预期的 VPN 路径开始，并将未经过隧道的基准状态标记为不可用。不要根据位置标签或地图推断普通 ISP 地址。位置数据库有时与实际网络运营方不一致。

## 连接 VPN 后重复测试

连接 VPN，并确认客户端显示隧道正常。使用**同一个浏览器配置文件**重新加载每个测试页面。再次运行 DNS 测试以产生新的查询。如果服务显示 IPv4 和 IPv6 结果，请分别记录。

按以下顺序比较结果：

1. **公网 IP：**Web 请求显示的地址应符合 VPN 出口或你主动配置的路径。如果浏览器本应处于隧道内，却显示普通 ISP 地址，则存在路由问题。
2. **DNS：**将显示的每个解析器与 VPN 和浏览器的 DNS 设置对照。如果预期隧道之外出现 ISP 解析器，应进一步调查。如果你主动在浏览器中选择了第三方解析器，显示其名称属于预期情况。
3. **WebRTC：**将公网 WebRTC 候选地址与 VPN 出口和基准公网 IP 对照。如果浏览器的所有流量都应经过 VPN，但普通 ISP 地址只出现在 WebRTC 中，应当调查。
4. **私有地址：**[RFC 1918 私有地址范围](https://www.rfc-editor.org/rfc/rfc1918)中的地址或 `.local` 候选地址不同于 ISP 公网地址。记录本地条目，并判断网站是否应得知该地址。

[WebRTC IP 处理标准](https://datatracker.ietf.org/doc/html/rfc8828)说明应用如何通过 ICE 候选地址发现其他公网或私有地址。Chromium 的 [mDNS 主机候选地址设计](https://groups.google.com/a/chromium.org/g/blink-dev/c/z5hSy6Rf_aE/m/aGND030cAgAJ)会用 `.local` 名称替代部分私有地址。如果 JavaScript、API 或测试服务器没有正常工作，空白的 WebRTC 结果就是**无法确定**。空白结果不能证明已获得全面保护。

> **预期结果：**浏览器的普通 Web 请求和公网 WebRTC 候选地址都经过所选路径。DNS 结果符合你记录的 VPN 或浏览器解析器策略。

## 调查 DNS 不匹配

首先检查浏览器是否自行选择了解析器。[Firefox 的 DNS over HTTPS 设置](https://support.mozilla.org/en-US/kb/dns-over-https)会显示启用状态和保护级别。默认保护在某些情况下会回退到系统解析器，并遵循网络信号。增强和自定义保护会使用选定提供商，并采用备用行为。最大保护会在安全解析失败时发出警告。状态和例外列表比单个开关更重要。

[Chrome 安全 DNS 指南](https://support.google.com/chrome/answer/10468685?co=GENIE.Platform%3DDesktop&hl=en)介绍了自动模式和自定义提供商。安全查询失败时，自动模式会回退到未加密查询。自定义提供商默认不会改用未加密模式。受管理设备和家长控制会限制此设置。更改受管理策略前，请先检查浏览器当前界面。

如果原因不是浏览器解析器，请比较 VPN 客户端的 DNS 设置、分流应用列表、操作系统解析器和 IPv6 路由。每次只改一项，然后重复 DNS 测试。浏览器 DNS 测试测量的是该浏览器的查询路径，无法说明其他应用如何解析名称。如果网络使用 [DNS 过滤](/articles/nextdns-vs-adguard-ad-blocker-comparison/)，请分别测试一个主动拦截的域名和一个允许的域名。广告没有显示不能证明解析器的路由方式。

## 调查 WebRTC 不匹配

检查浏览器是否被排除在 VPN 隧道外，或是否使用了预期路径之外的代理。修正路径后重新测试。不要因为一个含糊的结果就首先禁用 IPv6 或 WebRTC。[WebRTC 标准](https://datatracker.ietf.org/doc/html/rfc8828)介绍了地址暴露与直接通话性能之间的取舍。限制候选地址或强制使用代理会影响视频通话和其他对等连接。

如果浏览器或 VPN 提供了有文档说明的 WebRTC IP 处理控制项，请阅读当前说明，并根据你的通话需求选择策略。重新测试公网候选地址。仅出现本地地址不能证明 ISP 公网地址离开了 VPN。若 VPN HTTP 地址不同，同时出现了 ISP 公网地址，这是更有力的信号。

## 保存测试记录

| 字段 | 记录内容 |
|---|---|
| **日期和浏览器** | 版本、配置文件、扩展和网络 |
| **预期路径** | 整台设备使用 VPN、分流或浏览器代理 |
| **前后对比** | 公网 IP 运营方、DNS 运营方和公网 WebRTC 候选地址 |
| **不匹配项** | 哪项结果与预期策略不符 |
| **单项改动** | 修改的设置及原因 |
| **复测** | 新结果和仍存在的不确定性 |

更改浏览器、VPN 或网络配置后，重新运行检查。一次正常结果仅适用于受测的浏览器、配置文件、网络和时间点。它不能证明匿名性，也不涵盖所有应用。如果你还在选择浏览器，可先查看网站的[隐私浏览器对比](/articles/best-privacy-browsers-librewolf-brave-firefox-tor/)，了解功能，然后在自己的配置中运行本测试。
