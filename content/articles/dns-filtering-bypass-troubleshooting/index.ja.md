フィルタリング用リゾルバを設定したのに、ポリシーでブロックしているドメインへ端末がアクセスできています。原因はルール、端末へのDomain Name System（DNS）の割り当て、ブラウザの暗号化リゾルバ、またはVPNかもしれません。**設定を変更する前に経路を確認してください。**フィルタへの直接クエリと端末の通常クエリでは、確認できる内容が異なります。

<!--more-->

## 要点

- **最初にルールを確認:** フィルタが安全なテストドメインを受け取り、ブロックすることを確認します。
- **各レイヤーを追跡:** ルーター、OS、ブラウザ、VPN、モバイル設定がDNS経路に影響します。
- **新しいクエリを使う:** 新しいホスト名と時刻をフィルタのクエリログと照合します。
- **確認の限界を示す:** 1件のクエリから確認できるのは1つの経路です。すべてのアプリや端末の動作を証明するものではありません。

## 始める前に

約20分を見込んでください。フィルタリング用リゾルバのクエリログ、問題がある端末1台、ルーターのDNS設定記録が必要です。例ではWindowsノートPCと**Pi-hole**を使いますが、クライアントごとのクエリログを提供するリゾルバなら同じ比較ができます。まずフィルタの正確なアドレスを確認してください。公開レポートにプライベートなクライアントアドレス、クエリログ、ポリシールールを掲載しないでください。

ポリシーですでにブロックされている**安全なテストドメイン**を選びます。または、テストプロファイルで自分が管理するドメインに対し、一時的に完全一致の拒否ルールを追加します。ルールを記録し、テスト後に削除してください。実際に稼働しているマルウェアドメインを調査用に使わないでください。ブロックページは有用な症状ですが、リゾルバのログのほうが経路を示す強い証拠になります。

| レイヤー | 確認する内容 |
|---|---|
| **フィルタ** | 直接クエリが想定したリゾルバに届き、ルールに一致しますか。 |
| **端末** | ネットワークが割り当てたDNSサーバーはどれですか。 |
| **ブラウザまたはアプリ** | 端末のリゾルバを使いますか、それとも別経路を使いますか。 |
| **VPNまたはリレー** | 接続中のトンネルがクエリ先を変えますか。 |

## フィルタの動作を確認する

リゾルバのクエリログを開きます。選択したブロック対象ドメインをフィルタへ直接問い合わせます。WindowsではPowerShellを使い、入力を求められたらフィルタのアドレスとテストドメインを入力します。

```powershell
$filterAddress = Read-Host "Filtering DNS server address"
$testDomain = Read-Host "Harmless domain blocked by your test rule"
Resolve-DnsName -Name $testDomain -Server $filterAddress -Type A -DnsOnly
```

Microsoftの[**`Resolve-DnsName`**リファレンス](https://learn.microsoft.com/en-us/powershell/module/dnsclient/resolve-dnsname)では、**`-Server`**を指定したリゾルバへの問い合わせとして説明しています。フィルタログでクエリを探し、応答と一致したルールを確認します。Pi-holeの[クエリとログのドキュメント](https://docs.pi-hole.net/main/pihole-command/)にはローカルクエリツールの説明があります。直接クエリが許可された場合は、回避を調べる前にルールまたはクライアントグループの割り当てを修正します。フィルタに届かない場合は、アドレス、サービス、ネットワーク経路を確認します。

**この直接テストでは、ノートPCが通常フィルタを使っているとは証明できません。** **`-Server`**オプションは、このクエリに限って既定のリゾルバを上書きします。この違いを理解しておけば、よくある誤判定を防げます。

## 端末の経路を追跡する

以前のDNSキャッシュを避けるため、新しいホスト名を使います。次の例では、フィルタへ直接送るクエリと、ノートPCが通常のリゾルバ選択で送るクエリを1件ずつ実行します。名前を分けているため、ログの各項目がどちらの経路か分かります。**NXDOMAIN**応答は、DNSサーバーがホスト名は存在しないと返したことを意味します。ランダムな名前が使われていなければ正常です。ここではクエリがフィルタログに現れるかが重要です。

```powershell
$stamp = [guid]::NewGuid().ToString("N")
Resolve-DnsName -Name "direct-${stamp}.example.com" -Server $filterAddress -Type A -DnsOnly
Resolve-DnsName -Name "default-${stamp}.example.com" -Type A -DnsOnly
```

フィルタログで2つの名前を正確に検索し、時刻と記録されたクライアントを控えます。**`direct-`**は記録され、**`default-`**が記録されない場合は、ノートPCに割り当てられたDNSサーバーを確認します。Windowsの**`Get-DnsClientServerAddress`**はインターフェイス別にDNSサーバーアドレスを表示します。切断中のアダプターではなく、使用中のWi-FiまたはEthernetアダプターを確認してください。[MicrosoftのDNSクライアントリファレンス](https://learn.microsoft.com/en-us/powershell/module/dnsclient/get-dnsclientserveraddress)では、この読み取り専用コマンドを説明しています。

最初のテストではエラーを表示したままにします。エラーやタイムアウトは別途診断が必要で、ログ項目がない場合と同じではありません。

```powershell
Get-DnsClientServerAddress | Select-Object InterfaceAlias, AddressFamily, ServerAddresses
```

IPv4とIPv6の行を比較します。**DHCP**はDNSサーバーなどのネットワーク設定を割り当てます。**IPv6**は128ビットのアドレスを使う新しいInternet Protocolアドレスファミリーです。IPv4リースにはフィルタが設定されていても、IPv6ルーター広告が別のDNSサーバーを渡す場合があります。ルーターの**DHCP**と**IPv6 DNS**広告を確認し、修正後に端末のネットワークリースを更新します。Pi-holeの[インストール後ガイド](https://docs.pi-hole.net/main/post-install/)では、DHCPからPi-holeをクライアントへ指定する方法を説明しています。[ルーターの例](https://docs.pi-hole.net/routers/fritzbox/)ではIPv6 DNS広告を扱っています。

ログに**ルーター**がクライアントとして記録されている場合、ルーターが端末に代わってクエリを転送している可能性があります。その場合、フィルタログが示すのはルーターからフィルタへの到達であり、どの端末がクエリを開始したかではありません。クライアント識別情報が欠けていると判断する前に、ルーターの転送方式を確認します。

## ブラウザDNSを確認する

コマンドラインのクエリは端末のリゾルバ経路をテストします。ブラウザは代わりに**DNS over HTTPS（DoH）**を使う場合があります。ブロック対象のテストドメインをブラウザで開き、フィルタログに対応するクエリがあるか確認します。キャッシュ済みの結果が比較を妨げる場合は、ブラウザのDNSキャッシュを消去するか、テストルール対象の新しいホスト名を使います。

パソコン版**Chrome**では、**設定 > プライバシーとセキュリティ > セキュリティ > セキュア DNS を使用する**を開きます。[Google Chromeヘルプ](https://support.google.com/chrome/answer/10468685?co=GENIE.Platform%3DDesktop&hl=en)によると、自動モードは現在のプロバイダを使い、失敗時には暗号化されていない検索へフォールバックします。カスタムプロバイダを選んだ場合は同じようにはフォールバックしません。設定を変える前に選択中のモードとプロバイダを記録します。

**Firefox**では、**設定 > プライバシーとセキュリティ > DNS over HTTPS**を開きます。[Mozillaの保護レベルガイド](https://support.mozilla.org/en-US/kb/dns-over-https)では、既定、強化、最大、カスタム、オフの各モードを区別しています。[DoHの概要](https://support.mozilla.org/en-US/kb/firefox-dns-over-https)では、ブラウザリゾルバがローカルDNSフィルタを迂回する場合を説明しています。設定を1つだけ変更して再テストし、その後、希望するプライバシー設定に戻します。

**ブラウザのクエリが見つからないたびに回避と断定しないでください。**ブラウザがキャッシュ済みデータを再利用した、既知のアドレスへ接続した、またはプロキシを使った可能性があります。クエリの行き先を結論づける前に、新しい名前、対応する時間帯、ブラウザのリゾルバ設定を比較してください。

## モバイルとVPNの経路を確認する

**Android**では、**設定 > ネットワークとインターネット > プライベートDNS**を確認します。プロバイダのホスト名を指定すると、ルーターが通知するDNSとは別のプライベートDNSサービスを選択します。[GoogleのAndroidネットワーク設定](https://support.google.com/android/answer/9654714?hl=en)では、オフ、自動、プロバイダのホスト名の各選択肢を説明しています。ローカルでの結果を制御するには、Wi-Fi接続中にモバイルデータを無効にしてテストし、その後通常の設定へ戻します。

**Apple製デバイス**では、そのネットワークで**iCloud Private Relay**が有効か、Safariが想定した経路を使っているかを確認します。Appleは[Private RelayがSafariのブラウズとDNS情報を保護する](https://support.apple.com/en-gb/102602)と説明しています。[ネットワーク制御](https://support.apple.com/en-ie/102022)では、フィルタリングがPrivate Relayと競合する場合のネットワーク別の処理を説明しています。Safariの結果を端末上のすべてのアプリに一般化しないでください。

**VPN**は独自のDNSリゾルバを提供するか、クエリをトンネル経由で送信する場合があります。VPNの接続状態、DNS設定、スプリットトンネルポリシーを記録します。セキュリティポリシーで許可される場合に限り、VPNのオンとオフで同じテストを比較します。結果が変われば経路の違いが分かります。それだけで情報漏えいやフィルタ障害が証明されるわけではありません。

## 結果を読み取る

| 証拠 | 次に確認する内容 |
|---|---|
| **直接クエリがフィルタログにない** | フィルタアドレス、DNSサービス、ログ記録、ネットワーク到達性 |
| **直接クエリが許可された** | 完全一致の拒否ルール、グループポリシー、ルールの優先順位 |
| **直接クエリは記録され、通常クエリは記録されない** | DHCP、端末の静的DNS、IPv6 DNS、VPNリゾルバ |
| **通常クエリは記録され、ブラウザは記録されない** | ブラウザDoH、ブラウザキャッシュ、プロキシ、リレー |
| **両方記録されブロックされたのにサイトが開く** | 別のホスト名、キャッシュ済みコンテンツ、直接アドレス、アプリ経路 |

**ログがない場合は複数の解釈があります。**ログ記録が無効、ルーターがクライアントの代理で転送、テストが保存済みデータを再利用した、といった可能性があります。ファイアウォールルールを変更する前に、新しいホスト名で再試験し、クエリ時刻を確認してください。外部リゾルバへの平文DNSをブロックしても、暗号化ブラウザやVPNがフィルタを使うよう強制できません。Pi-holeの[OPNsenseガイド](https://docs.pi-hole.net/routers/opnsense/)では、外部DNSブロックを任意のネットワーク制御として紹介しています。端末ポリシーとブラウザ設定は引き続き別の制御です。

## 修正して再テストする

一度に1つのレイヤーだけ変更します。DHCPまたはIPv6 DNS広告を修正し、意図しない静的リゾルバを削除し、ブラウザで意図したDNSプロバイダを選択するか、VPNのDNSポリシーを調整します。1件のテスト失敗を解決するために、すべての端末の暗号化DNSやリレー保護を黙って弱めないでください。送信元端末、インターフェイス、フィルタアドレス、クエリ名、時刻、応答、ログ上のクライアント、ブラウザモード、VPN状態、変更内容を記録します。

変更のたびに**直接、通常、ブラウザ**の各テストを再実行します。毎回新しいホスト名を使います。端末に複数のネットワークプロファイルがあれば、個別にテストします。[DNSリゾルバ比較](/articles/dns-comparison-adguard-quad9-cloudflare-pi-hole/)はサービス選択に役立ちます。[ブラウザリークテスト](/articles/privacy-browser-leak-test-dns-webrtc/)は別の問い、つまりブラウザとVPNの構成からどのネットワーク情報が出るかに答えます。**信頼できるフィルタ結果には、検証済みのルールと検証済みのクライアント経路が必要です。**

## 次のステップ

管理された変更を行うたびに、直接、通常、ブラウザの各テストを繰り返してください。フィルタリングサービスを選ぶ際は、[DNSリゾルバ比較](/articles/dns-comparison-adguard-quad9-cloudflare-pi-hole/)を確認します。
