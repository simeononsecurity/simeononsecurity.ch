[AI ਸਹਿਯੋਗ ਕੋਰਸ ਵੱਲ ਵਾਪਸ ਜਾਓ](/ai-collaboration-course-start/)

**ਗੈਰ-ਕੋਡਿੰਗ ਯੋਗਦਾਨਕਰਤਾ ਬ੍ਰਾਊਜ਼ਰ ਰਾਹੀਂ ਵੀ ਸਰੋਤ-ਅਧਿਕਾਰ ਦੇ ਉਹੀ ਨਿਯਮ ਮੰਨਦੇ ਹਨ।** ਤੁਸੀਂ GitHub ਸਰੋਤ ਪੜ੍ਹਦੇ ਹੋ, ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਚੈਟ ਟੂਲ ਨਾਲ ਮਸੌਦਾ ਤਿਆਰ ਕਰਦੇ ਹੋ ਅਤੇ Issue ਜਾਂ ਬ੍ਰਾਂਚ ਸੋਧ ਭੇਜਦੇ ਹੋ। ਰਖ-ਰਖਾਅ ਕਰਤਾ ਜਾਂਚਾਂ ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਸਮੀਖਿਆ ਤੋਂ ਬਾਅਦ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਇਹ ਵਰਕਫਲੋ ਰਿਪੋਜ਼ਟਰੀ ਸੁਰੱਖਿਆ ਚਾਲੂ ਹੋਣ ਤੋਂ ਬਾਅਦ ਵਰਤੋ, ਤਾਂ ਜੋ ਬ੍ਰਾਊਜ਼ਰ ਪਹੁੰਚ ਕੋਡਿੰਗ ਏਜੰਟ ਦੇ ਨਿਯੰਤਰਣਾਂ ਨੂੰ ਪਾਰ ਨਾ ਕਰੇ।

## ਮੁੱਖ ਗੱਲਾਂ

- **ਬ੍ਰਾਊਜ਼ਰ ਰਾਹੀਂ ਕੰਮ** ਕਰਨ ਲਈ ਲੋਕਲ ਟਰਮੀਨਲ ਦੀ ਲੋੜ ਨਹੀਂ।
- **ਸੰਦਰਭ ਪੈਕੇਟ** ਦਾਇਰਾ ਅਤੇ ਸੋਧ ਦੇ ਸਬੂਤ ਸੰਭਾਲਦੇ ਹਨ।
- **Issues ਅਤੇ ਬ੍ਰਾਂਚਾਂ** ਪ੍ਰਸਤਾਵ ਹੀ ਰਹਿੰਦੇ ਹਨ।
- **ਹਵਾਲਗੀਆਂ** ਬਾਕੀ ਕੰਮ ਅਤੇ ਅਗਲੀ ਭੂਮਿਕਾ ਦੱਸਦੀਆਂ ਹਨ।

## ਸ਼ੁਰੂ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ

**ਪੂਰਵ-ਲੋੜਾਂ:** [ਰਿਪੋਜ਼ਟਰੀ ਹੱਦਾਂ ਵਾਲਾ ਪਾਠ](/articles/ai-collaboration-github-repository/), ਲੈਬ ਲਈ ਪੜ੍ਹਨ ਦੀ ਪਹੁੰਚ ਅਤੇ ਚਾਹੋ ਤਾਂ ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਚੈਟ ਟੂਲ। **ਅੰਦਾਜ਼ਨ ਸਮਾਂ:** 45 ਤੋਂ 60 ਮਿੰਟ। **ਮੁਸ਼ਕਲ:** ਸ਼ੁਰੂਆਤੀ। ਸਿਰਫ਼ Issue ਬਣਾਉਣ ਵਾਲੇ ਯੋਗਦਾਨਕਰਤਾ ਲੋਕਲ Git ਅਤੇ Actions ਛੱਡ ਸਕਦੇ ਹਨ। PR ਭੇਜਣ ਵਾਲੇ ਯੋਗਦਾਨਕਰਤਾ ਉਸ ਰਖ-ਰਖਾਅ ਕਰਤਾ ਨਾਲ ਤਾਲਮੇਲ ਕਰਦੇ ਹਨ ਜਿਸ ਨੇ [ਏਜੰਟ ਅਤੇ Actions ਪਾਠ](/articles/ai-collaboration-github-agents-actions/) ਪੂਰਾ ਕੀਤਾ ਹੋਵੇ।

**ਕਨੈਕਟਰ ਤੋਂ ਬਿਨਾਂ ਬੁਨਿਆਦੀ ਤਰੀਕਾ:** GitHub ਖੁਦ ਖੋਲ੍ਹੋ ਅਤੇ ਸਿਰਫ਼ ਕਾਲਪਨਿਕ ਉਦਾਹਰਨਾਂ ਵਾਲੇ ਅੰਸ਼ ਦਿਓ। ਕਿਸੇ ਭੁਗਤਾਨੀ ਚੈਟ ਵਿਸ਼ੇਸ਼ਤਾ ਦੀ ਧਾਰਨਾ ਨਹੀਂ ਕੀਤੀ ਗਈ। ਜੇ ਕੋਈ ਪ੍ਰਦਾਤਾ ਮਨਜ਼ੂਰ ਨਹੀਂ, ਤਾਂ ਉਹੀ ਰਿਕਾਰਡ ਵਰਤ ਕੇ ਹੱਥੀਂ ਮਸੌਦਾ ਬਣਾਓ।

**ਪੂਰਾ ਹੋਣ ਦਾ ਨਤੀਜਾ:** ਤੁਸੀਂ ਇੱਕ Issue ਜਾਂ PR ਹਵਾਲੇ ਕਰਦੇ ਹੋ ਜਿਸ ਵਿੱਚ ਨਿਰਧਾਰਤ ਸਰੋਤ ਵਰਜਨ, ਪ੍ਰਸਤਾਵਿਤ ਲਿਖਤ, ਪ੍ਰਭਾਵਿਤ ਫਾਈਲਾਂ, ਬਾਹਰ ਰੱਖੀਆਂ ਚੀਜ਼ਾਂ ਅਤੇ ਅਣਸੁਲਝੇ ਸਵਾਲ ਹੋਣ।

## ਸਰੋਤ ਪੈਕੇਟ ਪੜ੍ਹੋ

1. **`main` ਉੱਤੇ MAP-01 ਖੋਲ੍ਹੋ**, ਫਿਰ POL-01, REQ-17 ਅਤੇ RUN-04 ਲੱਭੋ।
2. **ਹਰ ਸਰੋਤ ਪੜ੍ਹੋ** ਅਤੇ ਬ੍ਰਾਊਜ਼ਰ ਦੇ commit ਦ੍ਰਿਸ਼ ਰਾਹੀਂ ਉਸਦਾ ਵਰਜਨ commit ID ਰਾਹੀਂ ਦਰਜ ਕਰੋ।
3. **ਸੰਬੰਧਤ ਕਾਲਪਨਿਕ ਭਾਗ ਕਾਪੀ ਕਰੋ** ਅਤੇ ਫਾਈਲ ਨਾਂ, ਵਰਜਨ, ਦਾਇਰਾ ਅਤੇ ਅਪਵਾਦ ਲਿਖੋ।
4. **ਪੈਕੇਟ ਨੂੰ snapshot-ਅਧਾਰਿਤ ਚਿੰਨ੍ਹਿਤ ਕਰੋ** ਜਦ ਤੱਕ ਰਖ-ਰਖਾਅ ਕਰਤਾ ਪ੍ਰਕਾਸ਼ਨ ਤੋਂ ਪਹਿਲਾਂ ਇਸਦੀ ਸਰੋਤਾਂ ਦੇ ਮੌਜੂਦਾ ਵਰਜਨਾਂ ਨਾਲ ਤੁਲਨਾ ਨਾ ਕਰੇ।

```text
ਪ੍ਰੋਜੈਕਟ: export-service-lab
ਕੰਮ: PROP-042 draft, no publication permission
ਅਧਿਕਾਰ: requirement.json, REQ-17 revision 1
ਆਧਾਰ ਮੁੱਲ: retention_days 7
ਨੀਤੀ: POL-01 version 1
ਮੰਗਿਆ ਪ੍ਰਸਤਾਵ: retention_days 30
ਸਬੂਤ: attach browser-verified commit references
ਗੁੰਮ ਸਬੂਤ: no runtime deletion observations
ਨਤੀਜਾ: proposed wording, affected files, questions, rollback
ਰੁਕੋ: source unavailable, changed revision, conflicting authority
```

**ਅਸਲ sandbox ਵਰਜਨ ਨਿੱਜੀ ਤੌਰ 'ਤੇ ਜੋੜੋ।** ਇਸ ਨਮੂਨੇ ਵਿੱਚ ਪੂਰੇ ਕੀਤੇ ਸਬੂਤ ਨਹੀਂ ਹਨ। ਪ੍ਰਕਾਸ਼ਨ ਦੀ ਸਿਫ਼ਾਰਸ਼ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਸਹਾਇਕ ਨੂੰ ਗੁੰਮ ਰਿਕਾਰਡ ਦੱਸਣ ਲਈ ਕਹੋ।

**ਲਾਈਵ ਸਰੋਤ ਪੜ੍ਹਨ ਤੋਂ ਪਹਿਲਾਂ ਭਰਿਆ ਕਾਲਪਨਿਕ ਪੈਕੇਟ:**

```text
ਪ੍ਰੋਜੈਕਟ: export-service-lab
ਕੰਮ: draft PROP-042 in an Issue
ਮਨਜ਼ੂਰ ਆਧਾਰ ਮੁੱਲ: REQ-17 revision 1, retention_days 7
ਪ੍ਰਸਤਾਵ: retention_days 30, synthetic export files only
ਪ੍ਰਭਾਵਿਤ ਰਿਕਾਰਡ: requirement.json, config.json, proposal.json, runbook.md
ਛੋਟਾਂ: ਉਤਪਾਦਨ ਡਾਟਾ, ਬੈਕਅੱਪ ਅਤੇ ਕਾਨੂੰਨੀ ਰੋਕਾਂ
ਜਾਣੇ ਸਬੂਤ: supplied lab baseline files
ਗੁੰਮ ਸਬੂਤ: current main commit, owner decisions, runtime deletion result
ਸਥਿਤੀ: Draft, publication blocked until current revisions and reviews exist
ਅਗਲੀ ਭੂਮਿਕਾ: maintainer supplies verified main commit and runs checks
```

**ਇਹ ਪੈਕੇਟ ਮਸੌਦਾ ਬੇਨਤੀ ਵਜੋਂ ਪੂਰਾ ਹੈ।** ਗੁੰਮ ਸਬੂਤ ਵਾਲੀ ਲਾਈਨ ਜਾਣਬੁੱਝ ਕੇ ਹੈ। ਪ੍ਰਕਾਸ਼ਨ ਮੰਗਣ ਤੋਂ ਪਹਿਲਾਂ ਦਿੱਤੇ ਲੈਬ ਆਧਾਰ ਨੂੰ sandbox ਦੀਆਂ ਮੌਜੂਦਾ ਵਰਜਨਾਂ ਨਾਲ ਬਦਲੋ।

## Issue ਖੋਲ੍ਹੋ

**Issues, New issue ਚੁਣੋ** ਅਤੇ ਸਿਰਲੇਖ **`PROP-042: propose thirty-day synthetic retention`** ਵਰਤੋ। ਇਹ ਵੇਰਵਾ ਪੇਸਟ ਕਰੋ ਅਤੇ ਸਰੋਤ ਪੈਕੇਟ ਜੋੜੋ।

```text
ਪ੍ਰਸਤਾਵ: PROP-042
ਸਥਿਤੀ: Draft
ਮੌਜੂਦਾ ਮਨਜ਼ੂਰ ਮੁੱਲ: 7 days, REQ-17 revision 1
ਮੰਗਿਆ ਮੁੱਲ: 30 days
ਕਾਰਨ: fictional pilot requirement, not compliance advice
ਦਾਇਰਾ: synthetic export records only
ਪ੍ਰਭਾਵਿਤ ਫ਼ਾਈਲਾਂ: requirement.json, config.json, runbook.md
ਸਬੂਤ: source revisions and policy version attached
ਸਮੀਖਿਆਕਾਰ: product-owner and operations-owner
ਲਾਗੂਕਰਨ ਸਮੀਖਿਆਕਾਰ: repository-maintainer
ਸਵੀਕਾਰਤਾ: consistent records, denied publication, fresh handoff
ਵਾਪਸੀ: reviewed restoration of the approved baseline
```

**ਚੈਟ ਨੂੰ ਪ੍ਰਸਤਾਵ ਅਤੇ ਪੈਕੇਟ ਦੀ ਤੁਲਨਾ ਕਰਨ ਲਈ ਕਹੋ**, ਧਾਰਨਾਵਾਂ ਦੀ ਸੂਚੀ ਬਣਾਉਣ ਅਤੇ ਮਾਲਕਾਂ ਲਈ ਸਵਾਲ ਤਿਆਰ ਕਰਨ ਲਈ ਕਹੋ। ਮਸੌਦਾ Issue ਵਿੱਚ ਸੰਭਾਲੋ। ਚੈਟ ਤੋਂ ਤਬਦੀਲੀ ਮਨਜ਼ੂਰ ਕਰਨ ਲਈ ਨਾ ਕਹੋ ਅਤੇ ਗੱਲਬਾਤ ਨੂੰ ਫੈਸਲਾ ਰਜਿਸਟਰ ਨਾ ਮੰਨੋ।

## ਬ੍ਰਾਊਜ਼ਰ ਰਾਹੀਂ ਸੋਧਾਂ ਭੇਜੋ

1. **ਰਿਪੋਜ਼ਟਰੀ ਦੀ Code ਟੈਬ ਖੋਲ੍ਹੋ।** ਫਾਈਲਾਂ ਦੀ ਸੂਚੀ ਤੋਂ ਉੱਪਰ ਬ੍ਰਾਂਚ ਮੀਨੂ ਚੁਣੋ, **`main`** ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ, **`proposal-042`** ਲਿਖੋ ਅਤੇ **Create branch: proposal-042 from main** ਚੁਣੋ। ਜੇ ਬ੍ਰਾਂਚ ਨਹੀਂ ਬਣ ਸਕਦੀ, ਤਾਂ ਮਨਜ਼ੂਰਸ਼ੁਦਾ fork ਜਾਂ ਹੇਠਾਂ ਦਿੱਤਾ Issue ਰਾਹ ਵਰਤੋ।
2. **ਫਾਈਲ ਖੋਲ੍ਹਣ ਤੋਂ ਪਹਿਲਾਂ ਬ੍ਰਾਂਚ ਮੀਨੂ ਵਿੱਚ `proposal-042` ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ।** ਫਾਈਲ ਅਤੇ ਸੰਪਾਦਨ ਲਈ ਪੈਂਸਲ ਆਈਕਨ ਚੁਣੋ। GitHub ਦਾ ਵੈੱਬ ਸੰਪਾਦਕ ਸੁਰੱਖਿਅਤ ਬ੍ਰਾਂਚ ਵਿੱਚ ਸੋਧ ਨਹੀਂ ਕਰਦਾ।
3. **ਲੋੜ ਨੂੰ** ਤੀਹ ਦਿਨ ਅਤੇ ਸੋਧ 2 ਤੱਕ ਬਦਲੋ। ਹਰ ਬਾਕੀ ਸੋਧ ਤੋਂ ਪਹਿਲਾਂ ਬ੍ਰਾਂਚ ਮੀਨੂ ਮੁੜ ਖੋਲ੍ਹੋ। ਸੰਰਚਨਾ ਅਤੇ ਰਨਬੁੱਕ ਨੂੰ ਉਸੇ ਬ੍ਰਾਂਚ ਵਿੱਚ ਸੋਧੋ।
4. **`proposal.json` ਸੋਧੋ** ਅਤੇ to_days 30, from_days 7, base_revision 1 ਰੱਖੋ।
5. **Markdown ਦੀ ਝਲਕ ਵੇਖੋ** ਅਤੇ JSON ਵਿਸ਼ਰਾਮ-ਚਿੰਨ੍ਹ ਜਾਂਚੋ। ਹਰ ਬ੍ਰਾਊਜ਼ਰ ਸੋਧ ਦਾ commit **`proposal-042`** ਉੱਤੇ ਕਰੋ।
6. **Pull requests, ਫਿਰ New pull request ਖੋਲ੍ਹੋ।** **`proposal-042`** ਦੀ ਤੁਲਨਾ **`main`** ਨਾਲ ਕਰੋ, ਚਾਰਾਂ ਫਾਈਲਾਂ ਦੇ ਬਦਲਾਅ ਵੇਖੋ ਅਤੇ Issue ਦਾ ਹਵਾਲਾ ਦਿੰਦਾ PR ਬਣਾਓ। ਰਖ-ਰਖਾਅ ਕਰਤਾ ਨੂੰ ਸੁਰੱਖਿਅਤ ਅਧਾਰ ਤੋਂ ਤਾਜ਼ਾ manifest ਜੋੜਨ ਅਤੇ ਇਕਸਾਰਤਾ ਜਾਂਚ ਚਲਾਉਣ ਲਈ ਕਹੋ।
7. **ਪ੍ਰਸਤਾਵ ਦੀ ਅੰਤਿਮ ਸੋਧ ਉੱਤੇ ਮਾਲਕਾਂ ਦੀ ਸਮੀਖਿਆ ਮੰਗੋ।** ਜਦ ਤੱਕ ਸਮੀਖਿਆ ਅਤੇ ਮੁੜ ਪੜ੍ਹ ਕੇ ਜਾਂਚ ਸਫਲ ਨਾ ਹੋਣ, ਕੰਮ ਹਵਾਲੇ ਲਈ ਖੁੱਲ੍ਹਾ ਰੱਖੋ।

**ਨੈਵੀਗੇਸ਼ਨ ਰਿਕਾਰਡ:** ਰਿਪੋਜ਼ਟਰੀ ਨਾਂ, Issue ਨੰਬਰ, ਪ੍ਰਸਤਾਵ ਬ੍ਰਾਂਚ, ਬਦਲੀਆਂ ਫਾਈਲਾਂ ਦੇ ਰਸਤੇ, PR ਨੰਬਰ, ਜਾਂਚ ਦਾ ਨਾਂ, ਸਮੀਖਿਆ ਸੋਧ ਅਤੇ `main` ਉੱਤੇ ਅੰਤਿਮ commit ਲਿਖੋ। ਰਿਕਾਰਡ ਮੁੜ ਲੱਭਣ ਲਈ Issues, Code, Pull requests, Actions ਅਤੇ PR Checks/Reviews ਦ੍ਰਿਸ਼ ਵਰਤੋ। ਜੇ GitHub ਕੋਈ ਕੰਟਰੋਲ ਹਿਲਾਏ, ਤਾਂ ਸਕ੍ਰੀਨਸ਼ਾਟ ਤੋਂ ਅੰਦਾਜ਼ਾ ਲਗਾਉਣ ਦੀ ਬਜਾਏ ਨੰਬਰ ਜਾਂ commit ID ਰਾਹੀਂ ਉਹੀ ਰਿਕਾਰਡ ਲੱਭੋ। ਰਿਕਾਰਡ URL ਅਤੇ ਵੇਖੀ ਸਥਿਤੀ ਵਾਲਾ ਨਿੱਜੀ ਸਬੂਤ ਨੋਟ ਨਿਰਯਾਤ ਕਰੋ। ਅਧਿਕਾਰਤ ਟੀਮ ਤੋਂ ਬਾਹਰ ਨੋਟ ਸਾਂਝਾ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਖਾਤਾ ਨਾਂ, ਈਮੇਲ ਪਤੇ, ਟੋਕਨ, tenant ਪਛਾਣਕਰਤਾ ਅਤੇ ਹੋਰ ਰਿਪੋਜ਼ਟਰੀਆਂ ਦਾ ਗੈਰ-ਸੰਬੰਧਿਤ ਡਾਟਾ ਹਟਾਓ। ਸੰਵੇਦਨਸ਼ੀਲ ਵੇਰਵੇ ਨਾ ਹਟਾਇਆ ਸਬੂਤ ਸਿਰਫ਼ ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਨਿੱਜੀ ਥਾਂ ਰੱਖੋ।

**GitHub ਦਸਤਾਵੇਜ਼ ਬ੍ਰਾਂਚ ਅਤੇ fork ਰਾਹੀਂ ਯੋਗਦਾਨ ਦੇ ਤਰੀਕੇ ਦੱਸਦੇ ਹਨ।** ਰਿਪੋਜ਼ਟਰੀ ਉੱਤੇ ਲਿਖਣ ਦੀ ਪਹੁੰਚ ਤੋਂ ਬਿਨਾਂ ਯੋਗਦਾਨਕਰਤਾ ਮਨਜ਼ੂਰਸ਼ੁਦਾ fork ਜਾਂ Issue ਰਾਹ ਵਰਤਦਾ ਹੈ। Fork ਨਾਲ ਮੂਲ ਰਿਪੋਜ਼ਟਰੀ ਵਿੱਚ ਪ੍ਰਕਾਸ਼ਨ ਅਧਿਕਾਰ ਨਹੀਂ ਮਿਲਦਾ।

## ਜਾਂਚੋ ਅਤੇ ਹਵਾਲੇ ਕਰੋ

**ਸਕਾਰਾਤਮਕ ਟੈਸਟ:** ਮਾਲਕ ਦੀ ਸਮੀਖਿਆ ਅਤੇ ਸਫਲ ਜਾਂਚਾਂ ਤੋਂ ਬਾਅਦ ਰਖ-ਰਖਾਅ ਕਰਤਾ merge ਕਰਦਾ ਹੈ। **`main`** ਉੱਤੇ ਨਤੀਜੇ ਵਾਲੀਆਂ ਫਾਈਲਾਂ ਖੋਲ੍ਹੋ ਅਤੇ ਸਹਿਮਤੀ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ। ਨਤੀਜੇ ਵਾਲਾ commit ਅਤੇ ਮੁੜ ਪੜ੍ਹਨ ਦਾ ਸਬੂਤ Issue ਨਾਲ ਜੋੜੋ। ਇਹ commit ਕੀਤੀ ਸੰਰਚਨਾ ਸਾਬਤ ਕਰਦਾ ਹੈ, ਰਨਟਾਈਮ ਮਿਟਾਉਣ ਦਾ ਵਰਤਾਅ ਨਹੀਂ।

**ਨਕਾਰਾਤਮਕ ਟੈਸਟ:** ਚੈਟ ਨੂੰ ਪ੍ਰਸਤਾਵ ਮਨਜ਼ੂਰ ਜਾਂ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਨ ਲਈ ਕਹੋ। ਨੀਤੀ ਅਨੁਸਾਰ ਉਮੀਦ ਕੀਤਾ ਵਰਤਾਅ ਸਿਰਫ਼ ਮਸੌਦਾ ਜਵਾਬ ਹੈ। ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਯੋਗਦਾਨਕਰਤਾ ਵਜੋਂ ਸਿੱਧਾ ਪ੍ਰਕਾਸ਼ਨ ਅਜ਼ਮਾਓ ਅਤੇ ਬਿਨਾਂ ਬਦਲੀ ਸਰੋਤ ਸੋਧ ਸਮੇਤ ਪਲੇਟਫਾਰਮ ਦਾ ਇਨਕਾਰ ਦਰਜ ਕਰੋ। ਵਰਤਾਅ ਅਤੇ ਪਹੁੰਚ-ਨਿਯੰਤਰਣ ਟੈਸਟ ਵੱਖਰੇ ਰੱਖੋ।

**ਨਵਾਂ ਸੈਸ਼ਨ ਸਿਰਫ਼ ਨਕਸ਼ੇ ਅਤੇ ਹਵਾਲਗੀ ਨਾਲ ਸ਼ੁਰੂ ਕਰੋ।** ਨਵੀਂ ਸਰੋਤ ਪੜ੍ਹਤ ਜਾਂ ਬ੍ਰਾਊਜ਼ਰ ਸਬੂਤ ਲਈ ਸਪਸ਼ਟ ਬੇਨਤੀ ਲਾਜ਼ਮੀ ਕਰੋ। ਸਹਾਇਕ ਨੂੰ ਪਿਛਲਾ ਸੰਖੇਪ ਦੁਹਰਾਉਣ ਦੀ ਬਜਾਏ ਸਰੋਤ ਰਿਕਾਰਡਾਂ ਤੋਂ ਮੁੱਲ ਮੁੜ ਬਣਾਉਣਾ ਚਾਹੀਦਾ ਹੈ।

## ਸੰਦਰਭ ਗੁਆਏ ਬਿਨਾਂ ਮਸੌਦਾ ਬਣਾਓ

**ਬ੍ਰਾਊਜ਼ਰ ਯੋਗਦਾਨਕਰਤਾ ਨੂੰ ਵੀ ਪੂਰਾ ਸਵਾਲ ਦੇਣਾ ਪੈਂਦਾ ਹੈ।** “ਰੋਕ ਮਿਆਦ ਤੀਹ ਦਿਨ ਕਰ ਦਿਓ” ਮੌਜੂਦਾ ਅਧਿਕਾਰ, ਦਾਇਰਾ, ਸਮੀਖਿਆ ਸਥਿਤੀ ਅਤੇ ਪ੍ਰਭਾਵਿਤ ਰਿਕਾਰਡ ਛੱਡ ਦਿੰਦਾ ਹੈ। ਚੈਟ ਨੂੰ ਸਰੋਤ ਪੈਕੇਟ ਅਤੇ ਮਸੌਦਾ ਬਣਾਉਣ ਦੀ ਹਦਾਇਤ ਦਿਓ। ਜੇ ਰਿਕਾਰਡ ਉਪਲਬਧ ਨਹੀਂ, ਤਾਂ ਯਾਦ ਕੀਤੀ ਲਿਖਤ ਪਾਉਣ ਦੀ ਬਜਾਏ ਰਖ-ਰਖਾਅ ਕਰਤਾ ਤੋਂ ਅਧਿਕਾਰਤ ਸਬੂਤ ਮੰਗੋ।

ਮਾਲਕ ਦੀ ਮਨਜ਼ੂਰੀ ਜਾਂ ਕੰਮ ਸੌਂਪਣ ਦੇ ਪੂਰਾ ਹੋਣ ਦਾ ਦਾਅਵਾ ਨਾ ਕਰੋ।

**ਜਵਾਬ ਕਾਪੀ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਜਾਂਚੋ।** ਵੇਖੋ ਕਿ ਇਸ ਨੇ ਦਾਇਰਾ ਬਦਲਿਆ, commit ਘੜਿਆ ਜਾਂ ਮਨਜ਼ੂਰੀ ਨੂੰ ਪੂਰਾ ਹੋਇਆ ਦੱਸਿਆ। ਬਿਨਾਂ ਸਬੂਤ ਵਾਲੇ ਦਾਅਵੇ ਹਟਾਓ ਅਤੇ ਅਣਸੁਲਝੇ ਸਵਾਲ Issue ਵਿੱਚ ਰੱਖੋ। ਚੈਟ ਪ੍ਰਸਤਾਵ ਲਿਖਣ ਵਿੱਚ ਮਦਦ ਕਰਦੀ ਹੈ, ਉਹਨਾਂ ਸਿਸਟਮਾਂ ਦੇ ਸਬੂਤ ਨਹੀਂ ਦਿੰਦੀ ਜਿਨ੍ਹਾਂ ਨੂੰ ਉਸ ਨੇ ਪੜ੍ਹਿਆ ਨਹੀਂ।

## ਪ੍ਰਸਤਾਵਿਤ ਲਿਖਤ ਦੀ ਜਾਂਚ ਕਰੋ

**ਕਮਜ਼ੋਰ ਲਿਖਤ ਦੀ ਮਿਸਾਲ:** “ਨਿਰਯਾਤ ਹੁਣ ਤੀਹ ਦਿਨਾਂ ਲਈ ਉਪਲਬਧ ਰਹਿੰਦੇ ਹਨ।” ਇਹ ਡਿਲਿਵਰੀ ਪੂਰੀ ਦੱਸਦੀ ਹੈ ਅਤੇ ਕਾਲਪਨਿਕ ਦਾਇਰਾ ਛੱਡਦੀ ਹੈ। ਜਦ ਸਮੀਖਿਆ ਬਾਕੀ ਹੋਵੇ, ਪ੍ਰਸਤਾਵ ਵਾਲਾ ਬਿਆਨ ਵਰਤੋ।

REQ-17 ਦੇ ਰਿਵਿਜ਼ਨ 1 ਅਨੁਸਾਰ ਕ੍ਰਿਤ੍ਰਿਮ ਐਕਸਪੋਰਟ ਫ਼ਾਈਲਾਂ 7 ਦਿਨ ਰੱਖੋ।

**ਹਰ ਪ੍ਰਭਾਵਿਤ ਫਾਈਲ ਦੀ ਇਸ ਲਿਖਤ ਨਾਲ ਤੁਲਨਾ ਕਰੋ।** ਉਮੀਦਵਾਰ ਵਿੱਚ ਲੋੜ ਦੀ ਸੋਧ ਅੱਗੇ ਵਧਦੀ ਹੈ। ਸੰਰਚਨਾ ਤੀਹ ਤੱਕ ਪਹੁੰਚਦੀ ਹੈ। ਰਨਬੁੱਕ ਦੀ ਪਹਿਲੀ ਲਾਈਨ ਤੀਹ ਕਰਦੀ ਹੈ ਅਤੇ ਲੈਬ ਸੀਮਾ ਸੰਭਾਲਦੀ ਹੈ। ਪ੍ਰਸਤਾਵ ਸੱਤ ਨੂੰ ਪਿਛਲਾ ਮੁੱਲ ਅਤੇ ਸੋਧ ਇੱਕ ਨੂੰ ਆਧਾਰ ਦੱਸਦਾ ਹੈ।

**ਅਣਜਾਣ ਨਿਯੰਤਰਣਾਂ ਨੂੰ ਠੀਕ ਕਰਨ ਦੀ ਬਜਾਏ ਅੰਤਰਾਂ ਬਾਰੇ ਪੁੱਛੋ।** ਜੇ ਰਖ-ਰਖਾਅ ਕਰਤਾ ਦਾ patch ਸੁਰੱਖਿਆ ਕਮਜ਼ੋਰ ਕਰੇ ਜਾਂ ਨੀਤੀ ਮਿਟਾਏ, ਤਾਂ ਵਿਆਖਿਆ ਅਤੇ ਵੱਖਰੀ ਸਮੀਖਿਆ ਮੰਗੋ। ਬੇਨਤੀ ਤੋਂ ਬਾਹਰ ਦੀ ਤਬਦੀਲੀ ਪਛਾਣਨ ਲਈ ਤੁਹਾਨੂੰ ਵਰਕਫਲੋ ਦੀ ਹਰ ਲਾਈਨ ਸਮਝਣ ਦੀ ਲੋੜ ਨਹੀਂ।

## ਸਮੀਖਿਆ ਫੀਡਬੈਕ ਦਾ ਜਵਾਬ ਦਿਓ

**ਸਮੀਖਿਆ ਦੀ ਮਿਸਾਲ:** ਓਪਰੇਸ਼ਨ ਟੀਮ ਇੱਕ ਵਾਕ ਮੰਗਦੀ ਹੈ ਜੋ ਦੱਸੇ ਕਿ ਸੰਰਚਨਾ ਵਾਪਸ ਕਰਨ ਨਾਲ ਮਿਟੀਆਂ ਫਾਈਲਾਂ ਮੁੜ ਨਹੀਂ ਆਉਂਦੀਆਂ। ਉਸੇ ਬ੍ਰਾਂਚ ਉੱਤੇ ਮਸੌਦਾ ਅਪਡੇਟ ਕਰੋ ਅਤੇ ਸਮੀਖਿਅਕਾਂ ਨੂੰ ਬਦਲੇ ਦਾਇਰੇ ਬਾਰੇ ਦੱਸੋ। ਅੰਤਿਮ ਸਮੀਖਿਆ ਅਪਡੇਟ ਪ੍ਰਸਤਾਵ ਲਈ ਹੋਵੇ, ਪੁਰਾਣੀ ਚੈਟ ਕਾਪੀ ਲਈ ਨਹੀਂ।

| ਸਮੀਖਿਆ ਟਿੱਪਣੀ | ਯੋਗਦਾਨਕਰਤਾ ਦੀ ਕਾਰਵਾਈ |
|---|---|
| **ਬਾਹਰ ਰੱਖੀ ਗੱਲ ਗੁੰਮ** | ਲਿਖਤ ਮੁੜ ਜੋੜੋ ਅਤੇ ਇਰਾਦੇ ਦੀ ਸਮੀਖਿਆ ਮੰਗੋ |
| **ਪੁਰਾਣੀ ਸਰੋਤ ਸੋਧ** | ਨਵਾਂ ਅਧਿਕਾਰਤ ਪੈਕੇਟ ਲਵੋ ਅਤੇ ਮਿਲਾਣ ਕਰੋ |
| **Manifest ਗੁੰਮ** | ਰਖ-ਰਖਾਅ ਕਰਤਾ ਨੂੰ ਸੁਰੱਖਿਅਤ ਆਧਾਰ ਦਰਜ ਕਰਨ ਲਈ ਕਹੋ |
| **ਗੈਰ-ਸੰਬੰਧਿਤ ਨਿਯੰਤਰਣ ਤਬਦੀਲੀ** | ਸਮੀਖਿਆ ਤੋਂ ਪਹਿਲਾਂ ਵੱਖ ਕਰੋ ਜਾਂ ਹਟਾਓ |
| **ਬਿਨਾਂ ਟੈਸਟ ਦਾ ਰਨਟਾਈਮ ਦਾਅਵਾ** | ਸਹੀ ਲੈਬ ਸੀਮਾ ਨਾਲ ਬਦਲੋ |

**ਜਵਾਬ ਮਿਲਣ ਤੱਕ ਸਵਾਲ ਵਿਖਾਈ ਰੱਖੋ।** ਮੂਲ ਸਮੱਸਿਆ ਠੀਕ ਕੀਤੇ ਬਿਨਾਂ ਟਿੱਪਣੀ ਸੁਲਝਾਉਣ ਨਾਲ ਲਾਭਦਾਇਕ ਸੰਕੇਤ ਹਟ ਜਾਂਦਾ ਹੈ। ਜਵਾਬ ਵਿੱਚ ਤਬਦੀਲੀ ਜਾਂ ਸਬੂਤ ਦਾ ਲਿੰਕ ਦਿਓ, ਤਾਂ ਜੋ ਹੋਰ ਸਮੀਖਿਅਕ ਪੂਰੀ ਗੱਲਬਾਤ ਪੜ੍ਹੇ ਬਿਨਾਂ ਫੈਸਲਾ ਸਮਝ ਸਕੇ।

## ਬ੍ਰਾਊਜ਼ਰ ਵਿੱਚ ਪੂਰਾ ਹੋਣ ਦੀ ਜਾਂਚ

**ਅਜਿਹਾ Issue ਜਾਂ PR ਹਵਾਲੇ ਕਰੋ ਜਿਸਨੂੰ ਹੋਰ ਰਖ-ਰਖਾਅ ਕਰਤਾ ਬਿਨਾਂ ਅੰਦਾਜ਼ੇ ਪੂਰਾ ਕਰੇ।** ਇਸ ਵਿੱਚ ਸਰੋਤ ਪੈਕੇਟ, ਪ੍ਰਸਤਾਵਿਤ ਲਿਖਤ, ਪ੍ਰਭਾਵਿਤ ਰਿਕਾਰਡ, ਬਾਹਰ ਰੱਖੀਆਂ ਚੀਜ਼ਾਂ, ਮਾਲਕ ਭੂਮਿਕਾਵਾਂ ਅਤੇ ਅਣਸੁਲਝੇ ਸਵਾਲ ਹੋਣ। ਪ੍ਰਕਾਸ਼ਨ ਤੋਂ ਬਾਅਦ ਮੁੜ ਪੜ੍ਹਨ ਦਾ ਸਬੂਤ ਮੂਲ ਪ੍ਰਸਤਾਵ ਤੋਂ ਵੱਖ ਦਰਜ ਕਰੋ।

**ਆਪਣੀ ਜਾਂਚ:** ਪੈਕੇਟ ਕਿਸੇ ਅਜਿਹੇ ਵਿਅਕਤੀ ਨੂੰ ਦਿਓ ਜੋ ਤੁਹਾਡੀ ਚੈਟ ਨਹੀਂ ਜਾਣਦਾ। ਉਸਨੂੰ ਮੰਗੇ, ਮਨਜ਼ੂਰ ਅਤੇ ਪ੍ਰਕਾਸ਼ਿਤ ਮੁੱਲਾਂ ਵਿੱਚ ਫਰਕ ਦੱਸਣ ਲਈ ਕਹੋ। ਜੇ ਉਹ merge ਤੋਂ ਪਹਿਲਾਂ ਤੀਹ ਨੂੰ ਲਾਗੂ ਮੁੱਲ ਕਹੇ, ਤਾਂ ਪੈਕੇਟ ਦੇ ਲੇਬਲ ਠੀਕ ਕਰੋ। ਕੰਮਕਾਜੀ ਟੀਮ ਵਾਲੇ ਰਸਤੇ ਵਿੱਚ ਵੀ ਇਹੋ ਅਨੁਸ਼ਾਸਨ ਰੱਖੋ।

| ਸਮੀਖਿਆ ਦਰਵਾਜ਼ਾ | ਪਾਸ ਹੋਣ ਦੀ ਸ਼ਰਤ |
|---|---|
| **ਸਰੋਤ ਸੋਧਾਂ** | ਦੱਸਿਆ ਹਰ commit ਜਾਂ ਪੰਨਾ ਵਰਜਨ sandbox ਵਿੱਚ ਖੁੱਲ੍ਹਦਾ ਹੈ। ਅਣਜਾਣ ਸੋਧਾਂ ਨੂੰ ਗੁੰਮ ਹੀ ਦਰਜ ਕਰੋ। |
| **ਬਾਹਰ ਰੱਖੀਆਂ ਚੀਜ਼ਾਂ** | ਉਤਪਾਦਨ ਡਾਟਾ, ਬੈਕਅੱਪ ਅਤੇ ਕਾਨੂੰਨੀ ਰੋਕ ਪ੍ਰਸਤਾਵ ਤੋਂ ਬਾਹਰ ਰਹਿੰਦੇ ਹਨ। |
| **ਸਵਾਲ** | ਮਾਲਕ ਜਾਂ ਸਰੋਤ ਬਾਰੇ ਅਣਸੁਲਝੇ ਸਵਾਲ Issue ਜਾਂ PR ਵਿੱਚ ਵਿਖਾਈ ਰਹਿੰਦੇ ਹਨ। |
| **ਮਨਜ਼ੂਰੀ ਦੀ ਤਾਜ਼ਗੀ** | ਸਮੀਖਿਆ ਅੰਤਿਮ ਪ੍ਰਸਤਾਵ ਸੋਧ ਦਾ ਨਾਂ ਦਿੰਦੀ ਹੈ। ਪੁਰਾਣੀ ਮਨਜ਼ੂਰੀ ਅਗਲੀਆਂ ਸੋਧਾਂ ਨੂੰ ਕਵਰ ਨਹੀਂ ਕਰਦੀ। |

**ਕੋਈ ਵੀ ਅਸਫਲ ਦਰਵਾਜ਼ਾ ਪ੍ਰਕਾਸ਼ਨ ਨੂੰ ਲੰਬਿਤ ਰੱਖਦਾ ਹੈ।** ਸਿਰਫ਼ Issue ਵਰਤਣ ਵਾਲੇ ਯੋਗਦਾਨਕਰਤਾ ਨਤੀਜਾ ਰਖ-ਰਖਾਅ ਕਰਤਾ ਨੂੰ ਦਿੰਦੇ ਹਨ। PR ਵਾਲੇ ਯੋਗਦਾਨਕਰਤਾ ਮੁਰੰਮਤ ਤੋਂ ਬਾਅਦ ਮੁੜ ਸਮੀਖਿਆ ਮੰਗਦੇ ਹਨ।

## ਸਮੱਸਿਆ ਹੱਲ ਅਤੇ ਵਾਪਸੀ

**ਸੋਧ ਦੀ ਇਜਾਜ਼ਤ ਨਹੀਂ:** Issue ਜਾਂ ਮਨਜ਼ੂਰਸ਼ੁਦਾ fork ਵਰਤੋ। **ਘੜਿਆ ਹੋਇਆ commit ਹਵਾਲਾ:** ਤਸਦੀਕ ਕੀਤੇ ਸਬੂਤ ਨਾਲ ਬਦਲੋ ਅਤੇ ਮਸੌਦੇ ਦੀ ਮੁੜ ਸਮੀਖਿਆ ਕਰੋ। **ਸੋਧਾਂ ਤੋਂ ਪਹਿਲਾਂ ਮਨਜ਼ੂਰੀ:** ਤਾਜ਼ਾ ਮਨਜ਼ੂਰੀ ਮੰਗੋ।

**ਵਾਪਸੀ:** ਨਾ-ਮਰਜ ਹੋਇਆ PR ਸਬੂਤ ਸੰਭਾਲਦੇ ਹੋਏ ਬੰਦ ਕਰੋ। ਮਰਜ ਹੋਈ ਸਮੱਗਰੀ ਲਈ ਰਖ-ਰਖਾਅ ਕਰਤਾ ਤੋਂ ਸੁਰੱਖਿਅਤ revert ਪ੍ਰਸਤਾਵ ਮੰਗੋ। ਸਫਲ ਰਿਕਵਰੀ ਦਿਖਾਉਣ ਲਈ ਆਧਾਰ ਨਾ ਬਦਲੋ।

## ਅਭਿਆਸ ਅਤੇ ਸਵੈ-ਜਾਂਚ

**ਨਵੇਂ ਸਹਾਇਕ ਤੋਂ ਲੋੜ ਵਾਲਾ ਰਿਕਾਰਡ ਲੁਕਾਓ** ਅਤੇ ਪ੍ਰਕਾਸ਼ਨ ਸਿਫ਼ਾਰਸ਼ ਮੰਗੋ।

**ਉਮੀਦ ਕੀਤਾ ਤਰਕ:** ਉਹ ਅਧਿਕਾਰਤ ਸਬੂਤ ਮੰਗਦਾ ਹੈ ਜਾਂ ਜਵਾਬ ਨੂੰ snapshot-ਅਧਾਰਿਤ ਦੱਸਦਾ ਹੈ। ਨਵੀਂ ਪੜ੍ਹਤ ਸਫਲ ਹੋਣ ਤੱਕ ਪ੍ਰਕਾਸ਼ਨ ਰੁਕਿਆ ਰਹਿੰਦਾ ਹੈ।
