ਹਰਾ ਬੈਕਅੱਪ ਟਾਸਕ ਦੱਸਦਾ ਹੈ ਕਿ Proxmox ਨੇ ਬੈਕਅੱਪ ਲਿਖਿਆ। ਇਹ ਨਹੀਂ ਦੱਸਦਾ ਕਿ ਗੈਸਟ ਬੂਟ ਹੁੰਦਾ ਹੈ, ਡਾਟਾ ਨਵਾਂ ਹੈ ਜਾਂ ਮੁੱਖ ਸੇਵਾ ਕੰਮ ਕਰਦੀ ਹੈ। **ਨਵੀਂ VM ID ਨਾਲ ਅਲੱਗ ਨੈੱਟਵਰਕ ਉੱਤੇ ਇੱਕ ਕਾਪੀ ਰੀਸਟੋਰ ਕਰੋ।** ਕਿਸੇ ਆਊਟੇਜ ਕਰਕੇ ਜਾਂਚ ਕਰਨੀ ਪਵੇ, ਉਸ ਤੋਂ ਪਹਿਲਾਂ ਨਤੀਜਾ ਰਿਕਵਰੀ ਦਾ ਸਬੂਤ ਦਿੰਦਾ ਹੈ।

<!--more-->

ਇਹ ਅਭਿਆਸ ਇੱਕ **Proxmox VE ਵਰਚੁਅਲ ਮਸ਼ੀਨ** ਲਈ ਹੈ। ਕਨਟੇਨਰਾਂ ਦੇ ਬੈਕਅੱਪ ਨਿਯਮ ਵੱਖਰੇ ਹਨ, ਖਾਸ ਕਰਕੇ bind mount ਅਤੇ device mount ਲਈ। ਸਾਈਟ ਦਾ [ਹੋਮਲੈਬ ਬੈਕਅੱਪ ਰੀਸਟੋਰ ਅਭਿਆਸ](/articles/homelab-backup-restore-drill/) ਫਾਈਲ ਰਿਕਵਰੀ ਦੇ ਵੱਡੇ ਦਾਇਰੇ ਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ। ਇੱਥੇ ਤੁਸੀਂ Proxmox VM ਬੈਕਅੱਪ ਅਤੇ ਇਸਦੇ ਵਰਕਲੋਡ ਦੀ ਜਾਂਚ ਕਰੋਗੇ।

**ਗੈਸਟ** ਉਹ ਓਪਰੇਟਿੰਗ ਸਿਸਟਮ ਹੈ ਜੋ ਵਰਚੁਅਲ ਮਸ਼ੀਨ ਦੇ ਅੰਦਰ ਚੱਲਦਾ ਹੈ। **Bind mount** ਅਤੇ **device mount** ਹੋਸਟ ਦੇ ਸਰੋਤ ਗੈਸਟ ਨੂੰ ਦਿਖਾਉਂਦੇ ਹਨ। ਇਨ੍ਹਾਂ ਸਰੋਤਾਂ ਦੀ ਜਾਂਚ ਵੱਖਰੀ ਰਿਕਵਰੀ ਯੋਜਨਾ ਨਾਲ ਕਰੋ।

## ਮੁੱਖ ਗੱਲਾਂ

- **ਪਹਿਲਾਂ ਕਾਮਯਾਬੀ ਤੈਅ ਕਰੋ:** ਇੱਕ ਡਾਟਾ ਆਈਟਮ, ਸੇਵਾ ਜਾਂਚ ਅਤੇ ਮਨਜ਼ੂਰ ਰਿਕਵਰੀ ਸਮਾਂ ਚੁਣੋ।
- **ਕਵਰੇਜ ਵੇਖੋ:** VM ਬੈਕਅੱਪ **No backup** ਵਾਲੀਆਂ ਡਿਸਕਾਂ ਛੱਡ ਦਿੰਦਾ ਹੈ ਅਤੇ ਬਾਹਰੀ ਸੇਵਾਵਾਂ ਜਾਂ ਛੱਡਿਆ ਡਾਟਾ ਮੁੜ ਨਹੀਂ ਬਣਾ ਸਕਦਾ।
- **ਵੱਖਰੇ ਤੌਰ ਤੇ ਰੀਸਟੋਰ ਕਰੋ:** ਨਾ ਵਰਤੀ VM ID ਲਓ ਅਤੇ ਰੀਸਟੋਰ ਕੀਤਾ ਨੈੱਟਵਰਕ ਪ੍ਰੋਡਕਸ਼ਨ ਤੋਂ ਅਲੱਗ ਰੱਖੋ।
- **ਸਬੂਤ ਦਰਜ ਕਰੋ:** ਬੈਕਅੱਪ ਦੀ ਉਮਰ, ਰੀਸਟੋਰ ਸਮਾਂ, ਬੂਟ, ਡਿਸਕ ਦੀ ਮੌਜੂਦਗੀ ਅਤੇ ਅਸਲ ਐਪ ਜਾਂਚ ਮਾਪੋ।

## ਸ਼ੁਰੂ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ

ਅਜਿਹੀ VM ਚੁਣੋ ਜਿਸਦਾ ਬੈਕਅੱਪ ਸੁਰੱਖਿਅਤ ਤਰੀਕੇ ਨਾਲ ਜਾਂਚਿਆ ਜਾ ਸਕੇ। ਤੁਹਾਨੂੰ Proxmox ਪ੍ਰਸ਼ਾਸਕ ਪਹੁੰਚ, ਫਾਈਲ ਸਟੋਰੇਜ ਜਾਂ Proxmox Backup Server (PBS) ਉੱਤੇ ਪੂਰਾ ਬੈਕਅੱਪ, ਦੂਜੀ VM ਲਈ ਕਾਫ਼ੀ ਥਾਂ, ਅਤੇ ਇੱਕ ਅਲੱਗ bridge ਜਾਂ ਡਿਸਕਨੈਕਟ ਕੀਤਾ ਨੈੱਟਵਰਕ ਯੰਤਰ ਚਾਹੀਦਾ ਹੈ। ਅਲੱਗ bridge Proxmox ਦਾ ਵਰਚੁਅਲ ਨੈੱਟਵਰਕ ਹੈ ਜਿਸਦਾ ਪ੍ਰੋਡਕਸ਼ਨ LAN ਵੱਲ ਕੋਈ ਰਸਤਾ ਨਹੀਂ। ਜੇ ਇਹ ਨਹੀਂ, ਤਾਂ ਡਿਸਕਨੈਕਟ adapter ਜਾਂ test VLAN ਵਰਤੋ। ਪ੍ਰੋਡਕਸ਼ਨ VM ਚੱਲਦੀ ਰਹਿਣ ਦਿਓ। ਵੇਖੋ ਕਿ ਹੋਰ ਗੈਸਟ ID ਨਾ ਵਰਤਦਾ ਹੋਵੇ, ਫਿਰ ਨਵੀਂ VM ID, ਜਿਵੇਂ **920**, ਰਾਖਵੀਂ ਕਰੋ। ਪੂਰੇ ਰੀਸਟੋਰ ਅਤੇ ਵਰਕਲੋਡ ਜਾਂਚ ਲਈ ਸਮਾਂ ਰੱਖੋ।

ਰੀਸਟੋਰ ਤੋਂ ਪਹਿਲਾਂ ਪਾਸ ਹੋਣ ਦੀਆਂ ਸ਼ਰਤਾਂ ਲਿਖੋ। ਫਾਈਲ ਸਰਵਰ ਲਈ ਹਾਲੀਆ ਫਾਈਲ ਅਤੇ ਇਸਦਾ ਉਮੀਦਵਾਰ checksum ਜਾਂ ਸਮੱਗਰੀ ਚੁਣੋ। ਡਾਟਾਬੇਸ ਲਈ ਸੁਰੱਖਿਅਤ read-only query ਅਤੇ ਬੈਕਅੱਪ ਤੋਂ ਪਹਿਲਾਂ ਲਿਖਿਆ ਰਿਕਾਰਡ ਚੁਣੋ। ਵੈੱਬ ਸੇਵਾ ਲਈ ਸਥਾਨਕ health check ਅਤੇ ਪ੍ਰਤੀਨਿਧੀ ਪੰਨਾ ਲਓ। ਡਾਟਾ ਦੀ ਸਭ ਤੋਂ ਨਵੀਂ ਮਨਜ਼ੂਰ ਮਿਤੀ, ਆਪਣਾ **recovery point objective (RPO)**, ਅਤੇ ਸੇਵਾ ਚਾਲੂ ਕਰਨ ਲਈ ਦਿੱਤਾ ਸਮਾਂ, ਆਪਣਾ **recovery time objective (RTO)** ਦਰਜ ਕਰੋ। ਸਿਰਫ਼ ਬੂਟ ਸਕ੍ਰੀਨ ਇਹ ਜਾਂਚਾਂ ਪੂਰੀ ਨਹੀਂ ਕਰਦੀ।

| ਦਰਜ ਕੀਤੀ ਗੱਲ | ਸਬੂਤ ਦੀ ਮਿਸਾਲ |
|---|---|
| **ਬੈਕਅੱਪ ਬਿੰਦੂ** | Snapshot ਦਾ ਸਮਾਂ ਅਤੇ ਆਖਰੀ ਉਮੀਦਵਾਰ ਡਾਟਾ ਆਈਟਮ |
| **ਰਿਕਵਰੀ ਟੀਚਾ** | ਨਾ ਵਰਤੀ VM ID, ਟਾਰਗੇਟ ਸਟੋਰੇਜ, ਅਲੱਗ bridge |
| **ਵਰਕਲੋਡ ਜਾਂਚ** | ਲੌਗਇਨ, ਵਾਲਿਊਮ ਮਾਊਂਟ ਅਤੇ ਐਪ ਤੋਂ ਪੜ੍ਹਨਾ |
| **ਸਮਾਂ ਹੱਦ** | ਰੀਸਟੋਰ ਅਤੇ ਸੇਵਾ ਜਾਂਚ ਦੇ ਸ਼ੁਰੂ ਤੇ ਅੰਤ ਦੇ ਸਮੇਂ |

ਨਾਮ, IP ਪਤਾ, MAC ਪਤਾ, ਨਿਯਤ ਕੰਮ ਅਤੇ ਬਾਹਰੀ ਇੰਟੀਗ੍ਰੇਸ਼ਨ ਵੇਖਣ ਤੋਂ ਪਹਿਲਾਂ ਰੀਸਟੋਰ ਕੀਤੇ ਗੈਸਟ ਨੂੰ ਪ੍ਰੋਡਕਸ਼ਨ ਨੈੱਟਵਰਕ ਨਾਲ ਨਾ ਜੋੜੋ। ਨਕਲ ਕੀਤੀ ਪਛਾਣ ਚੱਲਦੀ VM ਨਾਲ ਟਕਰਾ ਸਕਦੀ ਹੈ ਜਾਂ ਦੋਹਰਾ ਕੰਮ ਭੇਜ ਸਕਦੀ ਹੈ।

## ਵੇਖੋ ਬੈਕਅੱਪ ਵਿੱਚ ਕੀ ਸ਼ਾਮਲ ਹੈ

**ਵਰਜਨ ਦਾ ਦਾਇਰਾ:** ਲੇਖ ਤਿਆਰ ਕਰਦੇ ਸਮੇਂ ਇਹ ਮਿਸਾਲਾਂ ਨਹੀਂ ਚਲਾਈਆਂ ਗਈਆਂ। ਜਾਂਚ ਤੋਂ ਪਹਿਲਾਂ `pveversion --verbose` ਦਾ ਆਉਟਪੁੱਟ ਦਰਜ ਕਰੋ। ਇੰਸਟਾਲ Proxmox VE ਰਿਲੀਜ਼ ਨਾਲ ਮੇਲ ਖਾਂਦਾ ਦਸਤਾਵੇਜ਼ ਵਰਤੋ। ਜਾਂਚ ਰਿਕਾਰਡ ਵਿੱਚ ਸਟੋਰੇਜ ਬੈਕਐਂਡ, ਗੈਸਟ ਕਿਸਮ ਅਤੇ ਕਮਾਂਡ ਆਉਟਪੁੱਟ ਲਿਖੋ।

Proxmox ਨੋਡ ਉੱਤੇ ਹੇਠਾਂ ਦਿੱਤੀ ਸਿਰਫ਼-ਪੜ੍ਹਨ ਵਾਲੀ ਕਮਾਂਡ ਸਰੋਤ VM ਦੀ ਸੰਰਚਨਾ ਦਿਖਾਉਂਦੀ ਹੈ। **120** ਨੂੰ ਆਪਣੀ ਸਰੋਤ VM ID ਨਾਲ ਬਦਲੋ:

```bash
qm config 120
```

ਹਰ ਵਰਚੁਅਲ ਡਿਸਕ ਅਤੇ ਇਸਦੀ ਬੈਕਅੱਪ ਸੈਟਿੰਗ ਲਿਖੋ। Proxmox ਦਾ [VM ਡਿਸਕ ਦਸਤਾਵੇਜ਼](https://github.com/proxmox/pve-docs/blob/master/qm.adoc) ਦੱਸਦਾ ਹੈ ਕਿ **No backup** ਚੋਣ VM ਬੈਕਅੱਪ ਵਿੱਚੋਂ ਡਿਸਕ ਕੱਢਦੀ ਹੈ। ਵੇਖੋ ਕਿ ਐਪ ਡਾਟਾ ਛੱਡੀ ਡਿਸਕ, ਹੋਸਟ ਮਾਊਂਟ, ਸਿੱਧੇ ਪਾਸ ਕੀਤੇ ਹਾਰਡਵੇਅਰ ਜਾਂ ਦੂਰਲੀ ਸੇਵਾ ਉੱਤੇ ਤਾਂ ਨਹੀਂ। ਇਸਦੀ ਵੱਖਰੀ ਰਿਕਵਰੀ ਪ੍ਰਕਿਰਿਆ ਦਰਜ ਕਰੋ। VM ਬੂਟ ਜਾਂਚ ਇਹ ਸਾਬਤ ਨਹੀਂ ਕਰਦੀ ਕਿ ਛੱਡਿਆ ਡਾਟਾ ਸੁਰੱਖਿਅਤ ਹੈ।

ਸਭ ਤੋਂ ਨਵੇਂ ਬੈਕਅੱਪ ਦਾ ਸਮਾਂ, ਆਕਾਰ, ਟਾਸਕ ਲੌਗ ਅਤੇ ਸਟੋਰੇਜ ਟਿਕਾਣਾ ਵੇਖੋ। Proxmox ਇੰਟਰਫੇਸ ਵਿੱਚ ਬੈਕਅੱਪ ਸਟੋਰੇਜ ਦਾ **Backups** ਦ੍ਰਿਸ਼ ਜਾਂ VM ਦੀ **Backup** ਟੈਬ ਖੋਲ੍ਹੋ। ਪੱਕਾ ਕਰੋ ਕਿ ਟਾਸਕ ਬਿਨਾਂ ਗਲਤੀ ਮੁੱਕਿਆ। Proxmox ਦਾ [ਬੈਕਅੱਪ ਦਸਤਾਵੇਜ਼](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc) ਆਮ ਬੈਕਅੱਪ ਫਾਈਲਾਂ ਅਤੇ PBS ਸਟੋਰੇਜ ਵਿਚਲਾ ਫ਼ਰਕ ਦੱਸਦਾ ਹੈ। PBS ਦੁਹਰਾਅ-ਹਟਾਏ chunk ਅਤੇ metadata ਰੱਖਦਾ ਹੈ।

| ਬੈਕਅੱਪ ਮੋਡ | VM ਦਾ ਵਿਹਾਰ | ਇਸ ਅਭਿਆਸ ਦਾ ਫੈਸਲਾ |
|---|---|---|
| **Snapshot** | ਘੱਟ ਰੁਕਾਵਟ ਨਾਲ ਚੱਲਦੀ VM ਦਾ ਬੈਕਅੱਪ ਲੈਂਦਾ ਹੈ। ਗੈਸਟ ਦੀਆਂ ਲਿਖਤਾਂ ਨਾਲ ਥੋੜ੍ਹਾ consistency ਖ਼ਤਰਾ ਹੁੰਦਾ ਹੈ। | ਰੁਟੀਨ ਜਾਂਚ ਲਈ ਢੁੱਕਵਾਂ ਜੇ ਵਰਕਲੋਡ ਇਹ ਰਿਕਵਰੀ ਬਿੰਦੂ ਸਹਾਰ ਸਕੇ। |
| **Stop** | ਬੈਕਅੱਪ ਸ਼ੁਰੂ ਹੋਣ ਉੱਤੇ ਗੈਸਟ ਬੰਦ ਕਰਦਾ ਹੈ ਅਤੇ ਸਭ ਤੋਂ ਵਧੀਆ consistency ਦਿੰਦਾ ਹੈ। | ਜਦੋਂ ਵਰਕਲੋਡ ਨੂੰ ਸਾਫ਼ shutdown ਚਾਹੀਦਾ ਹੋਵੇ ਅਤੇ ਰੁਕਾਵਟ ਮਨਜ਼ੂਰ ਹੋਵੇ, ਵਰਤੋ। |
| **Suspend** | snapshot ਮੋਡ ਤੋਂ ਪਹਿਲਾਂ ਗੈਸਟ ਰੋਕਦਾ ਹੈ ਅਤੇ ਆਮ consistency ਲਾਭ ਤੋਂ ਬਿਨਾਂ ਰੁਕਾਵਟ ਵਧਾਉਂਦਾ ਹੈ। | suspend ਨੂੰ snapshot ਤੋਂ ਵਧੀਆ ਮੰਨ ਕੇ ਡਿਫਾਲਟ ਨਾ ਕਰੋ। |

ਇਨ੍ਹਾਂ ਮੋਡਾਂ ਦੇ ਲੈਣ-ਦੇਣ [Proxmox ਬੈਕਅੱਪ ਮੋਡ ਹਵਾਲੇ](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc) ਵਿੱਚ ਹਨ। **QEMU guest agent** ਗੈਸਟ ਅੰਦਰਲੀ ਸੇਵਾ ਹੈ ਜਿਸ ਰਾਹੀਂ Proxmox ਫਾਈਲ ਸਿਸਟਮ freeze ਜਾਂ thaw ਵਰਗੇ ਕੰਮ ਮੰਗ ਸਕਦਾ ਹੈ। ਚਾਲੂ ਗੈਸਟ ਵਿੱਚ agent ਚਾਲੂ ਅਤੇ ਠੀਕ ਹੋਵੇ ਤਾਂ snapshot ਬੈਕਅੱਪ ਦੌਰਾਨ ਇਹ ਕੰਮ ਹੋ ਸਕਦੇ ਹਨ। ਫਾਈਲ ਸਿਸਟਮ freeze consistency ਸੁਧਾਰਦਾ ਹੈ, ਪਰ ਡਾਟਾਬੇਸ-ਵਿਸ਼ੇਸ਼ ਰਿਕਵਰੀ ਜਾਂਚ ਦਾ ਬਦਲ ਨਹੀਂ। ਅਸਲ ਮੋਡ ਅਤੇ agent ਦੀ ਹਾਲਤ ਦਰਜ ਕਰੋ; ਇਹ ਨਾ ਮੰਨੋ ਕਿ ਨਿਯਤ ਟਾਸਕ ਤੁਹਾਡੀ ਪਸੰਦ ਦੀ ਸੈਟਿੰਗ ਵਰਤਦਾ ਹੈ।

## ਰਿਕਵਰੀ ਬਿੰਦੂ ਬਣਾਓ ਜਾਂ ਚੁਣੋ

ਰੁਟੀਨ ਰਿਕਵਰੀ ਦੀ ਜਾਂਚ ਲਈ ਹਾਲੀਆ ਸਫਲ ਨਿਯਤ ਬੈਕਅੱਪ ਵਰਤੋ। ਨਵਾਂ ਇੱਕ-ਵਾਰ ਬੈਕਅੱਪ ਚਾਹੀਦਾ ਹੋਵੇ ਤਾਂ VM ਦੀ **Backup** ਟੈਬ ਖੋਲ੍ਹੋ, **Backup now** ਚੁਣੋ, ਟਾਰਗੇਟ ਸਟੋਰੇਜ ਤੇ ਮੋਡ ਦਿਓ ਅਤੇ ਟਾਸਕ ਲੌਗ ਵਿੱਚ ਸਫਲਤਾ ਆਉਣ ਦੀ ਉਡੀਕ ਕਰੋ। Proxmox shell ਤੋਂ ਇਹ ਉਦਾਹਰਨ **120** VM ਦਾ **backup-nfs** ਸਟੋਰੇਜ ID ਉੱਤੇ snapshot ਮੋਡ ਵਿੱਚ ਬੈਕਅੱਪ ਲੈਂਦੀ ਹੈ:

```bash
vzdump 120 --storage backup-nfs --mode snapshot
```

ਦੋਵੇਂ ID ਆਪਣੇ ਨਾਲ ਬਦਲੋ। ਸਟੋਰੇਜ ਬੈਕਅੱਪ ਲੈਂਦਾ ਹੈ ਅਤੇ ਕਾਫ਼ੀ ਥਾਂ ਹੈ, ਇਹ ਪੱਕਾ ਕਰਕੇ ਹੀ ਕਮਾਂਡ ਚਲਾਓ। Proxmox ਦਾ [`vzdump` ਹਵਾਲਾ](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc) ਮੋਡ ਤੇ ਸਟੋਰੇਜ ਚੋਣਾਂ ਦੱਸਦਾ ਹੈ। ਕਮਾਂਡ ਮੁੱਕਣ ਮਗਰੋਂ ਟਾਸਕ ਲੌਗ ਵੇਖੋ। ਸਿਰਫ਼ ਫਾਈਲ ਦਾ ਨਾਂ ਨਵਾਂ ਲੱਗਣ ਕਰਕੇ ਪੁਰਾਣੇ ਬੈਕਅੱਪ ਨੂੰ ਮੌਜੂਦਾ ਰਿਕਵਰੀ ਬਿੰਦੂ ਨਾ ਮੰਨੋ।

ਟਾਰਗੇਟ **PBS** ਹੋਵੇ ਤਾਂ ਚੁਣੇ datastore ਲਈ verification ਟਾਸਕ ਚਲਾਓ ਜਾਂ ਵੇਖੋ। PBS ਦਾ [verification ਦਸਤਾਵੇਜ਼](https://pbs.proxmox.com/docs/maintenance.html) ਬੈਕਅੱਪ ਡਾਟਾ ਦੀ ਅਖੰਡਤਾ ਜਾਂਚਣ ਅਤੇ ਮੁੜ-ਮੁੜ ਜਾਂਚ ਨਿਯਤ ਕਰਨ ਦਾ ਤਰੀਕਾ ਦੱਸਦਾ ਹੈ। Verification ਖ਼ਰਾਬ ਬੈਕਅੱਪ chunk ਲੱਭਦੀ ਹੈ। **ਸਾਫ਼ verification ਇਹ ਸਾਬਤ ਨਹੀਂ ਕਰਦੀ ਕਿ ਰੀਸਟੋਰ ਕੀਤਾ OS, ਐਪ ਜਾਂ ਬਾਹਰੀ ਨਿਰਭਰਤਾ ਕੰਮ ਕਰਦੀ ਹੈ।** ਸਫਲ verification ਤੋਂ ਬਾਅਦ ਵੀ ਰੀਸਟੋਰ ਅਭਿਆਸ ਜਾਰੀ ਰੱਖੋ।

## ਅਲੱਗ VM ਉੱਤੇ ਰੀਸਟੋਰ ਕਰੋ

Proxmox ਇੰਟਰਫੇਸ ਵਿੱਚ ਸਟੋਰੇਜ ਦੇ **Backups** ਦ੍ਰਿਸ਼ ਤੋਂ ਬੈਕਅੱਪ ਚੁਣੋ ਅਤੇ **Restore** ਦਬਾਓ। ਨਾ ਵਰਤੀ VM ID ਅਤੇ ਮਨਚਾਹਾ ਟਾਰਗੇਟ ਸਟੋਰੇਜ ਦਿਓ। **Start after restore** ਬੰਦ ਰੱਖੋ। ਨਵਾਂ MAC ਪਤਾ ਬਣਾਉਣ ਦਾ ਵਿਕਲਪ ਵੇਖੋ। ਅਧਿਕਾਰਤ [`qmrestore` ਸੰਖੇਪ](https://github.com/proxmox/pve-docs/blob/master/generated/qmrestore.1-synopsis.adoc) ਵਿਲੱਖਣ VM ID, ਸਟੋਰੇਜ ਚੋਣ, ਬੇਤਰਤੀਬ Ethernet ਪਤੇ ਲਈ `--unique` ਅਤੇ ਰੀਸਟੋਰ ਕੀਤੀ VM ਨੂੰ ਨਾ ਚਲਾਉਣ ਵਾਲਾ ਡਿਫਾਲਟ ਦੱਸਦਾ ਹੈ।

ਫਾਈਲ ਵਾਲੇ `vzdump` archive ਲਈ ਇਹ shell ਕਮਾਂਡ ਉਹੀ ਢੰਗ ਦਿਖਾਉਂਦੀ ਹੈ। ਆਪਣੇ ਵਾਤਾਵਰਣ ਦੇ archive path, ਨਵੀਂ VM ID ਅਤੇ storage ID ਦਿਓ:

```bash
qmrestore /path/to/vzdump-qemu-120-2026_10_11-02_00_00.vma.zst 920 --storage local-lvm --unique 1
```

Proxmox ਦਾ [ਰੀਸਟੋਰ ਵੇਰਵਾ](https://github.com/proxmox/pve-docs/blob/master/qmrestore.adoc) ਦੱਸਦਾ ਹੈ ਕਿ ਟਾਰਗੇਟ ਸਟੋਰੇਜ ਨਾ ਦੇਣ ਉੱਤੇ ਅਸਲ ਸਟੋਰੇਜ ਵਰਤਣ ਦੀ ਕੋਸ਼ਿਸ਼ ਹੁੰਦੀ ਹੈ। ਟੈਸਟ ਨੋਡ ਉੱਤੇ ਪੁਰਾਣਾ ਸਟੋਰੇਜ ਨਾ ਹੋਵੇ ਤਾਂ **`--storage`** ਦਿਓ। ਅਭਿਆਸ ਲਈ **`--force`** ਨਾ ਵਰਤੋ। ਇਹ ਵਿਕਲਪ ਮੌਜੂਦਾ VM ਉੱਤੇ ਲਿਖਣ ਦਿੰਦਾ ਹੈ, ਜਦਕਿ ਇਸ ਵਿਧੀ ਨੂੰ ਨਾ ਵਰਤੀ ID ਚਾਹੀਦੀ ਹੈ। PBS ਬੈਕਅੱਪ ਵੀ Proxmox ਇੰਟਰਫੇਸ ਤੋਂ ਰੀਸਟੋਰ ਹੁੰਦੇ ਹਨ। PBS snapshot ਦੀ ਸਟੋਰੇਜ ਐਂਟਰੀ ਚੁਣੋ; ਇਸਨੂੰ ਸਥਾਨਕ `.vma.zst` ਫਾਈਲ ਨਾ ਸਮਝੋ।

ਪਹਿਲੇ ਬੂਟ ਤੋਂ ਪਹਿਲਾਂ ਹਰ ਰੀਸਟੋਰ ਕੀਤੀ ਨੈੱਟਵਰਕ ਇੰਟਰਫੇਸ ਵੇਖੋ, ਦੂਜੀਆਂ ਅਤੇ passthrough ਇੰਟਰਫੇਸਾਂ ਸਮੇਤ। **MAC ਪਤਾ** ਨੈੱਟਵਰਕ ਇੰਟਰਫੇਸ ਦੀ ਪਛਾਣ ਕਰਦਾ ਹੈ। **DNS** ਨਾਂ ਨੂੰ ਪਤਿਆਂ ਨਾਲ ਜੋੜਦਾ ਹੈ। **DHCP** ਨੈੱਟਵਰਕ ਸੈਟਿੰਗਾਂ ਦਿੰਦਾ ਹੈ। **VLAN** ਸਾਂਝੇ ਹਾਰਡਵੇਅਰ ਉੱਤੇ ਚੱਲਦਾ ਤਰਕਸੰਗਤ ਨੈੱਟਵਰਕ ਹੈ। **Virtual TPM** ਗੈਸਟ ਦੀ ਸੁਰੱਖਿਆ ਹਾਲਤ ਰੱਖਦਾ ਹੈ। ਹਰ ਇੰਟਰਫੇਸ ਡਿਸਕਨੈਕਟ ਕਰੋ ਜਾਂ ਸਿਰਫ਼ ਅਲੱਗ ਟੈਸਟ ਹਿੱਸੇ ਨਾਲ ਜੋੜੋ। ਪੱਕਾ ਕਰੋ ਕਿ ਕੋਈ ਪ੍ਰੋਡਕਸ਼ਨ route, DNS ਰਸਤਾ, DHCP ਸੇਵਾ, ਪ੍ਰਬੰਧਨ ਨੈੱਟਵਰਕ ਜਾਂ ਬਾਹਰੀ ਇੰਟੀਗ੍ਰੇਸ਼ਨ ਪਹੁੰਚ ਵਿੱਚ ਨਾ ਹੋਵੇ। ਵਰਕਲੋਡ ਨੂੰ ਹੋਰ ਟੈਸਟ ਸੇਵਾ ਚਾਹੀਦੀ ਹੋਵੇ ਤਾਂ ਅਲੱਗ ਨੈੱਟਵਰਕ ਉੱਤੇ ਟੈਸਟ ਕਾਪੀ ਦਿਓ। ਸਰੋਤ ਨਾਲ ਡਿਸਕ ਮੈਪਿੰਗ, firmware, virtual TPM ਦੀਆਂ ਲੋੜਾਂ ਅਤੇ ਖ਼ਾਸ ਯੰਤਰ ਮਿਲਾਓ। ਬਾਹਰੀ ਡਿਸਕਾਂ, passthrough ਯੰਤਰਾਂ ਅਤੇ VM ਤੋਂ ਬਾਹਰ ਰੱਖੇ ਗੁਪਤ ਡਾਟੇ ਲਈ ਵੱਖਰੀ ਯੋਜਨਾ ਚਾਹੀਦੀ ਹੈ।

## ਗੈਸਟ ਅਤੇ ਵਰਕਲੋਡ ਦੀ ਜਾਂਚ ਕਰੋ

ਰੀਸਟੋਰ ਕੀਤੀ VM ਚਲਾਓ ਅਤੇ ਪਹਿਲਾਂ console ਵਰਤੋ। ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ OS ਬੂਟ ਹੁੰਦਾ ਹੈ, ਸਾਰੇ ਉਮੀਦਵਾਰ volume mount ਹਨ, ਘੜੀ ਠੀਕ ਹੈ ਅਤੇ ਐਪ ਚਲਦੀ ਹੈ। ਫਿਰ ਪਹਿਲਾਂ ਲਿਖੀ ਪਾਸ ਸ਼ਰਤ ਜाँचੋ। ਜਾਣੀ-ਪਛਾਣੀ ਡਾਟਾ ਆਈਟਮ ਦਾ ਮੁੱਲ ਅਤੇ timestamp ਬੈਕਅੱਪ ਤੋਂ ਪਹਿਲਾਂ ਵਾਲੇ ਨਾਲ ਮਿਲਾਓ। ਲੌਗਇਨ prompt ਜਾਂ ਚੱਲਦੀ process ਇਕੱਲੀ ਇਹ ਨਹੀਂ ਦਿਖਾਉਂਦੀ ਕਿ ਸੇਵਾ ਕੋਲ ਸਹੀ ਡਾਟਾ ਹੈ।

| ਜਾਂਚ | ਪਾਸ ਹੋਣ ਦੀ ਸ਼ਰਤ |
|---|---|
| **ਬੂਟ** | ਗੈਸਟ repair mode ਜਾਂ ਮੁੜ-ਮੁੜ recovery prompt ਤੋਂ ਬਿਨਾਂ ਆਮ ਲੌਗਇਨ ਤੱਕ ਪਹੁੰਚਦਾ ਹੈ। |
| **ਡਿਸਕਾਂ** | ਬੈਕਅੱਪ ਵਿੱਚ ਸ਼ਾਮਲ ਹਰ ਡਿਸਕ ਦਿਖਦੀ, mount ਹੁੰਦੀ ਅਤੇ ਉਮੀਦਵਾਰ ਡਾਟਾ ਰੱਖਦੀ ਹੈ। |
| **ਸੇਵਾ** | ਪ੍ਰਤੀਨਿਧੀ ਸਥਾਨਕ ਬੇਨਤੀ ਜਾਂ ਪੜ੍ਹਨ ਦੀ ਕਾਰਵਾਈ ਸਫਲ ਹੁੰਦੀ ਹੈ। |
| **ਰਿਕਵਰੀ ਬਿੰਦੂ** | ਰੀਸਟੋਰ ਕੀਤਾ ਡਾਟਾ ਦਰਜ RPO ਪੂਰਾ ਕਰਦਾ ਹੈ। |
| **ਰਿਕਵਰੀ ਸਮਾਂ** | ਰੀਸਟੋਰ, ਬੂਟ ਅਤੇ ਸੇਵਾ ਤਸਦੀਕ ਦਰਜ RTO ਪੂਰਾ ਕਰਦੇ ਹਨ। |
| **ਅਲੱਗਾਵ** | ਕਿਸੇ ਪ੍ਰੋਡਕਸ਼ਨ ਪਤੇ, ਟਾਸਕ ਜਾਂ ਇੰਟੀਗ੍ਰੇਸ਼ਨ ਨੂੰ ਦੁਹਰਾ ਟ੍ਰੈਫਿਕ ਨਹੀਂ ਜਾਂਦਾ। |

ਨਿਯਤ ਟਾਸਕ, notification hook, ਬੈਕਅੱਪ ਏਜੰਟ ਅਤੇ ਐਪ credentials ਵੇਖਦੇ ਸਮੇਂ ਰੀਸਟੋਰ ਕੀਤਾ ਗੈਸਟ ਅਲੱਗ ਰੱਖੋ। ਅਸਲ ਗਾਹਕ ਸੁਨੇਹੇ ਭੇਜਣ ਜਾਂ ਪ੍ਰੋਡਕਸ਼ਨ ਸੇਵਾ ਵਿੱਚ ਲਿਖਣ ਵਾਲੀ ਜਾਂਚ ਨਾ ਚਲਾਓ। ਜਾਂਚ ਫੇਲ੍ਹ ਹੋਵੇ ਤਾਂ ਸਹੀ ਪੜਾਅ ਦਰਜ ਕਰੋ। **ਬੈਕਅੱਪ ਅਖੰਡਤਾ ਦੀ ਨਾਕਾਮੀ**, **VM ਬੂਟ ਦੀ ਨਾਕਾਮੀ**, **ਡਾਟਾ ਗੁੰਮ** ਅਤੇ **ਐਪ ਦੀ ਨਾਕਾਮੀ** ਵੱਖਰੀਆਂ ਰੱਖੋ। ਹਰ ਇੱਕ ਦਾ ਹੱਲ ਵੱਖਰਾ ਹੈ।

| ਨਾਕਾਮੀ ਦੀ ਕਿਸਮ | ਪੁਸ਼ਟੀ ਦਾ ਸਬੂਤ | ਪਹਿਲਾ ਸੁਧਾਰ | ਮੁੜ ਜਾਂਚ |
|---|---|---|---|
| **ਬੈਕਅੱਪ ਅਖੰਡਤਾ** | verification ਜਾਂ restore ਟਾਸਕ ਖ਼ਰਾਬ ਡਾਟਾ ਦੱਸਦਾ ਹੈ | ਹੋਰ ਤਸਦੀਕ ਕੀਤੀ ਰਿਕਵਰੀ ਬਿੰਦੂ ਚੁਣੋ ਅਤੇ ਸਟੋਰੇਜ ਦੀ ਸਿਹਤ ਵੇਖੋ | verification ਅਤੇ restore ਦੁਹਰਾਓ |
| **VM ਬੂਟ** | console firmware, disk ਜਾਂ recovery ਗਲਤੀ ਦਿਖਾਉਂਦਾ ਹੈ | firmware, disk ਮੈਪਿੰਗ ਅਤੇ boot ਕ੍ਰਮ ਸਰੋਤ ਨਾਲ ਮਿਲਾਓ | ਅਲੱਗ ਕਾਪੀ ਬੂਟ ਕਰਕੇ console ਨਤੀਜਾ ਦਰਜ ਕਰੋ |
| **ਡਾਟਾ ਗੁੰਮ** | ਉਮੀਦਵਾਰ ਫਾਈਲ, volume ਜਾਂ ਡਾਟਾਬੇਸ ਰਿਕਾਰਡ ਨਹੀਂ | ਛੱਡੀ ਡਿਸਕ, mount, snapshot ਅਤੇ ਬਾਹਰੀ ਨਿਰਭਰਤਾ ਵੇਖੋ | ਨਾਮਿਤ ਫਾਈਲ ਜਾਂ ਡਾਟਾ ਜਾਂਚ ਮੁੜ ਕਰੋ |
| **ਐਪ** | ਗੈਸਟ ਬੂਟ ਹੁੰਦਾ ਹੈ ਪਰ ਸੇਵਾ ਜਾਂਚ ਫੇਲ੍ਹ | ਸੇਵਾ ਲੌਗ, credentials, ਨਿਰਭਰਤਾ ਅਤੇ ਰਿਕਵਰੀ ਕਦਮ ਵੇਖੋ | ਉਹੀ ਸਥਾਨਕ health check ਤੇ ਵਰਕਲੋਡ ਜਾਂਚ ਚਲਾਓ |

Proxmox PBS ਬੈਕਅੱਪ ਲਈ [ਇੱਕ ਫਾਈਲ ਰੀਸਟੋਰ](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc) ਦੀ ਸਹੂਲਤ ਦਿੰਦਾ ਹੈ। ਜੇ ਵਰਕਲੋਡ ਨੂੰ ਇੱਕ ਫਾਈਲ ਦੀ ਰਿਕਵਰੀ ਚਾਹੀਦੀ ਹੈ ਤਾਂ ਇਹ ਰਸਤਾ ਜਾਂਚੋ। ਮੁੜ ਮਿਲੀ ਫਾਈਲ ਪੂਰੇ VM ਬੂਟ ਅਤੇ ਸੇਵਾ ਜਾਂਚ ਦਾ ਬਦਲ ਨਹੀਂ। Proxmox PBS ਤੋਂ live restore ਵੀ ਦਿੰਦਾ ਹੈ। ਦਸਤਾਵੇਜ਼ ਦੱਸਦਾ ਹੈ ਕਿ live restore ਫੇਲ੍ਹ ਹੋਵੇ ਤਾਂ VM ਦੀ ਹਾਲਤ ਅਣਪਰਿਭਾਸ਼ਿਤ ਰਹਿੰਦੀ ਹੈ। ਇਸ ਯੋਜਨਾਬੱਧ ਅਭਿਆਸ ਲਈ ਆਮ ਪੂਰਾ ਰੀਸਟੋਰ ਕਰੋ।

## ਨਤੀਜਾ ਦਰਜ ਕਰਕੇ ਅਭਿਆਸ ਮੁਕਾਓ

ਸਰੋਤ VM ID, ਬੈਕਅੱਪ ਸਟੋਰੇਜ, ਬੈਕਅੱਪ timestamp, ਮੋਡ, ਨਵੀਂ VM ID, ਟਾਰਗੇਟ ਸਟੋਰੇਜ, ਨੈੱਟਵਰਕ ਅਲੱਗਾਵ, ਰੀਸਟੋਰ ਦੇ ਸ਼ੁਰੂ ਤੇ ਅੰਤ ਦੇ ਸਮੇਂ, ਐਪ ਜਾਂਚ, ਡਾਟਾ timestamp ਅਤੇ ਫੇਲ੍ਹ ਜਾਂਚਾਂ ਦਰਜ ਕਰੋ। ਮਾਪੇ ਰਿਕਵਰੀ ਬਿੰਦੂ ਅਤੇ ਸਮੇਂ ਨੂੰ ਟੀਚਿਆਂ ਨਾਲ ਮਿਲਾਓ। ਨਾਕਾਮੀ ਤਦ ਹੀ ਲਾਭਦਾਇਕ ਸਬੂਤ ਹੈ ਜਦੋਂ ਤੁਸੀਂ ਬੈਕਅੱਪ ਯੋਜਨਾ ਬਦਲ ਕੇ ਅਭਿਆਸ ਦੁਹਰਾਉਂਦੇ ਹੋ।

ਟੈਸਟ ਖਤਮ ਹੋਣ ਉੱਤੇ ਰੀਸਟੋਰ ਕੀਤੀ VM ਬੰਦ ਕਰੋ। ਨਤੀਜਾ ਸੰਭਾਲਣ ਮਗਰੋਂ ਹੀ ਟੈਸਟ ਕਾਪੀ ਹਟਾਓ ਅਤੇ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਪ੍ਰੋਡਕਸ਼ਨ VM ਅਜੇ ਵੀ ਉਮੀਦ ਅਨੁਸਾਰ ਚੱਲਦੀ ਹੈ। ਬੈਕਅੱਪ ਆਮ retention policy ਅਨੁਸਾਰ ਰੱਖੋ। ਇੱਕ ਅਭਿਆਸ ਪਾਸ ਕਰਾਉਣ ਲਈ retention ਨਾ ਬਦਲੋ।

ਸਟੋਰੇਜ, ਗੈਸਟ ਜਾਂ ਬੈਕਅੱਪ ਸੈਟਿੰਗ ਵਿੱਚ ਵੱਡੇ ਬਦਲਾਅ ਮਗਰੋਂ ਜਾਂਚ ਦੁਹਰਾਓ। ਮਹੱਤਵਪੂਰਨ VM ਵਾਰ-ਵਾਰ ਚੁਣੋ, ਜਿਨ੍ਹਾਂ ਵਿੱਚ ਛੱਡੀਆਂ ਡਿਸਕਾਂ ਜਾਂ ਬਾਹਰੀ ਨਿਰਭਰਤਾ ਵਾਲੇ ਗੈਸਟ ਵੀ ਹੋਣ। [Hyper-V ਤੋਂ Proxmox ਮਾਈਗ੍ਰੇਸ਼ਨ ਗਾਈਡ](/articles/hyper-v-to-proxmox-migration-checklist/) ਸਰੋਤ VM ਹਟਾਉਣ ਤੋਂ ਪਹਿਲਾਂ ਇਹ ਰਿਕਵਰੀ ਸਬੂਤ ਵਰਤਦੀ ਹੈ। **ਕੰਮ ਦਾ ਬੈਕਅੱਪ ਜਾਣਿਆ ਰੀਸਟੋਰ ਰਸਤਾ, ਪਰਖਿਆ ਵਰਕਲੋਡ ਅਤੇ ਮਾਪਿਆ ਰਿਕਵਰੀ ਬਿੰਦੂ ਦਿੰਦਾ ਹੈ।**

## ਅਗਲੇ ਕਦਮ

ਸਟੋਰੇਜ, ਗੈਸਟ ਜਾਂ ਬੈਕਅੱਪ ਬਦਲਣ ਮਗਰੋਂ ਅਭਿਆਸ ਦੁਹਰਾਓ। ਫਾਈਲ ਰਿਕਵਰੀ ਲਈ [ਹੋਮਲੈਬ ਬੈਕਅੱਪ ਰੀਸਟੋਰ ਅਭਿਆਸ](/articles/homelab-backup-restore-drill/) ਵੇਖੋ।
