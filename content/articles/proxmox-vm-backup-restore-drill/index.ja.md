バックアップタスクが緑色なら、Proxmoxがバックアップを書き込んだことは分かります。ゲストが起動するか、データが新しいか、主要なサービスが動くかは分かりません。**新しいVM IDを使い、隔離ネットワーク上にコピーを復元してください。** 障害によってテストを強いられる前に、復旧できる証拠を得られます。

<!--more-->

この演習では、1台の**Proxmox VE仮想マシン**を扱います。コンテナのバックアップルールは異なり、特にbind mountとdevice mountに注意が必要です。サイトの[ホームラボ向けバックアップ復元テスト](/articles/homelab-backup-restore-drill/)では、より広い範囲のファイル復旧を扱います。ここではProxmox VMのバックアップとワークロードをテストします。

**ゲスト**とは、仮想マシン内で動作するオペレーティングシステムです。**Bind mount**と**device mount**は、ホストのリソースをゲストに公開します。これらのリソースは別の復旧計画でテストしてください。

## 要点

- **最初に成功条件を決める：** データ項目、サービス確認、許容できる復旧時間を選びます。
- **対象範囲を確認する：** VMバックアップは**No backup**に設定されたディスクを除外し、外部サービスや除外データを再作成できません。
- **別のVMに復元する：** 未使用のVM IDを使い、復元したネットワークを本番環境から隔離します。
- **証拠を記録する：** バックアップの経過時間、復元時間、起動、ディスクの有無、実際のアプリ確認を測定します。

## 始める前に

安全にバックアップをテストできるVMを選びます。Proxmox管理者アクセス、ファイルストレージまたはProxmox Backup Server（PBS）上の完了済みバックアップ、2台目のVMを置ける空き容量、隔離bridgeまたは切断したネットワークデバイスが必要です。隔離bridgeは、本番LANへの経路を持たないProxmox仮想ネットワークです。ない場合は、切断したアダプターかテストVLANを使います。本番VMは稼働させたままにします。他のゲストが使っていないことを確認し、新しいVM ID（例：**920**）を確保します。完全な復元とワークロードテストに必要な時間を見積もってください。

復元前に合格条件を書きます。ファイルサーバーなら、最近のファイルと期待するチェックサムまたは内容を選びます。データベースなら、安全な読み取り専用クエリとバックアップ前に書き込まれたレコードを選びます。Webサービスなら、ローカルのヘルスチェックと代表的なページを選びます。許容できる最新データの日時、**目標復旧時点（RPO）**、サービス復旧に許される時間である**目標復旧時間（RTO）**を記録します。起動画面だけではこれらの確認を満たしません。

| 記録項目 | 証拠の例 |
|---|---|
| **バックアップ時点** | スナップショットの時刻と最後に存在するはずのデータ項目 |
| **復旧先** | 未使用のVM ID、保存先ストレージ、隔離bridge |
| **ワークロードテスト** | ログイン、ボリュームのマウント、アプリからの読み取り |
| **時間制限** | 復元とサービス確認の開始時刻、終了時刻 |

名前、IPアドレス、MACアドレス、スケジュールされたジョブ、外部連携を確認するまで、復元したゲストを本番ネットワークに接続しないでください。複製されたIDは稼働中のVMと競合したり、作業を二重に送信したりする可能性があります。

## バックアップの対象範囲を確認する

**バージョンの対象範囲：** この記事の準備中に、以下の例は実行していません。テスト前に`pveversion --verbose`の出力を記録してください。インストール済みのProxmox VEリリースに対応するドキュメントを使います。テスト記録にはストレージバックエンド、ゲストの種類、コマンド出力を残してください。

Proxmoxノードで次の読み取り専用コマンドを実行すると、元のVMの設定を確認できます。**120**を元のVM IDに置き換えます。

```bash
qm config 120
```

各仮想ディスクとバックアップ設定を一覧にします。Proxmoxの[VMディスクに関するドキュメント](https://github.com/proxmox/pve-docs/blob/master/qm.adoc)によると、**No backup**オプションを指定したディスクはVMバックアップから除外されます。アプリデータが除外ディスク、ホストマウント、直接パススルーしたハードウェア、リモートサービスにないか確認します。それぞれ別の復元手順を記録します。VMの起動テストだけでは、除外データが保護されている証拠になりません。

最新バックアップのタイムスタンプ、サイズ、タスクログ、保存場所を確認します。Proxmoxの画面でバックアップストレージの**Backups**ビューまたはVMの**Backup**タブを開きます。タスクがエラーなく終了したことを確認してください。Proxmoxの[バックアップドキュメント](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc)では、通常のバックアップファイルと、重複排除されたチャンクやメタデータを保持するPBSストレージを区別しています。

| バックアップモード | VMの動作 | この演習での判断 |
|---|---|---|
| **Snapshot** | 稼働中のVMを短い停止でバックアップします。ゲストの書き込みには小さな整合性リスクがあります。 | ワークロードがこの復旧時点を許容する場合、通常のテストに適します。 |
| **Stop** | バックアップ開始時にゲストを停止し、最も高い整合性を得ます。 | ワークロードが正常なシャットダウンを必要とし、停止時間を許容できる場合に使います。 |
| **Suspend** | snapshotモードの前にゲストを一時停止します。一般的な整合性向上はないまま停止時間が増えます。 | snapshotより優れていると考えて、suspendを既定にしないでください。 |

モードごとのトレードオフは[Proxmoxのバックアップモード資料](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc)に記載されています。**QEMU guest agent**はゲスト内のサービスで、Proxmoxがファイルシステムのフリーズや再開などを要求できるようにします。guest agentが有効で正常な稼働中のゲストは、snapshotバックアップ時にこれらの操作をサポートします。ファイルシステムのフリーズは整合性を向上させますが、データベース固有の復旧確認の代わりにはなりません。スケジュールされたタスクが希望の設定を使うと思い込まず、実際のモードとguest agentの状態を記録してください。

## 復旧時点を作成または選択する

通常の復旧をテストする場合は、最近の成功したスケジュールバックアップを使います。新しい単発バックアップが必要なら、VMの**Backup**タブを開いて**Backup now**を選択し、保存先とモードを設定します。タスクログで成功を確認してください。Proxmoxシェルでは、次の例でVM **120**を**backup-nfs**というストレージIDにsnapshotモードでバックアップします。

```bash
vzdump 120 --storage backup-nfs --mode snapshot
```

両方のIDを環境に合わせて置き換えます。ストレージがバックアップを受け付け、十分な空き容量があると確認してから実行してください。Proxmoxの[`vzdump`資料](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc)にはモードとストレージのオプションが記載されています。コマンド終了後にタスクログを確認します。ファイル名が新しく見えるというだけで、古いバックアップを現在の復旧時点として扱わないでください。

保存先が**PBS**なら、選択したデータストアの検証タスクを実行または確認します。PBSの[検証ドキュメント](https://pbs.proxmox.com/docs/maintenance.html)では、バックアップデータの整合性を検証し、繰り返し実行する方法を説明しています。検証は破損したバックアップチャンクを検出します。**検証に成功しても、復元したOS、アプリ、外部依存関係が動作する証拠にはなりません。** 検証結果が正常でも、復元演習を続けてください。

## 隔離したVMに復元する

Proxmoxの画面でストレージの**Backups**ビューからバックアップを選び、**Restore**を選択します。未使用のVM IDと保存先ストレージを入力します。**Start after restore**はオフのままにします。新しいMACアドレスを生成するオプションを確認してください。公式の[`qmrestore`概要](https://github.com/proxmox/pve-docs/blob/master/generated/qmrestore.1-synopsis.adoc)には、一意のVM ID、ストレージの選択、ランダムなEthernetアドレスを生成する`--unique`、復元したVMを起動しない既定動作が記載されています。

ファイル形式の`vzdump`アーカイブでは、次のシェルコマンドが同じパターンを示します。アーカイブパス、新しいVM ID、ストレージIDを環境の値に置き換えます。

```bash
qmrestore /path/to/vzdump-qemu-120-2026_10_11-02_00_00.vma.zst 920 --storage local-lvm --unique 1
```

Proxmoxの[復元に関する説明](https://github.com/proxmox/pve-docs/blob/master/qmrestore.adoc)によると、保存先を指定しない復元では元のストレージが使われます。テストノードに古いストレージがない場合は**`--storage`**を指定してください。演習では**`--force`**を使わないでください。このオプションは既存VMの上書きを許可しますが、この手順では未使用IDが必要です。PBSバックアップもProxmoxの画面から復元します。PBSスナップショットをローカルの`.vma.zst`ファイルとして扱わず、PBSスナップショットのストレージ項目を選んでください。

初回起動の前に、復元したすべてのネットワークインターフェースを確認します。セカンダリやパススルーのインターフェースも対象です。**MACアドレス**はネットワークインターフェースを識別します。**DNS**は名前をアドレスに対応付けます。**DHCP**はネットワーク設定を割り当てます。**VLAN**は共有ハードウェア上で運ぶ論理ネットワークです。**仮想TPM**はゲストのセキュリティ状態を保持します。すべてのインターフェースを切断するか、隔離テストセグメントだけに接続してください。本番ルート、DNS経路、DHCPサービス、管理ネットワーク、外部連携に到達できないことを確認します。ワークロードに別のテストサービスが必要なら、隔離ネットワーク上にテスト用コピーを用意します。元のVMとディスク割り当て、ファームウェア、仮想TPMの要件、特殊デバイスを比較してください。外部ディスク、パススルーデバイス、VM外に保存された秘密情報には別の計画が必要です。

## ゲストとワークロードをテストする

復元したVMを起動し、まずコンソールを使います。OSが起動すること、必要なボリュームがすべてマウントされること、時計が正しいこと、アプリが起動することを確認してください。その後、事前に決めた合格条件を実行します。既知のデータ項目をバックアップ前の値とタイムスタンプに照らして比較します。ログイン画面やプロセスの実行中表示だけでは、サービスに正しいデータがあるとは分かりません。

| テスト | 合格条件 |
|---|---|
| **起動** | 修復モードや繰り返す復旧プロンプトなしで通常のログイン画面に到達する。 |
| **ディスク** | バックアップに含まれる各ディスクが表示され、マウントされ、期待するデータを保持している。 |
| **サービス** | 代表的なローカル要求または読み取りが成功する。 |
| **復旧時点** | 復元データが記録済みのRPOを満たす。 |
| **復旧時間** | 復元、起動、サービス確認が記録済みのRTOを満たす。 |
| **隔離** | 本番アドレス、ジョブ、連携先に重複した通信が届かない。 |

スケジュールされたタスク、通知hook、バックアップエージェント、アプリの認証情報を確認する間も、復元したゲストを隔離します。実際の顧客にメッセージを送ったり、本番サービスに書き込んだりするテストは避けてください。確認に失敗したら、正確な段階を記録します。**バックアップ整合性の失敗**、**VM起動の失敗**、**データ欠落**、**アプリケーションの失敗**を区別してください。それぞれ必要な修正が異なります。

| 失敗の種類 | 確認できる証拠 | 最初の修正 | 再テスト |
|---|---|---|---|
| **バックアップ整合性** | 検証または復元タスクがデータ破損を報告する | 別の検証済み復旧時点を選び、ストレージの状態を確認する | 検証と復元を繰り返す |
| **VM起動** | コンソールにファームウェア、ディスク、復旧エラーが表示される | 元のVMとファームウェア、ディスク割り当て、起動順を比較する | 隔離コピーを起動し、コンソール結果を記録する |
| **データ欠落** | 期待するファイル、ボリューム、データベースレコードがない | 除外ディスク、マウント、スナップショット、外部依存関係を確認する | 対象のファイルまたはデータを再確認する |
| **アプリケーション** | ゲストは起動するがサービス確認が失敗する | サービスログ、認証情報、依存関係、復旧手順を確認する | 同じローカルヘルスチェックとワークロードテストを実行する |

ProxmoxはPBSバックアップからの[単一ファイル復元](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc)を提供します。ワークロードでファイル復旧が必要なら、その経路をテストしてください。ファイルを復元しても、VMの完全な起動やサービスのテストの代わりにはなりません。ProxmoxはPBSからのライブ復元も提供します。ドキュメントによると、ライブ復元に失敗するとVMは未定義の状態になります。この計画的な演習では、通常の完了済み復元を使ってください。

## 結果を記録して演習を終える

ソースVM ID、バックアップストレージ、バックアップ時刻、モード、新しいVM ID、保存先、ネットワーク隔離、復元の開始・終了時刻、アプリテスト、データの時刻、失敗した確認項目を記録します。測定した復旧時点と時間を目標と比べます。失敗が有用な証拠になるのは、バックアップ計画を変更して演習を繰り返した場合です。

テスト終了後に復元VMをシャットダウンします。結果を保存し、本番VMが期待どおり動作していることを確認してからテストコピーを削除してください。バックアップは通常の保持ポリシーに従って保管します。1回の演習を成功させるためだけに保持期間を変更しないでください。

ストレージ、ゲスト、バックアップ設定に大きな変更を加えた後はテストを繰り返します。除外ディスクや外部依存関係を持つゲストを含め、重要なVMを順番にテストしてください。[Hyper-VからProxmoxへの移行ガイド](/articles/hyper-v-to-proxmox-migration-checklist/)では、ソースVMを廃止する前にこの復旧証明を使います。**使えるバックアップには、既知の復元経路、テスト済みのワークロード、測定済みの復旧時点があります。**

## 次の手順

ストレージ、ゲスト、バックアップを変更した後は演習を繰り返してください。ファイル復旧については[ホームラボ向けバックアップ復元テスト](/articles/homelab-backup-restore-drill/)を確認します。
