Зелёное задание показывает, что Proxmox записал резервную копию. Оно не подтверждает, что гость загрузится, данные будут актуальными, а основная служба заработает. **Восстановите копию с новым ID VM в изолированной сети.** Результат станет доказательством восстановления до того, как сбой вынудит вас проводить проверку.

<!--more-->

Эта проверка охватывает одну **виртуальную машину Proxmox VE**. Для контейнеров действуют другие правила резервного копирования, особенно для bind mount и подключённых устройств. [Проверка резервного копирования и восстановления домашней лаборатории](/articles/homelab-backup-restore-drill/) на сайте охватывает более широкий сценарий восстановления файлов. Здесь вы проверите резервную копию Proxmox VM и её рабочую нагрузку.

**Гость** — операционная система внутри виртуальной машины. **Bind mount** и **подключения устройств** предоставляют гостю ресурсы хоста. Проверяйте эти ресурсы по отдельному плану восстановления.

## Основные выводы

- **Сначала определите успех:** выберите элемент данных, проверку службы и допустимое время восстановления.
- **Проверьте охват:** копия VM пропускает диски с параметром **No backup** и не воссоздаёт внешние службы или исключённые данные.
- **Восстанавливайте отдельно:** используйте незанятый ID VM и держите восстановленную сеть изолированной от рабочей.
- **Записывайте доказательства:** измеряйте возраст копии, время восстановления, загрузку, наличие дисков и фактическую проверку приложения.

## Перед началом

Выберите VM, копию которой безопасно проверять. Нужны права администратора Proxmox, завершённая копия на файловом хранилище или в Proxmox Backup Server (PBS), достаточно места для второй VM и изолированный bridge или отключённое сетевое устройство. Изолированный bridge — виртуальная сеть Proxmox без маршрута в рабочую LAN. Если его нет, используйте отключённый адаптер или тестовый VLAN. Не выключайте рабочую VM. Зарезервируйте новый ID VM, например **920**, предварительно проверив, что другой гость его не использует. Выделите время на полное восстановление и проверку рабочей нагрузки.

До восстановления запишите критерии успешного прохождения. Для файлового сервера выберите недавний файл и ожидаемую контрольную сумму или содержимое. Для базы данных выберите безопасный запрос только для чтения и запись, созданную до копирования. Для веб-службы выберите локальную проверку состояния и типовую страницу. Запишите самую позднюю допустимую дату данных, **целевой показатель точки восстановления (RPO)** и время на возобновление службы, **целевой показатель времени восстановления (RTO)**. Одного экрана загрузки недостаточно.

| Что записать | Пример доказательства |
|---|---|
| **Точка резервной копии** | Время snapshot и последний ожидаемый элемент данных |
| **Цель восстановления** | Незанятый ID VM, целевое хранилище, изолированный bridge |
| **Проверка нагрузки** | Вход в систему, монтирование тома и чтение из приложения |
| **Лимит времени** | Время начала и завершения восстановления и проверки службы |

Не подключайте восстановленного гостя к рабочей сети, пока не проверите его имя, IP-адрес, MAC-адрес, запланированные задания и внешние интеграции. Скопированная идентичность может конфликтовать с работающей VM или запускать дублирующиеся задачи.

## Проверьте, что покрывает копия

**Область версий:** примеры не запускались при подготовке статьи. Перед проверкой запишите вывод `pveversion --verbose`. Используйте документацию для установленной версии Proxmox VE. В журнал проверки внесите серверную часть хранилища, тип гостя и вывод команд.

На узле Proxmox следующая команда только для чтения показывает конфигурацию исходной VM. Замените **120** на ID исходной VM:

```bash
qm config 120
```

Перечислите все виртуальные диски и их настройки копирования. В [документации Proxmox по дискам VM](https://github.com/proxmox/pve-docs/blob/master/qm.adoc) сказано, что параметр **No backup** исключает диск из резервной копии VM. Проверьте, не находятся ли данные приложения на исключённом диске, в монтировании хоста, на напрямую подключённом оборудовании или удалённой службе. Запишите отдельную процедуру восстановления для таких данных. Проверка загрузки VM не доказывает, что исключённые данные защищены.

Проверьте отметку времени, размер, журнал задания и расположение последней копии. В интерфейсе Proxmox откройте представление **Backups** хранилища копий или вкладку **Backup** VM. Убедитесь, что задание завершилось без ошибок. В [документации Proxmox по резервному копированию](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc) обычные файлы копий отличаются от хранилища PBS, которое сохраняет дедуплицированные блоки и метаданные.

| Режим копирования | Поведение VM | Решение для проверки |
|---|---|---|
| **Snapshot** | Копирует работающую VM с небольшим простоем. Запись гостя создаёт небольшой риск несогласованности. | Подходит для регулярных проверок, если рабочая нагрузка допускает эту точку восстановления. |
| **Stop** | Останавливает гостя при начале копирования и обеспечивает максимальную согласованность. | Используйте, если нагрузке нужно штатное выключение, а простой допустим. |
| **Suspend** | Приостанавливает гостя перед режимом snapshot и увеличивает простой без общего выигрыша в согласованности. | Не выбирайте suspend по умолчанию как улучшение по сравнению с snapshot. |

Компромиссы режимов описаны в [справочнике режимов резервного копирования Proxmox](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc). **QEMU Guest Agent** — служба внутри гостя, через которую Proxmox запрашивает такие действия, как заморозка и разморозка файловой системы. Работающий гость с включённым и исправным агентом поддерживает эти действия во время копирования snapshot. Заморозка файловой системы улучшает согласованность, но не заменяет отдельную проверку восстановления базы данных. Запишите фактический режим и состояние агента, а не предполагайте, что запланированное задание использует нужные настройки.

## Создайте или выберите точку восстановления

Если проверяется обычное восстановление, используйте недавнюю успешную запланированную копию. Для новой разовой копии откройте вкладку **Backup** VM, выберите **Backup now**, задайте целевое хранилище и режим, затем дождитесь успешного результата в журнале задания. В оболочке Proxmox следующий пример копирует VM **120** в хранилище с ID **backup-nfs** в режиме snapshot:

```bash
vzdump 120 --storage backup-nfs --mode snapshot
```

Замените оба ID своими значениями. Запускайте команду, только убедившись, что хранилище принимает копии и располагает достаточным местом. В [справочнике Proxmox для `vzdump`](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc) описаны параметры режима и хранилища. После выполнения команды проверьте журнал задания. Не считайте старую копию текущей точкой восстановления только потому, что имя файла выглядит свежим.

Если цель — **PBS**, запустите или проверьте задание верификации выбранного datastore. В [документации PBS по верификации](https://pbs.proxmox.com/docs/maintenance.html) описано, как проверять целостность данных и планировать повторные проверки. Верификация обнаруживает повреждённые блоки копии. **Успешная верификация не доказывает, что восстановленная ОС, приложение или внешняя зависимость работают.** Даже при успешной проверке продолжите упражнение восстановления.

## Восстановите на изолированную VM

В интерфейсе Proxmox выберите копию в представлении **Backups** хранилища и нажмите **Restore**. Укажите незанятый ID VM и целевое хранилище. Оставьте **Start after restore** выключенным. Проверьте параметр создания нового MAC-адреса. В официальной [сводке синтаксиса `qmrestore`](https://github.com/proxmox/pve-docs/blob/master/generated/qmrestore.1-synopsis.adoc) описаны уникальный ID VM, выбор хранилища, `--unique` для случайного Ethernet-адреса и стандартное поведение, при котором восстановленная VM не запускается.

Для файлового архива `vzdump` следующая команда показывает аналогичный способ. Замените путь к архиву, новый ID VM и ID хранилища значениями своей среды:

```bash
qmrestore /path/to/vzdump-qemu-120-2026_10_11-02_00_00.vma.zst 920 --storage local-lvm --unique 1
```

В [описании восстановления Proxmox](https://github.com/proxmox/pve-docs/blob/master/qmrestore.adoc) сказано, что без целевого хранилища восстановление пытается использовать исходное. Укажите **`--storage`**, если старого хранилища нет на тестовом узле. Не используйте **`--force`** в рамках проверки. Этот параметр разрешает перезаписать существующую VM, тогда как процедура требует незанятого ID. Копии PBS также восстанавливаются через интерфейс Proxmox. Выберите хранилище snapshot PBS, не рассматривайте его как локальный файл `.vma.zst`.

Перед первым запуском проверьте все восстановленные сетевые интерфейсы, включая дополнительные и напрямую переданные. **MAC-адрес** идентифицирует сетевой интерфейс. **DNS** связывает имена с адресами. **DHCP** назначает сетевые настройки. **VLAN** — логическая сеть, передаваемая через общее оборудование. **Виртуальный TPM** хранит состояние безопасности гостя. Отключите все интерфейсы или подключайте их только к изолированному тестовому сегменту. Убедитесь, что недоступны рабочие маршруты, DNS-пути, службы DHCP, сеть управления и внешние интеграции. Если нагрузке нужна другая тестовая служба, предоставьте её копию в изолированной сети. Сравните с источником сопоставление дисков, прошивку, требования виртуального TPM и специальные устройства. Для внешних дисков, переданных напрямую устройств и секретов вне VM нужны отдельные планы.

## Проверьте гостя и рабочую нагрузку

Запустите восстановленную VM и сначала воспользуйтесь консолью. Убедитесь, что ОС загрузилась, все нужные тома смонтированы, часы показывают верное время, а приложение запустилось. Затем выполните условие успеха, записанное заранее. Сравните известный элемент данных с его значением и отметкой времени до копирования. Экран входа или запущенный процесс сами по себе не подтверждают, что у службы есть правильные данные.

| Проверка | Условие успеха |
|---|---|
| **Запуск** | Гость доходит до обычного входа без режима восстановления и повторяющихся запросов на восстановление. |
| **Диски** | Каждый включённый в копию диск виден, смонтирован и содержит ожидаемые данные. |
| **Служба** | Представительный локальный запрос или чтение завершается успешно. |
| **Точка восстановления** | Восстановленные данные соответствуют записанному RPO. |
| **Время восстановления** | Восстановление, запуск и проверка службы укладываются в записанный RTO. |
| **Изоляция** | Ни один рабочий адрес, задача или интеграция не получает дублирующий трафик. |

Не выводите восстановленного гостя из изоляции, пока проверяете запланированные задачи, хуки уведомлений, агенты копирования и учётные данные приложения. Не запускайте тест, который отправляет настоящие сообщения клиентам или записывает данные в рабочие службы. Если проверка не пройдена, запишите точный этап. Различайте **ошибку целостности копии**, **ошибку запуска VM**, **отсутствующие данные** и **ошибку приложения**. Для каждого случая требуется отдельное исправление.

| Тип сбоя | Подтверждающие данные | Первое исправление | Повторная проверка |
|---|---|---|---|
| **Целостность копии** | Задание верификации или восстановления сообщает о повреждении данных | Выберите другую проверенную точку восстановления и проверьте состояние хранилища | Повторите верификацию и восстановление |
| **Запуск VM** | Консоль показывает ошибки прошивки, диска или восстановления | Сравните прошивку, сопоставление дисков и порядок загрузки с источником | Запустите изолированную копию и запишите результат консоли |
| **Нет данных** | Отсутствует ожидаемый файл, том или запись базы данных | Проверьте исключённые диски, монтирования, snapshot и внешние зависимости | Повторите проверку указанного файла или данных |
| **Приложение** | Гость запускается, но проверка службы не проходит | Проверьте журналы службы, учётные данные, зависимости и шаги восстановления | Выполните ту же локальную проверку и тест нагрузки |

Proxmox поддерживает [восстановление отдельных файлов из копий PBS](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc). Используйте его, чтобы проверить восстановление файла, если это нужно нагрузке. Восстановленный файл не заменяет полный запуск VM и проверку службы. Proxmox поддерживает и live restore из PBS. В документации указано, что при ошибке live restore VM остаётся в неопределённом состоянии. Для этого планового упражнения используйте обычное завершённое восстановление.

## Запишите результат и завершите упражнение

Запишите ID исходной VM, хранилище копии, время копирования, режим, новый ID VM, целевое хранилище, изоляцию сети, время начала и завершения восстановления, тест приложения, отметку времени данных и неудачные проверки. Сравните измеренную точку и время восстановления с целями. Сбой полезен как доказательство, только если вы измените план копирования и повторите упражнение.

После теста выключите восстановленную VM. Удаляйте её тестовую копию только после сохранения результата и проверки, что рабочая VM по-прежнему функционирует. Храните копию по обычной политике хранения. Не меняйте срок хранения только ради успешного прохождения одного упражнения.

Повторяйте тест после крупных изменений хранилища, гостя или настроек копирования. По очереди проверяйте важные VM, включая гостей с исключёнными дисками или внешними зависимостями. В [руководстве по миграции с Hyper-V на Proxmox](/articles/hyper-v-to-proxmox-migration-checklist/) это доказательство восстановления используется перед выводом исходной VM из эксплуатации. **У пригодной резервной копии есть известный путь восстановления, проверенная нагрузка и измеренная точка восстановления.**

## Что делать дальше

Повторите упражнение после изменений хранилища, гостя или копирования. Для восстановления файлов прочитайте [проверку резервного копирования и восстановления домашней лаборатории](/articles/homelab-backup-restore-drill/).
