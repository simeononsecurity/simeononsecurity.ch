绿色的备份任务表示 Proxmox 已写入备份。它无法说明来宾是否能启动、数据是否足够新，或主要服务是否可用。**请使用新的 VM ID，在隔离网络中恢复一个副本。** 这样你可以在故障迫使你测试之前，先获得恢复能力的证据。

<!--more-->

本演练针对一台 **Proxmox VE 虚拟机**。容器的备份规则不同，尤其是 bind mount 和设备挂载。本站的[家庭实验室备份恢复演练](/articles/homelab-backup-restore-drill/)涵盖更广泛的文件恢复。这里将测试 Proxmox VM 备份及其工作负载。

**来宾**是运行在虚拟机内部的操作系统。**Bind mount** 和**设备挂载**会向来宾公开主机资源。应通过单独的恢复计划测试这些资源。

## 要点

- **先定义成功条件：** 指定一个数据项、一项服务检查和可接受的恢复时间。
- **检查覆盖范围：** VM 备份会跳过标记为 **No backup** 的磁盘，也无法重新创建外部服务或被排除的数据。
- **单独恢复：** 使用未占用的 VM ID，并让恢复后的网络与生产环境隔离。
- **记录证据：** 测量备份时效、恢复时间、启动情况、磁盘是否存在，以及实际应用检查结果。

## 开始之前

选择一台适合安全测试备份的 VM。你需要 Proxmox 管理员权限、存放在文件存储或 Proxmox Backup Server (PBS) 中的已完成备份、可容纳第二台 VM 的空间，以及隔离 bridge 或已断开的网络设备。隔离 bridge 是无法路由到生产 LAN 的 Proxmox 虚拟网络。如果没有这种 bridge，请使用断开的网卡或测试 VLAN。让生产 VM 保持运行。确认没有其他来宾使用后，预留一个新的 VM ID，例如 **920**。为完整恢复和工作负载测试留出足够时间。

恢复前先写下通过条件。对于文件服务器，选择一个近期文件及其预期校验和或内容。对于数据库，选择安全的只读查询和一个在备份前写入的记录。对于 Web 服务，选择本地健康检查和一个有代表性的页面。记录可接受的最新数据时间、**恢复点目标 (RPO)**，以及恢复服务所允许的时间，即**恢复时间目标 (RTO)**。仅仅看到启动画面并不满足这些检查。

| 记录项 | 证据示例 |
|---|---|
| **备份点** | 快照时间和最后一个预期数据项 |
| **恢复目标** | 未占用的 VM ID、目标存储、隔离 bridge |
| **工作负载测试** | 登录、挂载卷并从应用中读取数据 |
| **时间限制** | 恢复和服务检查的开始与结束时间 |

检查名称、IP 地址、MAC 地址、计划任务和外部集成之前，不要将恢复的来宾连接到生产网络。复制的身份可能与运行中的 VM 冲突，或重复提交任务。

## 检查备份覆盖的内容

**版本范围：** 编写本文时没有执行这些示例。测试前记录 `pveversion --verbose` 的输出。使用与已安装 Proxmox VE 版本匹配的文档，并在演练记录中注明存储后端、来宾类型和命令输出。

在 Proxmox 节点上，以下只读命令会显示源 VM 配置。将 **120** 替换为源 VM ID：

```bash
qm config 120
```

列出每个虚拟磁盘及其备份设置。Proxmox 的 [VM 磁盘文档](https://github.com/proxmox/pve-docs/blob/master/qm.adoc)说明，**No backup** 选项会将磁盘排除在 VM 备份之外。检查应用数据是否位于被排除的磁盘、主机挂载、直通硬件或远程服务中，并记录相应的独立恢复步骤。VM 启动测试并不能证明被排除的数据受到保护。

检查最近备份的时间戳、大小、任务日志和存储位置。在 Proxmox 界面中打开备份存储的 **Backups** 视图，或 VM 的 **Backup** 选项卡。确认任务没有报错并已完成。Proxmox 的[备份文档](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc)区分普通备份文件和 PBS 存储，后者会保存去重后的数据块与元数据。

| 备份模式 | VM 行为 | 本演练的选择 |
|---|---|---|
| **Snapshot** | 以较短停机时间备份运行中的 VM。来宾写入会带来轻微的一致性风险。 | 如果工作负载能够接受此恢复点，可用于常规测试。 |
| **Stop** | 在备份开始时关闭来宾，并提供最高的一致性。 | 当工作负载要求正常关机且停机时间可接受时使用。 |
| **Suspend** | 在 snapshot 模式前暂停来宾，增加停机时间，却没有普遍的一致性收益。 | 不要默认把 suspend 当作优于 snapshot 的改进方式。 |

这些模式的取舍见 [Proxmox 备份模式参考](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc)。**QEMU Guest Agent** 是来宾内部的一项服务，可让 Proxmox 请求冻结和解冻文件系统等操作。启用且运行正常的来宾代理支持在 snapshot 备份期间执行这些操作。冻结文件系统有助于保持一致性，但不能替代数据库专属的恢复检查。应记录实际模式和来宾代理状态，不要假设计划任务使用了你偏好的设置。

## 创建或选择恢复点

如果演练测试日常恢复，请使用近期成功的计划备份。如果需要新建一次性备份，打开 VM 的 **Backup** 选项卡，选择 **Backup now**，设置目标存储和模式，然后等待任务日志报告成功。在 Proxmox shell 中，以下示例以 snapshot 模式将 VM **120** 备份到名为 **backup-nfs** 的存储 ID：

```bash
vzdump 120 --storage backup-nfs --mode snapshot
```

将两个 ID 都替换为自己的值。确认存储接受备份且空间充足后再运行命令。Proxmox 的 [`vzdump` 参考](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc)介绍了模式和存储选项。命令结束后检查任务日志。不要仅仅因为文件名看起来较新，就把旧备份当作当前恢复点。

如果目标是 **PBS**，请为选定的 datastore 运行或检查验证任务。PBS 的[验证文档](https://pbs.proxmox.com/docs/maintenance.html)说明了如何验证备份数据完整性并安排重复检查。验证可以发现损坏的备份数据块。**验证成功并不能证明恢复后的操作系统、应用或外部依赖可以正常工作。** 即使验证结果正常，也要继续完成恢复演练。

## 恢复到隔离的 VM

在 Proxmox 界面中，从存储的 **Backups** 视图选择备份，然后选择 **Restore**。输入未占用的 VM ID 和目标存储。保持 **Start after restore** 关闭。检查生成新 MAC 地址的选项。官方 [`qmrestore` 语法摘要](https://github.com/proxmox/pve-docs/blob/master/generated/qmrestore.1-synopsis.adoc)说明了唯一 VM ID、存储选择、用于生成随机以太网地址的 `--unique`，以及默认不启动恢复后 VM 的行为。

对于基于文件的 `vzdump` 归档，以下 shell 命令展示了等效方式。将归档路径、新 VM ID 和存储 ID 替换为当前环境中的值：

```bash
qmrestore /path/to/vzdump-qemu-120-2026_10_11-02_00_00.vma.zst 920 --storage local-lvm --unique 1
```

Proxmox 的[恢复说明](https://github.com/proxmox/pve-docs/blob/master/qmrestore.adoc)指出，如果没有指定目标存储，恢复过程会尝试使用原存储。如果测试节点上没有旧存储，请设置 **`--storage`**。演练中不要使用 **`--force`**。此选项允许覆盖现有 VM，而本流程要求使用未占用的 ID。PBS 备份同样可以从 Proxmox 界面恢复。选择 PBS 快照对应的存储项，不要把快照当作本地 `.vma.zst` 文件。

首次启动之前，检查恢复后的每个网络接口，包括辅助接口和直通接口。**MAC 地址**标识网络接口。**DNS**将名称映射到地址。**DHCP**分配网络设置。**VLAN**是通过共享硬件传输的逻辑网络。**虚拟 TPM**保存来宾的安全状态。断开所有接口，或只将它们连接到隔离的测试网段。确认生产路由、DNS 路径、DHCP 服务、管理网络和外部集成都无法访问。如果工作负载需要其他测试服务，请在隔离网络中准备测试副本。将磁盘映射、固件、虚拟 TPM 要求和特殊设备与源 VM 比较。外部磁盘、直通设备以及存储在 VM 外部的机密都需要独立计划。

## 测试来宾和工作负载

启动恢复后的 VM，并先使用控制台。确认操作系统能够启动、所有预期卷都已挂载、时钟正确且应用已经启动。然后执行之前写下的通过条件。将一个已知数据项与备份前的值和时间戳比较。登录提示或运行中的进程本身不能证明服务包含正确数据。

| 测试 | 通过条件 |
|---|---|
| **启动** | 来宾正常进入登录界面，没有修复模式或反复出现的恢复提示。 |
| **磁盘** | 备份中包含的每块磁盘都出现、完成挂载并包含预期数据。 |
| **服务** | 有代表性的本地请求或读取操作成功。 |
| **恢复点** | 恢复的数据符合记录的 RPO。 |
| **恢复时间** | 恢复、启动和服务验证符合记录的 RTO。 |
| **隔离** | 生产地址、任务或集成都没有收到重复流量。 |

检查计划任务、通知 hook、备份代理和应用凭据时，让恢复后的来宾保持隔离。不要运行会向真实客户发送消息或写入生产服务的测试。如果检查失败，记录具体失败阶段。区分**备份完整性失败**、**VM 启动失败**、**数据缺失**和**应用失败**。不同问题需要不同修复方式。

| 故障类型 | 确认依据 | 首要修复 | 重新测试 |
|---|---|---|---|
| **备份完整性** | 验证或恢复任务报告数据损坏 | 选择另一个经过验证的恢复点，并检查存储状态 | 重复验证和恢复 |
| **VM 启动** | 控制台显示固件、磁盘或恢复错误 | 将固件、磁盘映射和启动顺序与源 VM 比较 | 启动隔离副本并记录控制台结果 |
| **数据缺失** | 缺少预期文件、卷或数据库记录 | 检查被排除的磁盘、挂载、快照和外部依赖 | 重复检查指定文件或数据 |
| **应用** | 来宾已启动，但服务检查失败 | 检查服务日志、凭据、依赖项和恢复步骤 | 重新运行相同的本地健康检查和工作负载测试 |

Proxmox 为 PBS 备份提供[单文件恢复](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc)。如果工作负载需要单文件恢复，可以用它测试相应路径。恢复单个文件不能替代完整 VM 启动和服务测试。Proxmox 还支持从 PBS 实时恢复。文档指出，实时恢复失败后 VM 会处于未定义状态。因此，本计划演练应使用普通且已完成的恢复流程。

## 记录结果并结束演练

记录源 VM ID、备份存储、备份时间戳、模式、新 VM ID、目标存储、网络隔离情况、恢复开始和结束时间、应用测试、数据时间戳以及失败的检查。将测得的恢复点和恢复时间与目标比较。只有在调整备份计划并重复演练后，失败结果才是有用的证据。

测试结束后关闭恢复的 VM。保存结果并确认生产 VM 仍按预期运行后，再删除测试副本。按照常规保留策略保存备份。不要为了让一次演练通过而更改保留策略。

存储、来宾或备份配置发生重大变化后，重复测试。轮流检查重要 VM，包括带有被排除磁盘或外部依赖的来宾。[从 Hyper-V 迁移到 Proxmox 的指南](/articles/hyper-v-to-proxmox-migration-checklist/)要求在退役源 VM 前提供这种恢复证明。**可用的备份应有明确的恢复路径、经过测试的工作负载和测量过的恢复点。**

## 后续步骤

存储、来宾或备份发生变化后，重复此演练。文件恢复方法请参阅[家庭实验室备份恢复演练](/articles/homelab-backup-restore-drill/)。
