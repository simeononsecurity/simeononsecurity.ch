[AI ਸਹਿਯੋਗ ਕੋਰਸ ਵੱਲ ਵਾਪਸ ਜਾਓ](/ai-collaboration-course-start/)

**ਚਾਰਟਰ ਮਨਜ਼ੂਰ ਹੋਣ ਮਗਰੋਂ ਰੱਖ-ਰਖਾਅਕਾਰ GitHub-ਪਹਿਲੀ ਪ੍ਰਕਾਸ਼ਨ ਹੱਦ ਬਣਾਉਂਦਾ ਹੈ।** ਲੋੜਾਂ, ਕਨਫਿਗਰੇਸ਼ਨ, ਨੀਤੀ ਅਤੇ ਰਨਬੁੱਕ ਇੱਕ ਅਸਥਾਈ ਰਿਪੋਜ਼ਟਰੀ ਵਿੱਚ ਰਹਿੰਦੇ ਹਨ। ਯੋਗਦਾਨਕਰਤਾ Issues ਅਤੇ pull request ਰਾਹੀਂ ਪ੍ਰਸਤਾਵ ਦਿੰਦੇ ਹਨ। ਮਨਜ਼ੂਰ ਤੱਥ ਕਿੱਥੇ ਰਹਿੰਦੇ ਹਨ ਇਹ ਤੈਅ ਕਰੋ ਅਤੇ ਏਜੰਟ ਜੋੜਨ ਤੋਂ ਪਹਿਲਾਂ ਬਿਨਾਂ ਸਮੀਖਿਆ ਦੇ ਬਦਲਾਅ ਰੋਕੋ।

## ਮੁੱਖ ਗੱਲਾਂ

- **ਸੁਰੱਖਿਅਤ `main`** ਪ੍ਰਕਾਸ਼ਨ ਦੀ ਹੱਦ ਹੈ।
- **Issues** ਪ੍ਰਸਤਾਵ ਇਕੱਠੇ ਕਰਦੇ ਹਨ, ਨੀਤੀ ਮਨਜ਼ੂਰ ਨਹੀਂ ਕਰਦੇ।
- **CODEOWNERS** ਯੋਗ ਫਾਈਲ ਸਮੀਖਿਆਕਾਰ ਨਿਰਧਾਰਤ ਕਰਦਾ ਹੈ।
- **ਵੱਖਰੇ ਯੂਜ਼ਰ** ਸਮੀਖਿਆ ਅਤੇ ਇਨਕਾਰ ਨਿਯੰਤਰਣ ਦਿਖਾਉਂਦੇ ਹਨ।

## ਸ਼ੁਰੂ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ

**ਪੂਰਵ-ਸ਼ਰਤਾਂ:** [ਪਾਇਲਟ ਦੀ ਨੀਂਹ](/articles/ai-collaboration-pilot-foundation/), ਖੋਲ੍ਹੀ ਹੋਈ ਲੈਬ, ਰਿਪੋਜ਼ਟਰੀ ਪ੍ਰਸ਼ਾਸਕ ਅਤੇ ਵੱਖਰੇ ਉਤਪਾਦ ਤੇ ਕਾਰਜ-ਸੰਚਾਲਨ ਸਮੀਖਿਆਕਾਰ। **ਅੰਦਾਜ਼ਨ ਸਮਾਂ:** 60 ਮਿੰਟ। **ਮੁਸ਼ਕਲ:** ਦਰਮਿਆਨੀ।

**ਪਲਾਨ ਦੀ ਹੱਦ:** GitHub, Free ਪਲਾਨ ਦੇ ਜਨਤਕ ਰਿਪੋਜ਼ਟਰੀਆਂ ਅਤੇ Pro, Team ਜਾਂ Enterprise ਦੀਆਂ ਨਿੱਜੀ ਰਿਪੋਜ਼ਟਰੀਆਂ ਲਈ ਸੁਰੱਖਿਅਤ ਬ੍ਰਾਂਚਾਂ ਦਸਤਾਵੇਜ਼ ਕਰਦਾ ਹੈ। ਜਨਤਕ ਰਿਪੋਜ਼ਟਰੀ ਵਿੱਚ ਸਿਰਫ਼ ਨਮੂਨਾ ਸਮੱਗਰੀ ਵਰਤੋ। ਲਾਗੂਕਰਨ 'ਤੇ ਭਰੋਸਾ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਬ੍ਰਾਂਚ ਸੁਰੱਖਿਆ ਹਵਾਲੇ ਰਾਹੀਂ ਦਿੱਖ ਅਤੇ ਪਲਾਨ ਦੀ ਜਾਂਚ ਕਰੋ।

**ਮੁਕੰਮਲ ਨਤੀਜਾ:** ਸੁਰੱਖਿਅਤ ਪ੍ਰਕਾਸ਼ਨ ਬ੍ਰਾਂਚ, ਫਾਈਲ ਮਾਲਕ, ਸਰੋਤ ਨਕਸ਼ਾ ਅਤੇ ਸਬੂਤ ਵਜੋਂ ਦਰਜ ਇਨਕਾਰ ਟੈਸਟ।

## ਰਿਪੋਜ਼ਟਰੀ ਬਣਾਓ

1. **`export-service-lab` ਬਣਾਓ** README ਅਤੇ ਮੂਲ ਬ੍ਰਾਂਚ **`main`** ਨਾਲ।
2. **ਖੋਲ੍ਹੀ ਲੈਬ** ਰਿਪੋਜ਼ਟਰੀ ਦੇ ਰੂਟ ਵਿੱਚ ਕਾਪੀ ਕਰੋ ਅਤੇ **`check.py`**, **`test_check.py`** ਅਤੇ **`baseline/`** ਜਿਉਂ ਦੇ ਤਿਉਂ ਰੱਖੋ। `baseline/` ਦੀਆਂ ਰਿਕਾਰਡ ਫਾਈਲਾਂ ਸ਼ੁਰੂਆਤੀ ਰਿਕਾਰਡ ਵਜੋਂ ਰੂਟ ਵਿੱਚ ਕਾਪੀ ਕਰੋ।
3. **`docs/project-map.md` ਬਣਾਓ** ਪਾਇਲਟ ਰਜਿਸਟਰ ਤੋਂ। ਮਨਜ਼ੂਰਸ਼ੁਦਾ POL-01 ਨਾਲ **`docs/policy.md`** ਜੋੜੋ।
4. **`docs/decisions/DEC-12.md` ਬਣਾਓ** ਜਿਸ ਵਿੱਚ ਚਾਰਟਰ ਮਨਜ਼ੂਰੀ, ਭੂਮਿਕਾਵਾਂ, ਬੇਸਲਾਈਨ ਫੈਸਲਾ ਅਤੇ ਸਥਿਤੀ ਹੋਵੇ।
5. **ਪ੍ਰਸ਼ਾਸਕ ਵਜੋਂ ਸ਼ੁਰੂਆਤੀ ਸੈਟਅੱਪ commit ਕਰੋ।** ਇਸ ਸ਼ੁਰੂਆਤੀ ਛੋਟ ਨੂੰ ਦਰਜ ਕਰੋ। ਅਗਲੇ ਯੋਗਦਾਨਾਂ ਤੋਂ ਪਹਿਲਾਂ ਸੁਰੱਖਿਆ ਚਾਲੂ ਕਰੋ।

**Git Bash, macOS Terminal ਜਾਂ Linux ਸ਼ੈੱਲ ਲਈ ਸਥਾਨਕ ਸ਼ੁਰੂਆਤੀ ਰਸਤਾ:** ਬ੍ਰਾਊਜ਼ਰ ਵਿੱਚ GitHub ਖੋਲ੍ਹ ਕੇ ਸਾਈਨ ਇਨ ਕਰੋ, ਨਵੀਂ ਰਿਪੋਜ਼ਟਰੀ ਖੋਲ੍ਹੋ, **Code** ਚੁਣੋ ਅਤੇ HTTPS clone URL ਕਾਪੀ ਕਰੋ। ਅਸਥਾਈ ਕੰਮਕਾਜੀ ਡਾਇਰੈਕਟਰੀ ਵਿੱਚ ਹੇਠਲੇ ਕਮਾਂਡ ਚਲਾਓ। ਦੋ ਨਮੂਨਾ ਪਾਥਾਂ ਦੀ ਥਾਂ URL ਅਤੇ ਡਾਊਨਲੋਡ ਕੀਤੀ ਲੈਬ ZIP ਦਾ ਪਾਥ ਦਿਓ। URL ਵਿੱਚ ਟੋਕਨ ਨਾ ਪਾਓ।

```bash
git --version
git clone "https://github.com/OWNER/export-service-lab.git"
cd export-service-lab
unzip -n "/absolute/path/to/ai-collaboration-lab.zip"
cp baseline/config.json baseline/policy.json baseline/proposal.json baseline/requirement.json baseline/runbook.md .
mkdir -p docs/decisions
git status --short
```

Clone ਕਮਾਂਡ ਨਾਲ ਰਿਪੋਜ਼ਟਰੀ ਡਾਇਰੈਕਟਰੀ ਬਣਨੀ ਚਾਹੀਦੀ ਹੈ। ਜੇ `unzip` ਉਪਲਬਧ ਨਹੀਂ, ਫਾਈਲ ਮੈਨੇਜਰ ਨਾਲ ZIP ਖੋਲ੍ਹੋ ਅਤੇ ਰਿਪੋਜ਼ਟਰੀ README ਬਚਾ ਕੇ ਸਮੱਗਰੀ ਇਸ checkout ਵਿੱਚ ਕਾਪੀ ਕਰੋ। `git status --short` ਵਿੱਚ ਕਾਪੀ ਕੀਤੇ ਰਿਕਾਰਡ, checker, ਟੈਸਟ ਅਤੇ `baseline/` ਨਵੀਆਂ ਫਾਈਲਾਂ ਵਜੋਂ ਦਿਖਣੇ ਚਾਹੀਦੇ ਹਨ। ਪਾਇਲਟ ਪੈਕਟ ਤੋਂ `docs/project-map.md`, `docs/policy.md` ਅਤੇ `docs/decisions/DEC-12.md` ਟੈਕਸਟ ਐਡੀਟਰ ਨਾਲ ਸੰਭਾਲੋ। ਫਿਰ ਚਲਾਓ:

```bash
git add README.md baseline check.py test_check.py config.json policy.json proposal.json requirement.json runbook.md docs
git commit -m "Add synthetic collaboration baseline"
git push origin main
git status --short
git remote -v
```

Git ਨਵਾਂ commit ID ਅਤੇ ਫਿਰ `main` ਵੱਲ ਸਫਲ push ਦੱਸੇਗਾ। ਅੰਤਿਮ ਛੋਟਾ status ਖਾਲੀ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ। ਨਵੇਂ ਬ੍ਰਾਊਜ਼ਰ ਦ੍ਰਿਸ਼ ਵਿੱਚ GitHub ਰਿਪੋਜ਼ਟਰੀ ਖੋਲ੍ਹ ਕੇ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਫਾਈਲਾਂ ਅਤੇ commit ID `main` ਉੱਤੇ ਹਨ। ਸ਼ੁਰੂਆਤੀ ਸੈਟਅੱਪ ਦੇ ਸਬੂਤ ਵਜੋਂ commit URL ਸੰਭਾਲੋ। ਜੇ Git ਲੇਖਕ ਦੀ ਪਛਾਣ ਮੰਗੇ ਤਾਂ ਕੋਰਸ ਹੱਬ ਵਿੱਚ ਸੈਟਅੱਪ ਹਦਾਇਤਾਂ ਮੰਨੋ। ਅਥੈਂਟੀਕੇਸ਼ਨ ਫੇਲ੍ਹ ਹੋਵੇ ਤਾਂ GitHub ਦਾ ਸਮਰਥਿਤ credential ਰਸਤਾ ਵਰਤ ਕੇ ਉਹੀ push ਦੁਬਾਰਾ ਕਰੋ। ਜੇ ਬ੍ਰਾਂਚ ਜਾਂ remote ਗਲਤ ਹੋਵੇ ਤਾਂ ਹੋਰ ਲਿਖਣ ਤੋਂ ਪਹਿਲਾਂ `git branch --show-current` ਅਤੇ `git remote -v` ਜਾਂਚੋ। ਜੇ ਸੁਰੱਖਿਆ ਪਹਿਲਾਂ ਹੀ ਚਾਲੂ ਹੋਣ ਕਾਰਨ push ਰੱਦ ਹੋਵੇ ਤਾਂ ਨਿਯਮ ਬਾਈਪਾਸ ਕਰਨ ਦੀ ਥਾਂ ਪ੍ਰਸਤਾਵ ਬ੍ਰਾਂਚ ਅਤੇ PR ਖੋਲ੍ਹੋ। ਹੇਠਾਂ ਦਿੱਤਾ ਬ੍ਰਾਊਜ਼ਰ-ਮਾਤਰ ਰਸਤਾ ਵੀ ਰੱਖ-ਰਖਾਅਕਾਰ ਰਾਹੀਂ ਉਪਲਬਧ ਹੈ।

| ਰਿਕਾਰਡ | ਥਾਂ | ਮਾਲਕ |
|---|---|---|
| **POL-01** | `policy.json`, `docs/policy.md` | ਨੀਤੀ ਮਾਲਕ |
| **REQ-17** | `requirement.json` | ਉਤਪਾਦ ਮਾਲਕ |
| **RUN-04** | `runbook.md` | ਕਾਰਜ-ਸੰਚਾਲਨ ਮਾਲਕ |
| **ਵਰਤਾਅ** | `config.json` | ਰਿਪੋਜ਼ਟਰੀ ਰੱਖ-ਰਖਾਅਕਾਰ |
| **ਫੈਸਲੇ** | `docs/decisions/` | ਪ੍ਰੋਜੈਕਟ ਮੁਖੀ |

**ਨਕਸ਼ਾ ਮੁੱਲ ਕਾਪੀ ਕਰਨ ਦੀ ਥਾਂ ਥਾਵਾਂ ਨਾਲ ਜੋੜਦਾ ਹੈ।** README ਨੂੰ ਸੈਟਅੱਪ ਅਤੇ ਨਕਸ਼ੇ ਤੱਕ ਸੀਮਿਤ ਰੱਖੋ। ਇੱਕੋ ਰਿਪੋਜ਼ਟਰੀ ਵਿੱਚ ਵੀ ਧਾਰਨ-ਸਮੇਂ ਦੀ ਦੁਹਰਾਈ ਡ੍ਰਿਫਟ ਪੈਦਾ ਕਰਦੀ ਹੈ।

## ਫਾਈਲ ਮਾਲਕ ਨਿਰਧਾਰਤ ਕਰੋ

**`.github/CODEOWNERS` ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਬਣਾਓ** ਅਤੇ ਸੈਂਡਬਾਕਸ ਦੇ ਅਸਲ ਹੈਂਡਲ ਵਰਤੋ। ਹੈਂਡਲ ਤੋਂ ਸ਼ੁਰੂਆਤੀ **`@`** ਨਾ ਲਿਖੋ। ਖਾਤਾ ਪਛਾਣ ਨਿੱਜੀ ਲੈਬ ਵਿੱਚ ਰੱਖੋ, ਜਨਤਕ ਅਭਿਆਸ ਸਬੂਤ ਵਿੱਚ ਨਹੀਂ।

```bash
python3 - <<'PY'
from pathlib import Path
roles = ['product', 'operations', 'maintainer', 'policy']
handles = {r: input(r + ' GitHub handle: ').strip().lstrip('@') for r in roles}
if any(not h or not all(c.isalnum() or c == '-' for c in h) for h in handles.values()):
    raise SystemExit('Invalid handle')
paths = {'requirement.json': 'product', 'runbook.md': 'operations',
         'config.json': 'maintainer', 'policy.json': 'policy',
         'docs/policy.md': 'policy', 'AGENTS.md': 'policy',
         'CLAUDE.md': 'policy', '.clinerules/': 'policy',
         '.github/': 'maintainer', 'check.py': 'maintainer',
         'test_check.py': 'maintainer', 'baseline/': 'maintainer'}
Path('.github').mkdir(exist_ok=True)
Path('.github/CODEOWNERS').write_text(''.join(
    '/' + path + ' @' + handles[role] + '\n' for path, role in paths.items()))
PY
```

**GitHub ਵੱਲੋਂ ਮਾਲਕ ਪਛਾਣੇ ਜਾਣ ਲਈ ਉਨ੍ਹਾਂ ਕੋਲ ਲਿਖਣ ਦੀ ਪਹੁੰਚ ਹੋਵੇ।** ਬ੍ਰਾਊਜ਼ਰ ਵਿੱਚ CODEOWNERS ਫਾਈਲ ਦੀਆਂ ਗਲਤੀਆਂ ਜਾਂਚੋ। ਮਾਲਕੀ ਫਾਈਲਾਂ ਅਤੇ ਵਰਕਫ਼ਲੋ ਪਰਿਭਾਸ਼ਾਵਾਂ ਨੂੰ ਆਮ ਸਮੱਗਰੀ ਵਾਂਗ ਸੁਰੱਖਿਅਤ ਕਰੋ।

**ਇੱਕ ਲਾਈਨ ਵਿੱਚ ਕਈ ਨਾਂ ਹੋਣ ਨਾਲ ਸਾਰੇ ਮਾਲਕਾਂ ਦੀ ਮਨਜ਼ੂਰੀ ਲਾਜ਼ਮੀ ਨਹੀਂ ਹੁੰਦੀ।** GitHub ਮੇਲ ਖਾਂਦੇ ਪਾਥ ਲਈ ਇੱਕ ਯੋਗ ਮਾਲਕ ਦੀ ਮਨਜ਼ੂਰੀ ਮੰਨਦਾ ਹੈ। ਲੋੜ ਅਤੇ ਰਨਬੁੱਕ ਦੇ ਪਾਥਾਂ ਲਈ ਵੱਖਰੇ ਮਾਲਕ ਰੱਖੋ। ਪਾਇਲਟ ਵਿੱਚ ਅੰਤਿਮ ਪ੍ਰਸਤਾਵ ਨਾਲ ਜੁੜੀਆਂ ਉਤਪਾਦ-ਮਾਲਕ ਅਤੇ ਕਾਰਜ-ਸੰਚਾਲਨ-ਮਾਲਕ ਦੀਆਂ ਪੁਸ਼ਟੀਆਂ ਵੀ ਲੋੜੀਂਦੀਆਂ ਹਨ।

## ਪ੍ਰਕਾਸ਼ਨ ਸੁਰੱਖਿਅਤ ਕਰੋ

1. **Settings, Branches ਖੋਲ੍ਹੋ** ਅਤੇ **`main`** ਲਈ ਬ੍ਰਾਂਚ ਸੁਰੱਖਿਆ ਨਿਯਮ ਜੋੜੋ। ਇਸ ਅਭਿਆਸ ਵਿੱਚ ਇੱਕੋ ਸੁਰੱਖਿਆ ਰਸਤਾ ਵਰਤੋ, rulesets ਨਾਲ ਨਾ ਮਿਲਾਓ।
2. **Pull request,** ਦੋ ਮਨਜ਼ੂਰ ਸਮੀਖਿਆਵਾਂ ਅਤੇ code owner ਸਮੀਖਿਆ ਲਾਜ਼ਮੀ ਕਰੋ।
3. ਨਵੇਂ commit ਮਗਰੋਂ **ਪੁਰਾਣੀਆਂ ਮਨਜ਼ੂਰੀਆਂ ਰੱਦ ਕਰੋ** ਅਤੇ ਗੱਲਬਾਤ ਦੇ ਮੁੱਦੇ ਹੱਲ ਕਰਨਾ ਲਾਜ਼ਮੀ ਕਰੋ।
4. **ਉਪਰਲੀਆਂ ਸੈਟਿੰਗਾਂ ਨੂੰ ਬਾਈਪਾਸ ਕਰਨ ਦੀ ਮਨਾਹੀ ਚਾਲੂ ਕਰੋ।** Force push ਅਤੇ ਮਿਟਾਉਣਾ ਬੰਦ ਰੱਖੋ।
5. ਅਗਲੇ ਮੋਡੀਊਲ ਵਿੱਚ ਪਹਿਲੀ ਵਾਰ ਚੱਲਣ ਮਗਰੋਂ **ਇਕਸਾਰਤਾ ਜਾਂਚ ਜੋੜੋ।** ਮਰਜ ਤੋਂ ਪਹਿਲਾਂ ਬ੍ਰਾਂਚ ਅਪ-ਟੂ-ਡੇਟ ਹੋਣੀ ਲਾਜ਼ਮੀ ਕਰੋ।

**ਦੋ ਮਨਜ਼ੂਰੀਆਂ ਗਿਣਤੀ ਲਾਗੂ ਕਰਦੀਆਂ ਹਨ, ਕਾਰੋਬਾਰੀ ਭੂਮਿਕਾ ਦੀ ਮੈਂਬਰਸ਼ਿਪ ਨਹੀਂ।** CODEOWNERS ਪਾਥ-ਅਧਾਰਿਤ ਮਾਲਕੀ ਕਵਰੇਜ ਜੋੜਦਾ ਹੈ। ਰੱਖ-ਰਖਾਅਕਾਰ ਦੋ ਭੂਮਿਕਾਵਾਂ ਦੀਆਂ ਪੁਸ਼ਟੀਆਂ ਵੀ ਜਾਂਚਦਾ ਹੈ। ਇਸਨੂੰ ਸਵੈਚਾਲਿਤ ਦੋ-ਭੂਮਿਕਾ ਲਾਗੂਕਰਨ ਕਹਿਣ ਦੀ ਥਾਂ ਵਿਧੀਗਤ ਨਿਯੰਤਰਣ ਵਜੋਂ ਸਪੱਸ਼ਟ ਦਰਜ ਕਰੋ।

**ਪ੍ਰਸ਼ਾਸਕ ਹਾਲੇ ਵੀ ਕਨਫਿਗਰੇਸ਼ਨ ਸੰਭਾਲਦੇ ਹਨ।** ਟੈਸਟਾਂ ਤੋਂ ਪਹਿਲਾਂ ਅਤੇ ਬਾਅਦ ਨਿਯਮ ਦੀ ਕਾਪੀ ਲਵੋ। ਯੋਗਦਾਨਕਰਤਾ ਨੂੰ ਇਨਕਾਰ ਦਿਖਾਉਣ ਲਈ ਏਜੰਟ ਨੂੰ ਪ੍ਰਸ਼ਾਸਕ ਪਹੁੰਚ ਨਾ ਦਿਓ ਅਤੇ ਵਿਸ਼ੇਸ਼ ਟੋਕਨ ਨਾ ਵਰਤੋ।

## ਹੱਦ ਦੀ ਜਾਂਚ ਕਰੋ

| ਕੋਸ਼ਿਸ਼ | ਉਮੀਦ ਕੀਤਾ ਨਤੀਜਾ |
|---|---|
| **ਯੋਗਦਾਨਕਰਤਾ ਬ੍ਰਾਂਚ ਭੇਜਦਾ ਹੈ** | ਪ੍ਰਸਤਾਵ ਮਨਜ਼ੂਰ |
| **ਯੋਗਦਾਨਕਰਤਾ ਸਿੱਧਾ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ** | ਸੁਰੱਖਿਅਤ ਪ੍ਰਕਾਸ਼ਨ ਰੱਦ |
| **ਇੱਕ ਸਮੀਖਿਆਕਾਰ ਮਨਜ਼ੂਰ ਕਰਦਾ ਹੈ** | ਸਮੀਖਿਆ ਹੱਦ ਕਾਰਨ ਮਰਜ ਰੁਕਦਾ ਹੈ |
| **ਸਮੀਖਿਆ ਮਗਰੋਂ ਨਵਾਂ commit ਆਉਂਦਾ ਹੈ** | ਨਵੀਂ ਮਨਜ਼ੂਰੀ ਲੋੜੀਂਦੀ |
| **ਸੰਵੇਦਨਸ਼ੀਲ ਫਾਈਲ ਦਾ ਮਾਲਕ ਨਹੀਂ** | ਪ੍ਰਕਾਸ਼ਨ ਤੋਂ ਪਹਿਲਾਂ ਠੀਕ ਕਰੋ |

**ਰਸਤਾ ਜਾਂਚਣ ਲਈ ਯੋਗਦਾਨਕਰਤਾ ਦਾ ਬ੍ਰਾਊਜ਼ਰ ਸੈਸ਼ਨ ਵਰਤੋ।** GitHub ਵੈੱਬ ਐਡੀਟਰ ਸੁਰੱਖਿਅਤ **`main`** ਬ੍ਰਾਂਚ ਨਹੀਂ ਸੋਧਦਾ। ਬ੍ਰਾਂਚ ਬਣਾਉਣ ਦਾ ਸੁਨੇਹਾ ਸਮਰਥਿਤ ਬ੍ਰਾਊਜ਼ਰ ਰਸਤਾ ਦਿਖਾਉਂਦਾ ਹੈ। ਇਹ ਸਾਬਤ ਨਹੀਂ ਕਰਦਾ ਕਿ ਸਰਵਰ ਨੇ ਸਿੱਧਾ push ਰੱਦ ਕੀਤਾ। ਪਲੇਟਫਾਰਮ ਇਨਕਾਰ ਦਾ ਸਬੂਤ ਲੈਣ ਲਈ ਮਨਜ਼ੂਰ ਸਥਾਨਕ Git ਪਹੁੰਚ ਵਾਲੇ ਯੋਗਦਾਨਕਰਤਾ ਤੋਂ ਸੁਰੱਖਿਅਤ **`main`** ਉੱਤੇ ਨਿਰਦੋਸ਼ ਸਿੱਧੇ push ਦੀ ਕੋਸ਼ਿਸ਼ ਕਰਵਾਓ ਅਤੇ ਸਰਵਰ ਜਵਾਬ ਸੰਭਾਲੋ। ਸਥਾਨਕ ਪਹੁੰਚ ਨਾ ਹੋਵੇ ਤਾਂ ਇਨਕਾਰ ਟੈਸਟ ਨੂੰ ਰੁਕਿਆ ਹੋਇਆ ਮੰਨੋ।

**ਇਨਕਾਰ ਮਗਰੋਂ `main` ਪੜ੍ਹੋ** ਅਤੇ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਰਿਵਿਜ਼ਨ ਨਹੀਂ ਬਦਲੀ। ਅਦਾਕਾਰ ਦੀ ਭੂਮਿਕਾ, ਕੋਸ਼ਿਸ਼, ਨਤੀਜਾ ਅਤੇ ਸਰੋਤ ਰਿਵਿਜ਼ਨ ਦਰਜ ਕਰੋ। ਸਹਾਇਕ ਦਾ ਪ੍ਰਕਾਸ਼ਨ ਨਾ ਕਰਨ ਦਾ ਵਾਅਦਾ ਵਰਤਾਅ ਦਾ ਸਬੂਤ ਹੈ, ਪਲੇਟਫਾਰਮ ਅਨੁਮਤੀ ਟੈਸਟ ਨਹੀਂ।

**ਸਿੱਧੇ push ਟੈਸਟ ਲਈ ਯੋਗਦਾਨਕਰਤਾ ਦਾ ਆਪਣਾ ਪ੍ਰਮਾਣਿਤ ਸਥਾਨਕ clone ਵਰਤੋ।** ਰੱਖ-ਰਖਾਅਕਾਰ ਦਾ ਟੋਕਨ ਗਲਤ ਪਛਾਣ ਜਾਂਚੇਗਾ। ਇਹ ਨਮੂਨਾ ਜਵਾਬ ਦਿਖਾਉਂਦਾ ਹੈ ਕਿ ਕਿਸ ਕਿਸਮ ਦਾ ਸਰਵਰ ਸਬੂਤ ਰੱਖਣਾ ਹੈ। ਸਹੀ ਸ਼ਬਦਾਵਲੀ ਰਿਪੋਜ਼ਟਰੀ ਨਿਯਮਾਂ ਅਨੁਸਾਰ ਵੱਖ ਹੋ ਸਕਦੀ ਹੈ।

```text
Actor role: contributor
Attempt: harmless synthetic direct push to main
Remote result: rejected, protected branch update denied
Initial main commit: [record sandbox commit]
Final main commit: [record same commit after read-back]
Decision: platform denial supported only if both records are observed
```

**ਸਥਾਨਕ Git ਅਥੈਂਟੀਕੇਸ਼ਨ ਨਾ ਹੋਵੇ ਤਾਂ ਸਰਵਰ-ਪਾਸੇ ਇਨਕਾਰ ਨੂੰ ਰੁਕਿਆ ਹੋਇਆ ਦਰਜ ਕਰੋ।** ਬ੍ਰਾਂਚ ਬਣਾਉਣ ਵਾਲਾ ਬ੍ਰਾਊਜ਼ਰ ਸੁਨੇਹਾ ਰਸਤੇ ਦੇ ਸਬੂਤ ਵਜੋਂ ਰੱਖੋ, ਫਿਰ ਰੱਖ-ਰਖਾਅਕਾਰ ਤੋਂ ਵੱਖਰਾ ਯੋਗਦਾਨਕਰਤਾ ਟੈਸਟ ਕਰਵਾਉਣ ਲਈ ਕਹੋ। ਰਸਤੇ ਦੇ ਸੁਨੇਹੇ ਨੂੰ ਰੱਦ ਸਿੱਧੇ push ਵਜੋਂ ਅੰਕ ਨਾ ਦਿਓ।

## ਲਾਭਦਾਇਕ ਸਰੋਤ ਨਕਸ਼ਾ ਬਣਾਓ

**ਸਰੋਤ ਨਕਸ਼ਾ ਦਿਸ਼ਾ-ਨਿਰਦੇਸ਼ ਦਸਤਾਵੇਜ਼ ਹੈ,** ਦੂਜਾ ਲੋੜਾਂ ਦਾ ਦਸਤਾਵੇਜ਼ ਨਹੀਂ। ਚੈਟ ਤੋਂ ਆਉਣ ਵਾਲੇ ਵਿਅਕਤੀ ਨੂੰ ਵਿਰੋਧੀ ਸਾਰਾਂ ਵਿੱਚੋਂ ਚੁਣੇ ਬਿਨਾਂ ਮੌਜੂਦਾ ਇਰਾਦਾ, ਲਾਗੂ ਵਰਤਾਅ ਅਤੇ ਕਾਰਜਕਾਰੀ ਹਦਾਇਤਾਂ ਲੱਭ ਸਕਣੀਆਂ ਚਾਹੀਦੀਆਂ ਹਨ।

```text
Project: export-service-lab
Track: GitHub-first
Approved boundary: protected main

REQ-17 -> requirement.json
  Authority: retention intent for synthetic export files
  Owner: product-owner
  Revision: record revision plus protected commit

RUN-04 -> runbook.md
  Authority: operating instructions for the synthetic lab
  Owner: operations-owner
  Revision: protected commit

Behavior -> config.json
  Authority: committed retention configuration
  Owner: repository-maintainer
  Revision: protected commit

Proposals -> Issues and proposal branches
  Authority: requested changes only
```

**ਮੌਜੂਦਾ ਧਾਰਨ ਮੁੱਲ ਹਰ ਨਕਸ਼ਾ ਐਂਟਰੀ ਵਿੱਚ ਨਾ ਲਿਖੋ।** “ਸੱਤ ਦਿਨ” ਵਾਲਾ ਨਕਸ਼ਾ PROP-042 ਮਗਰੋਂ ਸਮਕਾਲੀ ਕਰਨ ਲਈ ਹੋਰ ਮੁੱਲ ਬਣ ਜਾਂਦਾ ਹੈ। ਨਕਸ਼ੇ ਵਿੱਚ ਸਥਿਰ ਪਛਾਣ ਅਤੇ ਥਾਂ ਰੱਖੋ, ਮੁੱਲ ਅਧਿਕਾਰਤ ਰਿਕਾਰਡ ਤੋਂ ਪੜ੍ਹੋ।

**ਨਕਸ਼ਾ ਬਦਲਾਅ ਨੂੰ ਰੂਟਿੰਗ ਬਦਲਾਅ ਵਾਂਗ ਸੁਰੱਖਿਅਤ ਕਰੋ।** REQ-17 ਨੂੰ ਮਸੌਦਾ ਫਾਈਲ ਵੱਲ ਮੋੜਨਾ ਸਰੋਤ ਦੀ ਚੋਣ ਬਦਲਦਾ ਹੈ, ਭਾਵੇਂ ਮਨਜ਼ੂਰ ਲੋੜ ਨਾ ਛੁਹੀ ਹੋਵੇ। ਨਕਸ਼ਾ ਬਦਲਣ ਵੇਲੇ ਮੰਜ਼ਿਲ, ਮਾਲਕ ਅਤੇ ਅਧਿਕਾਰ ਦਾ ਦਾਇਰਾ ਜਾਂਚੋ।

## ਪੂਰੇ ਬਦਲਾਅ ਦੀ ਸਮੀਖਿਆ ਕਰੋ

**PR ਦਾ ਵੇਰਵਾ ਮੰਨਣ ਤੋਂ ਪਹਿਲਾਂ Files changed ਖੋਲ੍ਹੋ।** ਵੇਰਵਾ ਲੇਖਕ ਦਾ ਇਰਾਦਾ ਦੱਸਦਾ ਹੈ। Diff ਭੇਜਿਆ ਬਦਲਾਅ ਦਿਖਾਉਂਦਾ ਹੈ। PROP-042 ਲਈ ਲੋੜ ਰਿਵਿਜ਼ਨ, ਦਾਇਰੇ ਦੇ ਅਪਵਾਦ, ਕਨਫਿਗਰੇਸ਼ਨ, ਰਨਬੁੱਕ, ਪ੍ਰਸਤਾਵ ਆਧਾਰ ਅਤੇ ਮੈਨੀਫੈਸਟ ਸਬੂਤ ਜਾਂਚੋ।

1. **ਉਤਪਾਦ ਸਮੀਖਿਆ:** ਤੀਹ ਦਿਨਾਂ ਦੇ ਇਰਾਦੇ ਅਤੇ ਅਣਬਦਲੇ ਅਪਵਾਦਾਂ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ।
2. **ਕਾਰਜ-ਸੰਚਾਲਨ ਸਮੀਖਿਆ:** ਰਨਬੁੱਕ ਪ੍ਰਸਤਾਵਿਤ ਕਨਫਿਗਰੇਸ਼ਨ ਨਾਲ ਮਿਲਦੀ ਹੋਵੇ ਅਤੇ ਰਨਟਾਈਮ ਸੀਮਾ ਰੱਖਦੀ ਹੋਵੇ।
3. **ਰੱਖ-ਰਖਾਅਕਾਰ ਸਮੀਖਿਆ:** JSON, ਸਰੋਤ ਕੈਪਚਰ, ਜਾਂਚ ਨਤੀਜੇ ਅਤੇ ਗੈਰ-ਸੰਬੰਧਿਤ ਸੋਧਾਂ ਵੇਖੋ।
4. **ਨਿਯੰਤਰਣ ਸਮੀਖਿਆ:** ਨਕਸ਼ੇ, ਨੀਤੀ, CODEOWNERS ਜਾਂ ਵਰਕਫ਼ਲੋ ਵਿੱਚ ਬਦਲਾਅ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਵੇਖੋ।

**ਹਰਾ check ਗੈਰ-ਸੰਬੰਧਿਤ ਮਿਟਾਉਣ ਦੀ ਵਜ੍ਹਾ ਨਹੀਂ ਦੱਸਦਾ।** ਜੇ ਧਾਰਨ ਬਦਲਣ ਵਾਲੀ ਬ੍ਰਾਂਚ ਨੀਤੀ ਦਸਤਾਵੇਜ਼ ਮਿਟਾਉਂਦੀ ਹੈ ਤਾਂ ਵੱਖਰਾ ਪ੍ਰਸਤਾਵ ਜਾਂ ਮਾਲਕ ਦੀ ਖਾਸ ਸਮੀਖਿਆ ਮੰਗੋ। ਸੀਮਿਤ ਦਾਇਰਾ ਸਮੀਖਿਆ ਨੂੰ ਸਮਝਣਯੋਗ ਰੱਖਦਾ ਹੈ।

## ਇਨਕਾਰ ਟੈਸਟ ਦਾ ਨਿਦਾਨ ਕਰੋ

**ਹਰ ਸਬੂਤ ਕਤਾਰ ਲਈ ਇੱਕ ਕੋਸ਼ਿਸ਼ੀ ਕਾਰਵਾਈ ਵਰਤੋ।** “ਯੋਗਦਾਨਕਰਤਾ ਫੇਲ੍ਹ ਹੋਇਆ” ਅਸਪੱਸ਼ਟ ਹੈ। ਵਰਤੋਂਕਾਰ ਕੋਲ ਆਮ ਲਿਖਣ ਦੀ ਪਹੁੰਚ ਨਾ ਹੋ ਸਕਦੀ ਹੈ, ਬ੍ਰਾਊਜ਼ਰ ਦੀ ਹੱਦ ਆ ਸਕਦੀ ਹੈ ਜਾਂ ਉਮੀਦ ਕੀਤਾ ਬ੍ਰਾਂਚ ਨਿਯਮ ਲਾਗੂ ਹੋ ਸਕਦਾ ਹੈ। ਇਹ ਵੱਖਰੀਆਂ ਹੱਦਾਂ ਦਿਖਾਉਂਦੇ ਹਨ।

## ਰਿਪੋਜ਼ਟਰੀ ਮੁਕੰਮਲਤਾ ਜਾਂਚ

**ਐਸੀ ਰਿਪੋਜ਼ਟਰੀ ਦਿਓ ਜਿਸ ਵਿੱਚ ਹੋਰ ਯੋਗਦਾਨਕਰਤਾ ਖੁਦ ਰਸਤਾ ਲੱਭ ਸਕੇ।** README ਨਕਸ਼ੇ ਵੱਲ ਦੱਸਦਾ ਹੈ, ਨਕਸ਼ਾ ਅਧਿਕਾਰਤ ਰਿਕਾਰਡ ਤੱਕ ਲੈ ਜਾਂਦਾ ਹੈ, ਮਾਲਕੀ ਕਵਰੇਜ ਸੰਵੇਦਨਸ਼ੀਲ ਪਾਥਾਂ ਨੂੰ ਸ਼ਾਮਲ ਕਰਦੀ ਹੈ ਅਤੇ ਸੁਰੱਖਿਆ **`main`** ਉੱਤੇ ਲਾਗੂ ਹੈ। ਇੱਕ ਮਨਜ਼ੂਰ ਪ੍ਰਸਤਾਵ ਅਤੇ ਇੱਕ ਰੱਦ ਪ੍ਰਕਾਸ਼ਨ ਕੋਸ਼ਿਸ਼ ਸੰਭਾਲੋ।

**ਸਿਰਫ਼ ਸੈਟਿੰਗ ਦੇ ਆਧਾਰ 'ਤੇ ਲਾਗੂਕਰਨ ਦਾ ਦਾਅਵਾ ਨਾ ਕਰੋ।** ਸੈਟਿੰਗ ਇਰਾਦਤਨ ਕਨਫਿਗਰੇਸ਼ਨ ਦਿਖਾਉਂਦੀ ਹੈ। ਸੈਂਡਬਾਕਸ ਕੋਸ਼ਿਸ਼ ਖਾਸ ਭੂਮਿਕਾ ਅਤੇ ਰਸਤੇ ਲਈ ਵੇਖਿਆ ਵਰਤਾਅ ਦਿਖਾਉਂਦੀ ਹੈ। ਏਜੰਟ ਅਤੇ GitHub Actions ਪਾਠ ਵਿੱਚ ਦੋਵੇਂ ਸਬੂਤ ਲਿਜਾਓ।

## ਸਮੱਸਿਆ-ਨਿਵਾਰਣ ਅਤੇ ਵਾਪਸੀ

**ਮਾਲਕ ਦੀ ਬੇਨਤੀ ਗੁੰਮ:** ਲਿਖਣ ਦੀ ਪਹੁੰਚ ਅਤੇ ਬੇਸ ਬ੍ਰਾਂਚ ਪਾਥ ਕਵਰੇਜ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ। **ਸੁਰੱਖਿਆ ਨਹੀਂ:** ਪਲਾਨ ਅਤੇ ਦਿੱਖ ਜਾਂਚੋ। **ਮਰਜ ਹਾਲੇ ਵੀ ਚੱਲਦਾ ਹੈ:** ਨਿਯਮ ਦਾ ਨਿਸ਼ਾਨਾ, ਬਾਈਪਾਸ ਕਨਫਿਗਰੇਸ਼ਨ ਅਤੇ ਸਮੀਖਿਆ ਗਿਣਤੀ ਵੇਖੋ।

**ਵਾਪਸੀ:** ਨਾ-ਮਰਜ ਪ੍ਰਸਤਾਵ ਬੰਦ ਕਰੋ ਅਤੇ ਲੈਬ ਆਟੋਮੇਸ਼ਨ ਬੰਦ ਕਰੋ। ਮਰਜ ਕੀਤੀ ਲੈਬ ਸਮੱਗਰੀ ਨੂੰ ਹੋਰ ਸਮੀਖਿਆ ਕੀਤੇ PR ਰਾਹੀਂ ਵਾਪਸ ਲਵੋ। ਅਸਥਾਈ ਰਿਪੋਜ਼ਟਰੀ ਮਿਟਾਉਣ ਤੋਂ ਪਹਿਲਾਂ ਸਬੂਤ ਸੰਭਾਲੋ। ਫੇਲ੍ਹ ਟੈਸਟ ਮੁਕਾਉਣ ਲਈ ਸੁਰੱਖਿਆ ਕਮਜ਼ੋਰ ਨਾ ਕਰੋ।

## ਅਭਿਆਸ ਅਤੇ ਸਵੈ-ਜਾਂਚ

**ਯੋਗਦਾਨਕਰਤਾ ਵਜੋਂ `docs/policy.md` ਵਿੱਚ ਸੋਧ ਦਾ ਪ੍ਰਸਤਾਵ ਦਿਓ।** ਫੈਸਲਾ ਕਰੋ ਕਿ ਕੀ ਸਿਰਫ਼ ਰੱਖ-ਰਖਾਅਕਾਰ ਦੀ ਮਨਜ਼ੂਰੀ ਨੀਤੀ-ਮਾਲਕ ਦੀ ਮਨਜ਼ੂਰੀ ਸਾਬਤ ਕਰਦੀ ਹੈ।

**ਉਮੀਦ ਕੀਤਾ ਤਰਕ:** ਸਮੀਖਿਆ ਗਿਣਤੀ ਇਕੱਲੀ ਅਧਿਕਾਰ ਸਾਬਤ ਨਹੀਂ ਕਰਦੀ। ਪਾਥ ਨੂੰ ਨੀਤੀ-ਮਾਲਕ ਦੀ ਕਵਰੇਜ ਅਤੇ ਮੌਜੂਦਾ ਭੂਮਿਕਾ ਸਮੀਖਿਆ ਦੀ ਲੋੜ ਹੈ। ਜਿਹੜੀਆਂ ਭੂਮਿਕਾ-ਖਾਸ ਲੋੜਾਂ ਲਾਗੂ ਨਹੀਂ ਹੁੰਦੀਆਂ, ਉਨ੍ਹਾਂ ਨੂੰ ਵਿਧੀਗਤ ਨਿਯੰਤਰਣ ਵਜੋਂ ਦਰਜ ਕਰੋ।
