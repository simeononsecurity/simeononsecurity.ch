## はじめに

**Tailscale**と**Headscale**は、どちらも[WireGuard](https://www.wireguard.com/)を使った安全なメッシュVPNを構築するための調整サーバーです。Tailscaleは無料枠が充実した商用のクラウドサービスです。HeadscaleはTailscaleの制御プロトコルを実装した、オープンソースのセルフホスト型の代替手段です。組織のネットワーク要件に合う方式を選ぶには、両者の違いを把握することが重要です。

主な判断基準は、**コントロールプレーンを誰が管理するか**です。ID管理、管理機能、サポートをサービス提供元に任せたい場合は、Tailscaleを選びます。セルフホスティングと調整用データの管理に、運用負担の増加を上回る価値がある場合は、Headscaleを検討します。以下では、機能、性能、費用、セキュリティ、保守を比較します。

## メッシュVPNとWireGuardの仕組み

比較に入る前に、基盤となる技術を確認します。

### WireGuardとは？

**WireGuard**は、次の特長を持つ高性能なVPNプロトコルです。
- **高い性能:** OpenVPNの最大10倍の速度
- **小さな攻撃対象領域:** コードは約4,000行（OpenVPNは100,000行以上）
- **新しい暗号技術:** Curve25519、ChaCha20、Poly1305
- **Linuxカーネルに内蔵:** Linux 5.6（2020年）以降

### メッシュVPNとは？

**メッシュVPN**は、すべてのトラフィックを中央サーバーに通す方式とは異なり、デバイス間にピアツーピア接続を確立します。
- **直接接続:** 可能な場合はデバイス同士が直接接続する
- **NATトラバーサル:** ファイアウォールやNATを自動的に通過する
- **遅延の低減:** 中央サーバーを経由する余分なホップがない
- **性能の向上:** ピア間で利用できる帯域を最大限に使う

### 調整サーバーの役割

WireGuard自体はプロトコルです。メッシュVPNの構築には、次の役割を担う**調整サーバー**（コントロールプレーン）が必要です。
- デバイスの認証と認可を管理する
- 暗号鍵を配布する
- NATトラバーサルとピアの検出を支援する
- アクセス制御ポリシーを管理する
- ネットワーク内のDNS名前解決を提供する

**Tailscale**と**Headscale**は、どちらもこれらの処理を担う調整サーバーです。

## 性能比較

### 遅延とスループット

TailscaleとHeadscaleはどちらもデータプレーンにWireGuardを使うため、**ピアツーピア接続の性能は同じ**です。

| 指標 | Tailscale | Headscale |
|--------|-----------|-----------|
| **P2P接続で増える遅延** | <1ms | <1ms |
| **P2Pスループット** | VPNなしに近い（1 Gbps回線で約900 Mbps） | VPNなしに近い |
| **中継トラフィック（DERP）のスループット** | 50〜300 Mbps | 10〜200 Mbps（サーバーによる） |
| **中継トラフィックの遅延** | +10〜50ms | +5〜100ms（設置場所による） |
| **接続確立にかかる時間** | 100〜500ms | 200〜800ms |
| **ACLポリシー更新の反映時間** | 5秒未満 | 30秒未満 |

**主な違い:** Tailscaleは世界各地にサーバーを配置したDERP（中継）ネットワークを運用しているため、直接接続に失敗して中継に切り替わった場合の性能が高くなります。Headscaleの内蔵DERPは自分のサーバー上で動作するため、地理的に分散配置していない場合は遅延が大きくなることがあります。

### スケーラビリティ

| 比較項目 | Tailscale | Headscale |
|--------|-----------|-----------|
| **最大ノード数** | 100,000以上（検証済み） | 約5,000（コミュニティからの報告） |
| **推奨ノード数** | 無制限 | サーバー1台あたり1,000未満 |
| **コントロールプレーンの毎分リクエスト処理数（RPM）** | 高度に最適化 | サーバーの仕様による |
| **ノードあたりのメモリ** | 該当なし（マネージド） | 約1〜5 MB（サーバー側） |
| **データベース** | PostgreSQL（マネージド） | SQLiteまたはPostgreSQL |

## セットアップと導入の比較

### Tailscaleのセットアップ手順

**所要時間:** 5〜10分

1. [tailscale.com](https://tailscale.com/)で**アカウントを作成**
2. 各デバイスに**クライアントをインストール**（コマンド1つ、またはアプリをダウンロード）
3. OAuthで**認証**（Google、Microsoft、GitHubなど）
4. **ACLを設定**（任意。後から設定可能）
5. **完了！** ネットワークをすぐに利用できます

**インストール例（Linux）:**

> **実行前にインストーラーを確認してください。** 一時ファイルにダウンロードして内容を確認し、ホストのディストリビューションとパッケージの取得元を確認します。インストール後は `tailscale version` と `tailscale status` を実行して結果を確認します。インストールに失敗した場合は、ディストリビューションのパッケージマネージャーでパッケージを削除し、システムのバックアップからパッケージを以前の状態に戻します。

```bash
curl -fsSL https://tailscale.com/install.sh -o /tmp/tailscale-install.sh
less /tmp/tailscale-install.sh
sh /tmp/tailscale-install.sh
sudo tailscale up
```

### Headscaleのセットアップ手順

**所要時間:** 30〜90分（初回）

1. **サーバーを用意**（パブリックIPを持つVPS、RAM 1GB以上を推奨）
2. **DNSを設定**（サーバーを指すAレコード）
3. **Headscaleをインストール**（パッケージマネージャーまたはDockerを使用）
4. **Headscaleを設定**（config.yamlにサーバーURL、データベースなどを指定）
5. **TLS証明書を設定**（Let's Encryptを推奨）
6. **Headscaleサービスを起動**
7. CLIで**ユーザーを作成**：`headscale users create alice`
8. 各デバイスに**Tailscaleクライアントをインストール**
9. 独自の調整サーバーを使うように**クライアントを設定**
10. Web認証または事前認証キーで**ノードを登録**
11. **ACLを設定**（policy.jsonファイル）

**Headscaleのインストール例（Ubuntu）:**
```bash
# Headscaleをインストール
curl -fsSL https://pkgs.headscale.net/headscale_<VERSION>_linux_amd64.deb -o headscale.deb
sudo apt install ./headscale.deb

# Headscaleを設定
sudo nano /etc/headscale/config.yaml
# server_urlをhttps://headscale.example.comに設定

# サービスを起動
sudo systemctl enable --now headscale

# ユーザーを作成
headscale users create myuser

# クライアント端末で
sudo tailscale up --login-server=https://headscale.example.com
```

**セットアップのしやすさ:** 初期セットアップは**Tailscale**の方が大幅に簡単です。

### 保守の負担

**Tailscale（マネージドサービス）:**
- ✅ サーバー保守が不要
- ✅ 更新とセキュリティパッチの適用が自動
- ✅ 冗長化とフェイルオーバーを標準装備
- ✅ 専門スタッフによるサポートを利用可能
- ❌ Tailscaleサービスの稼働状況に依存

**Headscale（セルフホスト）:**
- ⚠️ サーバーOSの更新とセキュリティパッチの適用（月1回）
- ⚠️ Headscaleソフトウェアの更新（1〜3か月ごと）
- ⚠️ データベースのバックアップ（毎日を推奨）
- ⚠️ TLS証明書の更新（Let's Encryptで自動化）
- ⚠️ 監視とアラートの設定
- ⚠️ 問題発生時の調査と解決
- ✅ インフラを全面的に管理できる
- ✅ 外部サービスに依存しない

**月あたりの作業時間の目安:**
- **Tailscale:** 30分（ポリシーの見直し、ユーザーの追加）
- **Headscale:** 2〜5時間（更新、監視、トラブルシューティング）

## 用途別の選び方

### Tailscaleが向いている場合

✅ **できるだけ早く導入したい** - アカウント作成からネットワークの稼働まで5分\

✅ **運用に時間をかけたくない** - 保守は不要で、更新は自動\
✅ **稼働率の保証が必要** - Tailscaleの稼働率SLAは99.99%（Enterprise）\
✅ **公式モバイルアプリを使いたい** - 全機能を備えたiOSとAndroidのネイティブアプリ\
✅ **専門スタッフのサポートが必要** - 有料プランに優先サポートが含まれる\
✅ **コンプライアンスを重視する** - SOC 2 Type II認証を取得\
✅ **営利事業で使う** - わかりやすいユーザー単位の料金で、隠れた費用がない\

### Headscaleが向いている場合

✅ **データ主権を完全に確保する必要がある** - すべてのメタデータを自分のインフラに保持\
✅ **プライバシーやコンプライアンス上の制約がある** - データを特定の法域内に保管する必要がある\

## 移行シナリオ

### TailscaleからHeadscaleへの移行

**移行の目的:** 費用削減、データ主権の確保、管理範囲の拡大

**手順:**
1. Headscaleサーバーを導入して動作を検証する
2. 重要度の低いデバイスの一部でHeadscaleをテストする
3. TailscaleからACLをエクスポートし、Headscale向けに調整する
4. デバイスをHeadscaleの調整サーバーに段階的に移行する
5. DNS設定とサブネットルートを更新する
6. Tailscaleの契約を終了する

**課題:**
- 自動移行ツールがない
- すべてのデバイスで再認証が必要
- 一部の機能（Funnel、Serve、Taildrop）は同じようには動作しない
- ACL構文には互換性があるものの、テストが必要

**所要時間:** 構成の複雑さに応じて5〜20時間

### HeadscaleからTailscaleへの移行

**移行の目的:** 運用負担の軽減、企業向け機能の利用、サポートの充実

**手順:**
1. Tailscaleアカウントを作成し、ACLを設定する
2. Tailscaleクライアントをインストールする（同じデバイスなら既存のクライアントを置き換え可能）
3. 独自サーバーを指定せずに `tailscale up` を実行してデバイスを移行する
4. 接続とアクセス制御を確認する
5. Headscaleサーバーの運用を終了する

**課題:**
- すべてのデバイスで再認証が必要
- 一部のユーザーはTailscaleアカウントが必要になる場合がある（メールまたはSSO）
- 変更管理とユーザーへの周知が必要

**所要時間:** 規模に応じて2〜8時間

## 実環境での性能ベンチマーク（2026年）

コミュニティのテストと公開ベンチマークに基づきます。

### スループットテスト（ピアツーピア）

| シナリオ | Tailscale | Headscale | 基準値（VPNなし） |
|----------|-----------|-----------|-------------------|
| **ギガビットLAN** | 940 Mbps | 940 Mbps | 945 Mbps |
| **WAN（100 Mbps）** | 98 Mbps | 98 Mbps | 100 Mbps |
| **WAN（1 Gbps光回線）** | 920 Mbps | 920 Mbps | 950 Mbps |
| **大陸間（DERP）** | 180 Mbps | 95 Mbps | 該当なし |

**分析:** ピアツーピアの直接接続では性能は同じです。中継接続では、世界各地のDERPネットワークを使うTailscaleが優位です。

### 遅延テスト

| シナリオ | Tailscale | Headscale | 基準値 |
|----------|-----------|-----------|----------|
| **LAN内のping** | 1.2ms | 1.2ms | 0.8ms |
| **地域内WAN（100マイル）** | 15ms | 15ms | 12ms |
| **国内横断** | 48ms | 48ms | 45ms |
| **大陸間（直接接続）** | 155ms | 155ms | 152ms |
| **大陸間（DERP）** | 185ms | 220ms | 該当なし |

**分析:** 直接接続で両者が加える遅延はわずかです（約1〜2ms）。HeadscaleのDERP経由の遅延はサーバーの設置場所によって変わります。

## 高度な設定例

### Docker ComposeでHeadscaleを動かす

```yaml
version: '3'
services:
  headscale:
    image: headscale/headscale:0.28.0
    container_name: headscale
    restart: unless-stopped
    ports:
      - "127.0.0.1:8080:8080"  # API/ウェブ
      - "443:443"              # HTTPS
      - "3478:3478/udp"        # STUN
    volumes:
      - ./config:/etc/headscale
      - ./data:/var/lib/headscale
    command: serve
    environment:
      - TZ=UTC
```

### HeadscaleのACL設定例

```json
{
  "groups": {
    "group:admin": ["alice@", "bob@"],
    "group:developers": ["charlie@", "diana@"]
  },
  "hosts": {
    "production-db": "100.64.0.10/32",
    "staging-db": "100.64.0.20/32"
  },
  "acls": [
    {
      "action": "accept",
      "src": ["group:admin"],
      "dst": ["*:*"]
    },
    {
      "action": "accept",
      "src": ["group:developers"],
      "dst": ["staging-db:5432", "autogroup:self:*"]
    }
  ]
}
```

### Tailscaleクライアントの設定（Headscaleを使用）

```bash
# Linux
sudo tailscale up \
  --login-server=https://headscale.example.com \
  --accept-routes \
  --advertise-tags=tag:server

# 事前認証キーを使用
headscale preauthkeys create --user engineering --expiration 1h

sudo tailscale up \
  --login-server=https://headscale.example.com \
  --authkey=<YOUR_AUTH_KEY>
```

## よくある問題のトラブルシューティング

### Tailscaleの問題

| 問題 | 解決方法 |
|---------|----------|
| **調整サーバーに接続できない** | ファイアウォールの設定とインターネット接続を確認する |
| **直接接続に失敗する** | 通常は自動的にDERPに切り替わる。NAT設定を確認する |
| **遅延が大きい** | 中継を介さずに直接接続が確立しているか確認する |
| **鍵の有効期限が切れた** | 再認証するか、管理コンソールで鍵の有効期限を無効にする |
| **ACLが通信をブロックする** | ACLルールを見直し、設定をテストする |

### Headscaleの問題

| 問題 | 解決方法 |
|---------|----------|
| **ノードを登録できない** | HeadscaleのURLにアクセスできるか確認し、TLS証明書を確認する |
| **DNSの名前解決に失敗する** | config.yamlでMagicDNSが正しく設定されているか確認する |
| **DERP中継が動作しない** | STUNポート（3478/udp）が開いているか確認し、DERP設定を確認する |
| **再起動後にノードがオフラインになる** | クライアントがシステム起動時に自動起動するよう設定されているか確認する |
| **ACLの変更が反映されない** | Headscaleの設定を再読み込みする：`systemctl reload headscale` |
| **データベースが破損した** | バックアップから復元し、本番環境ではPostgreSQLの利用を検討する |

### デバッグコマンド

```bash

tailscale ping <hostname>
tailscale debug derp

# Headscaleの診断
```

## セキュリティのベストプラクティス

### 両方に共通する対策

1. **鍵の有効期限を設定する** - 定期的な再認証を必須にする
2. **最小権限の原則を適用する** - ACLで必要最小限のアクセス権を付与する
3. **インフラのノードにタグを付ける** - ユーザーのデバイスとサーバーを分ける
4. **MFAを有効にする** - ユーザーのログインに多要素認証を必須にする
5. **アクセスログを監視する** - 接続パターンを定期的に確認する
6. **クライアントを最新に保つ** - セキュリティパッチを速やかに適用する

### Headscale固有のセキュリティ対策

1. **サーバーOSを堅牢化する** - CISベンチマークに従い、不要なサービスを無効にする
2. **Let's Encryptを使う** - TLS証明書の管理を自動化する
3. **fail2banを導入する** - 総当たり攻撃を防ぐ
4. **定期的にバックアップする** - データベースを別の場所にバックアップする処理を自動化する
5. **速やかに更新する** - Headscaleのリリースを確認し、セキュリティパッチを把握する
6. **ネットワークを分割する** - Headscaleサーバーを管理用VLANに隔離する
7. **ファイアウォールを有効にする** - 必要なポート（443、3478/udp）だけを公開する

## 結論

**Tailscale**と**Headscale**は、どちらもWireGuardベースの優れたメッシュVPN機能を提供します。対象となる利用者と用途は異なります。

**Tailscaleが向いている場合:**
- シンプルさを重視し、数分で使い始めたい
- 無料枠を活用できる小規模チームである（デバイス100台未満）
- SSO、監査ログ、専門スタッフのサポートといった企業向け機能が必要
- セルフホスティングよりもマネージドサービスを好む
- コンプライアンス認証（SOC 2）を重視する

**Headscaleが向いている場合:**
- インフラとメタデータを全面的に管理する必要がある
- 必要な技術があり、セルフホスティングを楽しめる
- 費用の最適化が重要（有料ユーザーが10人を超えると削減効果が大きい）
- データ主権とプライバシーを最優先する
- 自分で監査やカスタマイズができるオープンソース製品を好む

**2026年の主な推奨事項:**

1. **スタートアップと中小企業:** まずは**Tailscaleの無料枠**を使います。デバイス0〜100台の範囲では、他に並ぶ選択肢はありません。
2. **大企業のIT部門:** SSOとサポートを備えた**Tailscale Enterprise**は、スタッフの作業時間まで考慮すると総所有コストの面で最も有利です。
3. **プライバシーを重視する利用者:** **Headscale**なら、管理範囲とプライバシーを最大限に確保できます。
4. **ホームラボの技術を深めたい利用者:** **Headscale**は実践を通じて学ぶのに適しています。
5. **両方を使う組織:** **本番環境にはTailscale**を、**開発・テスト環境にはHeadscale**を使います。

どちらを選んでも、安全で現代的なネットワークを、同種の技術の中でも優れたWireGuardで構築できます。判断の軸は、**利便性と管理の自由度**、**マネージドとセルフホスト**、そして**費用と機能**のどちらを優先するかです。

2026年時点では、多くの組織にとって**Tailscaleのマネージドサービス**が、機能、使いやすさ、費用対効果のバランスに最も優れています。データ主権、プライバシー、費用に固有の要件がある組織には、**Headscaleが有力なセルフホスト型の選択肢**になります。
