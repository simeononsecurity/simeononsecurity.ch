**Cloudflare Tunnel** はアプリを Cloudflare に接続します。**Cloudflare Access** はアプリにアクセスできるユーザーを制御します。公開ホスト名で公開する自宅の非公開ダッシュボードには、両方を使います。トンネルが動作していても、ID確認が追加されるわけではありません。[Cloudflare のアプリ公開ガイド](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)でこの違いを確認できます。

## 要点

- **経路を説明する:** コネクター、オリジン、ID確認を区別します。
- **ポリシーを設定する:** 指定したユーザーだけに非公開ダッシュボードへのアクセスを許可します。
- **保護を評価する:** 許可、拒否、代替のアクセス経路をテストします。
- **アクセスを設計する:** 訪問者と自動化に必要な条件を個別に記録します。

## 始める前に

**対象読者:** ブラウザーで使うダッシュボードを保護したいホームサーバーの所有者。例では、Cloudflare 上で有効なドメイン、正常に動作するローカル Web アプリ、両方を管理する権限を想定します。**所要時間:** コネクター設定後のポリシー演習に 20～30 分。**難易度:** 初級から中級。

**読み進め方:** まず各製品の役割を把握し、1 つのリクエストの流れを追います。次に、小さなポリシーを設定して確認します。最後に、自分のサービスのアクセス仕様を作成します。

## 各製品の役割

**オリジン**はアプリを実行するサーバーです。**`cloudflared`** コネクターはインフラストラクチャから Cloudflare への接続を開始します。そのため、オリジンに公開ルーティング可能な IP アドレスは必要ありません。その後、リクエストと応答は確立済みの接続を通ります。[Cloudflare Tunnel の概要](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)。

| 質問 | Tunnel | Access |
|---|---|---|
| **Cloudflare はどのようにサーバーへ接続する？** | 接続を確立する | オリジンへの接続を代替しない |
| **誰がアクセスできる？** | 単独ではユーザーログインを提供しない | 設定済みのアクセスポリシーを評価する |
| **何を設定する？** | コネクターとアプリのルート | アプリ、ID プロバイダー、ポリシー |
| **成功によって何が分かる？** | ルート経由でオリジンに到達できる | リクエストが設定済みポリシーを満たした |

**ID プロバイダー（IdP）**は訪問者を認証します。**Access ポリシー**はアクションと一致条件を定義します。Allow は条件に合うユーザーを許可します。Bypass は条件に合うトラフィックについて Access の適用を無効にします。[Access ポリシーのリファレンス](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/)。

## ブラウザーのリクエストを追う

**`dashboard.example.com`** の論理的なリクエスト経路は次のとおりです。

```text
ブラウザー -> Cloudflare Access -> トンネル接続 -> cloudflared -> ダッシュボード
                      |
                      +-> 認証が必要な場合の ID プロバイダー
```

**コネクターはネットワークから外向きにトンネル接続を開始します。** その後、ブラウザーのリクエストは確立済みの接続を通ってオリジンへ届きます。外向き接続でアプリへの内向きリクエストを運ぶ仕組みが、一般的なオリジンポートの転送なしで Tunnel を使える主な理由です。[Tunnel の接続モデル](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)。

**アプリ内の権限**は別に決めます。ダッシュボードへのアクセスを許可しても、誰が設定を変更したりデータを削除したりできるかは自動的に決まりません。アプリに閲覧者と管理者のロールがある場合は、それぞれ個別に設定してテストします。

たとえば、**家族の閲覧者**にはバックアップ状態の確認を許可し、あなたには保存先の変更を許可する必要があります。ID を選ぶ前に、こうした要件を書き出します。同じ Access チェックを通過した 2 人に、同じアプリ権限を自動的に与えてはいけません。

## 両方が必要な場合

**保護方法は利用者によって決まります。** ルートを公開する前に、次の構成を比較します。

| 想定する利用者 | 推奨する構成 | 利用前の確認 |
|---|---|---|
| **公開サイトの読者全員** | オリジン接続に必要な場合は Tunnel | 公開が意図した設定である |
| **あなたと数人の家族** | Tunnel と Access | 想定した ID だけを許可する |
| **すでに公開されているオリジン** | オリジン保護を別に用意して Access を使う | オリジンへの直接アクセスでチェックを回避できない |
| **定期実行スクリプト** | Tunnel と Service Auth ポリシー | クライアントが認証方式に対応している |

**Tunnel を使わない Access**は、すでに到達可能なオリジンで利用できます。サーバーへの別経路も保護します。新しいトンネルルートを公開するときは、先に Access アプリを作成するよう Cloudflare は勧めています。[セルフホスト型アプリの要件](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)。

*公開ホスト名からアクセスする自宅の非公開ダッシュボードには、Tunnel と Access を使います。*

## ダッシュボードのポリシーを設定する

2 人の訪問者を想定した**設定例**を使います。サンプルのアドレスは、自分が管理する ID に置き換えます。公開トンネルルートを追加する前に Access アプリを作成します。

1. **アプリ:** Zero Trust → Access controls → Applications を開き、公開ホスト名を指定したセルフホスト型アプリを作成します。
2. **ホスト名:** ダッシュボード専用のホスト名を入力します。ホスト名全体を対象とする例なので、パスに制限を設けません。
3. **ポリシー:** `Dashboard viewers` という名前の Allow ポリシーを作成します。
4. **ID セレクター:** Emails を使う Include ルールを追加します。`alice@example.com` と `bob@example.com` を、対象の 2 人のアドレスに置き換えます。
5. **ログイン:** 訪問者が使う ID プロバイダーを選び、セッション期間を適切に設定します。
6. **ルート:** アプリを保存し、トンネル経由でホスト名をダッシュボードに接続します。

[公式のアプリ設定手順](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)に各設定の説明があります。**想定される結果:** 初めてアクセスする訪問者は、アプリに到達する前に認証を求められます。ポリシーを信頼する前に、以下の拒否テストを完了します。

## ルールのロジックを理解する

**Include** は OR で条件のいずれかを満たせば許可します。**Require** は AND で必須条件を追加します。**Exclude** は条件に一致するユーザーを除外します。Include 条件を追加すると、アクセス可能なグループが広がります。[Access ルールの意味](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/)。

| ポリシーの断片 | 論理的な動作 |
|---|---|
| **Include Alice or Bob** | 指定した 2 つの ID のどちらかで条件を満たす |
| **Include Alice, Include a country** | 国の条件に合う人もアクセスできる |
| **Include Alice, Require a country** | Alice は国の条件も満たす必要がある |

**ポリシー確認の演習:** 要件では Alice と Bob のみを指定していますが、同僚が別の Include 条件として国を追加しました。別の利用者集団が許可されるため、変更を拒否します。地理的な場所は、利用者が家庭の一員である証拠になりません。

## 定期実行スクリプトを認証する

**サービストークン**には、自動リクエスト用の Client ID と Client Secret が含まれます。トークンを **Service Auth** で受け入れるようアプリのポリシーを設定します。対応するポリシーなしでトークンを作成しても、アプリへのアクセスは許可されません。[Cloudflare のサービストークン](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/)。

バックアップスクリプトや監視チェックでは、**シークレット**をツールの保護された認証情報ストレージに保存します。各統合に別々のトークン名と適切な有効期限を設定します。統合を廃止するときは、トークンをローテーションまたは失効させます。サービストークンのドキュメントに、ライフサイクルの操作が記載されています。

**クライアントの互換性を明示的に確認します。** API 応答を想定するツールが、ブラウザーでの対話型ログインに対応するとは限りません。ポリシーを選ぶ前に、リクエストヘッダーや別のサポート対象認証方式に対応しているか確認します。

## アクセス制御をテストする

デプロイ時の**受け入れチェック**として次を使います。

| チェック | 記録する証拠 |
|---|---|
| **未ログインの訪問者** | 新しいブラウザーセッションからのリクエストを Access が遮断する |
| **許可した ID** | サインイン後に対象のアプリが読み込まれる |
| **拒否した ID** | 登録されていないアカウントはアプリにアクセスできない |
| **代替経路** | 古い DNS 名やオリジンポートから意図しないアクセスがない |
| **自動化** | 承認済みクライアントは動作し、認証情報なしのリクエストは失敗する |

**ログイン画面が表示されたこと**は、1 つの経路で認証があったことしか示しません。拒否ケースと代替経路もテストします。これは推奨する確認項目であり、デプロイ済み環境の測定結果ではありません。

## オリジンの境界を確認する

Access の ID を信頼する**オリジンは、署名済みのアプリトークンを検証する必要があります。** Cloudflare は **`Cf-Access-Jwt-Assertion`** ヘッダーでトークンを転送します。ヘッダーがあるだけでは真正性を証明できません。[Cloudflare の JWT 検証](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)。

**JSON Web Token（JWT）**には署名済みのクレームが含まれます。Access の ID をオリジンに統合する場合は、想定する issuer とアプリの audience を含む、ドキュメント化された検証方法を使います。トークンをデコードしてメールアドレスを読むだけでは、十分な検証になりません。

**Issuer** はトークンを発行する機関を示します。**Audience** は対象のアプリを示します。署名検証を一から実装するのではなく、サポート対象ライブラリでトークンの有効性と有効期限を確認します。

**境界を明確にします:** 検証を行う場所と、アプリに到達するルートを特定します。メインのホスト名でブラウザーテストにすべて合格していても、古いポート転送や別のホスト名は個別に確認します。

## ポリシーの不一致を解決する

| 状況 | 次に確認すること |
|---|---|
| **想定外の訪問者が通過する** | Include 条件、Bypass ポリシー、ホスト名の適用範囲 |
| **想定した訪問者が拒否される** | サインイン中の ID と正確なセレクター値 |
| **スクリプトにログインページが返る** | 認証情報と Service Auth ポリシー |
| **閲覧者が設定を変更できる** | アプリ独自のロール割り当て |

**セッションの動作**も再テストに影響します。Access にはアプリ単位やグローバルなど複数のセッション期間があります。設定を記録し、新しい ID をテストするときは新しいセッションを使います。[Access のセッション管理](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/)。

## アクセス仕様を作成する

別のサービスを追加する前に、**簡単な仕様**を作成します。

```text
サービスとホスト名:
許可する人間の ID:
必要なアプリのロール:
自動化の認証情報と有効期限:
オリジンへの別の経路:
Access トークンを検証する場所:
許可された ID のテスト結果:
拒否された ID のテスト結果:
```

**完了条件:** 別の管理者が、誰にアクセスを許可するか、各クライアントがどう認証するか、拒否を証明する証拠を理解できる状態にします。後から監視統合を追加した場合は認証情報の項目を更新し、認証なしのリクエストチェックを再実施します。
