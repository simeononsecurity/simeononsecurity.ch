**两个人向两种 AI 工具提出同一个问题：**服务应将导出文件保留多久？在这个示例中，开发人员的 IDE 智能体从 README 得出七天，运营负责人使用的聊天助手则从维基页面得出三十天。两种回答都很肯定。每个工具读取的都是不同版本的事实。

**问题出在责任归属，**而非提示词质量。维基中的要求上周已更新，但没人修改 README。开发人员让智能体修复保留期限任务。智能体依照旧文档生成了整洁的补丁，却恢复了错误行为。审查者检查代码时，看不到答案背后的要求版本。

**为每类事实指定唯一归属。**让每个工具读取该权威来源，并让每项持久变更都经由人员处理。代码库、维基和任务跟踪器用途不同。必须明确权限范围、负责人，以及信息在它们之间流转的共同流程。

**本指南提供一套本周即可采用的模型，**无论是否使用检索增强生成。先建立项目地图、版本化指令、证据记录和经过审查的提案。只有在确有检索需求时，才增加搜索基础设施。

**第一项交付物应是来源登记表，**而不是连接器。列出每类事实、其权威位置、负责人、当前版本，以及批准变更的人。

## 核心要点

- **按信息类型指定权威来源，**不要把所有内容强塞进一个应用。
- **将记忆和检索索引视为缓存，**不要让它们成为独立的策略来源。
- **在提案中附上来源版本，**让审查者知道变更依据。
- **在提示词之外落实审批，**使用访问控制和必需的审查门禁。
- **在不同工具间共享流程，**同时按各自界面调整呈现方式。

## 开始之前

**前提条件：**选择一个试点项目，其中包含代码库、维基或文档系统、任务跟踪器，以及愿意审查变更的负责人。没有维基的团队可改用版本化文档存储。保持责任模型不变。

**预计时间：**初次建立地图和模板需要两到四小时，随后进行一周试点。**难度：**中等。难点在于对权威来源达成一致，而不是安装另一个 AI 工具。

**范围：**这是一套建议的团队运行模型。审批规则和命名约定属于建议，并非 Claude Code、Codex、Cline、Cowork、Copilot 或 ChatGPT 保证提供的默认行为。上方自动目录链接到各个实施步骤。

## 工具不同，上下文也不同

**程序员和非程序员共同参与一个项目，**但他们使用不同界面。开发人员使用 IDE 或终端智能体。产品负责人使用聊天项目。运营负责人通过维基和任务跟踪器工作。根据任务选择界面，而非根据它能否访问权威事实来选择。

**上下文是当前回答可用的材料。**检查每个会话中的代码库文件、上传文档、聊天记录、保存的记忆、连接器结果和检索片段。两个会话依据不同证据时，即使问题相同，回答也不必一致。

| 问题 | 表现 |
|---|---|
| **文档漂移** | README 重复了过时要求 |
| **摘要升格为证据** | 会话摘要脱离原始来源后被当成证据 |
| **写入重叠** | 两个智能体从不同基础版本替换同一页面 |
| **决策丢失** | 会议约定没有进入决策登记册 |
| **缺少来源链** | 看似合理的回答没有说明页面版本或提交 |

**保留期限示例说明了这种区别。**维基描述经批准的目标行为。代码描述已经实现的行为。两者都不应悄悄改写另一方。记录冲突，并询问指定负责人是否需要修改实现或要求。

> **要点：**先对权威来源达成一致，再选择 AI 工具。先定义下面的共同术语。

### 侧栏：五个共同术语

| 术语 | 本框架中的含义 |
|---|---|
| **来源** | 针对某类信息指定的权威记录 |
| **缓存** | 为提高速度或便利性生成的副本 |
| **提案** | 等待负责人批准的变更建议 |
| **项目地图** | 包含来源位置、标识符和负责人的索引 |
| **清单** | 记录某项回答或提案实际依据的证据 |

## 为每类事实指定唯一归属

**唯一来源表示每类事实只有一个权威来源，**不是整个组织只有一个数据库。试点期间建立下列分工，并将示例角色换成团队实际负责人。

| 信息类型 | 归属系统 | 负责人 | 谁写入 | 智能体如何读取 |
|---|---|---|---|---|
| **代码、测试、配置、架构** | 代码库 | 工程维护者 | 贡献者通过审查后的 PR | 指定提交中的文件 |
| **已发布文档和 ADR** | 代码库 | 技术负责人 | 贡献者通过同一个 PR | 版本化文件 |
| **要求** | 维基 | 产品负责人 | 负责人或获准发布者 | 页面 ID 和版本 |
| **运行手册** | 维基 | 运营负责人 | 获准发布者 | 页面 ID 和版本 |
| **策略** | 维基 | 策略负责人 | 审查后由获准发布者发布 | 权威页面及本地适配器 |
| **跨团队决策** | 维基决策登记册 | 指定决策负责人 | 批准后由负责人写入 | 决策 ID 和状态 |
| **任务与发现** | 任务跟踪器 | 任务负责人 | 人员或获准的提案接收流程 | 问题编号和版本 |
| **聊天、摘要、嵌入向量** | 仅作缓存 | 会话或索引维护者 | 工具和参与者 | 只作参考，随后核对来源 |

**架构决策记录（ADR）**若管理代码库设计，应放在代码旁。跨团队决策属于共享登记册。跨越两种范围时，链接两份记录。不要维护两份独立的审批状态。

**本地策略副本从属于权威策略页面。**相反，代码库中的测试和架构在各自范围内属于来源。位置本身无法决定权威性，项目地图才可以。

**缓存不能覆盖来源。**若摘要写着七天，而已批准要求是三十天，则以要求为目标行为。把冲突摘要保留为漂移证据，不要将其视为另一条规则。明确权威来源后，再定义写入流程。

## 先读取证据，再提交提案

**智能体将证据读入会话上下文，**然后起草提案。智能体不自行批准持久事实。编辑任务分支或提交草稿，不等于发布策略、合并代码或标记决策已接受。

```text
来源 -> 检查权限后读取 -> 会话上下文
会话上下文 -> 提案 + 基础版本 -> 负责人审查
负责人批准 -> 受控发布 -> 变更日志
基础版本已变更 -> 协调提案 -> 重新审查
```

**申请审查前附上基础版本。**审查者需要了解旧值、提议值、原因、证据和受影响系统。批准必须指向特定提案版本，而不能指向持续变化的聊天线程。

```yaml
proposal_id: PROP-042
target: wiki:REQ-17
base_version: 8
change: "将导出文件的保留期限从七天改为三十天。"
evidence:
  - "decision:DEC-12 已接受"
affected_records:
  - "repo:export-service 保留期限配置"
  - "wiki:RUN-04 清理流程"
owner_role: product-owner
status: awaiting-review
```

**以上标识符仅为示例。**每项获准的逻辑变更在变更日志中占一行，记录提案 ID、目标记录、变更前后版本、审批者、时间戳，以及合并或发布引用。将各系统的审计事件链接到该行，而不是替换系统原有历史。

**决策由人员负责。**获准发布者或受约束的自动化应用已批准版本，并相应限制写入凭据。仅靠指令无法确保起草和发布分离。检索流程也要遵守相同边界。

## 无需 RAG 也能共享上下文

**项目地图是第一个检索索引。**每个项目维护一页，记录来源 ID、代码库位置、任务编号、权威范围和负责人。先读地图，再按 ID 获取相关记录。ID 未知时再使用搜索。

### 侧栏：示例项目地图

```yaml
project: export-service
map_id: MAP-01
policy:
  source_id: POL-01
  approved_version: 3
  owner_role: policy-owner
sources:
  requirements: {page_id: REQ-17, owner_role: product-owner}
  runbook: {page_id: RUN-04, owner_role: operations-owner}
  decisions: {register_id: DEC-REGISTER, owner_role: project-lead}
repository:
  key: export-service
  setup: README.md
  terms: CONTEXT.md
  decisions: docs/adr/
tracker:
  project_key: EXP
  active_task: EXP-42
```

**直接连接器可以减少手工复制。**模型上下文协议（MCP）是一种向 AI 应用公开工具和上下文的集成协议。在支持的场景中使用经批准的维基、任务跟踪器和代码库连接器。定向获取能减少无关结果，但不能替代授权和时效性检查。选择连接器权限时，遵循参考文献中的 MCP 安全指南。

**精确检索的设置成本较低。**它无需向量数据库即可提供可引用的证据。限制也很明确：有人需要维护地图；宽泛问题仍需额外搜索；大型页面会占用会话空间。获取相关章节及其相邻限制，不要粘贴整本手册。

**离线工作使用明确的快照。**记录导出版本，并标注回答基于快照。获准人员或连接器检查当前来源之前，不要发布变更。接着让相同策略在各个界面中可见。

## 一套策略，多种适配器

**保留一套共享策略，**再分发简短的工具专用适配器。每个适配器或复制的指令集第一行都标出获准策略版本。还要包含来源 ID，并为无法连接实时来源的会话提供经过审查的本地快照。

**不同工具的加载方式不同。**Codex 说明了分层发现 **`AGENTS.md`** 的方式。Claude Code 说明了 **`CLAUDE.md`**、导入和项目记忆。Cline 说明了 **`.clinerules/`** 和规则控制。使用参考文献中的官方指令文档。检查已安装版本实际加载的指令，不要假设文件名在各工具中表现一致。

### 侧栏：示例 AGENTS.md 标题

```markdown
策略版本: v3 | 来源: wiki:POL-01 | 状态: 已批准

# 项目指令

开始任务前阅读项目地图 MAP-01。
加载 docs/policy-snapshot.md 并记录来源版本。
将聊天记忆和搜索摘录视为缓存。
为每项事实提案附上来源版本。
每项编码任务使用一个任务分支和一个工作树。
不要发布策略、批准决策或合并自己的 PR。
遇到未解决的来源冲突或重叠写入时停止。
必要检查：测试、文档审查、策略时效性。
负责人：工程维护者、产品负责人、策略负责人。
```

**聊天项目指令也应使用同一标题和流程。**非程序员通过获准上传或连接器获得策略快照和项目地图。若界面无法实时访问，人员应提供有版本的导出文件并记录限制。

**版本标签是声明，不是内容相同的证明。**从获准快照生成适配器，或将策略部分与已存摘要进行比较。单独审查适配器例外。试点时检查被禁用的规则、嵌套覆盖和个人指令。然后记录每项任务使用的证据。

## 记录上下文清单

**上下文清单解释回答依据的证据。**记录页面 ID 和版本、问题编号及其版本或更新时间，以及完整代码库提交 ID。包括检索时间和相关章节。记录无法获取的内容，不要用记忆中的摘要代替。

```yaml
task: EXP-42
policy: {page_id: POL-01, version: 3}
wiki:
  - {page_id: REQ-17, version: 8, section: export-retention}
tracker:
  - {issue_key: EXP-42, revision: 5}
repository:
  commit: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  files: [README.md, config/retention.yaml]
limits:
  - "未获取运行手册。未提议修改运行手册。"
```

**提交值为虚构值。**实际清单中应替换为检查过的提交。实际读取时还需添加检索时间戳。检查之前创建的记录只是清单，不是证据。

**引用用于核查，**不能自动建立信任。将每项重要主张链接到支持它的记录和章节。若两个来源冲突，应在清单中保留双方并报告未解决的差异。不要只看时间戳就选择较新版本，还要检查范围和批准状态。语义检索也应遵循此证据纪律。

## 使用 RAG 共享上下文

**检索增强生成（RAG）**在模型生成回答时提供检索到的材料。语义索引即使问题措辞不同，也能帮助找到相关段落。微软的 RAG 概述介绍了依据来源、检索限制和访问控制要求。官方链接见参考文献。

**在大型资料集中搜索发现内容时使用 RAG，**包括旧文档、会议记录和文字稿。标注文档类别和审批状态。从原始录音索引的文字稿可作为参与者发言的来源，却不能作为已批准要求的权威来源。不要借助索引把对话升级为策略。

| 索引规则 | 必须做到 |
|---|---|
| **摄取来源，不摄取缓存** | 排除生成摘要和未跟踪的本地副本 |
| **保留来源链** | 每个片段保留来源 ID、版本、章节和文档状态 |
| **变更时刷新** | 重新索引编辑并使旧片段失效 |
| **遵守访问权限变更** | 更新权限并移除删除或撤销的内容 |
| **返回引用** | 在检索文本旁提供记录引用 |
| **检查实时记录** | 提议重要操作前获取当前证据 |

**在本框架中，检索片段只是指针。**它帮助定位证据。实时来源确认当前措辞、审批状态、相邻例外和访问权限。实时检索失败时，标注快照并暂停重要操作。这是一条治理规则，不是对每种 RAG 实现的描述。

**过期嵌入与缺失上下文带来不同风险。**旧片段会漏掉新版本。即使片段是最新的，若例外位于下一节，也仍会误导。保留标题，并获取相邻限制，再评估要求。

**权限泄漏需要单独测试。**在向模型返回片段之前落实授权，而不是在生成回答后才检查。在索引或向外部服务发送嵌入之前筛查敏感内容。考虑日志、模型请求和检索轨迹中的复制文本。选择本地模型不会让远程连接器变成本地连接器。根据这些检查决定试点是否需要 RAG。

## 选择地图、RAG 或两者兼用

**根据问题选择检索方式。**已知要求 ID 适合直接访问。关于分散历史资料的开放问题适合搜索。除非发现已成为有证据的问题，否则先从地图开始。

### 侧栏：要用 RAG 吗？

```text
任务通常会指定项目、页面、问题或文件吗？
  是 -> 试点中直接检索是否足够？
         是 -> 仅用地图
         否 -> 混合：已知 ID 用地图，发现内容用 RAG
  否 -> 证据是否散落在大型资料集中？
         否 -> 仅用地图，并使用原生搜索
         是 -> 工作是否为探索性且只读？
                是 -> 仅用 RAG 发现资料
                否 -> 混合，并检查实时来源

每种方案都保留负责人、授权和来源链。
仅用于发现的 RAG 仍须在持久操作前检查来源。
```

**仅用 RAG 描述的是检索界面，**不代表可以跳过治理。它适用于范围明确且仍可直接检查来源的探索性资料集。对于需要精确版本检查的已知 ID 变更，这不是好选择。

**混合模型将发现与验证分开。**地图处理已知查找，RAG 定位陌生记录。RAG 回答“在哪里”，来源回答“是什么”。保留期限示例应直接获取 **`REQ-17`**。若问“哪些旧导出决策解释了这个限制？”，就搜索登记册并获取每项相关决策。现在把代码库一侧落实到日常工作中。

## 代码库内的信息

**代码库知识随实现一同变化。**保持结构简洁，让智能体和审查者知道去哪里查找。

| 文件或目录 | 职责 |
|---|---|
| **`CONTEXT.md`** | 项目术语及权威记录链接 |
| **`docs/adr/`** | 已接受的代码库架构决策 |
| **`docs/design/`** | 经批准的系统行为说明 |
| **`docs/plans/`** | 明确标注状态的拟议实施计划 |
| **`AGENTS.md`** | 审查门禁、边界和负责人角色 |
| **`README.md`** | 设置和入口点，不重复要求 |

**执行同一 PR 规则：**代码和受影响的代码库文档应一并变更。若无需更新知识库，则要求在 PR 描述或约定的提交尾注位置写明例外。

```text
KB-Update: none (原因：内部重构保留了文档描述的行为)
```

**流水线负责执行声明。**必需检查应拒绝没有文档更新或例外说明的行为变更。文档负责人需要审查例外。基于路径的检查可以识别候选变更，但无法证明语义完整。通过分支保护或等效合并控制落实检查和审查。

**若门禁不在流水线中，它就不算门禁。**在指令文件中写“文档审查”只提供指导。试点时提交一个故意不完整的 PR，确认合并会被阻止，以此测试执行效果。

**每项任务使用一个任务、一个分支、一个工作树。**Git 官方工作树文档说明了各自拥有检出状态的独立工作树。独立工作树能减少本地编辑冲突，但不能阻止两个分支修改同一文件，也不能阻止两个智能体同时更新同一维基页面。

**不要直接提交到默认分支，**无论它叫 **`main`**、**`master`** 还是其他名称。将要求与代码之间的差异报告到任务跟踪器。附上冲突记录，让其负责人在调整任何一方之前确定预期行为。Git 之外也应采用等效控制。

## 代码库以外的信息

**维基需要文档标准。**每个权威页面都记录用途、状态、负责人、版本、审查日期和关联来源 ID。将提案放在明确标记为非权威的草稿区域。不要把提议措辞混入已批准要求页面。

**安全更新遵循固定顺序：**

1. **重新阅读**当前页面及相邻限制。
2. **比较**页面版本与提案基础版本。
3. **协调**期间发生的编辑，并为变更后的措辞重新审批。
4. **写入**带有预期版本条件的已批准修订。
5. **验证**已保存页面并添加变更日志引用。

**重新阅读本身不能消除写入竞争。**可用时使用系统的条件更新机制。若没有该机制，则由单一负责人串行发布并验证结果。若审查期间另一位作者修改了基础版本，就暂停。

**智能体工作流也要遵守禁止删除规则。**智能体可提出归档或移除建议。获准人员执行保留和删除流程。不要把此规则解释为可无限期保留敏感信息。

**任务跟踪器发现记录的是证据，**而不只是结论。记录观察到的内容、确切命令或检查方法、所检查的提交、预期行为、实际行为和验收标准。附加证据前移除秘密和敏感输出。建议但未执行的命令应标为未运行。

```text
发现：保留期限的实现与已批准要求不一致
证据：REQ-17 v8 和已检查的 config/retention.yaml
检查命令：git show HEAD:config/retention.yaml
提交：清单记录完整的已检查提交 ID
验收：已批准期限与代码、测试和运行手册一致
状态：等待产品和工程负责人审查
```

**该示例是发现记录模板，**不是测量结果。应依据实际检查填写，并通过提案 ID 将维基更新与任务跟踪器证据关联。

**决策登记册将规则与推理分开。**记录问题、选项、建议、权衡、负责人、审批状态和最终规则引用。智能体负责提案，人员负责决策。已批准规则进入策略和流程技能，理由仍留在登记册中。

**从会议和聊天中提取需要长期保存的事实。**提交带有来源证据的提案并申请批准。发布前将约定标为暂定。接着在代码库和维基之间连接已批准行为。

## 连接两个系统

**合并后同步将实现变更传递到外部。**创建维基更新任务，并链接已合并提交、已批准要求和受影响运行手册。智能体起草更新，维基负责人检查当前页面并批准发布。确认已保存版本之前不要关闭同步任务。

**策略时效性是一项单独审计。**将代码库适配器和聊天指令副本与权威批准版本比较。策略 **`v3`** 位于 **`POL-01`**。每个 **`AGENTS.md`** 的第一行都写明 **`v3`**。即使标签一致，审计也要标记 **`v2`**、缺失标签和内容差异。

| 检查 | 完成证据 |
|---|---|
| **策略时效性** | 对比权威版本和适配器摘要 |
| **要求协调** | 将要求版本与代码和测试进行比较 |
| **合并后同步** | 合并提交关联到已发布的维基版本 |
| **冲突解决** | 经负责人批准的决策链接到双方记录 |

**按计划或在 PR 阶段协调。**试点可每周审计。会改变行为的 PR 必须在合并前检查要求。根据漂移成本选择频率，并记录最近一次成功检查。

**三十天期限变更有多个检查点：**产品负责人批准要求，工程人员更新配置和测试，审查者合并 PR，运营人员发布运行手册更新。一条变更日志记录关联最终记录。维基同步失败应保持可见，不能被成功合并掩盖。共享交接流程让不同工具之间保持顺序。

## 一个流程，适用于每种工具

**将重复步骤打包为技能或提示词，**并分配版本化流程 ID。共享流程约定，不要假设所有工具使用相同文件格式。每个工具适配器使用其支持的加载或调用方式。

| 流程 | 必需输出 |
|---|---|
| **开始任务** | 负责人、范围、策略版本、来源清单、写入预留 |
| **文档检查** | 缺失元数据、重复权威来源、失效来源引用 |
| **知识检查** | 要求与代码之间的差异及其支持版本 |
| **交接** | 当前证据、提案、已完成检查、未解决问题 |

**非程序员无需 Git 也能工作。**他们在聊天项目中获取获准来源，填写同一提案模板，再通过草稿页面或任务提交给负责人。请求修正要求不需要检出代码库。

**程序员使用代码库文件和 PR 门禁。**他们在 PR 中链接已批准提案，记录检查过的提交并运行必需检查。两类参与者交接相同证据结构。

```yaml
handoff:
  task: EXP-42
  policy_version: 3
  manifest: "已附来源 ID、版本和检查过的提交"
  completed: [requirement-review]
  proposals: [PROP-042]
  pending: [implementation-review, runbook-publication]
  reservations: ["RUN-04 发布任务已分配给运营负责人"]
  unresolved: []
  next_owner_role: engineering-maintainer
```

**交接本身仍是缓存。**下一位负责人行动前重新读取来源并记录新版本。没有检查关联审批或测试证据之前，不要把“已完成”当作证明。每次写入前应用以下防护措施。

## 每次写入前的防护措施

**在数据离开归属系统前先筛查。**检查分类、连接器权限、获准目标、模型提供商的数据处理方式和日志记录。只发送最少的相关内容。不要将受限记录放入未获授权的聊天项目或嵌入服务。

**检索文本是证据，不是指令通道。**维基页面或工具响应即使要求智能体忽略策略，也不会改变其权威性。将内容本身携带的指令与已批准运行策略分开审查。检索时将连接器限制为只读，并让发布凭据与会话访问凭据相互分离。

**为每个页面或文件指定一位在任负责人。**在任务跟踪器中记录预留范围和到期时间。写入前重新读取并检查版本。工作树有助于本地隔离，预留和条件写入则用于处理共享记录。

| 暂停并询问的触发条件 | 必需响应 |
|---|---|
| **来源冲突且没有负责人** | 暂停并指定权威来源 |
| **目标已被其他任务预留** | 编辑前协调所有权 |
| **基础版本已变更** | 重新协调并申请批准 |
| **重要主张缺少证据** | 标记为未验证并请求来源 |
| **数据处理方式不明确** | 将内容留在归属系统 |
| **无法访问实时来源** | 记录快照限制并暂停持久操作 |

**提示词不是安全控制。**在模型之外测试权限拒绝、受保护分支、过时基础版本拒绝和写入责任。如果账户仍有不受限制的发布权限，那么合规演示并不足够。使用这些测试判断试点是否已准备好。

## 推广前先运行试点

**先以草案形式启动框架。**选择一个项目，由一位程序员、一位非程序员和指定来源负责人参与。通过两种工具提出同一个已知 ID 问题，再进行一次有意制造来源冲突的演练。审查清单和提案，不要只评判措辞流畅度。

**预期推理方式：**两位参与者都能识别当前获批要求，并单独描述已检查的实现。若两人意见不同，先比较清单条目。这是建议的演练，不是实测基准。

| 指标 | 定义 |
|---|---|
| **引用率** | 抽样输出中有来源支持的重要主张数 ÷ 重要事实主张数 |
| **每周漂移发现数** | 按来源类型归类的已确认权威或版本差异 |
| **提案处理时间** | 从提案可供审查到记录决策的中位时间 |
| **过期上下文返工** | 因过时或未验证证据而重新打开的任务 |

**先测基线，再设目标。**第一周发现更多漂移，可能表示检测能力更好，而非文档质量更差。除原始数量外，还要跟踪重复发生情况和解决时间。审查敏感证据时，不要将其复制到分析导出文件。

**在推广时提供示例代码库。**其中包含虚构地图、策略适配器、清单、提案模板、文档例外和可运行的审查检查。使用模拟维基与任务记录，不使用生产凭据。演示发布被拒、基础版本变更被拒、策略版本漂移和成功交接。

**模板代码库是推广交付物，**不是本文附带资产。领导和来源负责人审查试点结果后，再推广运行模型。将例外和未解决故障保留在决策登记册。推广前修复下列可预见问题。

## 排查共享上下文

| 症状 | 首要修复方法 |
|---|---|
| **两个工具给出不同回答** | 比较来源 ID、版本、范围和审批状态 |
| **指令看似最新但行为不同** | 检查已加载适配器、规则开关和本地覆盖 |
| **RAG 返回旧要求** | 检查索引刷新情况并获取实时页面 |
| **维基编辑覆盖了另一项变更** | 要求使用条件写入或串行发布 |
| **文档检查通过但措辞过时** | 增加负责人审查和要求协调检查 |
| **决策只留在聊天中** | 指定提案接收流程和登记册负责人 |

**先修复证据路径，再重写提示词。**然后重新运行失败的试点案例并记录结果。使用下方清单将修复后的流程变成每周可重复的实践。

## 本周十个步骤

1. **选择一个试点项目**并确定参与人员和工具。
2. **为每类信息指定归属位置和负责人。**
3. **发布项目地图，**记录来源 ID 和权威范围。
4. **起草一套共享策略**并交由负责人审查。
5. **在每个指令适配器首行标注版本**并确认其已加载。
6. **要求重要事实回答和提案附上下文清单。**
7. **建立提案接收流程，**记录基础版本和指定审批人。
8. **落实写入控制**和同一 PR 文档规则。
9. **使用虚构记录测试漂移、冲突和交接。**
10. **审查试点指标**并批准下一阶段推广。

**让每类事实各有归属，让每个工具都读取该来源，并让每项持久变更都经由人员处理。**
